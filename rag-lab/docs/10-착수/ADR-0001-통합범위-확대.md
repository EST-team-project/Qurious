# ADR-0001: 통합 범위 확대 (용어사전 단일 메뉴 → 두 사이트 전면 통합)

## 1. 개요
* **작성일**: 2026-09-22
* **상태**: 승인됨 (Approved)
* **작성자**: AI Agent
* **관련 요구사항**: REQ-001, REQ-002, REQ-003, REQ-004

## 2. 배경 (Context)
초기 기획 단계에서는 '투자 용어 사전' 등 1개 메뉴만을 대상으로 RAG(Retrieval-Augmented Generation) 시스템을 통합할 예정이었다. 그러나 병렬 조사 과정(IA 및 DRL RAG 조사)에서 두 개 사이트(33개 메뉴, 53개 뷰, 45개 API)의 데이터를 전면적으로 통합해야 할 필요성이 대두되었다.

## 3. 결정 사항 (Decision)
* 대상 범위를 '용어 사전 1개'에서 **두 사이트 전면 통합(전체 33개 메뉴/53개 뷰/45개 API)**으로 확대한다.
* 전체 코퍼스 용량(~2.2MB)과 청크 수(~1,190개), 벡터 크기(1.7MB)를 고려했을 때, 별도의 복잡한 벡터 DB나 외부 검색엔진(Meilisearch 등) 대신 **PostgreSQL + pgvector 단독 구성**으로도 성능 및 용량 처리가 충분하다고 판단하여 이를 확정한다.

## 4. 고려된 대안 (Alternatives Considered)
* **대안 1: 기존대로 1개 메뉴만 통합**
  * 장점: 개발 범위가 좁고 리스크가 적음.
  * 단점: 실제 서비스에서의 활용도가 떨어지며 전체 구조에 대한 테스트가 어려움.
* **대안 2: 외부 벡터 DB(Qdrant 등) 도입**
  * 장점: 확장성이 뛰어남.
  * 단점: 현재 데이터(청크 ~1,190개, 1.7MB) 수준에서는 오버엔지니어링이며 프리티어(t2.micro, 1GiB RAM) 환경에서 OOM(Out of Memory) 위험이 있음.

## 5. 결과 및 영향 (Consequences)
* **긍정적 영향**:
  * 단일 DB(PostgreSQL)를 통해 메타데이터와 벡터 데이터를 한 곳에서 관리하여 시스템 구조가 단순해짐.
  * t2.micro (1vCPU, 1GiB RAM) 환경 내에서 리소스를 효율적으로 사용할 수 있음 (프리티어 제약 충족).
* **부정적 영향 / 리스크**:
  * 통합해야 할 IA가 늘어남에 따라 크롤링 및 데이터 전처리 작업 공수가 다소 증가함.
  * 메모리 제약에 대비해 swap 파일(1~2GB)을 활용하고 무거운 모델(Ollama, diffusers 등)은 배제해야 함.

## 6. 후속 조치 (Next Steps)
* 10단원 매핑 확정안 문서에 IA 전면 통합 내역 반영
* 기존 Qdrant 등의 라이브러리 및 코드 제거 후 pgvector 기반 코드로 전면 대청소 착수
