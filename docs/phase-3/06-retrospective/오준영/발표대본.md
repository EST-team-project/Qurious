현재 통합 자료는 **62장**이다. 오준영 구분 화면은 **30쪽**, 설명은 **31~40쪽**, 영상은 **41~43쪽**이다. 아래 큰따옴표 안은 실제로 말할 문장이고, 각 장의 설명 방향은 발표자를 위한 메모다. 소요 시간은 리허설 전 예상이다.

30쪽 시작: “자산배분과 리밸런싱, 증권사 연동을 맡은 오준영입니다.”

## 1장. 판단을 계획으로, 실행을 기록으로 (35초)

통합 **31쪽** · 계획 → 실행 → 확인 순서로 화면의 세 칸을 짚는다.

“제 담당은 자산배분과 리밸런싱, 증권사 연동 자동화입니다. 자산배분은 자산별로 얼마씩 투자할지 정하는 것이고, 리밸런싱은 달라진 비중을 목표에 맞게 조정하는 것입니다.
저는 배분 계산 결과를 사용자가 확인한 계획으로 저장하고, 주문 전에 위험을 검사하고, 주문 이후에는 체결과 알림까지 확인하도록 연결했습니다. 앱 안에서 계산하는 가상계좌와 한국투자증권의 모의계좌는 구분해서 관리합니다. 먼저 비중을 계산해 계획으로 적용하는 과정부터 설명드리겠습니다.”

## 2장. 계산 결과는 사용자의 확인을 거쳐 적용합니다 (65초)

통합 **32쪽** · 네 모델을 한 줄씩 설명한 뒤 계산·저장 → 가져오기 → 확인 → 플랜 저장을 짚는다.

“성향별 기준 배분에 네 가지 모델을 추가했습니다. 리스크 패리티는 자산별 위험 기여를 고르게 맞추고, 최소분산은 정해진 비중 제약 안에서 변동성을 낮추는 조합을 찾습니다. Black–Litterman은 기준 비중에 사용자의 상대 전망과 신뢰도를 반영하고, 국면 배분은 시장의 추세와 변동성에 따라 비중을 바꿉니다.
계산할 때는 어떤 날짜의 자료와 조건을 썼는지도 남깁니다. 사용자가 저장한 배분을 가져와 목표와 설정을 확인한 뒤 플랜을 저장해야 적용됩니다. 국면에 따라 목표를 바꾸는 설정과 실제 자동 주문 예약도 각각 따로 켭니다.
기본 가져오기는 국내주식 부분만 적용하고 나머지는 현금으로 남깁니다. 예를 들어 국내주식이 15%라면 나머지 85%까지 자동으로 상품을 사는 것은 아닙니다. 이렇게 정한 계획을 실행할 때는 다음 장의 검사를 거칩니다.”

## 3장. 주문 전 검증하고, 접수 후 체결을 추적합니다 (60초)

통합 **33쪽** · 자료 준비 → 전략 판단 → 위험 검사 → 접수 → 체결 추적. 비상정지 범위는 아래 문구를 짚는다.

“먼저 판단에 필요한 자료가 준비됐는지 확인하고 전략을 계산합니다. 그다음 계좌와 보유 수량, 손실 한도, 비상정지 상태 등을 검사한 뒤 주문을 보냅니다. 주문이 접수되면 주문번호로 실제 체결 여부를 계속 확인합니다. 응답이 불명확할 때도 기존 주문을 먼저 조회해 중복 주문을 방지합니다.
기본 설정은 전략 판단이 10분 간격, 체결 추적이 2분 간격입니다. heartbeat는 주기 작업이 동작하는지 확인하기 위한 신호로, 1분마다 기록합니다.
비상정지는 자동매매 계열과 개인 KIS 모의 주문에 적용하고, 웹 직접매매·일반 PAPER·외부 Open API 주문은 적용 밖입니다. 보유 종목을 자동으로 모두 파는 기능도 아닙니다. QUANT 판 2에서 가격 조정 사건으로 보류되면 자동 손절·익절도 멈추며, 수량·가격의 자동 교정과 보류 해제는 아직 지원하지 않습니다.”

## 4장. 3종목 30주를 매수하고, 전량 매도했습니다 (45초)

통합 **34쪽** · 매수 3건 → 매도 3건 → 잔량·미체결 0 → 기존 보유 보존 순서로 짚는다.

“이 주문 흐름이 실제 증권사 모의계좌에서도 연결되는지 확인했습니다. 11월 6일 시험용 진단의 추천 목록에서 하나금융지주, S-Oil, 삼성에스디에스를 각각 10주씩 매수한 뒤 전량 매도했습니다.
매수 세 건과 매도 세 건 모두 앱 기록과 증권사의 직접 체결 조회를 대조했습니다. FILLED는 주문 수량 전부가 체결됐다는 상태입니다. 시험한 세 종목의 잔량과 미체결은 0이었고, 기존 삼성전자 1주와 위험 설정은 유지했습니다.
이것은 가상 자금으로 주문 연결을 확인한 기능 시험입니다. 이 과정과 후속 점검에서 발견한 오류 두 가지를 이어서 설명드리겠습니다.”

## 5장. 체결은 한 번인데, 알림이 두 번 왔습니다 (85초)

통합 **35쪽** · 현상 → 두 조회 경로 → 같은 주문 ID 선점 → 신규 시험과 244건의 의미 순서로 설명한다.

“첫 번째는 삼성에스디에스 10주 매수에서 체결은 한 번인데 알림이 2초 간격으로 두 번 온 문제입니다. 서버가 주기적으로 체결을 확인하는 기능과, 시험 중 특정 주문 상태를 직접 다시 조회하는 기능이 같은 체결을 각각 발견했습니다. 슬라이드의 복구 조회가 이 두 번째 기능입니다. 증권사에서 상태를 다시 읽어 앱에 저장된 체결 수량과 가격을 최신으로 맞추는 작업입니다.
두 경로가 같은 주문의 알림을 각각 보낸 것이 원인이었습니다. 그래서 같은 주문을 식별하는 ID를 전달하고, DB에 발송 권한을 먼저 확보한 호출만 보내도록 수정했습니다. 이후 같은 주문을 다시 확인해도 추가 알림을 보내지 않고, 다른 주문이면 별도로 보냅니다.
이를 실제 DB에서 전달 성공과 실패 두 조건으로 시험했습니다. 그리고 수정 때문에 기존 기능이 망가지지 않았는지 다시 확인하는 회귀 시험도 실행했습니다. 주문·복구·알림·암호화·화면 관련 244개 시험이 모두 통과했습니다. 이 숫자는 시험 사례 수이며, 최초 거래에서 주문 자체가 중복된 것은 아니었습니다.”

## 6장. 긴급정지에서 KIS 미체결 취소가 빠졌습니다 (60초)

통합 **36쪽** · 신규 주문 차단과 기존 미체결 취소를 구분한다. 취소 요청 뒤 확정 조회까지 짚는다.

“두 번째는 긴급정지를 해도 이미 접수된 개인 KIS 모의 주문의 미체결 잔량이 취소되지 않는 문제였습니다. 신규 주문은 막혔지만, 기존 취소 함수가 직접 KIS 주문을 제외하고 있었습니다. 정지한 뒤 취소 기능을 따로 시험했을 때는 각각 동작해서 이 연결 누락을 찾지 못했습니다.
수동 긴급정지와 일손실 한도에 따른 자동 정지가 KIS 취소 서비스를 호출하도록 수정했습니다. 수정 후에는 실제 모의계좌의 미체결 5주를 긴급정지 API만으로 취소했고, 취소가 확정된 것까지 조회했습니다. 같은 정지를 반복해도 취소 요청이 중복 전송되지 않았고, 관련 자동 시험 300건도 통과했습니다.
보유 중인 주식은 유지하면서 아직 체결되지 않은 주문을 취소하는 기능입니다. 이어서 사용자가 실제로 받는 알림을 원본으로 보여 드리겠습니다.”

## 7장. 매수 접수와 체결 확정 알림 원본 (50초)

통합 **37쪽** · 원본 위쪽 접수 → 아래쪽 체결 → 단가·총액·다음 행동을 짚는다. 원문을 전부 읽기보다 달라진 상태를 설명한다.

“11월 9일 실제로 받은 Discord 매수 알림입니다. 위쪽은 5주를 117,100원에 주문한 접수 알림이고, 주문번호와 체결 미확인 상태를 함께 보여 줍니다. 아래쪽은 5초 뒤 평균 117,000원에 체결됐다는 알림입니다.
가격이 다른 이유는 지정가 주문이기 때문입니다. 매수 지정가 117,100원은 그 가격 이하에서 사겠다는 한도이므로, 더 낮은 117,000원에 체결될 수 있습니다. 이 사례에서는 주당 100원, 약 0.0854% 더 싸게 샀습니다.
접수와 체결 확정을 나눠 알리고 실제 체결 수량과 총액을 보여 줍니다. 체결 후에는 모의투자·포트폴리오 화면에서 보유 현황을 확인하도록 다음 행동도 안내합니다.”

## 8장. 매도 접수와 체결 확정 알림 원본 (35초)

통합 **38쪽** · 매도 지정가는 하한이라는 점과 재주문 1% 조건을 구분한다.

“매도도 같은 구조입니다. 위쪽은 5주를 117,100원에 접수한 알림이고, 아래쪽은 평균 117,200원에 체결된 결과입니다. 매도 지정가는 그 가격 이상에서 팔겠다는 한도여서, 이 사례에서는 주당 100원 더 높은 가격에 팔렸습니다.
따라서 두 사례의 가격 차이는 일정한 오차율을 허용해서 생긴 것이 아니라, 지정가보다 유리하게 체결된 것입니다. 별도로 취소 후 재주문할 때는 원 지정가와 현재가의 차이가 기본 1% 이내인지 검사합니다. 이 1%는 재주문 가능 여부를 정하는 조건입니다.”

## 9장. 비상정지 알림 원본 (35초)

통합 **39쪽** · 이유 → 위험 → 다음 행동을 원본에서 짚는다. 정지·해제·매도를 연속된 증거로 묶지 않는다.

“이것은 비상정지 알림 원본입니다. 새 자동 주문이 멈췄다는 상태와 함께, 이번에는 임시 기능 검증 때문에 정지했다는 이유를 보여 줍니다. 정지 중에는 신호가 나와도 주문이 나가지 않는다는 영향과, 원인을 확인한 뒤 설정에서 비상정지를 해제해야 다시 시작된다는 다음 행동도 안내합니다.
적용 범위는 앞에서 설명한 자동매매 계열과 개인 KIS 모의 주문입니다. 이 캡처에는 정지 해제 시점이 없어서 앞의 매수·매도와 연속된 정지·재개 검증으로 설명하지는 않습니다.”

## 10장. 운영 조건과 남은 확인 (80초)

통합 **40쪽** · 세 서비스의 역할 → 동일 코드 확인 → Windows 독립 경보의 목적과 조건 → 남은 일 순서로 설명한다.

“마지막으로 운영 환경에 반영한 내용입니다. 여기서 세 서비스는 웹 요청을 처리하는 app, 백그라운드 작업을 실제 실행하는 worker, 정해진 시간마다 작업을 보내는 beat입니다. 11월 9일에는 이 세 실행 환경의 717개 코드 파일을 대조해 같은 코드가 배포됐는지 확인했고, 데이터베이스 구조 버전도 0046인지 확인했습니다.
알림 설정 암호화는 11월 6일 운영에 적용했습니다. 앱 내부 알림이 영향을 받는 상황도 확인할 수 있도록, 앱과 별도로 실행되는 독립 경보를 Windows 작업 스케줄러에 등록했습니다. 이것이 슬라이드에 Windows가 나오는 이유입니다. 5분마다 Docker 서비스의 가동 상태와 암호화 오류 로그를 검사하며, Discord 연결 시험의 실제 수신도 확인했습니다.
다만 Windows 사용자 로그인 중에 실행하므로 로그아웃이나 절전 중 감시까지 보장하지는 않습니다. 인수자가 새 PC에서 복원하는 실습과 앱 가상계좌의 보유 자산이 정기 회차에서 평가되는지 확인하는 작업은 남아 있습니다. 이제 배분 계산, 국면 변경, 개인 전략 실행 기록을 영상으로 보여 드리겠습니다.”

## 영상 A · 통합 41쪽 — 배분 모델 비교

시작: “같은 성향과 기간을 유지하면서 모델만 바꿨을 때 자산별 비중이 어떻게 달라지는지 보여 드리겠습니다.”

영상 중: 리스크 패리티 → 최소분산 → 시장 국면 순서로 비중이 달라지는 것을 짚는다. 이미 설명한 모델 정의는 길게 반복하지 않는다.

마무리: “이 단계에서는 계산 결과만 저장됩니다. 리밸런싱 목표 적용과 주문 예약은 별도 설정입니다.”

## 영상 B · 통합 42쪽 — 국면 변화와 목표 변경 이력

시작: “저장한 국면 배분을 가져오고, 목표 비중과 변경 이력을 확인하는 영상입니다. 가져온 값은 편집안에 채워지며 저장 전에는 기존 플랜이 유지됩니다.”

이력 장면: “시험용 과거 국면과 실제 수집 자료를 이용해 목표 비중 변경을 재현했습니다. 종목은 유지하면서 자산군별 목표 비중이 어떻게 달라졌는지 기록으로 확인할 수 있습니다.”

마무리: “촬영 중에는 저장하거나 주문하지 않았고, 자동 주문 예약도 꺼 둔 상태입니다.”

## 영상 C · 통합 43쪽 — 개인 전략 판단과 차단 기록

시작: “마지막은 앱 내부 가상계좌에서 개인 전략의 초기 판단과 차단 사유를 확인한 영상입니다.”

로그 장면: “자료가 준비되지 않았거나 같은 봉을 이미 처리했거나 비상정지가 켜져 있으면, 실행하지 않은 이유를 기록합니다. 이번 영상의 체결은 0건이고 KIS 주문 체결을 보여 주는 장면은 아닙니다.”

다음 발표자 연결: “여기까지 배분 계획을 모의 실행과 위험관리, 결과 확인으로 연결한 부분이었습니다. 이어서 강민석 님이 LEAN 대사와 모의투자를 설명드리겠습니다.”

### 시험 수치 참고 — 질문이 있을 때

- **244건:** 원본 `owned.xml`의 14개 파일·244개 사례를 직접 집계했다. 주문·체결 62 + 복구·재주문 76 + 알림 66 + 암호화 13 + 화면 27 = 244건이다. 11/6 담당 범위 회귀다. 체결 알림 신규 2건을 포함하며 전부 알림 전용 시험이라는 뜻은 아니다. 수정 직후 새 KIS 주문을 추가한 검증도 아니다.
- **300건:** 11/9 긴급정지·KIS 취소 관련 회귀다. 실제 미체결 5주 취소 확인은 별도 실연동 근거이며 pytest 건수에 더하지 않는다.
- **4,481통과·2실패·3건너뜀:** 11/6 당시 전체 회귀 결과다. 이후 수수료·인코딩·공통 화면 시험 수정 병합과 구분한다.
- **170건:** 11/9 성향 설명·배분·모델 관련 수정 후보 검증이다. 운영 배포 완료를 뜻하지 않는다. 서로 겹칠 수 있는 시험 묶음은 합산하지 않는다.
