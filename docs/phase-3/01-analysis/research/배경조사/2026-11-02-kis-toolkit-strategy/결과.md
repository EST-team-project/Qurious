# KIS 개발자센터 「전략 빌더」(toolkit-strategy) 조사 결과

## 0. 세 줄 요약

1. GitHub `koreainvestment/open-trading-api` 의 `strategy_builder/` 를 내려받아 **내 PC 에서 돌리는 로컬 도구**다. 프리셋 10종을 YAML 로 만들어 신호 확인 · KIS 주문까지 잇고, 「백테스트 엔진」(LEAN · Docker)이 그 YAML 을 받는다.
2. 겹치는 곳은 전략 카드 · LEAN 백테스트 · KIS 모의다. 그러나 **우리 카드 계약(`validate_card`)과 구조가 달라 그대로 못 쓴다.** 조건 표현 꼴과 프리셋 목록을 참고하는 수준이다.
3. **코드 라이선스는 확인 못 했고**, 포털 약관에는 코드 조항이 없다. 오히려 시세 제3자 제공 금지 조항(고객 약관 제5조 ③)이 Qurious 구조에 걸린다. 「검증된 전략」이라는 문구의 성과 근거는 페이지에 없다.

### 2.1 키 설정 파일 (빠른시작 2번 탭, 원문 요지)

`kis_devlp.yaml` 에 `my_app` / `my_sec`(실전), `paper_app` / `paper_sec`(모의), `my_htsid`, `my_acct_stock`, `my_paper_stock` 등 계좌 칸과, 접속 주소 `prod: https://openapi.koreainvestment.com:9443` · `vps: https://openapivts.koreainvestment.com:29443`(모의) · 웹소켓 `ops` / `vops` 를 적는다. 탭 설명: 「모의/실전 키를 구분해 전략 실행 환경을 안전하게 준비합니다.」

→ 설정에 모의 칸이 있으므로 **모의투자를 지원하는 것으로 보인다.** 다만 「주문 실행」 단계가 실제로 모의 주소로 가는지는 코드를 못 봐서 **추정**이다.

### 2.2 같은 메뉴의 두 페이지

- **에이전트 툴킷 개요**: 전략 빌더 · 백테스트 엔진 · AI(MCP) 세 갈래를 묶어 소개한다. 문구: 「복잡한 API 연동을 직접 구현할 필요 없이, 전략 수립부터 주문 실행까지 하나의 흐름으로 이어집니다.」
- **백테스트 엔진**: 머리 문구는 「Lean 엔진 기반의 정밀 시뮬레이션」, 「백테스트 엔진은 Docker 설치를 전제로 합니다.」 주요기능은 20+ 성과 지표(CAGR · MDD 등), 전략 빌더 YAML 연동, Grid Search 파라미터 최적화, HTML 상세 리포트다. 이용 가이드에는 "기본 예제를 실행하면 KIS 인증부터 전략 분석, 리포트 저장까지 한 번에 진행" 이라고 적혀 있다.
  - 이 페이지의 코드 블록은 넷이다: `git clone … && cd open-trading-api/backtester`, 같은 `kis_devlp.yaml`, `uv run python examples/basic_backtest.py --example basic`, `./start.sh && open http://localhost:3001`. 탭을 눌러도 패널 글이 바뀌지 않아서, **코드 블록 넷을 탭 1~4 에 순서대로 대응시킨 것은 추론**이다.

| 1 | 골든크로스 · 추세추종 | sma 5 · sma 20 | sma_fast `cross_above` sma_slow | sma_fast `cross_below` sma_slow | 5% / 없음 |

YAML 의 칸: `metadata`(name · description · author · tags) / `strategy`(id · category · `indicators[]`(id · alias · params) · `entry` / `exit`(`logic: AND|OR` · `conditions[]`(indicator · operator · compare_to))) / `risk`(stop_loss · take_profit · trailing_stop 각각 enabled · percent). 연산자는 `cross_above` · `cross_below` · `greater_than` · `less_than` · `greater_equal` · `less_equal` 을 봤다. **종목 · 기간 · 수량 · 체결 시점 칸은 YAML 에 없다.** 실행 화면과 백테스트 화면에서 따로 정하는 것으로 보인다(추정).

## 3. 이용 조건 (원문 그대로)

### 3.1 페이지 면책 문구 (전략 빌더 페이지 하단)

> 본 서비스는 투자 판단에 참고할 수 있는 정보를 제공하기 위한 것으로, 투자 권유 또는 투자자문을 목적으로 하지 않습니다.

### 3.2 코드 라이선스 · 재배포 — **확인 못 함**

- 페이지 안에 라이선스 · 저작권 · 재배포 · 상업적 이용 문구가 **없다.** 코드는 GitHub 저장소로만 안내한다.
- 저장소의 LICENSE 는 규칙상 github.com 을 열지 않아 **보지 못했다.** "약관에 제한이 없으니 써도 된다"고 결론 내리면 안 된다.
- 낱말 검색 결과 (모두 0건):
  - 고객 약관(7,092자): `저작 · 재배포 · 상업 · 소스 · 샘플 · 라이선스 · 라이센스 · GitHub · 오픈소스 · 지적재산 · 복제`
  - 제휴기관 약관(8,374자): `저작 · 재배포 · 상업 · 소스 · 샘플 · 라이선스 · 재판매 · 가공 · 배포`
  - 포털 약관은 API 이용 계약을 다루고, 샘플 코드의 권리는 다루지 않는다.

### 3.3 「오픈 API 서비스 이용 약관(고객)」 — 푸터 「이용약관」 (제정 2022. 8. 8., 시행 2022. 10. 1.)

> 제 5 조 (고객의 의무) ② 고객은 자신의 보안코드(앱키, 시크릿키)가 유출 및 도용되지 않도록 관리해야 하고, 제3자에게 대여, 위임, 양도 또는 본인 이외의 제3자에게 누설해서는 아니 된다.

> 제 5 조 (고객의 의무) ③ 고객은 회사에서 제공하는 시세(국내주식, 해외주식, 국내선물/옵션 등)정보를 고객이 직접 개발한 프로그램 등 개인의 업무에 한하여 이용해야 하며, 제3자에게 제공해서는 아니 된다.

> 제 9 조 (이용 중지) ① … 4. 회사의 서버에 일정수준 이상의 부하를 유발하는 등 오픈API서비스의 안정적인 운영을 위하여 필요하다고 인정하는 경우

> 제 10 조 (이용 해지) ① … 4. 최근 1년간 오픈 API 서비스 이용 실적이 없는 경우 … 6. 회사의 서버에 일정수준 이상의 부하를 유발하는 등 오픈API서비스의 안정적인 운영을 위하여 필요하다고 인정하는 경우

> 제 12 조 (유량 제어) ① 회사는 원활한 오픈 API 서비스 제공을 위해 유량 제어 정책에 의거하여 고객의 API 요청을 제한한다.

> 제 17 조 (손해배상 및 면책) ④ 회사는 오픈 API 서비스의 변경 또는 정지로 인해 발생되는 문제에 대해 고의나 중과실이 없는 이상 어떠한 책임도 지지 않는다.

### 3.4 「오픈 API 서비스 이용 약관(제휴 이용기관)」 — 푸터 「제휴기관 이용약관」 (제정 2022.8.8.)

> 제2조 ① … 1. "이용기관"이란 회사와 오픈 API 이용계약을 체결하고 회사의 이용 승인을 받은 기관을 의미한다. … 3. "사용자"란 이용기관의 연계 금융 서비스를 통해 회사의 오픈 API 서비스를 사용하는 회사의 계좌를 보유한 회사의 계좌를 보유한 자를 의미한다.

(원문에 "회사의 계좌를 보유한"이 두 번 반복되어 있다. 원문 그대로 옮겼다.)

> 제 5 조 (이용기관의 의무) ⑦ 이용기관은 회사에서 제공하는 시세(국내주식, 해외주식, 국내선물/옵션 등)정보를 회사의 거래고객 대상 오픈 API 서비스에 한하여 이용 허용되며 이외의 목적으로 사용하여서는 아니 되며 부당 사용에 대하여 발생하는 과태료 등에 대해서는 이용기관이 부담하여야 한다

> 제 5 조 (이용기관의 의무) ⑨ 이용기관은 수시로 전산테스트와 보안취약점 점검을 진행하여 업무 정상 여부를 확인하여야 한다.

→ 여러 사람에게 서비스하는 앱은 "고객"(개인 업무)보다 "제휴 이용기관"(회사와 계약하고 승인받은 기관)에 가깝다. 다만 Qurious 가 어느 쪽에 해당하는지는 **법적 해석이라 이 조사에서 판단하지 않는다.**

- 반면 `strategy_builder/` 와 `backtester/` 를 언급한 곳은 `app/` · `docs/phase-3/`(지난판 제외)에서 **찾지 못했다.** 즉 지금까지는 API 호출 예제만 참고했고, 전략 툴킷은 새 대상이다.

| 항목 | Qurious (읽은 코드) | KIS 전략 빌더 (본 YAML · 페이지) |

### 4.3 쓸 수 있어 보이는 곳 (제안 · 추정 포함)

1. **조건 표현 꼴 참고.** `indicators[] + entry/exit.conditions[] + logic` 꼴은 우리 카드가 앞으로 규칙 종류를 늘릴 때 칸 설계의 참고가 된다. 그대로 넣으면 `validate_card` 를 통과하지 못한다. 쓰려면 변환 계층이나 계약 확장이 필요하다.
2. **프리셋 목록을 후보 아이디어로 쓰기.** 기준 전략 탐색(110개 시도에서 합격 0 — 이번 조사가 아니라 프로젝트 기록 PR #441)에 넣어 볼 후보 이름 · 파라미터 목록으로 쓸 수 있다. 성과 근거는 없으니 "검증된 전략"으로 옮기면 안 된다.
3. **LEAN 대사 참고.** KIS 가 LEAN 위에서 어떤 수수료 · 체결 가정을 쓰는지 알면 우리 ①-11 LEAN 대조에 비교점이 생긴다. 코드를 봐야 알 수 있다(추정).
4. **KIS 호출 예시 출처.** 이미 하는 일이다. `examples_llm/` 처럼 TR ID · 필드 근거로 계속 쓴다.

## 5. 반박 근거 (같은 비중으로)

1. **구조가 안 맞는다.** 우리 카드는 고정 계약 + digest 검증 + 종가 판단 · 다음 시가 체결 · ATR 손절 · 위험 % 수량이다. KIS YAML 에는 종목 · 수량 · 체결 시점 · 가격 기준 칸이 없다. 가져와도 의미가 맞는 칸은 지표 · 조건 정도다.
2. **"검증된 전략 10종" 의 근거가 없다.** 페이지 어디에도 성과 수치 · 검증 기간 · 표본이 없다. 지표 1~2개와 임계값으로 된 교과서 수준의 규칙이다. 우리 기준 전략 탐색 결과(110개 시도, 합격 0 — 프로젝트 기록 PR #441)를 생각하면 성능을 기대할 근거가 없다.
3. **일부 프리셋의 논리가 이상해 보인다 (추정 — 엔진 계산식은 못 봄).**
   - 「돌파 실패」: 설명은 "전고점 돌파 후 다시 아래로 빠지면 손절"이다. 그런데 YAML 은 `prev_high > close` 에서 진입하고 `prev_high < close` 에서 청산한다. 고점 아래면 사고, 돌파하면 파는 꼴이라 설명과 반대로 읽힌다.
   - 「52주 신고가」: `maximum(252) < close` 로 진입한다. maximum 이 당일 봉을 포함해 계산하면 이 조건은 결코 참이 될 수 없다. 당일을 빼는지 확인이 필요하다.
   - 「모멘텀」: 설명은 "최근 N일 수익률이 높은 종목을 매수"인데, 실제로는 단일 종목의 ROC > 30 임계값이다. 종목 간 순위가 아니다.
4. **시세 이용 범위 약관.** 고객 약관 제5조 ③은 시세를 "개인의 업무에 한하여 이용해야 하며, 제3자에게 제공해서는 아니 된다"고 한다. 툴킷은 개인 PC 도구로 설계되어 이 범위 안에 있는 것으로 보인다(추정 · 약관 해석). 반면 여러 사용자에게 화면을 보여 주는 Qurious 가 툴킷의 KIS 시세 백테스트 방식을 따라 하면 이 조항에 걸릴 수 있다. 제휴기관 약관(제5조 ⑦)은 기관 계약 · 승인을 전제로 한다. 판단은 사용자 몫이다.
5. **부하 · 해지 조항.** 툴킷 흐름(여러 종목 신호, Grid Search 최적화가 KIS 자료를 부르는 경우)을 따라 KIS 를 많이 부르면 제9조 ①4 · 제10조 ①6(서버 부하 시 중지 · 해지)과 제12조(유량 제어)에 걸릴 수 있다.
6. **실행 환경 차이.** `./start.sh` · `open` 명령은 macOS/Linux 기준이다. 백테스터는 Docker 가 전제다. 팀은 Windows 위주라 바로 돌리기 어렵다(작은 근거). 우리 앱은 이미 Docker 로 돌고 LEAN docker 모드도 있어서, 새로 얻는 것은 적다.
7. **로컬 단일 사용자 도구.** 앱키를 `~/KIS/config/kis_devlp.yaml` 한 파일에 적는 구조라, 사용자별로 키를 따로 저장하는 우리 구조(`BrokerSettings`, 사용자 단위)와 다르다. 코드를 가져오면 키 관리 부분은 다시 짜야 한다(추정).
8. **페이지 내용이 얕다.** 페이지는 소개 · 그림 · 명령 한 줄이 전부다. 실제 내용(지표 계산 · 체결 가정 · 모의/실전 분기)은 GitHub 코드에만 있어서, 이 페이지만으로는 참고할 양이 적다.

## 7. 사용자가 정할 것 (제안일 뿐, 결정하지 않았다)

1. GitHub `koreainvestment/open-trading-api` 의 LICENSE 를 사용자가 직접(웹 브라우저로) 확인할지. 확인 전에는 코드를 복사하지 않고 "참고" 수준에 머무는 것을 제안한다.
2. KIS 전략 빌더 YAML 을 Qurious 의 **가져오기 형식으로 지원할지, 아니면 칸 설계 참고만 할지.** 지원하면 `validate_card` 계약 확장(규칙 종류 · 조건 조합)과 변환 계층이 필요하다.
3. 프리셋 10종을 **기준 전략 탐색의 추가 후보**로 넣을지. 넣는다면 "KIS 프리셋 출처, 성과 미검증"으로 표시하자는 제안이다.
4. KIS 백테스터의 LEAN 설정을 우리 LEAN 대조(①-11)의 비교점으로 쓸지. 쓰려면 코드 열람이 먼저다.
5. 툴킷 흐름을 따라 KIS 시세를 여러 사용자 화면이나 백테스트에 쓰는 방향을 검토할 때, 시세 약관 조항(고객 제5조 ③ · 제휴 제5조 ⑦)을 어떻게 해석할지(강사님이나 KIS 문의).
