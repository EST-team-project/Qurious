## 맨 위 요약

**요청 1 — 2차 구현이 phase-2 설계서에 다 반영됐나: 아니다.** 반영된 곳이 많지만 빈 곳이 뚜렷하다.

1. **API** — 태그 코드의 라우트 **271개** 전부가 p2 API 명세서 4절에 있다(메서드 + 경로 기계 대조 271/271 · 명세서에만 있고 코드에 없는 줄 0). 다만 이것은 「표에 있다」 는 뜻이고, 동작을 풀어 쓴 시스템 · 화면 설계서가 있는 라우트는 따로 센다(A-1).
2. **데이터** — 앱 DB 표 **47개** 중 **45개** 는 ERD · 데이터 사전에 있고 **2개**(`allocation_results` · `task_ownership`)와 칸 **9개**(마이그레이션 0022 ~ 0024)가 p2 데이터 사전 v1.10 에 없다. 이 둘은 3차 ERD v1.11(10-24)이 「2차 코드에서 뒤늦게 들어온 것」 으로 채웠다. 수집 DB 표는 20/20 있다(A-2).
3. **시스템** — 2차 범위 요구 28개(확정 19 · 제안 9) 가운데 **목표 기능 ④(강민석 님 — 성과 · 모의투자)에는 별도 설계서가 p2 에 없다**(09-29 계획인 기능 설계서 4.4절뿐). 완료보고서가 2차 실적으로 적은 QFRS 6대 지표 · 100일 백테스트 · 코스콤 테스트베드 · 모의계좌 현황 · 스탑 주문 · 스냅샷은 p2 설계서(system · ui)에 서술이 없다. 기능 동작 원리(v0.1)는 09-30 기준에서 멈춰 있다(A-3).
4. **화면** — 앱 화면 **77개** 모두 UI 명세서 6절 목록에 있고 IA 70/77 · 와이어프레임 21/77 이다. 화면 한 장을 풀어 쓴 상세 절은 **29개** 화면뿐이고 그중 7개(팀원 화면)는 10-29 ~ 30 에 소급해 더했다. 팀원 화면 17개 중 **10개는 지금도 상세 절이 없다**(A-4).
5. **판정 건수(A.5)** — api 라우트 271 중 반영됨 121 · 부분 135 · 설계서 없음 15(명세서에는 271 전부 있음) · data 표 67 중 누락 2 · 칸 9 중 부분 6 · 누락 3 · system 26줄 중 반영됨 16 · 부분 6 · 설계서 없음 3(+ 2차 문서 안의 3차 1) · ui 화면 77 중 상세 설계가 있는 것 29 · 없는 것 48.

**요청 2 — 2차/3차 구분 현황:** p2 설계서 22개(api 1 · data 2 · system 14 · ui 5)가 **전부 p3 에 사본으로 있고**, p3 에만 있는 문서는 14개(system 10 · ui 4)다. p3 사본 22개는 모두 2차 줄을 81 ~ 100% 그대로 담고 있어 「3차에는 개선된 부분만」 규칙에 비추면 **22개 전부가 후보**다. 이 가운데 **13개는 3차에서 늘어난 줄이 20줄 이하**(5개는 바이트까지 같음)이고 **9개는 20줄을 넘게 늘었다**(API 명세서 · ERD · 데이터 사전 · 기능 설계서 · 목표 기능 ① · 인프라 · 기능 동작 원리 · UI 명세서 · IA). 2차 문서만 있는 것은 0. 2차 내용을 가리키기만 하는 3차 문서는 사실상 없다(B).

**요청 3 — 권장:** 3안(1. 판 스트림 유지 + 맨 위 「2차 → 3차 차이」 표 · 2. p2 를 기준선으로 두고 p3 는 변경분만 · 3. 혼합 — 스캐너가 읽는 정본 문서는 안 1, 바뀐 곳이 거의 없는 서술 설계서 사본은 정리, 새 3차 기능은 새 문서) 가운데 **안 3** 을 권한다(C.3). 사용자 규칙(「개선분만」)을 문자 그대로 하면 안 2 이고 마무리 기간 비용이 가장 크다. arc42 는 델타 문서 방법을 아직 정하지 않았다(FAQ J-5 · To be done).

**요청 4 — 특강 구조:** 문서 · 저장소 구조를 말하는 항목 12개를 발췌했고(특강 PDF 8 · 강사님 일정표 · 제안요청서 · 산출물 표 · 번호 폴더 피드백), 우리 저장소가 **이미 따르는 것 4 · 일부 4 · 아직 4** 이다(D.1). 특강에는 이슈 · PR · 브랜치 규칙이 없고 「README 설계도(수식 · 아키텍처 · 한계점)」 · 「CI/CD」 · 「5단 기획서」 · 「심사 루브릭」 이 있다. 반영 후보 시점 의견은 표 마지막 칸에 한 줄씩 적었다.

## A. 2차 구현 ↔ phase-2 설계서 대조표

### A.0 기준 · 판정 말 · 한계

- **2차 범위** = 완료보고서 v1.1(`phase-2/00-management/plans/완료보고서.md`) 3절이 적은 목표 기능 ① ~ ④ 와 요구 대장 `차수 = 2차` 28줄(확정 19 · 제안 9). 제안 9개는 28 안에 들지만 완료보고서가 실적(「완료」)에서 뺐으므로 표에서 따로 적었다. 28 밖의 구현은 「범위 밖」 으로 적었다.
- **판정** — **반영됨** = 설계서의 해당 절을 열어 구현 핵심과 맞음을 본 것 · **부분** = 설계서가 있으나 일부 구현 · 2차 말(10-14 ~ 10-21) 변경이 빠지거나, 대표 항목만 적힘 · **누락** = 구현이 있는데 p2 설계서(system · ui · data)에 서술 없음(API 명세서 행은 제외) · **설계서 없음** = API 명세서 · 목록 한 줄 말고는 어느 설계서에도 없음. 「확인 못 함」 은 따로 적음.
- **라우트 수 · 표 수는 정의에서 뽑았다** — 라우트: 태그 코드에서 `scripts/api_scan.py --json`(앱을 import 하지 않는 AST 스캔) · 표: `app/models/*.py` 의 `__tablename__` 과 `alembic/versions` 의 `create_table` · 화면: `scripts/view_scan.py --json`. 모두 태그 코드를 임시 폴더에 풀어 돌렸다.
- **만든 사람** — 그 파일을 태그 시점까지 고친 커밋 작성자(가장 많은 사람). 파일 하나에 여러 사람이 있으면 함께 적고, 요구의 주담당은 요구 대장 「주담당」 칸을 따랐다.
- **한계** — 「설계서 위치」 는 절 제목 · 문장을 열어 본 곳(확실도 상)과 경로 · 이름 글자 검색(중)을 섞었다. 문장이 구현과 한 줄씩 맞는지까지는 전부 보지 못했다 → 「반영됨」 은 **그 기능이 거기에 서술돼 있다** 는 뜻이지 「모든 칸이 최신이다」 가 아니다.
- **기준일 문제** — p2 설계서의 최종 수정일: ERD v1.9 = 10-13 · 데이터 사전 v1.10 = 10-14 · 목표 기능 ① v1.7 = 10-15 · ② v0.6 = 10-16 · ③ v0.1(보조 설계 넷 v0.2 = 10-14) · 기능 동작 원리 v0.1 = 09-30 · 기능 설계서 v0.1 = 09-29 · 용어사전 v0.1 = 09-30. **2차는 10-21 에 끝났으므로 이 날짜 뒤의 구현은 설계서가 따라가지 못했을 수 있다.**

### B.3 읽은 결과

1. **3차 문서가 2차를 통째로 담은 곳 = 22개 전부.** 「개선된 부분만」 규칙을 문서 안 내용으로 판정하면 위반이다. 그러나 이것은 docs README 3.2 · 3.4절이 정한 방식(「3차 사본을 만들어 거기서 판을 이어 올린다」)을 그대로 따른 결과이며 규칙 위반이 아니라 **정책 충돌**이다(C 와 「사용자가 정할 것」).
2. **3차에서 의미 있게 바뀐 것은 9개** — API 명세서 · ERD · 데이터 사전 · 기능 설계서 · 목표 기능 ① · 인프라 · 기능 동작 원리(판 안 올림) · UI 명세서 · IA. 나머지 13개는 「바뀐 곳이 없거나 20줄 이하」 인 사본이다. 이 13개는 3차에서 따로 둘 이유가 약하다.
3. **2차 내용을 가리키기만 하는 3차 문서는 없다.** 3차에만 있는 14개 중 2차 문서 링크가 있는 것은 2개(각 1건)뿐이고, 델타 꼴(「2차 → 3차 차이」 소절)을 쓴 것은 UI 명세서(13곳)와 화면 대장(6곳) 둘뿐이다.
4. **2차 문서 안에 3차가 섞인 곳이 있다** — p2 기능 설계서 v0.1 은 5절(415 ~ 628줄)에 3차 PROJECT 02 의 15개 요구 설계를 이미 담고 있다. p2 UI 명세서 v0.32 의 16 · 17 · 19장은 3차 대상 화면의 2차 소급 절이다.
5. **2차 문서의 판 날짜가 구현을 따라가지 못한 곳** — 기능 설계서 v0.1(09-29) · 기능 동작 원리 v0.1(09-30) · 용어사전 v0.1(09-30)은 2차 내내 판이 오르지 않았다. 그 사이 구현은 계속 늘었다(A.3 「부분」 · 「설계서 없음」).

### C.2 읽은 것에서 얻은 원칙

1. **옛 문서는 지우지 않고 관계로 잇는다** — RFC `Obsoletes` · `Updates`, PEP `Replaces` · `Superseded-By`, ADR 「superseded」. 우리 `지난판/` 폴더와 같은 생각이다. 빠진 것은 **같은 주제의 새 문서가 옛 문서의 무엇을 바꿨는지 머리에서 바로 보이는 줄**이다.
2. **변경은 종류를 나눠 쓴다** — 델타 명세(`ADDED` · `MODIFIED` · `REMOVED`) · 변경 기록(Added · Changed · Removed). 「무엇이 새로 생겼나 · 무엇이 바뀌었나 · 무엇이 없어졌나」 3분류면 「발전」 이 한눈에 보인다.
3. **델타는 이유와 근거를 함께** — OpenSpec 의 `REMOVED` = 이유 + 이전 방법. 발전 서사는 「바뀌었다」 보다 「왜 바꿨나」 에서 나온다(우리는 ADR · 결정 대장 · 이슈 번호가 이미 있다).
4. **기준선은 고정하고, 그 위에 변경을 쌓는다** — 기준선(= phase-2 얼림 · 태그 `phase2-final-2026-10-21`) + 변경 요청 → 새 판. 우리 구조와 같은 모양이다.
5. **통째 복사(스냅샷)는 비용이 있다** — Docusaurus 도 「대부분은 버전 관리가 필요 없다」 고 한다. 복사 후 확장은 중복 · 갈림 · 판 날짜 불일치(B.3 의 5)를 낳는다.
6. **델타만 두면 「지금 전체」 를 볼 곳이 사라진다** — OpenSpec 은 끝난 변경을 기준 명세에 **합쳐서** 이것을 푼다. 우리 phase-3 문서가 지금 하는 일이 사실은 이 합침이다(= 3차 사본이 「현재 전체」 역할).
7. **arc42 는 델타 문서를 아직 정하지 않았다**(J-5 · To be done) — 업계 표준이 없으므로 우리 규칙을 우리가 정해도 된다.

**한 쪽짜리 3차 델타 문서 틀(안 2 · 안 3 ④ 용)** — 머리표(판 · 상태 · 기준선 = p2 문서와 판 · 태그) → 「이 판이 바꾼 것」 표(`ADDED` / `MODIFIED` / `REMOVED` · 대상 · 2차 값 → 3차 값 · 까닭 · 근거 번호) → 「2차 그대로(링크)」 목록 → 새 내용 본문 → 개정 이력. 「발전」 서사는 맨 위 표 하나가 맡는다.

## 사용자가 정할 것

1. **「3차 설계서에는 개선분만」 규칙을 어떻게 적용하나** — C.3 의 안 1 · 2 · 3 가운데 하나. 현재 정책(docs README 3.2 · 3.4절: 3차 사본에서 판을 이어 올림)과 이 규칙은 **충돌**한다. 안 2 · 3 으로 가면 README 3.4절 문장과 `docs_scan --check` 규칙을 함께 고쳐야 한다.
2. **같은 파일 사본 5개와 거의 그대로인 8개**(B.1)를 어떻게 하나 — 3차 사본을 두고 「그대로」 표기만 할지, 사본을 걷고 p2 를 가리킬지(걷으면 `지난판` 짝 규칙 · 링크 · 산출물목록 영향).
3. **누락으로 나온 것을 p2 에서 바로잡을지** — A.2 의 앱 DB 표 2 · 칸 9 와 A.3 의 ④ 설계서 부재. docs README 3.3절 예외 ②(틀린 사실 바로잡기)로 볼 수 있는지, 예외 ③(화면 소급)처럼 사용자 결정으로 새 예외를 두는지. 3차 ERD v1.11 이 이미 일부를 채웠다는 점도 함께.
4. **목표 기능 ④ 설계서를 누가 언제 쓰나** — 강민석 님 몫이면 요청 글을 올릴지, 이동원 님이 as-is 로 쓸지(10-23 점검 「강민석 님 3차 설계서 없음」 이 아직 같은지는 이번에 다시 보지 않음).
5. **기능 동작 원리 3차 사본의 판 안 올린 +101줄** — 판 올림이 빠진 것인지 확인.
6. **특강 항목의 반영 시점** — D.1 의 11-05 전 후보(4 ~ 7 · 9)를 11-05 전에 할지, 마무리 기간으로 미룰지.
7. **2차 설계서의 「범위 밖」 표시** — 제안 9개(최적화 · 스크리닝 · 스트레스)가 2차 문서에 완료처럼 보이지 않게 할지.

## 확인 못 한 것

- **문장 단위 일치** — A 의 「반영됨」 은 해당 절에 그 기능이 서술돼 있다는 확인이지, 칸 하나하나가 구현과 같다는 확인이 아니다.
- **만든 사람** — 커밋 작성자 계정과 이름의 짝(`rkdalstjr` = 강민석 등)은 저장소 기록 · 사용자 기억에서 가져왔고, 파일당 커밋 수가 1 ~ 5 로 적어 이력이 합쳐졌을 수 있다. `us_reserve` 작성자는 확인 못 함.
- **설계서 부재 판정**(`library` · `kis_monitor` · `admin` · `dashboard` · `openapi` · `macro`)은 이름 · 경로 글자 검색 기준이다. 다른 말로 서술돼 있을 수 있다.
- **ERD 의 수집 21표** 중 `CREATE TABLE` 로 센 20표 외 1표.
- **기능 설계서 4.4 · 7절이 「설계 계획」 인지 「구현 서술」 인지** — 09-29 계획 꼴(「지금」 「설계 초안」 칸)로 읽었다.
- **웹 리서치** — 표 C.1 의 2 · 3 · 9 · 10 · 11 은 검색 요약만 봤고 원문 열람은 1 · 4 · 5 · 6 · 7 · 8 이다. 현행 PEP 1 · Nygard 원문은 열지 못했다.
- **특강 PDF 전수 재확인은 하지 않았다** — 노트 검색 + 4쪽 직접 확인. 3일차 항목(D.1 의 6 · 7)은 10-28 결과를 인용했다. 「이슈 · PR · 브랜치 규칙 없음」 은 노트 검색 기준이다.
- GitHub 웹 페이지는 보지 않았다(규칙). 4일차4 의 사례 저장소 실재(ksm26 ✓ · CrazyLegendop 404)는 10-31 낮 점검 기억에서 가져온 것이고 이번에 다시 열지 않았다.
