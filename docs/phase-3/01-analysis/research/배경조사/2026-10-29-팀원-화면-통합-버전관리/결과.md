# 팀원 담당 화면까지 포함한 통합본 버전 관리 — 조사 결과 (S164 · 2026-10-29)

> **질문(사용자 피드백 10-29)**: 설계서 · UI 명세서의 통합본 버전 관리는 팀원 화면까지 병렬로 관리해야 하는데, 지금은 이동원 담당 화면만 Figma · UI 명세서에 올라가고 팀원 화면은 구현 뒤에 따라 적는다. 2차와 3차로 나뉜 문서에서 팀원 몫은 어디에 반영돼 있나? 실제 팀 프로젝트는 어떻게 관리하나?
>
> **성격**: 조사 초안(검색 3묶음 · 저장소 직접 확인). 제안은 **팀이 정할 일**이며 아직 아무것도 바꾸지 않았다. 웹 자료는 발췌만 읽었다(본문 전체를 읽지 않음).

## 1. 저장소에서 직접 확인한 현재 상태

| 확인 | 결과 | 확인 방법 |
|---|---|---|
| Figma 로 설계한 화면 | 이동원 담당(데이터 수집 · AI 상담 · 개념 학습 · 마이페이지 · 신호 순위 · 전략 신뢰성 · 랜딩). 현재 판 문서에 서로 다른 Figma 파일 20개 | docs 의 `figma.com/design` 링크 집계 |
| 팀원 파트별 할 일 문서 | **3차(phase-3)에만** 넷(강민석 · 신장환 · 오준영 · 이동원). **2차(phase-2)에는 이동원 것만** 있음 | `plans/` 폴더 |
| 파트별 할 일의 Figma 링크 | 강민석 · 신장환 · 오준영 문서 0개 · 이동원 문서 4개 | grep |
| 팀원 담당 화면의 설계 | 신장환 님 인디케이터 셋은 UI 명세서 16장(v0.31)과 설계서가 있다. **오준영 님 화면(자산배분 · 리밸런싱 · 자동매매 · 증권사 설정)과 강민석 님 화면(백테스트 · 모의투자 등)은 UI 명세서에 화면 절이 없다**(2차 UI 명세서 19절 · 3차 20절 가운데 해당 제목 0건) | 절 제목 grep |
| 2차 설계 문서의 팀원 몫 | 시스템 설계 폴더에는 있다(목표기능 2 · 3 · 리밸런싱 · 자동매매 위험 계층 등). 그러나 UI 설계 쪽은 비어 있다 | `02-design/system` 목록 |
| 팀원이 직접 쓴 문서 | 작성 칸에 신장환 4건(설계서 · 결과 문서), 오준영 · 강민석 0건 | grep |
| 통합본 ↔ 팀원 원천 연결 | 동기화 대장(SY-01 ~ 10)이 **신장환 님 설계서 한 갈래**만 시험 계획서 · RTM · 기능동작원리에 잇는다 | `설계-동기화.tsv` |
| 저장소 규칙 장치 | `.github/` 없음 — PR 템플릿 · CODEOWNERS 없음 | `ls -a .github` |

→ **사용자 지적은 대체로 맞다.** 다만 「전혀 반영 안 됨」 은 아니다 — 2차 **시스템 설계**에는 팀원 몫이 있고, 비어 있는 것은 **UI 설계(화면별 명세 · Figma)와 파트별 계획의 2차 쪽**이다. 오준영 · 강민석 님 화면은 **설계 단계의 문서 자체가 없고** 구현 · 시험 근거(기능 완성도 점검 등)만 있다.

## 2. 실제 팀들이 쓰는 방법 (조사)

| 방법 | 내용(조사에서 읽은 것) | 출처 |
|---|---|---|
| **CODEOWNERS** | 파일 · 폴더마다 책임자를 적어 두면, 그 파일을 바꾸는 PR 에 책임자가 **자동으로 리뷰 요청**된다. 분기 보호 설정에서 「코드 소유자 리뷰 필수」 를 켤 수 있다. 문서 폴더(`/docs/`)에도 쓸 수 있다 | GitHub Docs 「About code owners」 · GitLab Docs 「Code Owners」 |
| **RFC · 설계 문서** | 기술 결정을 글로 먼저 제안하고 여러 팀이 검토한다. 결정 과정이 투명해지고, 설계 문서가 **정본**으로 참조된다 | Pragmatic Engineer 「Scaling Engineering Teams via RFCs」 · InnerSource Patterns 「Transparent Cross-Team Decision Making using RFCs」 · Attentive 「Pragmatic RFC Process」 |
| **Figma 개발 인계** | 파일마다 **어느 부분이 구현 준비됐는지 · 아직 작업 중인지**를 표시하고, 개발자에게 진행 중 파일을 열어 둔다(왜 그렇게 정했는지가 보이게). 정리된 인계용 페이지와 작업 페이지를 나눈다. 브랜치는 적절한 때만 쓴다 | Figma 「Guide to Developer Handoff」 · 「Best Practices for Branching in Figma」 |

(우리 쪽과 겹치는 것: 화면설계절차의 「개발 준비됨」 표시 · 결정 기록 표 = RFC 의 가벼운 형태. 없는 것: 책임자 자동 지정 · PR 단계의 문서 갱신 확인.)

## 3. 제안(초안 — 팀이 고르는 것)

원칙: **팀원 몫은 팀원이 원천 문서를 쓰거나 PR 에 근거를 남기고, 통합본(UI 명세서 · 설계서 · RTM)은 이동원이 동기화 대장으로 받아 판을 올린다.** 이미 신장환 님 설계서에서 하고 있는 방식을 화면 쪽으로 넓히는 것이다.

1. **화면 대장 한 장** — 화면(65개) 하나당 한 줄: 담당자 · 설계 원천(Figma 링크 또는 설계 문서) · UI 명세서 절 · 구현 위치 · 마지막으로 통합본에 옮긴 판. 비어 있는 칸이 팀원 화면 갭이다(지금은 오준영 · 강민석 님 화면 대부분이 비어 있을 것).
2. **동기화 대장 확장** — SY 대장에 화면 줄을 더해, 팀원 원천이 올라가면 `docs_scan --sync` 가 「통합본에 옮겨라」 경고를 낸다(지금 신장환 님 설계서와 같은 방식).
3. **PR 템플릿 + CODEOWNERS(최소)** — PR 템플릿에 「화면이 바뀌나요? 바뀌면 원천 링크(Figma · 이슈의 경우 표 · 캡처)」 한 칸. 화면 코드(`public/`)와 팀원 설계 문서 폴더에 책임자를 적어 리뷰 요청이 자동으로 가게.
4. **Figma 는 선택 · 경우 표는 필수** — 팀원이 Figma 가 부담이면 이슈에 경우 표 + 화면 캡처로 충분하다고 정하고, 이동원이 필요할 때 Figma 로 옮긴다. (사용자 의견: 「팀원이 변경한 것을 잘 보고 반영하면 된다」 와 맞는다.)
5. **2차 문서 처리** — 2차(phase-2)는 **2차 제출 시점의 기록**으로 두고, 팀원 화면 보완은 3차(현재 판)에서 한다. 2차에 소급하려면 먼저 「2차 문서를 이후에도 고치는가」 를 정해야 한다(docs README 의 규칙 확인 필요).

## 4. 정할 것(팀 논의 후보)
- ① 위 1 ~ 4 중 어디까지 11-05 안에 하나 — 일정이 이미 2.5 ~ 3배 초과라 **1(화면 대장)과 3(PR 템플릿)만** 먼저를 제안한다.
- ② 팀원 화면의 설계 원천은 Figma · 이슈 경우 표 중 무엇을 최소 요건으로 하나.
- ③ 2차 문서에 팀원 UI 를 소급할지(비용 큼 · 가치는 제출물 정합성).
