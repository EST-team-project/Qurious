# 금요일 종가 공백 — 공식 게시 시각 · KRX · 증권사 API · 빈 값 표시 · 설계안 (조사 결과)

작성일 2026-11-01(일) KST · 읽기 전용 조사(코드 · 설정 · git 을 바꾸지 않음) · 웹 출처는 2026-11-01 접속

> 읽는 법: 「열어 읽음」 = 원문 페이지를 이번에 직접 열었다(단 열람 도구가 작은 모델로 요약해 옮긴 따옴표라 **문장 끝 한두 낱말은 도구가 다듬었을 수 있다**) · 「우리 기록」 = 우리 저장소 파일 · 수집 DB 를 읽기 전용으로 본 것 · 「2차」 = 블로그 · 패키지 문서 등 공식이 아닌 출처 · 「확인 못 함」 = 못 찾았거나 로그인 · 스크립트 때문에 못 엶.
> 앞선 조사 [금요일 종가 수급(10-31)](../2026-10-31-금요일종가-수급/결과.md) 가 같은 문제의 시장 관행 · 코드 읽기를 이미 했다. 이 문서는 그 위에 **수집 DB 의 실제 적재 시각 · KRX Open API 약관 원문 · KIS 약관 · 설계안**을 더한다.

## 0. 요약 다섯 줄

1. **① 게시 시각** — 공식 문구는 「기준일자로부터 영업일 하루 뒤 오후 1시 이후」(일 1회). 그런데 우리 수집 DB 적재 기록 21건 중 18건은 **다음 영업일 12:30 회차에서 이미 받았다**(월요일 10-19 · 금요일 10-30 등). 11-01(일) 12:59 현재 기준일은 **10-29(목)** 이고 금요일 10-30 은 5회 연속 「빈 응답」 — 설계상 정상이며 월요일 낮 회차에 채워질 것이다. 월요일 13시 전 정확한 게시 시각은 **확인 못 함**(회차가 하루 한 번이라 12:30 이전 기록이 없다).
2. **② KRX** — 무료 공식 길은 KRX Open API(인증키 + API별 신청 · 승인, 키당 하루 10,000회). 약관이 **비상업 한정 · 제3자 제공 금지**라 「우리 서버가 받아 여러 사용자에게 보이는」 쓰임은 맞지 않는다. 정보데이터시스템 웹은 자동 수집 · 복제 · 배포 금지. 제공 시각은 공식 확인 못 함(2차: 다음 영업일 08:00).
3. **③ 증권사** — 사용자 본인 KIS 키로 본인 화면에 보이는 것은 약관 안이고 우리 기록상 KIS 는 토요일에 이미 금요일 종가를 줬다. 공용 수집 계정으로 모아 배포하는 것은 약관 제5조③(제3자 제공 금지)에 걸린다. 공식 명세 · 호출 한도 수치는 확인 못 함.
4. **④ 표시** — 추천 한 가지: **직전 확정 종가를 기준일 · 출처와 함께 보이고 「금요일 종가 반영 전」 을 말한다.** 예측 · 보간으로 빈 값을 채우지 않는다(가격처럼 보이는 추정치가 가장 위험).
5. **⑤ 설계안 · 사용자가 정할 것** — 표시(「금요일 종가 반영 전」 배지 · 장 전 / 장중 라벨 구분)와 「예상 거래일인데 시세가 비면 13:30 뒤 한 번 더 받는 보조 시도」 만 바꾸고, `price_daily` · `ohlcv-v2` · 수집기의 KIS 금지는 그대로. 정할 것: (가) 월요일 장 시작 전에 사람이 볼 금요일 종가를 「본인 KIS 키 · 본인 화면」 으로만 풀지 (나) 월요일 이른 아침(예 08:30) 포털 단발 확인으로 실제 게시 시각을 잴지 (다) 「반영 전」 배지를 어느 화면에 붙일지 (라) KRX Open API 를 시험 신청할지(약관상 개인 · 비상업 범위 안에서만).

### 1.2 우리 수집 기록이 말하는 실제 (우리 기록 · 수집 DB 읽기 전용)

`data/collector/market.sqlite3` 의 `ingest_day`(source = `portal`)에서 읽은 값이다. `updated_at` 은 **우리가 마지막으로 시도한 시각**이라 「포털이 올린 시각」 의 **상한**일 뿐이다.

| 기준일(bas_dt) | 적재 완료 시각 | 시도 횟수 | 읽는 법 |
|---|---|:-:|---|
| 2026-09-18(금) | 09-21(월) 14:46:40 | 14 | 09-19(토) 11:00 에도 0건이었음(`collector/sources/portal.py` 머리말 실측) · 월요일 12:30 이전엔 아직 일일 회차가 없던 때(확인 못 함) |
| 2026-10-02(금) | 10-06(화) 12:30:03 | 5 | 10-03(토) 개천절, 10-05(월)는 대체공휴일(개천절) — 수집 DB `market_calendar` 에서 읽음 → 다음 영업일이 10-06 |
| 2026-10-16(금) | **10-19(월) 12:30:04** | 5 | 월요일 12:30 회차에서 받음 → 13시 이전에 있었다 |
| 2026-10-23(금) | 10-26(월) 18:54:36 | 5 | 그날 12:30 회차 기록이 없다(앞 조사 E.1-1) → 포털이 늦었다는 증거 아님 |
| 2026-10-29(목) | **10-30(금) 12:30:04** | 2 | 평일도 다음 날 12:30 에 받음 |
| 2026-10-30(금) | **받지 못함** — 10-31(토) · 11-01(일) 12:30 모두 `empty`, 시도 5회 | 5 | 일요일 현재 정상(월요일 낮 대기) |

- 같은 DB 에서 기준일 09-29 ~ 10-29 의 적재 21건 중 **18건이 다음 영업일 12:30:03 ~ 12:30:06**, 1건(기준일 10-27)이 12:37:00, 2건(기준일 10-23 · 10-26)이 저녁(18:54 · 19:05)이다. 저녁 2건은 그날 12:30 회차 기록이 없는 날이라 포털이 늦었다는 뜻이 아니다(앞 조사 E.1-1) → 대부분 13시 전에 올라온다고 읽는 것이 맞고, 공식 「오후 1시 이후」 는 **실제보다 늦게 잡은 안내에 가깝다**(이 해석은 우리 기록에서 나온 추정이며, 12:30 이전 게시 시각은 확인 못 함).
- **11-01(일) 12:59 현재 기준일** — `data/collector/state/daily_update_last.json` 의 `after.price_max = 20261029`. 즉 화면의 최신 종가는 **10-29(목)** 이다. 금요일 10-30 종가는 월요일 낮 회차(12:30)에 들어오는 것이 정상 경로다(이 채움 시각은 앞날 일을 내다본 추정이며 이번에 측정한 값이 아님).
- **금요일 종가가 비는 구간** — 금요일 장 마감 뒤부터 **월요일 12:30 회차까지**가 보통이다. 그러나 공식 「오후 1시 이후」 는 하한이라 **끝이 정해져 있지 않다**: 12:30 회차가 빈 응답을 받은 날은 아래 재시도 구조 때문에 **다음 날 12:30 까지 밀릴 수 있다**(관측된 사례는 이 표본에 없음 — 아래 재시도 구조 불릿). 평일은 같은 구조로 「전 거래일 종가가 다음 날 낮에 들어오기 때문에」 장 열기 전 화면의 마지막 종가는 항상 하루 더 앞이다(데이터 SLA 1절: 「시세는 다음 거래일 낮에 들어오므로 화면의 시세는 늘 하루 앞의 종가다」 — [데이터-SLA.md](../../../../02-design/system/데이터-SLA.md)).
- **같은 날 재시도 구조 (우리 코드 · 로그)** — 예약 작업은 12:30 부터 1시간마다 10시간(12:30 ~ 22:30) 깨어나지만(`scripts/daily_update.py` 머리말 · `REPEAT_EVERY_H`), **그날 자리를 다른 회차가 끝냈으면 받기만 하고 시세 단계를 다시 돌지 않는다**(「따라가기」). 로그가 그렇게 보인다: 10-30 19:04 · 20:02 회차는 「임대 — 2026-10-30 자리는 DESKTOP-KD12JUJ 가 끝냈다 · 따라가기」 로 끝났다(`data/collector/logs/daily_update-20261030-190448.log` · `-200217.log`). 따라서 **12:30 회차가 빈 응답을 받고 `ok` 로 끝나면, 포털이 13:05 에 올려도 다음 자동 시세 시도는 다음 날 12:30** 이라고 읽힌다. 빈 응답이 같은 슬롯 안에서 다시 시도되는 길(실패 코드 → 채우기)이 있는지는 **확인 못 함**(`scripts/daily_update.py` 의 `followup: fill` 은 앱 DB 단계 중심으로 보임). 이 표본(21건)에는 「12:30 에 비어 같은 슬롯에서 못 받은 날」 이 없다 — 18건이 12:30 에 받았다.
- **한계** — 월요일 12:30 이전(예 08:30)에 포털에 금요일 자료가 있는지는 우리 기록에 없다. 회차가 하루 한 번(12:30)이기 때문이다. **측정하지 않았다**(수집기를 돌리지 않는다는 이번 조사 규칙).
- 신선도 규칙은 이미 이 구조를 안다: `FRESHNESS["price_daily"] = deadline 다음 거래일 14:00`(`app/services/data_status.py:142-143`, [데이터-SLA.md](../../../../02-design/system/데이터-SLA.md) 2절). 14:00 은 공식 13:00 + 1시간 여유라 실측(12:30 이전)보다 **보수적**이다.

### 2.2 KRX Open API (openapi.krx.co.kr) — 무료 공식 길 후보

약관 페이지 [KRX Open API 이용약관](https://openapi.krx.co.kr/contents/OPP/INFO/OPPINFO005.jsp)(열어 읽음 · 영문 · 「effective as of December 26, 2025」). 조항 번호와 문장은 열람 도구가 옮긴 그대로다.

| 항목 | 원문 |
|---|---|
| 비상업 | 제6조② 「API Users may only use the API Service for non-commercial purposes」 |
| 제3자 제공 금지 | 제11조② 「The API User may not provide the data provided by the KRX to any third parties.」 · 제11조④ (도구 요약, 따옴표 아님) 위반 시 이용 권한을 철회할 수 있음 |
| 호출 한도 | 제8조④ 「The maximum number of requests for one (1) key shall be 10,000 a day (00:00 – 24:00 daily)」 · (도구 요약, 따옴표 아님) 초과하면 서비스가 중단될 수 있음 · 제8조⑤ 12개월 안 쓴 인증키는 사전 통지 없이 삭제될 수 있음 |
| 인증키 | 제5조② 「The KRX provides an Authentication Key to API Service applicants who meet certain requirements」 · 제7조⑤ 인증키의 양도 · 담보 금지 |
| 출처 표시 | 제10조③ 결과로 만든 쪽은 「created by using "KRX statistical information"」 임을 밝혀야 함 |
| 결과 변경 | 제6조③ 「The API User shall not insert other items before, after, or in the middle of the results of the API service」 |

- **회원가입 · 키 신청** — 소개 페이지 본문은 도구가 읽지 못했다(제목과 목차뿐). 절차(가입 → 키 신청 → **API별 서비스 신청 · 승인**)는 2차 출처 [krx-openapi (PyPI)](https://pypi.org/project/krx-openapi/) 의 설명이다. 가입 · 로그인 페이지는 열지 않았다 → 공식 절차는 **확인 못 함**.
- **제공 시각** — 2차 출처 [krx-openapi (PyPI)](https://pypi.org/project/krx-openapi/): 「다음 영업일 오전 8시에 갱신됩니다」(주말 · 휴일 · 갱신 전 조회는 빈 결과) · 같은 값을 적은 다른 2차 [openkrx-mcp (PyPI)](https://pypi.org/project/openkrx-mcp/) 「매일 오전 8시(KST)에 갱신」. **공식 확인 못 함.** 맞다면 금요일 종가는 월요일 08:00 으로, 포털(월요일 ≤ 12:30)보다 4시간 안팎 이르다.
- **우리 쓰임과의 충돌** — 「제3자에게 제공하지 않는다」 · 「비상업」: 우리 앱은 수업 프로젝트(비상업)이지만 서버가 받은 값을 여러 사용자 화면에 보이면 제3자 제공으로 읽힐 소지가 있다. 이는 법률 판단이 아니라 조항과 우리 쓰임을 맞대 본 것이며 KRX 의 해석은 **확인 못 함**.
- 앞 조사도 같은 결론: 「약관: 비상업만 · 제3자 제공 금지 · 승인 필요 · 웹 스크래핑은 금지」.

## 4. 금요일 데이터가 없을 때 화면 · 신호 · 예측은 무엇을 보여야 하나

### 4.1 업계 관행 (출처가 약해서 **참고 수준**)

- 값에 **기준 시각 · 기준일(as of)** 을 붙이고, 배치 데이터를 「live」 라 부르지 않는다 — 2차 [Basedash: data freshness](https://www.basedash.com/blog/data-freshness-how-current-your-dashboard-data-really-is) (「data as of」 는 원천 데이터 시각으로, 마지막 갱신 실패 시 낡은 숫자를 경고 없이 계속 보이는 것을 문제로 지적). 공식 UX 지침은 **못 찾음**.
- 종가는 잠정 → 확정 순서로 나오는 공급사도 있다 — 앞 조사 C절 인용: CSI Data 「Preliminary 4:45pm → 공식 업데이트 약 7pm」 · dxFeed 「최종 종가는 거래소 정정 때문에 마지막 체결가와 어긋날 수 있다」(앞 조사가 열어 읽음). 이번에 원문을 다시 열지는 않았다.
- 직전 종가 정의: previous close = 직전 정규장의 마지막 가격(시간외 체결로 안 바뀜) — 2차 [yfin-docs: Financial Fields](https://yfin-docs.pages.dev/concepts/financial-fields) 의 필드 설명. Yahoo 화면 「At close」 라벨의 공식 뜻은 **확인 못 함**.
- **장중 시세로 대체하지 않기** — 장 열린 뒤의 현재가(월요일 09:00 ~ 15:30 의 KIS ① 값)는 월요일의 가격이지 금요일 종가가 아니다. 이를 직전 종가 자리에 넣으면 날짜가 다른 숫자가 같은 칸에 섞인다. 업계 문서로 확인한 것은 previous close(직전 정규장 마지막 가격)와 현재가가 별개 필드라는 점뿐이고(위 yfin-docs), 한국 서비스의 화면 규칙은 **확인 못 함**. 우리 `quote_now` 는 이미 라벨로 구분한다(`app/services/quote_now.py` 머리말: 「10월 16일 종가」 · 「장 마감 ·」 접두).
- 빈 값 채우기: 마지막 관측값 이월(LOCF)은 「새 관측이 없으면 가격이 안 변했다」 고 가정하는 것이고, 전체 표본 평균 같은 채움은 미래 정보가 섞이는 look-ahead 편향을 만든다 — 2차 [Hackernoon: Dealing with Missing Data in Financial Time Series](https://hackernoon.com/dealing-with-missing-data-in-financial-time-series-recipes-and-pitfalls) · 연구 [arXiv 2102.12736](https://arxiv.org/pdf/2102.12736). 「빈 값을 표시만 하고 채우지 않는다」 를 직접 권하는 출처는 이번 검색에서 **못 찾음**(위험 · 백테스트 쪽 관행이라는 말은 근거 없이 쓰지 않는다).

### 4.2 대안 비교

| 안 | 보이는 것 | 장점 | 위험 |
|---|---|---|---|
| **A. 직전 확정 종가 + 기준일 + 「금요일 종가 반영 전」** (추천) | 「10-29 종가 · 공공데이터 · 금요일(10-30) 종가는 월요일 낮 반영」 | 사실만 말함. 우리 원칙(모름 · 기준일 · 출처)과 일치. 이미 `as_of` · `data_note` · `quote_now` 라벨이 있음(`app/services/stock.py:412-415`, `app/services/quote_now.py`) | 월요일 아침 결정이 이틀 전 가격 기준(그대로 — 숨기지 않고 밝힘) |
| B. 사용자 본인 KIS 키로 「참고 현재가」 | 키가 있는 사용자 화면에 **시각이 붙은 현재가 라벨만**. 주말 · 장 전에는 「장 마감 · 직전 종가」, 월요일 장중에는 그 시각의 현재가이며 **금요일 종가 자리에 넣지 않는다** | 약관 안(본인 키 · 본인 화면 · 저장 안 함) · 이미 있음 | 키 없는 사용자는 A 로 내려감 · 신호 입력 · 점수에는 섞지 않음 |
| C. 서버 공용 키 / KRX 로 금요일 종가를 받아 전원에 보임 | 모두에게 금요일 값 | 빈 구간이 줄어듦 | KIS 제5조③ · KRX Open API 제11조② 에 걸릴 소지 · 포털 표에 섞으면 출처 구분이 사라짐(앞 조사 C.3) |
| D. 예측 · 보간으로 금요일 값 채우기 | 금요일 종가 추정치 | 화면이 비지 않음 | 추정치가 가격처럼 보임 → 신호 · 백테스트 · 대사에 새어 들어가면 되돌리기 어려움 · look-ahead 위험 · 우리 원칙(지어내지 않음) 위반 |
| E-1. 12:30 회차를 **앞당기기** | — | — | 월요일 13시 전 게시가 확인 안 됨 · 이미 12:30 에 받고 있음(1.2) → 효과 불확실 |
| **E-2. 보조 시도: 예상 거래일인데 시세가 비어 있으면 13:30 뒤 한 번 더 받기** | 화면은 그대로, 받는 시점만 달라짐 | 호출 1회 · 12:30 에 못 받은 날을 **다음 날 12:30 이 아니라 같은 날 오후**로 당김(최대 하루 단축) · 13:30 뒤라 HF 맞추기 금지 창(11:00 ~ 13:30)과 안 겹침 · 앞 조사 D절 안 D 에서도 검토 대상 | 이 표본에서 필요했던 날은 관측 안 됨(1.2) → 효과는 가설 · 구현은 팀 파일 `scripts/daily_update.py` 라 안내 이슈 필요 · 달력이 거래일인데 시세가 0건인 날만 대상으로 좁힐 것 |

**추천 = A (+ 사용자 키가 있을 때만 B 를 「참고 표시」 로 허용, 이미 구현됨).** 버린 것: D(가격처럼 보이는 추정), C(약관), E(측정 전 효과 모름). 「예측」 기능이 있다면 그 출력은 **예측 대상일 · 입력 기준일을 명시**하고 금요일 값을 입력으로 만들어 넣지 않는다(예측 화면이 대상일을 지금 어떻게 말하는지는 이번에 확인 못 함).

| 바꾸지 않을 것 | 12:30 회차 시각을 **앞당기는** 것 | 평일 적재가 이미 12:30 대에 되고 있어 앞당길 근거가 없음(1.2). 앞당기기와 위의 「보조 시도」 는 다른 안이다 |
| 결정 보류 | KRX Open API 시험 신청 | 비상업 · 제3자 제공 금지라 서버 공용 수집에는 못 쓰고, 개인 확인용에 그침. 효용이 작음 |

### 5.2 사용자가 정할 것

1. 월요일 장 시작 전 금요일 종가가 필요한 쓰임이 (가) 사람이 보는 화면인가 (나) 일일 신호 스냅샷 · 예측 점수인가 (다) 자동매매 판단인가 — (가)만 본인 키로 가능하고 (나)(다)는 공용 서버 배치라 약관상 어렵다(앞 조사 E.2-1 과 같은 결론).
2. 「반영 전」 배지를 붙일 화면(시그널 · 퀀트 대시보드 · 투자 인디케이터 · 종목 허브).
3. 월요일 이른 아침 포털 단발 확인을 할지, 한다면 시각.
4. KIS 공식 명세(기간별 시세의 모의 지원 · 건수 · 한도)를 사용자가 KIS 포털에서 직접 확인해 줄지(이번 조사는 스크립트 페이지라 못 엶).

## 6. 확인 못 한 것 (추측으로 닫지 않음)

1. 월요일 13시 이전 포털 게시 시각 — 12:30 이전 기록이 없다.
2. 데이터셋 페이지의 갱신 주기 표기 불일치(「실시간」 vs 「일 1회」)의 공식 설명.
3. KRX Open API 소개 · 신청 절차 · 서비스 명세의 공식 문장과 제공 시각(2차의 「다음 영업일 08:00」 만 있음).
4. KIS 기간별 시세 · 일별 시세 TR 의 공식 명세(모의 지원 · 건수 · 마감 직후 확정 여부) · 공식 호출 한도 수치 · 고객 이용약관 전문 재확인.
5. 우리 기록 `collector/README.md:278-279` 의 「KIS 가 금요일 종가를 줬다」 가 어느 TR 이었는지.
6. 키움증권 API 의 마감 직후 제공 · 약관.
7. 화면별로 「종가 반영 전」 이 이미 어떻게 보이는지 전수 점검(이번에 화면을 열지 않았다).
8. 10-26(월) 12:30 회차가 왜 없었는지(앞 조사 E.1-1 과 같음).
