# API 명세서 넓은 표 44개 — 열 나누기 설계 조사 (2026-10-31)

- **결론**: 넓은 표 44개는 두 갈래다 — 라우터별 엔드포인트 표 **43개(12열 · 행 합계 285)** + 닿는 곳 × 라우터 행렬 **1개(15열 · 44행)**. 15줄을 넘는 행은 **단 1개**(`API-STK-30`, 22줄 추정)이고, 나머지 문제는 전부 「열 수」다.
- **원인**: 12열 표는 `scripts/api_scan.py` 의 `markdown()` 한 함수가, 15열 행렬은 `markdown_overview()` 가 만든다. 시험(`tests/`)은 이 표의 열 머리 · 순서를 한 군데도 읽지 않는다(grep 확인). 카탈로그(`catalog.json`)도 이 표가 아니라 `Route` 필드에서 만든다.
- **추천**: (가) 한 라우터 절 안에서 **표 둘로 나누기**(계약 7열 + 연결 6열) + 소작업 둘(`API-STK-30` 요청 칸 「외 N」 · 행렬 7+7 분할). 열 최대 8 · 행 최대 11줄(추정)로 내려가고, 고칠 코드는 세 함수(`markdown` · `markdown_overview` · `_params_cell`)와 시험 한 개 추가다.
- **사용자가 정할 것**: ① 위 (가) 로 갈지, 아니면 문서 작성 기준 부록 ⑧(「대장 · 추적표는 열 8개 예외」)을 4절 표까지 넓혀 **안 고치기**(작업량 0)로 갈지 ② 「닿는 곳」을 계약 표에 두지 않고 연결 표로 보내도 되는가(3절 발견이 이 칸에 기댐).
- 측정은 `docs/_local/도구/table_readability.py` 의 함수를 그대로 써서 같은 추정식(화면 폭 100 · 칸 폭 비례)으로 한 값이다 — 브라우저 실제 줄 수가 아니라 **추정**이다.

## 1. 44개 표의 종류

## 4. 설계안

시뮬레이션: 43개 표의 285행을 `table_readability` 의 추정식에 그대로 넣어 안마다 다시 쟀다(표마다 열 폭 평균으로 비례 배분). 「행 합」은 안마다 늘어나는 문서 줄 수의 대략이다.

| 안 | 열 수 | 행 합 | 최대 추정 줄 | 15줄 초과 | 8줄 초과 | 추정 줄 합 |
|---|---|---:|---:|---:|---:|---:|
| 현재 | 12 | 285 | 22 | 1 | 2 | 858 |
| (가) 계약 표 + 연결 표 | 7 + 6 | 570 | 11 | 0 | 1 | 891 |
| (나) 핵심 7열만 본문 + 연결 정보는 부록 | 7 (+부록 별도) | 285 | 11 | 0 | 1 | 472 (+부록) |
| (나') 닿는 곳을 계약 표에 남긴 변형 | 8 + 5 | 570 | 17 | 1 | 1 | 981 |
| (다) 열 합치기 8열(`<br>` 로 칸 겹침) | 8 | 285 | 22 | 1 | 3 | 1041 |

### (가) 한 라우터 안에서 표 둘 — 「계약」 + 「연결」
- 계약 표: `API ID · 메서드 · 경로 · 인증 · 요청 · 응답 · 오류`(7). 연결 표: `API ID · 닿는 곳 · 화면 · 파트(제안) · 요구 ID · 코드`(6). 두 표의 행 차례 · API ID 가 같다.
- 장점: 정보 손실 0 · 열 최대 7 · 최대 11줄 · 한 라우터 절 안에서 위아래로만 움직임 · 「닿는 곳」(3절 발견의 근거)이 문서에 그대로 남음 · 의미 단위가 자연스럽다(받고 주는 것 / 어디에 닿고 누가 부르고 누구 몫인가).
- 단점: 한 API 를 보려면 표 둘을 ID 로 맞춰야 함 · 문서 줄 수 +약 457(285행 + 43절 × 머리 4줄 어림) → 1642 줄 → 약 2100 줄.
- 바꿀 파일: `scripts/api_scan.py` `markdown()` 1122~1140(머리 문자열 둘 · 행 만들기 분리) · API 명세서 4절 재생성(`--doc`) · 1.3절 한 문장(「4절은 표를 둘로 나눴다」) · 개정 이력 한 줄 · 판 올림 · 시험 `tests/test_api_scan.py` 에 TC-AP 하나 추가(모든 표 열 ≤ 8 · 두 표 행 수 · API ID 차례 동일) · 「TC-AP 15건」 문구 2곳.
- 렌더링: GitHub 에서 7열 표는 100자 폭에서 대부분 1~4줄. 가장 읽기 쉬움(추정).
- 작업량: **중**(코드 한 함수 + 시험 하나 + 문서 재생성 · 판 올림).

### (나) 본문은 핵심 7열, 연결 정보는 부록 표
- 4절 표는 계약 7열만. 「닿는 곳 · 화면 · 파트 · 요구 ID · 코드」는 새 표시 블록(`<!-- api_scan:links -->`) 한 곳에 모은다. 앱 안에서는 이미 `/api-docs/` 화면이 같은 칸을 카탈로그로 보여 준다(API 명세서 1567 줄).
- 장점: 본문이 가장 짧음(추정 줄 합 472) · 부록은 한 표라 검색 쉬움.
- 단점: 부록이 285행 한 표(또는 43개 표)라 길고, 본문에서 「닿는 곳」이 사라져 3절 · F2 등 발견과 거리가 생김 · `DOC_BLOCKS`(1254) · `main()` 1326 호출 · 문서에 표시 쌍 신설이 필요(`fill_doc` 는 표시 쌍이 없으면 종료) · 부록 표도 5~6열이라 새 코드 · 새 시험 필요 → (가) 보다 손이 더 감.
- 작업량: **중~큼**.

### (다) 열 합치기 — 비추천
- `메서드 + 경로` · `API ID + 코드` · `화면 + 파트 + 요구 ID` 를 한 칸에 `<br>` 로 쌓아 8열로. 열 수는 맞지만 최대 22줄 그대로 · 줄 수 합이 오히려 늘고(1041) · 칸이 좁아져 8줄 초과가 3개. 가독성 이득 없음.

### (라) `<details>` 접기 — 기각
- 확인된 근거: 측정 도구는 HTML 을 지우지 않고 글자를 그대로 세므로(`cleanCell` 은 링크 · 굵게 · 백틱만 벗김) **접어도 추정 줄 수가 줄지 않는다** — 이 프로젝트의 15줄 기준으로는 해결책이 못 된다. 또 표는 한 행이 한 줄이라 행 단위 접기가 어렵다고 보며(GitHub 가 표 칸 안 `<details>` 를 어떻게 그리는지는 직접 열어 보지 않았다 — **미확인**), 접으려면 API 285개를 표가 아닌 목록 블록으로 바꿔야 해 스캐너 전체 출력이 바뀐다.
