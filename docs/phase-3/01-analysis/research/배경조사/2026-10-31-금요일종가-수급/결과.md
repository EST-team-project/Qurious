## 0. 한 줄 결론 (먼저)

1. **공식 설명이 이미 답을 적어 두었다** — 공공데이터포털 「금융위원회_주식시세정보」 설명: 「데이터 갱신은 기준일자로부터 영업일 하루 뒤 오후 1시 이후에 업데이트됩니다」 · 「갱신주기는 일 1회」. 금요일 기준일 자료는 **다음 영업일(월요일) 13:00 이후**가 정상이다. 포털 쪽 고장이 아니라 **설계상 그렇다.**
2. **매일 아침의 문제이고, 월요일은 달력 시간만 더 길다.** 평일 자료도 「영업일 하루 뒤 13:00 이후」라 장 열기(09:00) 때 수집 DB 의 마지막 종가는 항상 **하루 전 거래일 종가**가 아니라 **그 전 거래일 종가**다(금요일 아침이면 수요일 종가). 월요일 아침이 목요일 종가인 것과 거래일로는 똑같이 하루가 빠진다. 월요일이 더 나빠 보이는 까닭은 달력 시간(평일 약 21시간 vs 주말 약 69시간)이 길어 그 사이 뉴스 · 가격 변동이 더 쌓이기 때문이다. 앞 조사서 v1.0 1.3절 2번(「12:30 회차 전까지 D-2」)도 같은 말이다.
2-1. **회차 시각을 옮겨서(안 D)는 월요일 아침을 못 푼다** — 공식 일정이 월요일 13:00 이후라서. 다만 안 D 가 쓸모없는 것은 아니다(D절).
3. 월요일 장 열기 전에 금요일 종가가 필요하면 **다른 출처**(증권사 일봉 · KRX)가 필요하다. 우리 코드에는 증권사 일봉을 부르는 함수가 **이미 있다**(`KisBroker.get_daily_ohlcv`) — 단 수집 파이프라인에는 연결돼 있지 않고, 약관상 「자기 키 · 자기 화면」 범위다(5절).

### C.3 수집 파이프라인이 빈 응답을 어떻게 다루나 — 임시 종가를 끼울 자리

- 시세 단계: `scripts/daily_update.py:257` `Step("price", ["-m","collector.backfill","recent","--quiet"], 30, warn_codes=(EX_UNAVAILABLE,))` — 매일 12:30(`:145` `DEFAULT_TIME`).
- `collector/backfill.py:206` `run_recent` · `RECENT_WINDOW=14`(`:61`): 최근 14일을 되돌아보며 빈 날을 다시 받는다. `pick_targets`(`:83-134`): `done`/`holiday` 건너뜀 · `empty`는 10일(`SETTLE_DAYS=10`, `:57`) 안이면 **다시 받음** · 지나면 휴장 확정.
- `collector/sources/portal.py:160-182`: `totalCount=0` → `status = "empty"`(행 0건). 모듈 머리말(`:17-33`)이 「휴장일과 아직 안 올라온 날이 구분되지 않음 · 당일 받기는 성립하지 않음」을 명시.
- 즉 **빈 날은 이미 「보류」로 취급되고 재시도된다.** 월요일 13:00 이후 회차에서 금요일이 자연히 채워진다. 이 부분은 의도대로 동작한다.
- **임시 종가를 끼울 자리**: `price_daily`(PK `bas_dt, srtn_cd`, `collector/db.py:89-108`)에는 「잠정/확정」 구분 칸이 **없다**(`raw_sha256` · `halted` 만). `ingest_day.status` 는 `done|empty|holiday|error` 뿐. 따라서 포털 표에 증권사 값을 섞어 넣으면 (a) 약관 문제(portal 표는 공공누리 4유형 · HF 로 나감) (b) 나중에 포털이 같은 PK 로 덮어쓸 때 출처 구분 불가 — **별도 표/별도 읽기 경로**가 안전하다. 읽기 쪽 합류 지점은 `collector_db.read_daily_candles`(`:154`) 한 곳이다(`stock.get_candles` 가 가장 먼저 부르므로 지표 · 시그널 · 자동매매가 모두 여기를 지난다).
- 앱은 수집 DB 에 쓰지 않는다(읽기 전용 `mode=ro`, `collector_db.py:181-182`) — 임시 종가를 이 DB 에 써 넣는 설계는 이 원칙과 충돌한다.
- 참고(우리 문서): `collector/README.md:278-279` — 2026-09-19 에 「KIS 는 09-18 금요일 종가를 이미 주고 있었다」(삼성전자 260,000). 즉 증권사 쪽이 금요일 종가를 주말에 이미 갖고 있다는 **우리 실측 기록이 있다.**
- 참고(우리 문서): `docs/phase-2/01-analysis/research/실시간시세-지연표기-조사.md` v1.0 — 화면별 「현재가」 출처 · 약관 원문 · 받는 길 다섯(4절 표 4-1) · `quote_now` 도입 경위. 이번 질문과 겹치는 부분은 이 문서를 다시 쓰지 않고 가리킨다.

### A.1 공공데이터포털 금융위원회 주식시세정보 — 공식 문구 (핵심)

- 「데이터 갱신은 기준일자로부터 영업일 하루 뒤 오후 1시 이후에 업데이트됩니다.」 · 「※ 데이터 갱신주기는 일 1회입니다.」
- 같은 페이지 메타정보는 「업데이트 주기: 실시간」 으로 적혀 본문과 **어긋난다**(페이지 자체의 불일치 — 본문 쪽이 우리 관측과 맞는다).
- **금요일은 어떻게 다른가**: 문구가 「영업일 하루 뒤」 이므로 금요일 기준일 자료는 **다음 영업일 = 월요일 13:00 이후**. 휴일이 끼면 그 뒤 영업일(우리 기록 10-02(금)→10-06(화)는 10-05 대체공휴일을 낀 같은 규칙). 우리 적재 기록 세 건(금→월)이 모두 이 규칙과 맞는다.
- 우리 관측과 문구의 어긋남 하나: 10-19(월)에 금요일 자료가 **12:30 회차에서** 들어왔다(조사서 v1.0 1.1절 · 회차 12:30:01~13:24:43 · 시세 단계가 첫 단계). 「13:00 이후」 가 최악 기준의 보수적 문구이거나 실제 올리는 시각이 더 이를 수 있다는 뜻이다. **그러나 월요일 장 열기(09:00) 전에 이미 올라와 있는지는 우리 기록으로는 모른다**(회차가 12:30 에만 돌아 그 전에 본 적이 없다 — 확인 못 함).
- 이용허락: 「이용허락범위 제4유형 : 출처표시 + 상업적 이용금지 + 변경금지」. 본문: 「본 데이터는 상업적 목적 여부와 상관 없이 제3자 무단 제공 및 재배포가 엄격히 금지됩니다.」(원천 소유자 한국거래소에서 유료 구매 안내 포함). **⚠ 이 문장이 새로 들어간 것인지는 확인 못 함**(수정일 2026-10-28). 우리가 HF private 으로 팀에 공유 중인 것과 부딪히는지는 E 에 올린다.
- 일일 호출 한도: 이 페이지에서 **확인 못 함**(우리 실측은 응답 헤더 `X-RateLimit-Limit: 10000` — `collector/README.md` 6절).

### A.2 KRX

- KRX Open API(openapi.krx.co.kr): 약관상 비상업 목적만(제6조②) · 제3자 제공 금지(제11조②) · 키당 하루 10,000건(제8조④). 서비스별 이용 신청과 담당자 승인이 필요하다는 2차 자료(PyPI 래퍼 설명) — 공식 확인 못 함. **「일별매매정보」가 마감 뒤 몇 시에 올라오는지는 공식 문구를 못 찾음.**

- 참고(이미 우리 기록): 코스콤 정보이용정책상 계약 없는 서비스가 다른 사람에게 시세를 데이터피드로 주는 것은 승인 대상(조사서 v1.0 3.1).

## B. 업계 일반 패턴 — 「확정 종가가 늦는 문제」를 푸는 방식

| 패턴 | 근거(출처 · 확인 방법) | 우리에게 |
|---|---|---|
| 1. **잠정 값으로 먼저, 확정 값으로 정정** — 공급사가 두 단계를 상품으로 나눠 판다 | ICE EOD 「unconfirmed 와 confirmed」(열어 읽음) · CSI Data 「Preliminary 4:45pm → 공식 업데이트 약 7pm · 잠정은 개정될 가능성이 높다」 https://csidata.com/custserv/onlinehelp/OnlineManual/preliminarystockdata.htm (열어 읽음) · Databento 용어집 「잠정 정산가 후 최종 정산가」(검색 요약) | 안 B 의 구조. 단 우리 포털은 「확정 한 가지」만 주므로 잠정 값은 **다른 출처**에서 온다 |
| 2. **정정이 끝난 뒤 실행** — 시그널을 교정 창 뒤에 돌린다 | Wealth-Lab 포럼 글 「Fidelity 교정이 저녁에 반영되니 다음 날 새벽 6시(ET) 뒤에 갱신하라, 아니면 시그널이 어제 떴다가 사라진다」(검색 요약 · 사용자 경험담) | 안 D 의 취지. 우리는 이미 「확정 값 뒤에 계산」 구조 |
| 3. **교정 사실을 인정하고 점 시점 보관** — 종가는 마지막 체결가와 다를 수 있어 공급사가 비조정/공식/조정 세 파일을 따로 낸다 | dxFeed 「최종 종가는 거래소의 정정 때문에 마지막 체결가와 어긋날 수 있다. 하루 세 파일」(열어 읽음) | 「그 시그널을 만든 시점의 가격이 무엇이었나」 기록(`as_of` · 출처 칸)을 남기는 편이 안전 |
| 4. **화면에 기준 시각/기준일 명시** — 지연·종가를 쓸 때 쓰는 시각을 표기 | 인베스팅닷컴 「지연 데이터 · 시각」 · 네이버 「KRX 제공」 · 트레이딩뷰 「20분 지연」(우리 조사서 v1.0 표 2-1) | 안 A. 본보기가 우리 화면에 이미 셋(전략 분석 · 상품 안내 · 종목 허브 카드) |
| 5. **데이터 일정에 맞춰 일정 자체를 바꿈** — 일일 일괄 데이터를 다음 날 이른 아침으로 약속 | QuantConnect 일괄 데이터 「다음 날 07:00 ET」 등(검색 요약) | 안 D. 단 포털 갱신이 「영업일 다음 13:00」이므로 우리에겐 맞춰 옮길 이른 시각이 없다 |

위 5개 중 어떤 것도 「한 출처만으로 마감 직후 확정 종가를 얻는다」 가 아니다. 업계는 (a) 잠정/확정 구분 (b) 교정 뒤 실행 (c) 기준일 표기 중 하나 이상을 쓴다. 한국 퀀트 서비스가 어느 방식을 쓰는지는 공개 설명을 못 찾았다(확인 못 함).

### D.1 추천 (한 줄 — 결정은 사용자)

**안 A 를 먼저 하고, 월요일 이른 아침에 포털에 금요일 자료가 있는지 한 번 재 보는 측정(안 D 의 확인판)을 붙이며, 안 D 의 13:30 이후 보조 회차는 비용이 작아 함께 검토하고, 안 B 는 「내 키로 내 화면만, 저장 없음, 잠정 표시」 로 좁힌 B-lite 만 후보로 둔다** — 근거: 공식 문구가 월 13:00 이후라 시각 조정만으로는 안 풀리고, 증권사 값을 공용 시그널에 쓰면 KIS 약관 제5조③ 에 걸린다.

## E. 확인 못 한 것 · 사용자가 정할 것

### E.1 확인 못 한 것

1. **포털이 월요일 몇 시에 금요일 자료를 올리는가** — 공식은 13:00 이후, 우리 10-19 는 12:30 회차에서 이미 들어옴. 월요일 09:00 전에 있는지는 기록이 없다(회차가 12:30 하나뿐). 측정이 안 D 의 선행 조건이다.
1-1. **10-26(월) 「18:54 회차에서야 들어옴」 은 포털이 늦었다는 증거가 아닐 수 있다** — 러너 이력(`data/collector/state/daily_update_history.jsonl`, 읽기만)에서 10-26 에는 시작 18:54:23 회차만 있고 12:30 회차 줄이 없다(PC 가 꺼졌거나 다른 PC 가 돌았을 가능성 — 까닭은 확인 못 함). 즉 그날 12:30 에 포털에 자료가 있었는지는 모른다. 10-27 도 19:05 시작이 처음이다. 반면 10-19 · 10-30 은 12:30:01 시작 회차가 있다. **이 이력만으로 「포털이 월요일 오후에 늦게 올린다」 고 단정할 수 없다.**
2. **페이지 문구 「상업적 목적 여부와 상관 없이 제3자 무단 제공 및 재배포가 엄격히 금지」 가 새로 들어간 것인지, HF private 팀 공유와 어떻게 만나는지** — 페이지 수정일 2026-10-28. 우리 쪽 근거는 공공누리 4유형(`collector/README.md` §8). 이 조사는 법적 판단이 아니라 문구 발견까지.
3. **KRX 정보데이터시스템 · Open API 의 일별 자료 공개 시각** — 약관·소개 페이지에는 없음. 담당자 승인 후 서비스 명세에 있을 수 있다.
4. **KIS 일봉 TR(`FHKST01010400`/`FHKST03010100`)의 모의 도메인 지원 · 마감 몇 분 뒤 당일 봉이 확정값인지 · 수정주가 파라미터 공식 정의** — 공식 명세 페이지가 스크립트라 못 엶. 2차 자료만.
5. **키움 REST 마감 직후 제공 · 약관 원문**, **FnGuide · Bloomberg · 국내 퀀트 서비스 · 네이버 · 토스의 갱신 시각** — 공개 설명을 못 찾음(Bloomberg 는 조사 안 함).
6. **2026-09-14 애프터마켓 개설 뒤 포털 `clpr`/`trqu` 가 정규장 기준 그대로인가** — 확인 못 함. 종가 산정 변경 여부는 기사에 없음.
7. **앱의 월요일 화면이 실제로 목요일 종가를 「현재가」 로 보이는 곳이 지금 몇 곳 남았나** — 조사서 v1.0(10-19) 이후 `quote_now` 도입으로 줄었으나, 이번에 화면 전수를 다시 하지 않았다.

### E.2 사용자가 정할 것

1. 월요일 장 열기 전 금요일 종가가 필요한 쓰임이 무엇인가 — (가) 화면에서 사람이 볼 값 (나) 일일 신호 스냅샷/예측 점수 (다) 자동매매 판단. **(가)는 사용자 키로 가능성이 있고, (나)(다)는 공용·서버 배치라 약관상 어렵다.**
2. 안 A 의 기준일 문구를 어느 화면에 붙일지(시그널 · 퀀트 대시보드 · 투자 인디케이터).
3. 월요일 이른 아침 포털 존재 여부 측정(한 번의 단발 호출 — 사용자가 직접 또는 지시).
4. KRX Open API 신청 여부(시험 호출 가능하면 안 C 의 효과가 판가름).
5. (E.1-2) 포털 재배포 문구 관련 팀 확인을 할지.
