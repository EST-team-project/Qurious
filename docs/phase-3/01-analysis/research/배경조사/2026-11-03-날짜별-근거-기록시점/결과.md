# 날짜별 근거와 「기록 시점」 — 뒤늦게 계산한 신호를 어떻게 알릴까 (2026-11-03)

> 작업 기록 · 정본 아님. 읽기 전용 조사(코드·문서 읽기 + 공개 자료). 코드·문서는 고치지 않았다.
> 사용자 피드백(11-03, 종목 근거 화면): 「날짜별 근거를 확인할 수 있으면 좋겠다. 신호가 바로바로 기록되는 것이 아니고 나중에 작성(소급)되는 경우에는 그 기록을 믿고 판단하기 어렵다. 다른 서비스·분야는 어떻게 처리하는지 리서치가 필요하다.」

## 0. 맨 위 5줄 요약

1. **우리 기록 한 줄에는 기준일(`as_of`)과 계산 시각(`computed_at`)이 이미 둘 다 있다**(`app/models/signal.py:24,39`). 그러나 **종목 근거 모달(허브 `signal` 칸)에는 기준일만 보이고 계산 시각은 안 나간다**(`stock_hub.py:311`, `stockdrawer.js:196,201`). 계산 시각은 신호 순위 머리줄에만 있다(`stock_hub.py:336-367`).
2. **「소급」을 구분하는 칸은 없다.** 게다가 같은 날 줄을 다시 돌리면 **`computed_at` 까지 새 값으로 덮어써서**(`mtf_signals.py:238-240`) 「처음 언제 기록됐나」가 사라진다. 이력 테이블도 없다.
3. **날짜를 고르는 길은 API 에만 있고 화면에는 없다.** `GET /api/stock-hub/signal-rank?on=` · `GET /api/explain?date=` 는 되지만 허브(`/api/stock-hub`)는 `on` 이 없고, 화면 어디에도 날짜 입력이 없다. 또 우리는 **「실시간」 기록이 없다** — 정상 기록도 다음 거래일 낮 12:30 회차에 계산된다(`stock_hub.py:319-333`).
4. 외부 관행은 한 줄로 모인다: **「값이 가리키는 날」과 「그 값을 알게 된(기록된) 날」을 따로 저장하고, 화면·조회에서 둘을 모두 보인다**(Zipline `asof_date`/`timestamp` · ALFRED vintage · Fowler bitemporal · Feast `created_timestamp`). 소급 항목은 숨기지 않고 **표시**한다(Statuspage 「backfill」 — 알림도 안 보냄).
5. **추천: 안 A(새 칸 없이 서버가 기존 `computed_at` 으로 「정기/늦게 계산」을 판정해 보이고, 모달에 날짜 고르기)** 를 11-05 전에, 안 B(기록 방식·최초 기록 시각 칸)는 팀원 파일을 건드리므로 이슈 안내 후 동결 뒤 또는 합의될 때, 안 C(추가 전용 이력)는 후속 과제로 문서에 남긴다.

### 1.4 지금 구조에서 생기는 정직성 문제 (코드에서 읽은 것만)

1. **「덮어쓰기」가 이력을 지운다.** 같은 `(as_of, symbol, definition)` 을 다시 돌리면 값도 시각도 바뀐다 → 「11-02 줄이 11-03 에 한 번 기록됐고 11-05 에 다시 계산됐다」는 사실이 남지 않는다.
2. **「실시간」이 없다.** 우리 신호는 종가 기준이라 정상 경로도 다음 거래일 낮에 계산된다. 즉 「바로바로 기록」의 기준선 자체가 「다음 거래일 낮」이다. 사용자 피드백의 `실시간/회차/소급` 3분류 중 **「실시간」은 우리에게 해당 없음**.
3. **PC 마다 앱 DB 가 따로다**(여러 PC 회차 설계: 쥔 PC 만 돌고 나머지는 따라감 — `daily_update.py:102-110, 222-224`). 한 PC 의 DB 에서는 정상 기록이 다른 PC 의 DB 에서는 「늦게 따라잡은」 기록이 된다. **`computed_at` 만으로 판정하면 이 PC 에서는 거짓 경보(소급처럼 보임)가 날 수 있다** — 발표 환경의 DB 가 어떤 PC 것인지에 따라 달라진다(확인 못 함).
4. **`load_snapshot`/`load_day` 는 현재 정의 판(`DEFINITION`)만 읽는다**(`signal_explain.py:283-284, 328`). 지표 정의 판이 바뀌면 **옛 판으로 기록된 날의 근거는 날짜를 골라도 안 보인다**(기본키에 `definition` 이 있어 지워지진 않음).
5. **소급 계산의 내용 자체는 look-ahead 가 없게 설계돼 있다**(D 까지의 봉만). 그러나 읽는 시세가 수정주가이고(`stock_hub.py:80` 「일봉 종가(수정주가)」 — 신호 계산이 수정주가를 쓰는지는 **확인 못 함**) 이후 분할·병합이 있으면 **그날 계산했다면 나왔을 값과 달라질 수 있다**. 그래서 「그날 화면이 실제로 보였던 값이 아니다」라는 표시가 필요하다 — 계산 오류가 아니라 **공개 시점**의 문제다.
6. **보존 기간**: `signals_all` 이 다루는 종목은 최근 120거래일만 둔다(`signals_all.py:17, 39, 58-71`) → 「날짜 고르기」는 그 종목들에서 120거래일 밖은 비어 있다.
7. 기록을 분석·검증에 쓸 때는 **봉인 구간(2026-09-01~)을 뺀다**는 규칙이 이미 있다(`signals_daily.py:14`) — 「기록 시점이 믿을 만한가」에 대한 우리 쪽 기존 장치.

### 2.2 빠진 것 / 못 한 것 (정직하게)

- WRDS·Refinitiv·Bloomberg 의 as-of 조회 **공식 매뉴얼은 열지 못했다**(유료/로그인). Bloomberg `OVERRIDE_START`류 확인 못 함.
- SEC `end/filed/fy/fp` 필드 정의의 **SEC 원문 못 찾음**.
- Fung & Hsieh 원문 수치는 못 열었다. 위 표의 수치는 후속 연구가 인용한 값이다.
- 「뒤늦게 계산한 값을 사용자에게 알리는」 **우리 규모의 한국 주식 서비스** 사례(증권사·핀테크 앱)는 찾지 못했다 — 검색해도 일반 면책 문구뿐이었고 근거로 쓸 만한 페이지가 없었다.
- 소매 화면에서 쓰는 「소급 배지」의 **표준 문구는 없다.** 문구는 3절에서 우리가 정한다.

### 2.3 사례에서 뽑은 공통 원칙

1. **두 날짜를 따로 저장한다**(대상 날짜 vs 기록 날짜). → 우리는 이미 저장 중.
2. **조회·화면에서 둘을 모두 보인다.** → 우리 모달에 빠진 부분.
3. **소급은 막지 않고 표시한다**, 그리고 사용자가 「그때 알려졌던 것」만 보겠다고 고를 수 있게 한다(ALFRED · Feast 필터).
4. **덮어쓰지 않는다**(Compustat PIT · 17a-4 · bitemporal). → 우리의 약점이지만 11-05 전에 고칠 일은 아님.
5. 정정·갱신 표시는 **무엇이 왜 바뀌었는지**와 함께(GOV.UK).

## 3. 우리에게 맞는 안

공통 원칙: **서버는 새 계산을 하지 않는다** — 이미 쓴 줄을 읽기만 한다(`stock_hub.py:21-22, 29` 의 원칙 유지). `mtf_signals.signal_at` · `DEFINITION` 은 건드리지 않는다.
**판 지문**: 모의 일지 판 지문은 `app/services/paper_journal.py:203-224` `_code_parts` 의 함수 목록(`stock._generate_signal`(정의는 `app/services/stock.py:420`) · `stock._calc_*` · `ta_utils.rma/rsi/bollinger` · `collector_db.read_daily_candles` · `risk_guard` · `trading_cost.*` …)의 소스로 만든다. 내가 읽은 범위(`:203-224`)에는 **`mtf_signals` · `signal_snapshots` · `signal_explain` · `stock_hub` 가 없다** → 안 A·B 가 고치는 파일은 지문에 들어가지 않는다고 본다. (목록 끝까지는 `:224` 이후를 읽지 않았다 — 구현 전 `_code_parts` 전체를 한 번 더 확인한다.)

### 3.0 「기록 방식」 어휘 제안 (실시간이 없으므로)

| 말 | 뜻 | 판정 |
|---|---|---|
| **정기 기록** | 기준일 다음 거래일 안에 계산(정상 12:30 회차 경로) | `computed_at`(KST 날짜) ≤ 기준일 다음 거래일 |
| **늦게 계산** | 그 뒤에 계산 — 놓친 날 채우기, 수동 `--from/--to`, **또는 같은 날 줄 재계산** | 위에 해당하지 않음 |
| (안 B 부터) **다시 계산** | 정기로 한 번 기록된 뒤 덮어씀 | 안 B 의 `first_computed_at` 필요 |

「늦게 계산」 안에 「소급 채움」과 「재계산」이 섞인다는 것을 문구에 숨기지 않는다(안 A 한계).

### 안 A — 최소안 (새 칸 없음 · 마이그레이션 없음)

**데이터**: 새 칸 없음. 서버가 `load_snapshot` 이 이미 돌려주는 `computed_at`(`signal_explain.py:290`)으로 판정한다.
- 허브 `signal` 칸 `data` 에 `computed_at`(KST 분) · `record_kind`(`regular`/`late`) · `lag_days` 추가. 판정 함수 하나(기대 기록일 = `as_of` 다음 거래일 · `_is_trading_day` 재사용 `stock_hub.py:314`).
- 허브에 `signal_on`(선택 날짜) 질의 인자: `signal(db, sym, in_universe, on)` → `load_snapshot(db, sym, on)`. 응답에 `requested_on` 과 `fell_back`(고른 날 줄이 없어 앞 날짜가 나옴) 도 싣는다 — 순위의 `older_note` 와 같은 정직함.
- 「그날 볼 수 있었나」(`visible_on_asof_next_day`): `computed_at ≤ 기준일 다음 거래일 23:59(KST)` — Feast 필터를 읽기 전용 표시로.

**화면** (`public/js/stockdrawer.js` 신호 칸 `sdSignalPlainBody`/`sdSectionHtml`):
- 머리: 「11-02 기준 · 11-03 12:59 계산」(지금은 「11-02 기준」뿐).
- 날짜 입력 하나 + 「앞 거래일 / 다음 거래일」 단추(모달 신호 칸 안). 고른 날 줄이 없으면 안내문.
- `late` 면 칩 「늦게 계산」 + 접이식 설명.

**고치는 파일**: `app/services/stock_hub.py` · `app/routes/stock_hub.py`(`signal_on` 인자) · `public/js/stockdrawer.js` 만. `load_snapshot` 이 이미 `on` 을 받고 `computed_at` 을 돌려주므로(`signal_explain.py:276-290`) **`signal_explain.py` 는 고치지 않는다** — 그 파일에는 팀원 코드(`load_day`·`side_counts` — 신장환 님 PR #352)가 있다. `/api/explain` 응답에 `computed_at` 을 더하는 일은 팀원 파일을 건드리므로 **안 A 범위 밖**.

**시험 영향**: `tests/test_stock_hub.py`(칸 꼴 · 판정 경계: 정시 / 다음날 / 주말 / 공휴일) · (`tests/test_signal_explain.py` 는 고치지 않음) · 프런트 순수 함수 시험(`signal-rank.js` 와 같은 방식 — `tests/test_signal_rank_screen.py` 가 현재 작업 트리에서 수정 중이라 겹침 주의). `stock_hub.VERSION`(=3, `:54` — 「칸 이름·꼴을 바꾸면 올린다」)을 4 로 올려야 하는지 확인. 명세 쪽은 API 명세서(허브 `signal_on` 인자) · 화면대장 · UI 명세서에 반영(동결 뒤 일괄 판올림 규칙).

**위험/한계**:
- 「늦게 계산」이 **재계산**과 **소급**을 못 가른다(1.4-1).
- **PC 가 다르면 거짓 경보**(1.4-3). 발표 DB 가 정기 회차를 직접 돈 PC 의 것인지 확인 필요.
- 팀원 파트 침범: **없음** — 고치는 파일이 `stock_hub.py` · 라우트 · `stockdrawer.js` 뿐이다(위 「고치는 파일」). 이 파일들의 최근 팀원 수정 여부는 구현 전 `git log` 로 한 번 더 본다.
- 예상 작업량(내 어림, 검증 안 함): 표시만 반나절, 날짜 고르기까지 하루 안팎.

### 안 B — 중간안 (새 칸 둘 · 마이그레이션 1건)

**데이터**: `signal_snapshots` 에 nullable 칸 추가(알벰빅 선례 `0023_signal_opinion.py`):
- `record_mode` — `daily`(인자 없는 정기) / `backfill`(`--date`·`--from/--to`·`run --fill`·`gap_fill`).
- `first_computed_at` — **최초 기록 시각**. upsert 의 `set_` 에서 제외해 덮어쓰지 않음(`mtf_signals.py:238-240`). 이후 `computed_at`=마지막 재계산 시각.
- 기존 줄은 NULL → 화면은 「기록 방식 모름 — 계산 시각으로 짐작」(안 A 규칙으로 대체).

**서버**: 안 A + `record_kind` 를 칸 값 우선, 없으면 짐작. `regular / backfill / recomputed` 셋을 가른다.

**화면**: 안 A + 순위 화면 날짜 선택기 + 머리줄에 「늦게 계산된 줄 n개」 + 「그날 볼 수 있던 기록만 보기」 토글.

**위험**: **`mtf_signals.write_snapshots`(`mtf_signals.py:211-243`)와 `signals_daily.py` · `signals_all.py` 를 고쳐야 한다.** 신호 배치 코드는 팀원(주담당) 것으로 적혀 있다(`daily_update.py:333-335` 「팀원 #140 배치 … 배치 코드는 목표 기능 ② 주담당 것」, `daily_update.py:348` 「기존 `signals`(401종목) 코드는 신장환 님 것이라 건드리지 않고」) → **안내 이슈 필수 · 팀원 동의/PR 필요**(프로젝트 규칙: 팀원 백엔드 로직은 이슈로 안내). 판 지문은 위 `_code_parts` 에 이 파일들이 없어 영향이 없다고 본다(전체 목록 재확인 전제).
**시험(B)**: `tests/test_mtf_signals.py` · `tests/test_signals_all.py`(쓰기 인자 · 방식 값) + 마이그레이션 왕복(upgrade/downgrade) + **upsert 가 `first_computed_at` 을 보존하는지** + 기존 NULL 줄의 대체 판정. 11-05 동결 전에는 팀원 합의가 늦으면 못 한다. `DEFINITION`·`signal_at` 은 안 바뀐다. 기존 데이터가 많아(전 종목) 마이그레이션 시간·두 PC 의 DB 정합도 확인해야 한다(확인 못 함).

### 안 C — 큰 안 (추가 전용 이력 · bitemporal)

**데이터**: `signal_snapshot_log`(또는 `recorded_at` 을 키에 포함한 이력 표) — `(as_of, symbol, definition, recorded_at, record_mode, 값…)`. **덮어쓰지 않고 줄을 더한다.** 현재 `signal_snapshots` 는 「최신 값 뷰」로 유지.

**서버**: 질의 두 축 — `as_of`(어느 날 신호) × `known_at`(어느 시점까지 알려진 값). 「11-02 신호를 11-03 오후에 알았던 대로」 = ALFRED vintage · Feast 필터. 정정 이력 타임라인 API.

**화면**: 날짜 선택 + 「기록 이력 보기」(첫 기록 / 재계산 n회 / 값이 바뀐 곳 비교).

**시험(C)**: 이력 쓰기(덮어쓰지 않고 줄 추가) · `known_at` 필터 경계 · 최신 값 뷰와 이력의 일치 · 마이그레이션 · 기존 `test_mtf_signals.py`/`test_signals_all.py` 전부 영향.

**위험**: 용량 — `load_day` 주석이 「기록이 약 3,950종목이면 한 번에 수 MB」(`signal_explain.py:319`)라 적었다. 이는 **하루치를 한 번에 읽을 때의 크기**이지 저장 용량이 아니다 — 저장 용량은 실측하지 않았다(확인 못 함). 거래일 × 재계산 횟수만큼 늘어나고 보존 정책(120거래일, `signals_all.py`)도 다시 짜야 한다. 쓰기 경로 변경이 크고 여러 PC DB 정합 문제가 커진다. **11-05 동결·11-12 발표 안에는 무리 — 후속 과제/한계 문단**으로 적는 것을 권한다. (예상 작업량: 내 어림 3일 이상, 검증 안 함.)

| 위험 | 거짓 경보(PC 차이) | 팀원 파일 · 마이그레이션 | 용량 · 규모 |

**추천: 지금 안 A, 그리고 B 는 이슈로 제안만 해 두고 팀원이 받으면 동결 뒤, C 는 한계 문단.**
이유: (1) 요구의 핵심(날짜별로 보기 + 늦게 계산됐다는 사실 표시)을 A 가 이미 채운다. (2) 새 칸·팀원 파일을 안 건드려 동결 전 회귀 위험이 가장 작다. (3) 외부 공통 원칙 2·3(둘 다 보이기 · 표시하되 막지 않기)을 만족한다. 거짓 경보 가능성은 문구에 「이 앱 DB 기준」 한 줄을 넣어 줄인다.

발표 때 말할 수 있는 한 문장(제안): 「기준일과 계산 시각을 둘 다 보이고, 늦게 계산된 기록은 표시합니다. 같은 날을 다시 계산하면 덮어쓰는 한계가 있어 추가 전용 이력은 후속 과제입니다.」

---

## 5. 사용자가 정할 것

1. **안**: A만 / A + B 이슈 제안 / 그 밖.
2. **어휘**: 「실시간」을 빼고 「정기 기록 / 늦게 계산 (/ 다시 계산)」으로 할지.
3. **날짜 고르기 자리**: 종목 근거 모달 안만 / 신호 순위 화면에도(순위는 API 가 이미 `on` 지원 — 화면 입력만 없음).
4. **「늦게 계산」 판정 기준**: 다음 거래일 23:59 까지는 정기로 볼지, 아니면 12:30 회차 후 몇 시간까지로 좁힐지. 재계산 때문에 정기 줄이 「늦게」로 보이는 것을 받아들일지.
5. **그날 볼 수 있던 기록만 보기** 토글을 안 A 에 넣을지(Feast/ALFRED 식) 아니면 표시만.
6. **팀원 안내**: B 의 마이그레이션·`write_snapshots` 변경을 신장환 님께 이슈로 먼저 묻을지.
7. **옛 정의 판** 기록을 날짜 고르기에서 보일지(1.4-4) — 지금은 현재 판만.
8. 발표 시연 DB 가 정기 회차를 돈 PC 의 것인지(거짓 경보 점검) — **확인 못 함**.
