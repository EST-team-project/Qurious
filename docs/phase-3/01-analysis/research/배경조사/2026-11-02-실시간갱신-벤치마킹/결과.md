# 실시간 시세와 분석의 관계 · 갱신 방식 — 다른 서비스 · 오픈소스 벤치마킹 (2026-11-02)

사용자 질문(11-02): 「주가는 실시간으로 변하는데 분석은 수집된 이전 데이터로 하니 뭔가 어색하다 — 한계인가 구현 잘못인가, 다른 서비스 · 깃허브 프로젝트는 어떻게 하나」. 우리 쪽 사실은 [실시간 표시 · 저장 자료 구분 설계](../../../02-design/system/실시간표시-저장자료-설계.md)와 코드(`quote_now.py` · `signal-rank.js` · `company.js`)에서 읽었다. 여기서는 바깥 사례만 모았다. github.com 페이지는 열지 않았고(운영 규칙), 검색 결과의 발췌와 각 프로젝트의 공식 문서 사이트만 읽었다.

> **정정(같은 날 원문 확인판 [결과-상세.md](결과-상세.md))** — 아래 KIS 한도(실전 초당 20건 · 모의 2건)는 2026.04.20 이전 값이다. 지금은 실전 **18건** · 모의 **1건**(웹소켓 41건은 그대로). KRX 애프터마켓(2026-09-14 · 16:00~20:00 · ETF · ETN 제외)도 아래 표에 없다.

## 1. 한눈에

| 질문 | 바깥 사례의 답 | 우리 지금 | 차이 |
|---|---|---|---|
| 일봉 기반 신호는 언제 확정하나 | 봉이 닫힌 뒤(TradingView · Freqtrade · QuantConnect 모두 「봉 완성」 이벤트가 기본) | 마감 일봉으로 확정 | 같다 |
| 장중에는 신호를 어떻게 보이나 | 따로 켜야 하는 선택(TradingView `calc_on_every_tick` · Freqtrade `process_only_new_candles=false`) · 되돌려 칠해질(repainting) 수 있다고 경고 | 장중 값을 신호에 섞지 않음 · 현재가 칸만 지금 값 | 같다(보수적) |
| 지금 값은 누가 어디까지 보이나 | 무료는 지연 + 지연 표기, 실시간은 유료 · 라이선스(Finviz · 네이버 미국 시세) | 내 KIS 키 → 지연 시세 → 종가 순서 + 출처 글 | 비슷하다 |
| 갱신은 어떻게 하나 | 토스증권은 웹소켓 + 폴링 폴백 · 개인 프로젝트는 폴링 + 배치 | 현재가 카드 10초 폴링 · 신호 순위 화면은 갱신 없음 | 신호 순위 화면만 비어 있다 |

## 2. 사례

**표 1 — 사례와 확인한 문장(출처는 3절)**

| # | 사례 | 확인한 내용 | 우리에게 |
|---|---|---|---|
| 1 | TradingView 알림 | 장중 봉에서 나간 알림은 봉이 닫힌 뒤 조건과 다를 수 있어 「Once Per Bar Close」 를 권한다 · 「믿을 수 있게 하려면 확정된 정보를 기다려야 하고 즉시성을 포기해야 한다」 · 전략은 기본이 실시간 봉의 종가에서만 실행 · 백테스트에서는 `calc_on_every_tick` 을 끄라고 권한다 | 마감 신호 확정은 업계 기본 설계다 |
| 2 | Freqtrade(오픈소스 봇) | 데이터는 캔들당 한 번만 받는다 · `process_only_new_candles` 최신 문서 기본값 true — 켜면 새 캔들이 올 때만 지표 계산, 끄면 같은 캔들을 반복 계산해 부하가 크지만 틱 데이터에 기대는 전략에 쓸 수 있다 · 백테스트와 실거래 결과가 다를 수 있는 원인을 분석하는 도구도 문서에 있다 | 「봉당 한 번」 은 우리 12:30 회차와 같은 사상. 틱 단위 갱신은 선택 기능 |
| 3 | QuantConnect LEAN | 분 단위 자료를 `Consolidate` 로 묶고, 새 봉이 만들어질 때 핸들러가 불린다(봉 완성 이벤트) | 같은 이벤트 모델 |
| 4 | Finviz | 무료는 「주식 호가 1분 지연 · 선물 · 옵션 15분 지연」 을 화면 아래에 항상 적고, 실시간은 유료 등급 | 지연 표기를 숨기지 않는 관행. 우리 `quote_label` 이 같은 일을 한다 |
| 5 | 네이버 증권(미국 시세) | 15분 지연으로 제공하다 나스닥과 라이선스 계약을 맺은 뒤 로그인 없이 실시간 제공 | 실시간은 데이터 제공자와의 계약 문제라는 사례 |
| 6 | 토스증권(개인 블로그가 정리한 기술 글) | 차트 · 호가창 · 현재가에 웹소켓, 연결 실패나 지연 때는 기존 폴링 API 가 대신한다 | 웹소켓 + 폴링 폴백 구조 |
| 7 | KIS 오픈 API 이용자 글 | 실전 REST 초당 20건 · 모의 초당 2건(계좌 단위), 웹소켓 한 세션에 실시간 구독 합산 41건 · 키당 한 세션. 종목 70개를 초당 20건 안에서 돌리려고 배치와 지연을 계산한 글이 있다 | 우리 모의 초당 2건 제한과 일치. 전 종목 실시간은 구조적으로 안 된다 |

## 4. 우리에게 주는 뜻(제안 — 결정은 사용자)

1. **마감 신호 확정은 그대로 둔다.** 1 · 2 · 3 사례가 같은 결론이다.
2. **신호 카드는 「기준일 신호 + 지금 가격(출처 · 몇 초 전)」 두 칸으로.** 4 사례처럼 지연 표기를 숨기지 않는다. 이 계약은 이미 있다.
3. **갱신은 보이는 행만 10초 폴링 + 새로고침 단추.** 숨은 탭과 장 마감 뒤에는 멈춘다. 서버는 10초 저장본을 그대로 쓴다. 모의 초당 2건이면 화면 행 수가 한도를 정한다(7 사례).
4. **웹소켓은 KIS 키가 있는 사용자의 관심 종목(41건 이내)만 후속으로.** 실패하면 폴링으로 내려가는 구조(6 사례).
5. **장중 참고 신호는 기본 끄고, 켠다면 「미확정」 표시.** 1 · 2 사례가 둘 다 선택 기능으로만 둔다.
