# app.html 첫 로딩 정적 성능 점검 (2026-11-03)

- 방식: 코드 읽기와 바이트 · 태그 수 세기만. 브라우저 · Lighthouse · 네트워크 측정은 하지 않았다.
- 표시: 🟢 직접 확인 / 🟡 추측 / 🔴 못 본 것.
- 대상: `public/app.html`, 그것이 부르는 `public/js` · `public/css` · 외부 CDN, `app/main.py` 서빙 방식.
- 성능 수치(LCP · INP · CLS 등)는 전부 **측정 안 함**이다. 아래 영향은 「가능성」이다.

## 1. 발견

### F1. 응답 압축이 코드에 없다 — 원본 크기 그대로 내려갈 수 있다 🟢(코드 기준) / 🟡(실제 배포)
- 근거: `app/main.py` 에 `GZipMiddleware` · gzip · brotli 가 없다(전체 `*.py` 검색에서도 0건). Dockerfile 은 `uvicorn app.main:app` 을 바로 띄운다(39줄). 저장소 안 docker-compose 에 앞단 프록시(nginx 등) 흔적은 못 찾았다.
- 영향: HTML 237 KB · CSS 228 KB · JS 1.41 MB 가 압축 없이 전송되면 위 환산치(0.6 MB)의 약 3배다. 느린 회선 · 모바일에서 첫 로딩 시간의 가장 큰 덩어리일 가능성이 높다.
- 가장 싼 방법: 앞단 프록시가 있으면 거기서 gzip/brotli, 없으면 `GZipMiddleware(minimum_size=1024)` 한 줄. 정적 파일에만 적용하고 API 의 SSE · 스트리밍 응답은 제외해서 확인한다.
- 위험: 낮음. 스트리밍(SSE) 응답이 버퍼링되지 않는지만 점검. 🔴 실제 운영 서버 앞단 설정은 못 봤다 — 이미 압축 중이면 이 항목은 무효다.

### F2. Tailwind Play CDN — 렌더 차단 + 브라우저 안 컴파일 + 버전 미고정 🟢
- 근거: `app.html:10` `<script src="https://cdn.tailwindcss.com"></script>` — head 안, `defer` 없음, 버전 없음. `tailwind.config` 는 저장소에 없다.
- 영향: 이 스크립트가 도착 · 실행되기 전에는 문서 파싱이 멈춘다(렌더 차단). 실행 뒤에도 DOM 을 훑어 CSS 를 브라우저에서 만들고, 화면 JS 82개가 `innerHTML` 로 마크업을 넣을 때마다 다시 훑을 가능성이 있다(🟡). Tailwind 공식 문서도 Play CDN 을 운영용으로 권하지 않는다. 버전이 고정돼 있지 않아 어느 날 외부에서 동작이 바뀔 수 있다.
- 사용 규모: 유틸리티 클래스 사용이 많다(예: `text-xs` 371회 · `font-semibold` 216 · `grid` 214 · `flex` 200).
- 가장 싼 방법: Tailwind CLI 로 쓰는 클래스만 뽑은 정적 `tailwind.css` 하나를 만들어 `<link>` 로 교체. 빌드 스텝이 이 저장소에 없으므로(번들러 없음) 한 번 만들어 커밋하는 방식이 현실적이다. 급하면 최소한 `defer` 는 안 되니(스타일 지연 → 깜빡임) CLI 교체가 정답.
- 위험: 중간. JS 가 문자열로 만드는 클래스 이름이 스캔 대상에서 빠지면 일부 스타일이 사라진다. `content` 에 `public/js/**/*.js` 를 반드시 포함. 교체 전후 화면 비교 필요.

### F3. 동기 스크립트 · 외부 스타일이 head 에서 렌더를 막는다 🟢
- 근거: `app.html:11` ApexCharts `apexcharts@3.49.2`(동기, 버전은 고정됨) · `:19` Font Awesome 6.5.2 CSS(렌더 차단) · `:13~15` Pretendard CSS · `:20~41` 앱 CSS 20개.
- 영향: 첫 화면은 외부 호스트 3곳(`cdn.tailwindcss.com` · `cdn.jsdelivr.net` · `cdnjs.cloudflare.com`)의 응답에 걸린다. 한 곳이 느리거나 막히면 빈 화면 시간이 길어진다. ApexCharts 는 첫 화면(대시보드)이 쓰는지 확인하지 못했다(🔴) — 쓰지 않는다면 필요한 화면에서 늦게 읽는 편이 낫다.
- Pretendard 줄은 의도(비차단 로딩)와 다르게 동작한다: `rel="stylesheet" as="style" onload="this.rel='stylesheet'"` 는 `rel="preload"` 로 시작해야 하는 관용구인데 처음부터 `stylesheet` 라 그냥 차단 로딩이다(`app.html:13~14`). 🟢
- 가장 싼 방법: Pretendard 는 `rel="preload" as="style"` 로 고치거나 `media="print" onload="this.media='all'"` 패턴 사용. Font Awesome 은 쓰는 아이콘만 자체 서브셋하거나 최소한 `preconnect` 에 cdnjs 를 더한다(지금은 jsdelivr 만 있음, `:12`). ApexCharts 는 사용 화면에서 동적 삽입.
- 위험: 낮음~중간. 글꼴 · 아이콘이 늦게 나타나는 깜빡임(FOUT)이 생길 수 있다. `font-display` 지정은 앱 CSS 에서 못 찾았다(🟢 `@font-face` 검색 0건 — 글꼴은 전부 외부 CSS 안에서 정의).

### F4. 모든 화면 마크업이 첫 응답에 실린다 — 숨겨진 DOM 이 크다 🟢(수치) / 🟡(비용)
- 근거: `app.html` 에 `class="view"` 76개, 태그 2,415개. 숨김은 `app.css:418` `.view { display:none }` 로만 처리한다.
- 영향: 보이는 화면은 한 번에 하나지만 파서와 스타일 계산은 2,415개 전부를 만든다. 이 규모(수천 노드)는 현대 기기에서 치명적이진 않다 — 영향은 주로 HTML 바이트(237 KB)와 파싱 시간이고, 1번(압축)이 해결되면 상당 부분 줄어든다(🟡). `display:none` 부분은 레이아웃 비용이 거의 없다.
- 가장 싼 방법: 지금은 그대로 두고 F1 만 먼저. 나눈다면 큰 화면부터 `<template>` 이나 fetch 조각으로 뺀다(아래 마지막 단락).
- 위험: 화면 JS 가 `document.querySelector` 로 다른 화면 요소를 직접 잡는 곳이 많다면(🔴 전수 확인 안 함) 조각으로 빼는 순간 null 오류가 난다.

### F5. 모듈 78개를 시작 때 전부 정적으로 불러온다 — 화면 단위 지연 로딩이 없다 🟢
- 근거: `js/main.js:3~43` 가 화면 40여 곳의 모듈을 정적 `import` 한다(예: `robo.js` 91,382 B · `core.js` 89,411 B · `paper.js` 88,292 B · `collect.js` 42,497 B …). 동적 `import()` 는 `finlearn.js` 한 곳뿐이다(glossary).
- 영향: 사용자가 대시보드만 봐도 JS 1.41 MB(원본) 전체를 내려받고 파싱 · 실행한다. ES 모듈 그래프는 의존이 다 풀릴 때까지 `main.js` 실행이 시작되지 않는다. 이 앱의 INP · 첫 화면 표시 지연의 가장 구조적인 원인 후보다(🟡 측정 전).
- 근거 보강: `main.js` boot 는 `getMe()` 응답을 기다린 뒤(`await`) 첫 `navigate` 를 호출한다 — 즉 JS 전체 로딩 + API 1회가 직렬이다.
- 가장 싼 방법: 이미 `onXxxViewActivated` 형태로 화면 활성화 훅이 있으므로, `registerViewActivation` 에 `() => import("/js/xxx.js")` 를 물리는 식으로 화면 단위로 바꾼다. 대시보드 · 공통 모듈만 정적 유지.
- 위험: 중간. 일부 모듈이 `init...` 을 시작 때 불러 이벤트를 붙이는 구조(`initPaperViews` · `initRebalanceView` 등)라서, 지연 로딩하면 첫 진입 시 한 번 더 기다림이 생기고 순서 의존이 깨질 수 있다. 화면별로 하나씩 옮기며 확인.

### F6. 캐시 무효화가 「매번 재검증」뿐이다 — 요청 수가 많다 🟢
- 근거: `app/main.py:93~125` `StaticNoCacheMiddleware` 가 `/js/` · `/css/` · `.html` 에 `Cache-Control: no-cache` 를 붙인다. 파일 이름 해시 · `?v=` 없음. 설계 이유는 주석에 있다(옛 common.js 재사용으로 SyntaxError 가 났던 일).
- 영향: 정확성은 확보된다. 대신 재방문에도 JS 78 + CSS 20 + HTML 1 = 약 99건을 매번 조건부 요청(ETag → 304)한다. 본문은 안 내려가지만 왕복 지연은 남는다. HTTP/1.1 이면(uvicorn 단독이면 그렇다 — 🟡) 브라우저 호스트당 동시 연결 제한(보통 6)에 걸려 직렬에 가깝게 밀린다. 또 모듈 그래프는 깊이 만큼 단계별로 발견된다(의존 폭포).
- 가장 싼 방법: ① `modulepreload` 를 app.html head 에 핵심 몇 개(core · common · main) 추가해 폭포를 줄임. ② 장기적으로 빌드 때 파일명에 해시를 붙이고 `max-age=31536000, immutable` — 번들러 없는 구조라 스크립트 하나(해시 + import 경로 재작성)가 필요.
- 위험: ②는 높다(import 경로 재작성 실수 = 앱 전체 멈춤, 정확히 주석이 막으려던 사고). ①은 낮다.

### F7. 앱 CSS 20개가 각각 별도 요청 · 전부 렌더 차단 🟢
- 근거: `app.html:20~41` 순차 `<link>` 20개, 합계 228,320 B. 많은 파일이 특정 화면 전용이다(`signalrankview.css` · `riskcb.css` · `clusters.css` …).
- 영향: 모두 렌더 차단 자원이라 첫 화면 표시는 20개 응답이 다 와야 가능하다(HTTP/1.1 이면 F6 과 같은 연결 제한 영향 🟡).
- 가장 싼 방법: 화면 전용 CSS 는 해당 화면 첫 진입 때 `<link>` 를 삽입(F5 와 같은 시점). 또는 빌드 시 하나로 합치기.
- 위험: 낮음~중간. 지연 로딩하면 화면이 처음 열릴 때 스타일이 늦게 입혀지는 깜빡임.

### F8. 사소한 것 🟢
- 인라인 `style="..."` 376곳 — HTML 크기에 약간 기여, 캐시 불가. 급하지 않음.
- 주석 16.5 KB — 압축 전 기준 7%. 서버 압축이 켜지면 영향은 작다. 운영용 주석 제거를 굳이 할 필요는 없다.
- 이미지가 없어 LCP 후보는 텍스트나 글꼴 렌더가 될 가능성이 높다(🟡) — 즉 F2 · F3(스타일 · 글꼴 차단)이 LCP 에 직접 연결된다.
- `lightweight-charts` 는 자체 호스팅 · 버전 고정 · 필요할 때만 읽는다(`company.js:56` 등) — 좋은 예.
- `marked` · `dompurify` · `mermaid` · highlight.js 도 버전 고정 + 동적 로딩(`conceptlearn.js:76~80`, `finlearn.js:205~206`) — 좋은 예.

## 2. 우선순위 제안 (비용 대비 효과)

1. F1 압축 확인 · 적용 (한 줄, 위험 낮음, 효과 큼 가능성)
2. F3 Pretendard 로딩 방식 수정 + cdnjs preconnect (분 단위)
3. F2 Tailwind CDN → 정적 CSS (반나절 · 화면 비교 필요)
4. F6① modulepreload 몇 개
5. F5 · F7 화면 단위 지연 로딩 (큰 모듈 3~4개부터)

측정 없이는 순위가 바뀔 수 있다. 위 순서로 하기 전에 Lighthouse 한 번(모바일 · 4G 느림 설정)과 Network 탭 전송 크기로 F1 이 실제로 해당하는지 먼저 확인하는 것이 좋다. 🔴 이번에는 하지 않았다.

## 3. 분리하면 좋아지는 것 / 안 좋아지는 것

화면 마크업이나 모듈 · CSS 를 조각으로 나누면 첫 응답 바이트(HTML 237 KB · JS 1.41 MB · CSS 228 KB)와 파싱 · 스타일 계산이 줄어 첫 화면이 가벼워지고, 안 쓰는 화면의 코드는 아예 받지 않게 된다. 반대로 조각마다 요청이 하나씩 늘고(지금도 재방문마다 약 99건을 `no-cache` 로 재검증하므로 늘어난 만큼 304 왕복이 더해진다), 처음 그 화면에 들어갈 때 기다림이 생기며(로딩 표시 필요), 시작 때 이벤트를 붙이던 `init...` 함수와 다른 화면 요소를 직접 잡는 코드의 순서 의존이 깨질 위험이 있다. 그래서 「압축 → 렌더 차단 외부 자원 정리 → 큰 화면 모듈부터 하나씩 지연 로딩」 순으로 작게 가고, 해시 파일명 같은 전면 개편은 마지막에 하는 것이 안전하다. HTML 조각 fetch 는 압축이 켜진 뒤의 이득이 작을 수 있어 가장 나중에 판단한다(🟡).
