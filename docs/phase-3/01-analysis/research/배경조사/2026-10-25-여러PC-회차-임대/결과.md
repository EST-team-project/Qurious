## 2. 물음마다

### Q1. `HfApi.create_commit(..., parent_commit=...)` 은 비교 후 교체(CAS)인가

**답.** 그렇다. `parent_commit` 을 주고 `create_pr=False` 면, 서버는 `revision`(브랜치) 머리가 그 SHA 가 아닐 때 커밋을 거절한다. 거절은 **412** 이고 라이브러리는 412 를 따로 다루지 않아 일반 `HfHubHTTPError` 로 올린다(`.response.status_code` · `.server_message` · `.request_id`). 메시지 문구는 판마다 달랐으므로(2023 운영 「A commit has happened since…」 · 2026 시험 「The branch was updated since you opened this page…」) **상태 코드로만** 판정한다. 같은 parent 로 동시에 둘이 보내면 하나만 이길 것이 git 참조 교체의 성질상 자연스럽지만, 그 「동시」 경우를 적은 1차 근거는 찾지 못했다(실험 1).

**근거 — 소스 · 시험 · 명세**

| 무엇 | 자리 | 원문(영어 그대로) · 요지 |
|---|---|---|
| 인자 설명 | `hf_api.py:5096-5102`(공식 문서 S4 와 같은 글) | "If specified and `create_pr` is `False`, the commit will fail if `revision` does not point to `parent_commit`." · "Specifying `parent_commit` ensures the repo has not changed before committing the changes, and can be especially useful if the repo is updated / committed to concurrently." |
| 형식 검사(클라이언트) | `hf_api.py:5138-5141` · `constants.py:61` | `REGEX_COMMIT_OID = re.compile(r"[A-Fa-f0-9]{5,40}")` — 5 ~ 40자면 통과, 아니면 보내기 전에 `ValueError` |

**`upload_file` · `upload_folder` · 짧은 SHA**

- `upload_file` — 설명 `hf_api.py:5675-5680`, 그대로 `create_commit(..., parent_commit=parent_commit)` 로 넘긴다(`5755-5766`). `delete_file`(6046) · `delete_files`(6136) · `delete_folder`(6215)도 같은 인자를 받는다.
- `upload_folder` — 설명 `hf_api.py:5886-5891`: "If the upload is split into several commits (large folders), `parent_commit` only applies to the first one." xet 가 있으면 `pipelined_upload` 로 간다(`6008-6023`). 파이프라인은 첫 커밋에만 parent 를 싣고(`_upload_pipeline.py:645-647` "# Deletions and `parent_commit` ride the first commit." · `665`), 커밋 요청을 `retry_on_error=True` 로 보낸다(`653-666`). 쪼개는 기준은 처음 256개 · 일반 파일 100MB · 묶음 5분(`_upload_pipeline.py:66-75` · `531-535`).
- `upload_large_folder` — 1.31.0 에는 있었으나(`hf_api.py:6340`, 다른 프로젝트의 1.31.0) **2.0.0 · 2.3.0 에는 없다**(두 판의 `hf_api.py` 에 이름이 0번).
- 짧은 SHA — 설명은 "Shorthands (7 first characters) are also supported." 이고 클라이언트 정규식은 5 ~ 40자, 공식 명세는 「40-character hex SHA」 다. 짧은 parent 로 거절 · 통과를 확인한 공식 시험은 없다(태그 만들기에서 7자 revision 을 쓰는 시험만 있다 · `tests/test_hf_api.py:1495-1516`). `repo_info().sha` 와 `CommitInfo.oid` 는 40자를 주므로 늘 그것을 쓴다.

**설계에 바로 걸리는 함정 넷**

1. **같은 내용이면 CAS 를 건너뛴다.** `hf_api.py:5222-5277` — 올릴 파일이 **현재 브랜치 머리의 파일과 같으면**(preupload 가 돌려준 `_remote_oid` · `_commit_api.py:764` · `779`) 커밋을 보내지 않고 "No files have been modified since last commit. Skipping to prevent empty commit." 경고와 함께 **현재 머리 정보**를 돌려준다. 이때 `parent_commit` 은 검사되지 않는다. → 임대 JSON 에 매번 새 nonce · 시각을 넣어 내용이 늘 다르게 하고, 받은 `oid` 가 내가 준 parent 와 다른지 확인한다.
2. **응답을 잃으면 결과를 모른다.** `_commit_api.py:1035-1037` "Caution: if a commit succeeds but its response is lost, the retry will create a duplicate commit". HF 저장소 안내도 "even if the timeout is raised client-side, the process is still completed server-side"(S8). `create_commit` 자신은 커밋 요청을 다시 보내지 않지만(`retry_on_error` 기본 False · `5280-5293`), `upload_folder` 파이프라인은 다시 보낸다 — parent 를 준 첫 커밋이 서버에서 성공하고 응답만 잃으면 **재시도가 412 로 돌아온다(내 커밋인데 진 것처럼 보임).** → 임대 쓰기는 `create_commit` 으로 하고, 전송 오류 · 5xx · 시간 초과 뒤에는 머리를 다시 읽어 **내 nonce 가 있으면 이긴 것**으로 본다.
3. **시간 한도가 없다.** 기본 HTTP 클라이언트가 `timeout=None`(`utils/_http.py:341-349`) — 커밋 요청이 끝없이 걸릴 수 있다. `set_client_factory`(`utils/_http.py:372`)로 한도를 준 클라이언트를 쓰거나 바깥에서 기한을 건다. 읽기 쪽 `repo_info` 는 `timeout` 인자가 있다(`hf_api.py:3476`).
4. **429 는 자동으로 기다려 주지 않는다.** HF 안내의 똑똑한 429 처리는 "file downloads (i.e. Resolvers) and paginated Hub API calls" 에만 걸린다(S7). `create_commit` 의 커밋 요청(POST)이 받은 429 는 그대로 예외다(앞 단계 preupload 만 `http_backoff` 로 재시도 · `_commit_api.py:762-768`) → 「진 것」 이 아니라 「나중에」(러너의 `EX_TEMPFAIL` 75)로 다룬다.

**2.0.0 ↔ 2.3.0 대조(이 기능)** — PyPI 2.0.0 휠과 설치본을 줄 단위로 비교했다. `_commit_api.py` · `_upload_pipeline.py` 바뀐 줄 0 · `constants.py` 1줄(추론 카탈로그 주소) · `file_download.py` 2곳(dry-run 표시 · 오프라인일 때 트리 캐시 조건) · `utils/_http.py` 는 주소 해석 · 인증 머리말을 보낼 호스트 판정 · `hf_api.py` 의 `create_commit` 은 kernel 저장소 종류 추가와 「같은 커밋에서 지운 경로의 추가는 no-op 으로 치지 않음」(2.3.0 `5222-5243`)뿐. **`parentCommit` 을 싣는 방식 · 정규식 · 재시도 정책 · no-op 건너뛰기는 두 판이 같다.** 1.29.0 · 1.31.0(다른 프로젝트 `.venv`)도 같은 방식이었다(`_commit_api.py:925` · `constants.py:61`).

### Q3. 읽기 일관성 — 막 커밋한 머리가 바로 보이나 · SHA 고정 읽기

**답.** HF 는 「커밋 직후 다른 클라이언트의 읽기가 새 머리를 본다」 를 어디에도 약속하지 않는다. 공식 시험(시험 서버)은 커밋 직후 `hf_hub_download(revision="main")` 으로 새 내용을 바로 읽어 통과하므로 실제로는 거의 바로 보일 것이지만, 같은 시험 파일에 「서버 캐시가 갱신되길 기다리는」 0.2 ~ 1초 잠이 몇 곳 있다. 그러니 **읽기는 낡을 수 있다고 보고, 결정은 CAS 로** 한다 — 낡은 머리를 보고 내린 결정은 그 머리를 parent 로 준 커밋에서 412 로 걸러진다. 낡은 읽기가 할 수 있는 나쁜 일은 「헛된 412 한 번」 과 「남이 이미 잡은 것을 늦게 앎」 뿐이고, 둘 다 다시 읽기로 풀린다. 더 위험한 것은 **라이브러리가 오류를 숨기고 캐시를 주는 읽기**다.

### Q4. 임대 설계의 정석과 우리 경우의 펜싱

**답 — 정석 넷**

1. **임대는 기한이 있는 권리다(Gray & Cheriton 1989).** 쥔 쪽이 죽거나 끊겨도 남은 쪽은 **임대가 끝날 때까지만** 기다리면 되고, 장애는 「정확성이 아니라 성능」(기다림)으로만 나타난다. 짧은 임대일수록 기다림이 짧다.
2. **임대는 시계에 기댄다.** 판정하는 쪽 시계가 빠르거나 쥔 쪽 시계가 느리면 겹친다 — 최소 조건은 「시계 흐름의 어긋남에 알려진 한도가 있을 것」. 우리 경우 만료를 판정하는 것은 HF 가 아니라 **읽는 PC 의 시계**이므로, 만료 시간(시간 단위)에 견줘 넉넉한 여유(분 단위)를 두거나 공통 시계(HF 응답의 `Date` 머리 등 · 추정)를 쓴다.
3. **임대만으로는 좀비를 못 막는다(Kleppmann 2016).** 쥔 쪽이 멈췄다가(GC · 절전 · 망 끊김) 임대가 끝난 뒤 깨어나면 자기가 아직 쥐었다고 믿고 쓴다. 막는 길은 **펜싱 토큰** — 잡을 때마다 커지는 번호를 쓰기에 붙이고, **저장 쪽이 더 큰 번호를 이미 봤으면 거절**한다. Kleppmann 은 임대를 「효율」(같은 일 두 번 막기)과 「정확성」(상태 망가짐 막기)으로 나누고, 정확성이 필요하면 저장 쪽 검사가 있어야 한다고 한다.
4. **Chubby(Burrows 2006)는 같은 생각을 「sequencer」(잠금 세대 번호를 담은 표 · 받는 서버가 검사)와 「lock-delay」 로 둔다.** lock-delay = 쥔 쪽이 죽어 풀린 잠금은 일정 시간(최대 1분) 아무도 못 잡게 하는 유예 — 지연된 옛 요청이 새 쥔 쪽의 일을 덮지 않게 한다.

**근거 인용**

| 출처 | 원문 |
|---|---|
| S17 초록 | "Leases are proposed as a time-based mechanism that provides efficient consistent access to cached data in distributed systems. Non-Byzantine failures affect performance, not correctness, with their effect minimized by short leases." |
| S17 2절 | "A lease is a contract that gives its holder specified rights over property for a limited period of time." · "When the server cannot communicate with a client, the server must delay writes to a file for which the failed client holds a lease until that lease expires." |
| S17 5절 | "Leases depend on well-behaved clocks. In particular, a server clock that advances too quickly can cause errors because it may allow a write before the term of a lease held by a previous client has expired at that client." · "As a minimum, the correct functioning of leases requires only that clocks have a known bounded drift, in which case the lease term can be communicated as its duration t." |
| S18 | "if the GC pause lasts longer than the lease expiry period, and the client doesn't realise that it has expired" · "In this context, a fencing token is simply a number that increases (e.g. incremented by the lock service) every time a client …" · "Note this requires the storage server to take an active role in checking tokens" · "Efficiency: Taking a lock saves you from unnecessarily doing the same work twice (e.g. some expensive computation)." · "Redlock assumes that delays, pauses and drift are all small relative to the time-to-live of a lock" |

**우리 경우의 펜싱(한두 줄)** — 임대를 쓴 커밋의 **40자 SHA 가 곧 펜싱 토큰**이다. 같은 브랜치에 `parent_commit = 내가 마지막으로 본 머리` 로만 쓰면 그 사이 누가 임대를 가져간(=커밋한) 순간 머리가 바뀌어 **HF 가 412 로 좀비의 쓰기를 거절**한다 — Kleppmann 이 말한 「저장 쪽의 토큰 검사」 를 HF 가 해 준다. 다만 이 보호는 **그 브랜치에 쓰는 커밋에만** 걸리므로, 백업(main)처럼 다른 곳에 쓰는 일은 그쪽 머리를 parent 로 한 CAS 와 「원격 백업의 세대(gen) ≤ 내 세대」 검사를 따로 건다(3절 ④).

### Q5. Windows 작업 스케줄러 — `StartWhenAvailable` 과 짝 설정

**답.**

- **뜻** — 「예약 시각이 지난 뒤 언제든 시작할 수 있다」. 놓친 시작은 서비스 큐에 들어가 **지연 뒤 시작하고 기본 지연은 10분**이다. 이때 이벤트 114 가 남는다. 프로젝트가 본 「켜진 뒤 약 10분에 돈다」(`scripts/daily_update.py:85`)가 문서와 맞다. 「끝 경계가 있거나 무한히 반복하는 시간 기반 작업」 에만 걸린다 — 날마다 도는 `CalendarTrigger`(끝 없음)는 여기에 든다.
- **꺼져 있었을 때** — 문서가 직접 예로 든다("the computer was turned off"). 켜진 뒤 서비스가 놓친 시작을 보고 10분 뒤 돌린다.
- **절전이었을 때** — `WakeToRun` 이면 깨워서 제시각에 돈다(이벤트 145). 아니면 「놓친 시작」 이 되어 깨어난 뒤 `StartWhenAvailable` 로 도는 것이 문서의 일반 논리지만, 절전을 콕 집은 현행 문서는 없고, **우리 PC 에서 깨어난 뒤 안 돈 기록**(TIL 2026-10-11 · 까닭 모름)과 옛 Windows 7 의 반대 방향 결함(KB2698800 · 옵션을 꺼도 깨어나면 돎)이 있다 → 낮음 ~ 중간 · 실험 5.
- **로그온 전** — 지금 작업은 `InteractiveToken`(`daily_update.py:1684`)이라 「이미 로그온한 대화형 세션에서만」 돈다. 로그온 안 한 채 시각이 지나면 이벤트 332(「사용자가 로그온해 있지 않아 시작 안 함」). **그 뒤 로그온하면 따라잡는지는 문서에 없다** — 프로젝트 문서는 「로그인하면 곧바로 따라잡는다」(`collector/README.md:1363`)고 적었으나 근거 기록은 못 찾았다 → 낮음 · 실험 5.
- **며칠을 놓쳤을 때** — 「몇 번 도나」 를 적은 문서가 없다. `IgnoreNew` 라 한 번에 하나만 돌고, 러너가 빠진 날을 스스로 채우므로(`FILL_MAX_DAYS = 31`) 횟수에 기대지 않게 설계하면 된다 → 낮음.
- **「10분 뒤」** — 문서에 있다(S21 · S22). 바꾸는 설정 이름은 이번에 찾지 못했다.
- **짝 설정** — `MultipleInstancesPolicy` 기본 `IgnoreNew`(돌고 있으면 새 실행을 버림 · 이벤트 322) · `ExecutionTimeLimit` 기본 72시간(`PT0S` = 무한 · 지금 우리 값은 `PT4H` = `LOCK_STALE_HOURS`) · `WakeToRun` 기본 false · 「사용자의 로그온 여부에 관계없이 실행」 = `Password`(등록 때 암호 저장) 또는 `S4U`(암호를 저장하지 않지만 **망 · 암호화 파일 접근 없음**) — 둘 다 「일괄 작업으로 로그온」 권한이 있어야 돈다. HF 와 통신해야 하므로 S4U 는 문서상 맞지 않고, Password 는 암호 저장이 걸린다 → 지금의 `InteractiveToken` 유지가 맞다. 트리거에는 `RandomDelay`(시작에 무작위 지연을 더함 · 기본 `PT0M`)와 `Repetition`(간격 · 기간)을 둘 수 있다.

## 3. 설계에 주는 뜻

1. **임대 자리** — 백업 저장소 `qurious-quant/krx-daily-market` 의 **전용 브랜치**(예: `runner-lease` · 한 번만 `create_branch(exist_ok=True)` — 사용자 승인)에 `lease.json` 하나. 백업 커밋(main)이 임대 CAS 를 흔들지 않고 이력도 섞이지 않는다. 칸: `date` · `state`(running · done · failed) · `pc` · `nonce`(uuid) · `gen`(잡을 때마다 +1) · `started_at` · `renewed_at` · `ttl_min` · `base_backup_sha` · `result_backup_sha`.
2. **잡기 = CAS 한 번** — `H = repo_info(revision=브랜치).sha`(40자) → `H` 에 고정해 읽기 → 오늘 것이 아니거나 만료면 `create_commit([lease.json], revision=브랜치, parent_commit=H)`. **412 = 짐**(다시 읽고 끝) · 전송 오류 · 5xx · 시간 초과 = 머리를 다시 읽어 **내 nonce 면 이김** · 429 = 「나중에」(EX_TEMPFAIL) · 받은 `oid ≠ H` 확인. nonce 덕에 no-op 건너뛰기(CAS 생략)가 생기지 않는다. 임대 쓰기에 `upload_folder` 는 쓰지 않는다(자동 재시도가 이긴 커밋을 412 로 보이게 함).
3. **만료 시간** — 살아 있는 쥔 쪽을 빼앗지 않을 만큼 길게, 죽은 쪽을 그날 안에 이어받을 만큼 짧게: `ttl ≥ 가장 긴 단계 한도(FILL_TIMEOUT_CAP_MIN 120분) + 여유` — 예 150분, **단계 사이에서 30분 넘었을 때만 CAS 로 갱신**(하루 커밋 3 ~ 6). 이어받기는 `renewed_at + ttl + 유예(Chubby lock-delay 꼴 · 예 10분)` 뒤에만. PC 시계 어긋남은 이 여유가 덮는다(필요하면 HF 응답 `Date` 머리를 공통 시계로 · 실험 3).
4. **펜싱 — 임대는 효율, 정확성은 백업 커밋에** — 백업은 `main` 머리를 읽고 「원격 매니페스트의 날짜 · `gen` ≤ 내 것」 을 확인한 **그 SHA 를 `parent_commit` 으로** 올린다 → 그사이 남이 올렸으면 412 로 멈춰, 좀비 · 뒤처진 PC 가 새 백업을 옛것으로 덮지 못한다. 쪼개지는 업로드는 첫 커밋만 보호되므로 증분 백업은 한 커밋(`create_commit`)으로 묶거나 쪼개지지 않음을 확인한다. 임대 갱신 · 닫기도 parent = 내 마지막 임대 커밋 — 412 면 다시 읽어 nonce 가 내 것일 때만 이어 간다(squash 같은 무관한 머리 이동 흡수).
5. **읽기** — 임대 · 머리 판정은 `repo_info(...).sha` 와 40자 SHA 고정 읽기만. 브랜치 이름으로 받는 `hf_hub_download` · `resolve_revision` · `snapshot_download` 는 오류를 캐시로 덮으므로 판정에 쓰지 않는다. 맞추기(②)는 임대 · 매니페스트의 백업 SHA 로 고정해 받고, 오늘 임대가 남의 `done` 이면 **맞추기만 하고 수집은 건너뛴다**(맞추기는 로컬 쓰기라 임대가 필요 없고 로컬 `O_EXCL` 잠금이 맡는다).
6. **작업 스케줄러** — 모든 PC 에 같은 작업: `StartWhenAvailable` true(놓치면 약 10분 뒤) · `IgnoreNew` · `InteractiveToken` 유지(S4U 는 문서상 망 없음 · Password 는 암호 저장) · `RunOnlyIfNetworkAvailable` true. 트리거에 `RandomDelay`(예 `PT3M`)로 같은 분 시작을 흩고(안전은 CAS 가, 흩기는 412 소음만 줄임), 쥔 PC 가 죽은 날 이어받기를 원하면 `Repetition`(예 1시간 간격 · 10시간 — 임대가 done 이거나 살아 있으면 몇 초 만에 끝남)을 더한다. `WakeToRun` 은 켜 둔 PC 가 하나라도 있으면 필요 없다.
7. **좀비 · 끊김** — 절전에서 깨어난 쥔 쪽은 아무 일 없던 듯 이어 간다(Kleppmann 의 멈춤). 공유 쓰기(백업 · 임대 닫기) 앞에서 늘 CAS 를 거치므로 이미 빼앗겼으면 412 로 멈춘다. 각 PC 의 수집 DB 는 그 PC 만 쓰므로 펜싱이 필요 없다.
8. **HF 가 안 될 때** — 임대를 못 잡으면 아무도 돌지 않는다(fail-closed). 로컬 수집만 하고 백업은 건너뛰는 fail-open 도 가능하다(겹쳐 돌면 KRX · DART 호출이 두 배) — 사용자 결정. 어느 쪽이든 다음 회차가 빠진 날 채우기로 메운다.

### 4.2 남은 불확실

- **동시 경합의 원자성** — 공식 시험은 순차 경우뿐이다. git 참조를 「옛 값일 때만」 바꾸는 방식이면 하나만 이기지만 HF 서버 구현은 비공개다(실험 1).
- **412 문구** — 2023 「A commit has happened since…」, 2026 시험 「The branch was updated since you opened this page…」 로 바뀌었다. 상태 코드 412 만 본다. parent 가 **아예 없는 SHA** 일 때의 코드도 확인 못 함(실험 1 덤).
- **짧은 SHA** — 클라이언트 설명(7자 지원)과 공식 명세(40자)가 어긋난다. 40자만 쓰면 신경 쓸 필요 없다.
- **커밋 시간당 한도 수치** — 비공개. 2차 주장(100 · 128)은 근거가 없다. 우리 쓰임은 하루 10 미만이라 수치를 몰라도 된다 — **찾아보려고 일부러 많이 커밋하지 않는다**(계정 경고 위험).
- **커밋 직후 읽기 지연 · 커밋 시각** — 다른 PC 에서 새 머리가 보이기까지의 시간, `list_repo_commits` 의 `created_at` 을 서버가 찍는지(추정)는 실험 2 로.
- **작업 스케줄러** — 절전 뒤 따라잡기(10-11 TIL 의 「안 돎」 까닭), 로그오프 중 놓친 시작을 로그온 뒤 따라잡는지, 며칠 놓쳤을 때 횟수, 10분 지연을 바꾸는 방법 — 모두 현행 문서에 없다(실험 5). `WakeToRun` 이 실제로 깨우려면 전원 옵션의 「절전 해제 타이머 허용」 이 켜져 있어야 한다는 안내가 흔하나 1차 문서는 이번에 못 찾았다.
- **S4U 와 HTTPS** — 문서는 「망 접근 없음」 이다. 쓰지 않을 것이므로 확인하지 않는다.
- **HF Storage Bucket 조건부 쓰기** — 문서 한 줄뿐 · 미검증.
