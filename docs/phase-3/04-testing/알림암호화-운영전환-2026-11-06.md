## 1. 결과

09:20 KST에 앱·worker·beat의 동일 이미지 반영과 DB `0044_notification_secrets`를 확인했다. 기존 알림 설정 1행 중 값이 있던 Discord 웹훅·SMTP 비밀번호 2칸을 암호화하고, 비어 있던 7칸은 유지했다. 복호화한 전체 설정의 지문은 전환 전과 같다. 증권사 암호문·주문·주문 의도·보유·현금·리밸런싱 플랜도 보존했다. 자동매매 ON 0명, 미체결 0건이며 이번 검증의 신규 주문·외부 알림 발송은 없다.

암호화 대상은 **9칸**, 현재 설정 GET에서 고정 마스킹하는 비밀칸은 **8칸**이다. `kakao_sender_key`는 구현 PR에 적힌 기존 평문 응답 후속이며 이번 운영 행에서는 빈 값이다. 9칸 모두 마스킹했다고 보고하지 않는다.

## 3. 운영 전환과 보존

1. 현재 Compose의 전체 설정 파일 순서를 이어받고 이미지 태그만 추가했다. 기존 환경·마운트·포트·명령·네트워크·재시작 정책을 전후 대조했다.
2. Beat를 멈춘 뒤 worker의 실행·예약·대기 작업이 0인지 확인하고 worker·app을 중지했다.
3. **중지 후 새 암호화 백업**을 별도로 만들고 키·원래 값·DB 상태가 성공한 리허설과 같은지 다시 확인했다.
4. 새 이미지로 `alembic upgrade head`를 실행하고 전환·보존을 확인했다.
5. app·worker 시작 → 인증 HTTP 점검 → beat 시작 → 새 heartbeat 및 각 서비스의 실제 DB 복호화를 확인했다.

## 4. 로그 점검과 남은 확인

호스트용 [로그 점검 도구](../../../scripts/check_credential_storage_logs.py)를 추가했다. 세 컨테이너의 **stdout과 stderr**에서 `[CREDENTIAL_STORAGE]`를 찾고 서비스별 건수만 출력한다. 종료 코드는 정상 0, 암호화 오류 1, Docker 조회 실패 2다. 타임아웃·없는 실행 파일·조회 실패를 정상 0건으로 처리하지 않는다. 로그 원문·비밀값은 출력하지 않는다.

```bash
python3 scripts/check_credential_storage_logs.py --since 10m
```

WSL의 이 PC에서는 Linux 소켓 대신 `--docker /mnt/c/Users/Administrator/AppData/Local/Programs/DockerDesktop/resources/bin/docker.exe`를 붙인다. 다른 PC는 실제 Docker CLI 경로를 쓴다. 도구 시험 **4통과**, 실제 세 서비스 검사 `ok`·오류 0건을 확인했다. 앞의 132건과 별도 시험이다.

- **상시 경보:** 이 도구는 단발 검사다. 자동 스케줄·외부 경보 수신처 연결은 아직 하지 않았다. 후속 감시에서는 1 또는 2를 모두 운영 확인 대상으로 처리하고, 암호화 오류로 막힐 수 있는 같은 알림 경로만 경보 수단으로 사용하지 않는다.
- **외부 알림:** 실제 개인 채널 테스트 발송·수신은 이번에 하지 않았다. 발송 경로의 DB 복호화와 오류 처리 시험은 통과했지만 외부 수신 성공을 대신하지 않는다.
- **저장·철회:** 마스킹 재저장과 키 오류 상태의 동의 철회는 일회용 DB 시험으로 확인했다. 운영 사용자의 설정을 덮어쓰거나 삭제하지 않았다.
- **키 교체:** 이번에는 키를 바꾸지 않았다. 현재는 두 회전 스크립트를 별도 트랜잭션으로 실행하는 계약을 유지한다. 양쪽 전환·검증이 모두 끝나기 전에는 옛 키를 제거하지 않는다. 한 트랜잭션 통합은 후속 검토다.
- 전화번호·채팅 ID·이메일 주소 암호화, `kakao_sender_key` 응답 마스킹, 키 오류 때 화면의 철회 진입 개선은 #576의 기존 후속이다.

암호화 백업 2개·원본 로그·개인 설정 지문·Compose 사본·검증 도구는 Git 제외 `.codex-work/issue577-20261106/`에 보관했다. 운영 백업 파일은 권한 0600이다. 일회용 시험·복원 컨테이너와 네트워크는 정리했다.
