## 1. 배포 전 시험과 제한

최종 #537 앱 이미지에서 외부 통신이 차단된 네트워크와 일회용 PostgreSQL을 사용해 관련 27개 시험 파일을 실행했다. **383건 통과·2건 실패·2건 건너뜀(387건)**이다. 전체 프로젝트 시험을 다시 전부 통과했다고 기록하지 않는다.

| 실패 | 담당·위치 | 재현과 판단 |
|---|---|---|
| 비용 판정 기대값 | 강민석, [#534](https://github.com/EST-team-project/Qurious/pull/534) `scripts/daily_lean_reconcile.py:judge_fee()` | 일지 거래대금 1,000·비용 10, LEAN 거래대금 2,000·비용 20이면 요율은 둘 다 100bp다. `test_daily_lean_reconcile_fee.py:22`는 `참고용(요율)`을 기대하지만 현재 코드는 총비용·총거래대금도 비교해 `불일치`를 반환한다. 변경한 판정 계약과 시험 기대값을 담당자가 맞춰야 한다. |
| Yahoo 참조 줄 수 | #534의 강민석 코드 변경·이동원 기준선 시험 | `test_no_yahoo_regression.py:142`: `app/services/lean_backtest.py` 20줄, 기준선 19줄. 새 `price_source`의 `Yahoo Finance` 출처 표기 1줄이 증가 원인이다. 그 줄에 새 외부 호출은 없으며 기준선 변경은 담당 확인이 필요하다. |

비용 대사 스크립트는 Dockerfile 복사 대상과 후보 이미지에 없다. Yahoo 실패는 앱의 출처 문자열과 봉인 기준선 차이다. 관련 동작 시험은 통과해 배포했으며 두 실패를 숨기거나 담당 외 코드·시험을 수정하지 않았다. 실제 주문 실패로 단정하지 않는다.

건너뜀은 실제 수집 DB가 필요한 `test_collector_candles_df08.py` 1건과 Chrome 실행 경로·격리 프로필이 필요한 `test_rebalance_screen.py` 1건이다. 합성 수집 DB·임시 PostgreSQL 시험의 성공과 구분한다.

1차 #535 후보는 DB 없이 323통과·1실패·36건너뜀, DB를 붙인 뒤 358통과·1실패·1건너뜀이었다. 최종 #537에는 신선도·수집 일봉·Yahoo 기준선 시험을 포함한 위 결과를 적용한다. 실행 간 건수는 더하지 않고 원본 로그와 JUnit XML을 보존한다.

오늘 오전 전체 시험은 [전체 회귀 결과](전체회귀-2026-11-04.md)의 별도 커밋·환경 근거다. 환경별 중복 제외 4,253통과·3건너뜀이며 Linux 일괄 실행에는 Windows 경로 관련 실패 7건이 있었다. 이 수치를 오후 최신 main의 전체 통과로 옮기지 않는다.

수집 수신기는 별도 새 이미지에서 `test_hf_collector_follower.py` **45건 통과·실패/건너뜀 0**을 확인했다. main의 수신기·collector 모듈을 반영했으며 가격 저장소의 같은 수신 세대·11/3 자료 준비·키/환경/볼륨과 계좌 장부 보존을 확인했다. 외부 통신을 사용하는 운영 수신은 원격 읽기이며 HF 쓰기·그림자 일지 삭제를 수행하지 않는다.

## 2. 운영 확인

- 배포 직전 쓰기를 멈추고 암호화 DB 백업을 생성해 암복호화 왕복을 확인했다. 앞선 12:54 백업은 격리 PostgreSQL에 실제 복원해 주문·설정·잔고 지문 일치를 검증했다. 두 백업의 검증 시점을 구분한다.
- 인증 HTTP 10경로(앱·플랜·상태·이력·새 KIS 결과용 JS·KIS 본인 주문 조회 포함) 200, 비로그인 변경 이력 조회 401. 정적 HTML/JS는 이미지 파일과 일치하며 임시 세션을 삭제했다.
- 세 서비스의 키 읽기와 실전 허용 OFF를 확인했다. 새 heartbeat와 기존 주문·설정·현금·보유 지문 보존을 대조했다.
- 11/3 일봉과 11/4 수신 검증 기록으로 `readiness.ready=true`. 고정 판2의 `execute=False`는 11/3 기준 `HOLD / 진입 조건 없음`을 반환했다. 새 주문을 생성한 결과가 아니다.
- 15:40 자연 배치의 기존 읽기 관측은 유지한다. PAPER 보유 계좌는 0개이므로 현금 스냅샷 성공을 보유 자산 평가 성공으로 바꾸지 않는다. 결과가 나오기 전에는 완료로 기록하지 않는다.

## 3. #533 그림자 일지 판 2 — 오준영 검토 의견

[#533 후속 댓글](https://github.com/EST-team-project/Qurious/issues/533#issuecomment-6623310852)과 [#537](https://github.com/EST-team-project/Qurious/pull/537)은 이동원 PC에서 B안 복구를 먼저 수행했다고 알린다. 판 2는 11/4부터 시작하므로 그대로 두면 11/3 행이 어느 판에도 남지 않는다는 정정도 포함한다. 지운 대상은 판 등록 2개와 관련 메모 2개의 총 4개 파일이다.

작성자에 따르면 DB 판 2/관련 메모를 제거하고 판 1 설명 메모를 추가했으며, HF 원장은 `5ecb5767`로 복구했다. 삭제 전 원본은 `ac4f91be`에 보존했다. 전체 규칙 지문·`daily --dry-run`·pull/업로드 계획 확인은 작성자 보고이고 이번 작업에서 원격 원장을 다시 수정하지 않았다.

**검토 의견: 판 1의 계좌 이어짐과 11/3 공백을 복구하는 B 방향은 타당하다. 우리 PC에는 추가 삭제가 필요 없다.** 우리 운영 DB의 `paper_journal_versions`·`paper_journal_days`·`paper_journal_notes`는 각각 0건이고 판 2를 수신하지 않았다. 가격 수신기는 `qurious-quant/krx-daily-market`, 그림자 일지는 `qurious-quant/qurious-paper-log`로 저장소가 다르다. 가격 재수집은 필요하지 않으며 실제 최신화 뒤 같은 가격 세대와 11/3 준비 상태가 유지됐다.

독립 확인한 범위:

1. `get_quant_indicators`의 구문 지문은 #529 전 `9b646702ddac` → #529 뒤 `8e2a5e2b99e5` → #537 뒤 `9b646702ddac`로 돌아왔다.
2. 상승·하락·등락·자료 부족·빈 자료의 합성 입력 5종에서 자동매매 사이클 밖의 세 버전 지표 결과가 일치했다. 원격 봉인된 전체 일지 행·두 규칙 전체 지문을 직접 대조한 결과는 아니다.
3. 현재 `_pull()`은 로컬 판 1·2, 원격 판 1 조건에서 `same / imported=0`을 반환하고 로컬 판 2를 지우지 않는다. `plan_upload()`는 그 로컬의 판 2를 새 업로드 대상으로 잡는다. 정상 판 1 내보내기에는 새 파일이 없다.

따라서 **이미 판 2를 수신한 다른 PC의 정리는 여전히 필요**하다. 먼저 관련 DB·내보내기를 보존하고 일자 행 0·후속 판 없음·메모 참조를 확인한다. 최신 main을 받은 상태에서 판·메모·내보내기·manifest를 함께 맞추고 재업로드 계획에 삭제한 판이 없는지 확인해야 한다. 기존 판 1 행을 삭제하거나, 조건 확인 없이 다른 PC의 ID를 그대로 적용하지 않는다.

우리 로컬 main과 앱은 #537로 갱신했다. 내일 11/5 12:30에 11/3·11/4 행이 판 1로 이어지는지는 실제 회차 후 확인할 사항이다. 현재 확인을 내일 회차 성공으로 기록하지 않는다. 이 작업에서는 원격 삭제나 다른 PC DB 정리를 실행하지 않았다.
