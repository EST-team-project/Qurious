## 기록 규칙

앞으로 발생하는 오류와 처리 결과는 **이 파일에 계속 누적**한다. 오류마다 날짜와 고유 번호를 붙이고, 증상·재현 조건·원인·처리 내용·수정 파일·검증 결과·남은 작업을 기록한다. 원인이 확인되지 않았으면 추정과 확인된 사실을 구분한다.

상태는 `미해결`, `조사 중`, `수정 완료·시험 통과`, `운영 확인 완료`로 구분한다. 코드 시험 통과를 실제 서비스 반영 완료로 표시하지 않는다. 재발하면 기존 기록을 지우지 않고 같은 항목에 재발일과 추가 조치를 남긴다. 새 오류는 다음 번호로 추가한다. PR·커밋·배포 근거는 확인되는 대로 덧붙인다.

키·토큰·계좌번호·응답 원문은 기록하지 않는다. 안전하게 분류한 오류 코드와 필요한 시험 결과만 남긴다.

## ERR-001 — 불완전한 잔고 응답을 0원으로 처리

- **증상·재현:** 필수 잔고 필드가 누락된 응답을 기본값 `0`으로 처리하거나, `NaN`·무한대 등 유효하지 않은 값을 계산에 전달할 수 있었다. 실제 보유 내역이 없다는 의미와 조회 실패가 구분되지 않았다.
- **원인:** `get_balance`에서 응답 구조와 필수 수치의 유효성 검사 없이 `get(..., 0)`과 숫자 변환을 사용했다.
- **처리:** 성공 코드, 보유 목록·요약 구조, 필수 금액·수량을 검사한다. 누락·비정상 수치는 `BrokerBalanceError`로 실패 처리한다. 정상적인 0원 계좌와 음수 평가손익은 허용한다.
- **수정 파일:** `app/services/brokers/kis.py`, `app/services/brokers/quote_feedback.py`
- **검증:** `tests/test_broker_balance_feedback.py`에서 누락 응답·잘못된 금액·보유 종목 평가값 누락·정상 0원·음수 손익을 확인했다. 아래 공통 시험 결과 참조.
- **남은 작업:** 10:44 KST 배포 코드의 잔고·현재가·매수 가능 금액 조회까지 확인했다. PR 검토는 별도이며, 보유 종목 연속 조회는 이번 빈 계좌 점검으로 검증하지 않았다.

## ERR-002 — 잔고 오류 응답의 원문 노출과 초기화 오류 누락

- **증상·재현:** `/api/broker/balance`가 예외 문자열을 그대로 응답해 URL·계좌 등 민감 정보가 포함될 가능성이 있었다. 클라이언트 준비 단계의 예외는 기존 처리 범위 밖이었다. 실제 정보 유출이 관측됐다는 뜻은 아니다.
- **원인:** `HTTPException(502, f"증권사 API 오류: {e}")`와 `try` 바깥의 클라이언트 준비 코드.
- **처리:** 준비 단계까지 예외 처리에 포함하고, `balance_failure`로 오류 코드·한국어 안내·후속 행동만 반환한다. 인증 거절·호출 제한·시간 초과를 구분하고 원문은 응답과 해당 진단 로그에 남기지 않는다.
- **수정 파일:** `app/routes/stocks.py`, `app/services/brokers/quote_feedback.py`
- **검증:** 가짜 민감 문자열이 응답과 분류 로그에 없는지, 준비 단계 실패도 502 안내로 변환하는지, 로그인 없이 조회할 수 없는지 확인했다. 기존 현재가 안내 시험도 통과했다.
- **남은 작업:** 10/22 배포 및 실제 HTTP 200 조회를 확인했다. PR 검토는 별도다. 다른 증권사 API 전체의 원문 오류 처리를 이번 변경으로 해결했다고 보지 않는다.

## ERR-003 — 후보 코드 점검 환경의 import 불일치

- **증상:** 기존 앱 이미지에서 신규 KIS 코드만 메모리에 불러오자 기존 모듈에 `BrokerBalanceError`가 없어 import에 실패했다.
- **원인:** 후보 KIS 코드와 기존 오류 안내 모듈을 섞어 실행했다.
- **처리:** 일회성 점검 프로세스에서 후보 오류 안내 모듈을 먼저 불러온 뒤 후보 KIS 코드를 실행하도록 점검 스크립트를 수정했다. 실행 중인 서비스 파일은 변경하지 않았다.
- **수정 대상:** 임시 점검 스크립트 `/tmp/qurious-candidate-balance-probe.py`.
- **검증:** 이후 점검은 import 단계를 지나 실제 HTTP 요청 단계까지 진행했다. 그 단계의 실패는 ERR-004로 분리한다.

## ERR-004 — 실제 잔고 재점검 중 HTTP 오류
