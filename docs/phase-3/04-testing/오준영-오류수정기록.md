## 기록 규칙

앞으로 발생하는 오류와 처리 결과는 **이 파일에 계속 누적**한다. 오류마다 날짜와 고유 번호를 붙이고, 증상·재현 조건·원인·처리 내용·수정 파일·검증 결과·남은 작업을 기록한다. 원인이 확인되지 않았으면 추정과 확인된 사실을 구분한다.

상태는 `미해결`, `조사 중`, `수정 완료·시험 통과`, `운영 확인 완료`로 구분한다. 코드 시험 통과를 실제 서비스 반영 완료로 표시하지 않는다. 재발하면 기존 기록을 지우지 않고 같은 항목에 재발일과 추가 조치를 남긴다. 새 오류는 다음 번호로 추가한다. PR·커밋·배포 근거는 확인되는 대로 덧붙인다.

키·토큰·계좌번호·응답 원문은 기록하지 않는다. 안전하게 분류한 오류 코드와 필요한 시험 결과만 남긴다.

## ERR-001 — 불완전한 잔고 응답을 0원으로 처리

- **증상·재현:** 필수 잔고 필드가 누락된 응답을 기본값 `0`으로 처리하거나, `NaN`·무한대 등 유효하지 않은 값을 계산에 전달할 수 있었다. 실제 보유 내역이 없다는 의미와 조회 실패가 구분되지 않았다.
- **원인:** `get_balance`에서 응답 구조와 필수 수치의 유효성 검사 없이 `get(..., 0)`과 숫자 변환을 사용했다.
- **처리:** 성공 코드, 보유 목록·요약 구조, 필수 금액·수량을 검사한다. 누락·비정상 수치는 `BrokerBalanceError`로 실패 처리한다. 정상적인 0원 계좌와 음수 평가손익은 허용한다.
- **수정 파일:** `app/services/brokers/kis.py`, `app/services/brokers/quote_feedback.py`
- **검증:** `tests/test_broker_balance_feedback.py`에서 누락 응답·잘못된 금액·보유 종목 평가값 누락·정상 0원·음수 손익을 확인했다. 아래 공통 시험 결과 참조.
- **남은 작업:** 10:44 KST 배포 코드의 잔고·현재가·매수 가능 금액 조회까지 확인했다. PR 검토는 별도이며, 보유 종목 연속 조회는 이번 빈 계좌 점검으로 검증하지 않았다.

## ERR-002 — 잔고 오류 응답의 원문 노출과 초기화 오류 누락

- **증상·재현:** `/api/broker/balance`가 예외 문자열을 그대로 응답해 URL·계좌 등 민감 정보가 포함될 가능성이 있었다. 클라이언트 준비 단계의 예외는 기존 처리 범위 밖이었다. 실제 정보 유출이 관측됐다는 뜻은 아니다.
- **원인:** `HTTPException(502, f"증권사 API 오류: {e}")`와 `try` 바깥의 클라이언트 준비 코드.
- **처리:** 준비 단계까지 예외 처리에 포함하고, `balance_failure`로 오류 코드·한국어 안내·후속 행동만 반환한다. 인증 거절·호출 제한·시간 초과를 구분하고 원문은 응답과 해당 진단 로그에 남기지 않는다.
- **수정 파일:** `app/routes/stocks.py`, `app/services/brokers/quote_feedback.py`
- **검증:** 가짜 민감 문자열이 응답과 분류 로그에 없는지, 준비 단계 실패도 502 안내로 변환하는지, 로그인 없이 조회할 수 없는지 확인했다. 기존 현재가 안내 시험도 통과했다.
- **남은 작업:** 10/22 배포 및 실제 HTTP 200 조회를 확인했다. PR 검토는 별도다. 다른 증권사 API 전체의 원문 오류 처리를 이번 변경으로 해결했다고 보지 않는다.

## ERR-003 — 후보 코드 점검 환경의 import 불일치

- **증상:** 기존 앱 이미지에서 신규 KIS 코드만 메모리에 불러오자 기존 모듈에 `BrokerBalanceError`가 없어 import에 실패했다.
- **원인:** 후보 KIS 코드와 기존 오류 안내 모듈을 섞어 실행했다.
- **처리:** 일회성 점검 프로세스에서 후보 오류 안내 모듈을 먼저 불러온 뒤 후보 KIS 코드를 실행하도록 점검 스크립트를 수정했다. 실행 중인 서비스 파일은 변경하지 않았다.
- **수정 대상:** 임시 점검 스크립트 `/tmp/qurious-candidate-balance-probe.py`.
- **검증:** 이후 점검은 import 단계를 지나 실제 HTTP 요청 단계까지 진행했다. 그 단계의 실패는 ERR-004로 분리한다.

## ERR-004 — 실제 잔고 재점검 중 HTTP 오류

- **증상:** 2026-10-22 10:28 KST 후보 코드의 읽기 전용 잔고 점검에서 `HTTPStatusError`가 발생했다. 확인된 출력은 `balance_ok=false`, `order_calls=0`이다.
- **비교 근거:** 같은 날 10:08 KST 기존 실행 앱의 KIS 모의 인증·잔고·현재가 사전 조회는 성공했다. 이는 후보 파서 검증 성공을 의미하지 않는다.
- **원인:** 미확정. HTTP 단계에서 실패해 후보 잔고 파서의 실제 응답 호환성 확인을 완료하지 못했다. 토큰 제한이나 키 오류라고 단정하지 않는다.
- **처리:** 원문 대신 HTTP 상태·조회 단계·허용된 오류 코드만 출력하도록 점검 스크립트를 보완했다. 후속 결과가 확인되기 전까지 해결로 표시하지 않는다.
- **후속 확인:** 10:37 후보 코드와 10:44 배포 코드에서 정상 조회를 확인했다(아래 후속 기록 참조). 최초 실패 원인은 미확정이며, 재발하면 안전한 상태 코드와 실패 단계를 추가한다.
- **10/26 재발·재확인:** 배포 후 `/api/broker/balance`가 502 `BALANCE_UNAVAILABLE`를 1회 반환했다. 이후 같은 배포 코드의 직접 KIS 조회와 09:50 HTTP 재확인은 성공(200)했다. 계좌 설정 지문은 일치하며 원인은 미확정이다. 10/22 오류와 같은 원인이라고 단정하지 않는다. 실패 결과는 `data/local-run/kis-deploy-20261026/http-first-check.json`에 보존했다.

## ERR-005 — Docker 빌드 컨텍스트 형식 인식 실패

- **발견일·증상:** 2026-10-22, Windows Docker CLI로 빌드 컨텍스트를 전달할 때 `unknown instruction: ././@PaxHeader`로 빌드가 실패했다.

## ERR-006 — 배포 점검 스크립트의 잘못된 가정

- **발견일:** 2026-10-22.
- **증상·원인:** 사용자 이름만으로 조회해 동명이인 때문에 `MultipleResultsFound`가 발생했다. 마운트 경로를 문자열 그대로 대조해 Docker Desktop의 드라이브·소켓 표기 변환을 변경으로 판단했다. 잔고 HTTP 응답에 기존 계약에 없는 `cash` 필드를 요구해 검증이 실패했다.

## ERR-015 — #393 증권사 설정 통합과 숨은 화면 의존

- **근거:** https://github.com/EST-team-project/Qurious/issues/393
- **확인:** `settings`와 `indicator-api`가 동일 증권사 설정을 편집한다. 직접매매는 설정 화면의 입력 ID 네 개를 읽고 E2E 두 개는 기존 view 위치에 의존한다. 실제 장애가 발생했다는 뜻은 아니며 이동 시 깨질 의존을 확인했다.
- **처리 계획:** 기존 ID·`#settings` 링크를 보존해 마이페이지 증권사 구역으로 본체를 이동한다. 자동화 설명/이름은 유지하고 중복 입력 폼을 설정 링크로 바꾼다. 투자성향 설문은 원래 위치에 두고 계정별 현재 브라우저 값만 요약한다.
- **상태:** 수정 완료·시험 통과. 마이페이지 정적 본체·호환 딥링크·중복 입력 제거·현재 브라우저 성향 요약을 구현했다. 기존 입력 ID는 그대로다.
- **검증:** 관련 Python 103건 통과, 실제 Chrome 딥링크/저장/재진입/계정 전환/모드/연결 오류 안내 검사. 초기 브라우저 시험은 화면 대신 같은 data-view의 메뉴 버튼을 잡아 실패했고 `.view`로 선택자를 한정한 후 통과했다. Windows localhost 시작 지연도 시험 서버 준비 대기로 보완했다. 운영 배포와 혼동하지 않는다.
- **증거:** `data/local-run/broker-settings-393/`. 다음으로 ERR-016을 진행한다.

## ERR-016 — #397 자격증명 평문 저장과 계좌번호 원문 응답

- **근거:** https://github.com/EST-team-project/Qurious/issues/397 · ADR-0004 §4.2
- **확인:** `broker_settings.app_key/app_secret/account_no`는 문자열로 직접 저장된다. `_connection_view`는 키만 일부 가리고 계좌번호는 원문 반환한다. 실거래 차단은 저장 보호를 대신하지 않는다. 유출 사고를 관측했다는 뜻은 아니다.
- **처리 계획:** DB와 분리한 키로 인증된 저장 암호화, 기존 값 전환, 키 누락/복호화 실패 시 차단, 키 교체·백업 복원 검사. 계좌번호 응답을 가리고 일치한 마스크/빈 값 재저장 시 기존 값을 보존한다. 알림 설정 암호화는 이동원 담당 범위로 분리한다.
- **상태:** 미해결. #393 다음 바로 진행한다. 기존 평문 백업은 새 암호화 적용만으로 바뀌지 않으므로 별도 보관·처리 근거도 남긴다. 이 파일에는 실제 키·계좌·토큰을 기록하지 않는다.
