이 문서는 다음 운영자가 담당 기능을 찾고, 정상 상태를 확인하고, 장애 때 주문 상태를 보존하면서 조사하기 위한 안내다. 현재 PC의 읽기 점검은 완료했다. 새 PC 설치·키 전달·수신자의 복원 실습은 아직 완료하지 않았다.

## 1. 담당 기능과 계좌 구분

| 기능 | 사용 경로 | 주요 코드·문서 |
|---|---|---|
| 성향·배분 모델 | 로보 어드바이저 → 자산배분 | `app/services/asset_allocation.py`, `allocation_models.py`, [배분 연결](../02-design/system/배분-리밸런싱-연결.md) |
| 리밸런싱 | `app.html#robo-rebalance` | `app/services/rebalance.py`, `rebalance_regime.py`, `rebalance_daily.py` |
| 자동매매·위험관리 | `app.html#quant-auto` | `app/services/auto_trade.py`, `strategy_v2_execution.py`, `execution_control.py` |
| 증권사·알림 설정 | 마이페이지의 증권사 연동·알림 | `app.html#mypage`, [증권사 설계](../02-design/system/증권사-연동-자동화-설계.md) |
| 취소·잔량 재주문 | 실행·주문 기록과 모의 시험 도구 | [재시험 절차](../04-testing/KIS-잔량재주문-재시험.md) |

PAPER는 앱 내부 직접 모의주문 장부, QUANT는 전략용 가상 장부, KIS 모의는 증권사 모의계좌다. 각각의 현금·보유·주문 기록을 따로 확인한다. KIS에 주식이 있다고 PAPER 일일 스냅샷의 보유 평가를 검증한 것은 아니다.

배분 계산·저장은 주문을 만들지 않는다. 기본 가져오기는 국내주식 부분만 적용하고 나머지는 현금으로 남긴다. ETF를 포함하는 선택 경로에서는 사용자가 확인한 국내 상장 ETF와 적용되지 않은 자산군을 함께 표시한다. 국면 자동 갱신도 별도로 켜고 저장해야 하며 자동 예약 설정과 구분된다.

## 2. 시작 전 준비

1. Docker Desktop, 저장소, 현재 PC의 환경 설정과 수집 DB 연결을 확인한다.
2. `scripts/personal/compose.local.yml` 등 PC 전용 설정의 존재와 적용 순서를 확인한다. 비공개 설정·키·수집 DB는 Git에서 받는 대상이 아니다.
3. 증권사·알림 저장 암호화 키는 app·worker·beat·마이그레이션에 같은 파일을 읽기 전용으로 제공한다. 기존 키를 새 난수로 덮어쓰면 이전 암호문을 읽을 수 없다.
4. 기존 설정의 자동매매·자동 예약·실전 허용 여부와 미확인 주문을 먼저 확인한다. 기능 점검을 위해 임의로 켜지 않는다.

저장소의 PowerShell 시작 도구는 PC 전용 Compose 설정과 키 마운트를 검사한다.

```powershell
git status --short
git pull --ff-only
.\scripts\personal\start.ps1 -NoBrowser
.\scripts\personal\status.ps1
```

작업 파일이 남아 있으면 먼저 보존하고 갱신한다. `start.ps1`은 필요한 경우 이미지를 다시 만들므로 진행 중 주문·작업이 없는 배포 창에서 실행한다. 기존 운영 PC에 적용하는 재시작 절차와 새 PC 설치는 별도 검증이다.

**0043에서 처음 갱신하는 PC:** 위의 pull·재시작 전에 [알림 0044 전환 절차](알림-비밀값-암호화-운영.md)를 먼저 따른다. 평문 알림 설정이 있는 상태에서 새 모델을 읽거나, 전환된 암호문을 옛 이미지가 읽는 구간이 없도록 세 서비스를 중지하고 백업·복원 검증·같은 키 마운트를 준비한다. 이 PC의 WSL에서는 Windows Docker Desktop의 `docker.exe`를 사용하며 Linux `/var/run/docker.sock` 존재 여부만으로 운영 중단을 판정하지 않는다.

## 3. 정상 여부 확인

11/4 점검 PC는 `qurious-app`, `qurious-celery-worker`, `qurious-celery-beat`, `qurious-postgres`를 사용한다. 가격 수신기는 `qurious-hf-collector-sync`이며 11/4 14:27에 최신 main의 수신기/collector 모듈 57파일과 정상 회차를 확인했다. 다른 PC에서는 `status.ps1` 출력의 컨테이너 이름을 사용한다.

```powershell
docker exec qurious-app python -c "import urllib.request; print(urllib.request.urlopen('http://127.0.0.1:8000/api/health', timeout=5).read().decode())"
docker exec qurious-app alembic current
docker logs --since 10m qurious-celery-beat
docker logs --since 10m qurious-celery-worker
```

| 확인 대상 | 정상 기준 | 점검 시 주의할 구분 |
|---|---|---|
| 앱 | `/api/health` 성공, 본인 로그인 후 플랜·상태 조회 성공 | 앱 응답만으로 worker 정상까지 확정하지 않음 |
| DB | 현재 배포의 마이그레이션 head 일치. 11/6 기준 `0044_notification_secrets` | 버전은 새 배포 때 다시 확인 |
| 예약 실행 | Beat 전송, worker 수신·성공, DB 결과가 같은 회차 | 예약 등록과 실제 실행 성공 구분 |
| 자료 | 판단에 필요한 직전 거래일과 수집 세대·완료 기록 일치 | 단순 최대 날짜와 유효한 갱신 회차 구분 |
| 사용자 설정 | 선택한 전략·계좌·판·자동 실행 상태 일치 | 고정 시험 전략을 정식 합격 전략으로 표시하지 않음 |

현재 예약은 heartbeat 60초, 전략 점검 기본 600초, 체결 추적 120초, 리밸런싱 자료 준비 확인 300초다. 리밸런싱 판단은 거래일별 1회 기록으로 중복을 막는다. PAPER 일별 스냅샷은 KST 15:40에 실행된다. 예약 정의는 `app/celery_app.py`가 기준이다.

암호화 오류는 `python scripts/check_credential_storage_logs.py --since 10m`으로 세 서비스의 stdout·stderr를 함께 점검한다. 필요하면 `--docker`로 CLI 경로를 지정한다. 원문 없이 건수만 반환하며 종료 코드 0은 정상, 1은 `[CREDENTIAL_STORAGE]` 발견, 2는 로그 조회 실패다. 11/6 단발 검사는 오류 0건이다. 자동 주기 실행·외부 경보 연결까지 설치한 것은 아니다.

11/4 오전에는 11/3 자료를 기다렸고, 오후에는 검증된 11/3 일봉과 오늘 수신 기록으로 준비 완료를 확인했다. 16:16 판2 읽기 판단은 HOLD이며 새 주문은 없었다. [마감 운영·시연 검증](../04-testing/운영마감-시연검증-2026-11-04.md)의 기준일·배포 시각·제한을 따른다. 자료 준비가 전체 수집 단계의 성공이나 실제 KIS 주문 성공을 뜻하지 않는다.

## 4. 오류가 있을 때

QUANT 판 2가 보유 중 가격 조정 사건을 감지하면 추가 진입·자동 청산을 보류한다. 자동매매 현황의 빨간 「전략 실행 보류」 상자와 알림에 **보류 중에는 자동 손절·익절도 실행되지 않는다**고 표시한다. 수량·평단·손절·익절선은 임의로 교정하지 않으며 자동 교정·보류 해제는 미지원이다. 로그 필터를 바꿔도 이 경고는 유지된다. #563·#568을 포함한 위 배포 기준이며 KIS 판 2 주문 지원을 뜻하지 않는다.

| 증상 | 먼저 할 일 | 다음 판단 |
|---|---|---|
| `DATA_NOT_READY` | 자료 기준일·거래일 달력·갱신 완료 기록 확인 | 자료를 기다린다. 날짜를 바꾸거나 오래된 봉으로 주문하지 않음 |
| 같은 플랜 저장이 409 | 다른 화면/자동 점검의 변경 확인 | 편집안을 보존한 뒤 최신 플랜을 다시 읽고 선택 |
| 주문 응답 불명 | 기존 요청·주문 번호와 증권사 조회 결과 대조 | 같은 주문을 새 요청으로 반복하지 않고 기존 주문 추적 |
| 취소 요청 접수 | 실제 취소 확정 수량·체결·잔량 확인 | 취소 확정 뒤 남은 수량에만 재주문 규칙 적용 |
| 키 오류·503 | 같은 키 파일의 읽기 전용 마운트와 키 ID 확인 | 기존 키 복구. DB 암호문을 평문으로 변경하지 않음 |
| 스냅샷 불완전 | 가격 기준일·출처·보유 수량·누락 자산 확인 | 불완전 평가를 완전한 일수익률로 발표하지 않음 |

공통 장애 분류와 연락·기록 방식은 [장애 대응 절차](장애대응절차서.md)를 따른다. 다른 담당의 수집·성과 계산 오류는 재현 근거와 담당을 남기고 협의한다.

## 5. 배포·백업·복원

1. 현재 커밋/이미지, DB 버전, 활성 설정, 미확인 주문, 실행 중 작업을 기록한다.
2. 새 배포의 관련 시험을 별도 PostgreSQL·Redis에서 수행한다. 앱·worker·beat는 같은 실행 소스로 묶는다.
3. Beat의 신규 전송을 멈추고 worker의 실행·대기 작업을 정리한 다음 쓰기를 중지한다.
4. DB 백업을 암호화하고 별도 DB에서 복원·마이그레이션·계좌 설정/장부 보존을 확인한다. 키는 백업과 분리해 관리한다. `scripts/protect_database_backup.py`가 봉인·복호화를 제공한다.
5. 앱·worker를 시작해 인증 조회·키 읽기·DB 버전을 확인하고 Beat를 시작한다. 새 heartbeat와 실제 기록을 확인한다.
6. 오류가 나면 DB와 호환되는 이전 이미지로 복귀하거나 검증된 백업·대응 키·코드를 함께 복원한다. 운영 DB에 되돌리기 명령을 먼저 실행하지 않는다.

일부 Redis 상태는 재시작 후 전략 상태와 관련된다. 팀의 `backup-appdb.ps1`, `restore-appdb-state.ps1`과 [암호화 운영 절차](증권사-자격증명-암호화-운영.md)의 보관·복원 범위를 함께 확인한다. 상태 파일도 비공개 대상이며 DB 백업 파일 하나만으로 전체 운영 상태 복원을 보장하지 않는다.

### 알림 암호화와 그림자 일지 복구의 경계

알림 암호화 #576은 병합됐고, #577 요청에 따라 **11/6 09:20 운영 DB0044 전환·세 서비스 검증까지 완료**했다. 복제 DB에서 63개 비대상 테이블 보존과 알림 원래 값 일치를 확인한 뒤, 서비스 중지 후 새 암호화 백업을 만들고 전환했다. [상세 결과와 제한](../04-testing/알림암호화-운영전환-2026-11-06.md).

키를 교체할 때는 `rotate_broker_credentials.py`와 `rotate_notification_credentials.py` **모두 성공하고 양쪽 복호화를 확인한 뒤에만** 옛 키를 제거한다. 두 스크립트는 별도 트랜잭션이며 이번 배포에서 키 자체는 바꾸지 않았다. 0044 성공 뒤 옛 이미지로만 돌아가거나 자동 downgrade하지 않는다. 09:20 전환 검증은 외부 발송을 포함하지 않았다. 이후 모의 주문에서 접수 6건·체결 7건(중복 1 포함)의 전달 성공 기록을 확인했다. 수신자의 직접 읽음 확인·개인 테스트 알림의 별도 점검과 상시 경보 연결은 잔여다.

#537에서 판 1을 잇는 코드와 이동원 PC의 원장 복구가 보고됐으며, #533의 일지 판 2는 우리 DB에 없었다. 다른 PC에서는 HF에서 파일을 지워도 로컬 판이 남아 다시 업로드될 수 있다. 가격 수신기와 일지 저장소를 구분하고, 일지의 판·메모·내보내기·manifest 복구는 담당자 합의와 보존된 원본에 근거해 수행한다. 단순 pull을 삭제 동기화로 사용하지 않는다. [검토 근거](../04-testing/운영최신화-2026-11-04.md#3-533-그림자-일지-판-2--오준영-검토-의견).

## 6. 현재 완료 범위와 다음 운영자의 확인

**11/6 최종 운영:** 09:20 DB0044 전환 후 체결 알림 중복 수정까지 `qurious-app:paper-fill-dedupe-owned-20261106`으로 반영했다. 10:05:40 새 heartbeat, HTTP 11경로·세 서비스 각각 712파일·키/설정/장부 보존을 확인했다. #583·#584는 main에 병합됐다. 같은 주문의 정기·직접 체결 확인은 동일한 `client_order_id`로 `order_fill` 발송 권한을 선점한다. 수정 관련 244통과, 고유 전체 집계 4,481통과·2실패·3건너뜀이다. [최종 결과](../04-testing/전체회귀-2026-11-06.md).

**모의 주문:** 하나금융지주·S-Oil·삼성에스디에스 각 10주 매수·매도, 6건 FILLED·시험 잔량/미체결 0·기존 삼성전자 1주 보존을 확인했다. 수수료는 ‘불일치 유지’로 [#579](https://github.com/EST-team-project/Qurious/issues/579)에 게시했다. 강민석 담당 수수료 시험·이동원 담당 인코딩/공통 UI 시험은 미해결이며 임의로 변경하지 않는다. 발표자료는 v0.6이다. 이후 main 변경이나 이후 시각의 운영 상태까지 이 결과로 보증하지 않는다.

**작업환경:** 11/6 자료 마감 중 Windows Docker API의 Linux 엔진 파이프가 없는 오류를 다시 관측했다. 마지막 운영 성공 근거는 위 10:05 점검이며, 현재 Docker 가동·복구 완료는 미확인이다. 원인 확정 없이 WSL 재시작·서비스 재배포를 반복하지 않는다. [작업환경 기록](../04-testing/작업환경-발표마감-2026-11-06.md).

**11/5 오후 갱신:** #561 보류 경고를 포함한 제품 `9c8a88a5`를 배포하고 인증 조회 17경로·새 heartbeat·설정/장부 보존과 관련 회귀 442통과를 확인했다. 기술 시연 19항목은 오전 소스의 결과다. 시험 보완 #569까지 환경별로 대조한 전체 결과는 고유 4,453건 중 4,449통과·1실패·3건너뜀이다. ERR-037 비용 판정 실패는 강민석 담당 후속이다. 11/4 일봉과 수신 근거는 오후에 준비됐으며 실제 KIS 모의 10주 매수·4/6주 분할 매도도 완료했다. 이 수동 주문은 자연 전략 주문 검증을 대신하지 않는다. 11/5 15:40 자연 스냅샷은 Beat→worker→DB의 현금 3건 완전·실패 0으로 확인했다. 보유 자연 평가·새 가드의 자연 주문은 미확인이다. 사용자는 발표 연습 전이며 팀 검토·수신자 실습도 대기다.
