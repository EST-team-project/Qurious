# 증권사 자격증명 저장 암호화 — #397

## 범위와 계약

`broker_settings.app_key/app_secret/account_no`를 AES-256-GCM 인증 암호문으로 저장한다. 저장할 때마다 무작위 12바이트 nonce를 만들고 버전·키 ID·필드 이름을 인증 데이터로 사용한다. 같은 값을 저장해도 암호문은 달라진다. 키/비밀키 칸의 암호문을 서로 바꾸거나 암호문을 변조하면 복호화에 실패한다. 사용자별 조회 권한은 기존 인증과 user_id 조건을 유지한다. 이 방식이 DB 관리자에 의한 같은 필드의 사용자 간 행 교체까지 검출한다는 뜻은 아니다.

근거: [cryptography AESGCM 공식 문서](https://cryptography.io/en/latest/hazmat/primitives/aead/#cryptography.hazmat.primitives.ciphers.aead.AESGCM). 별도 암호 알고리즘은 구현하지 않는다. 현재 잠금 파일의 cryptography 의존성을 사용한다.

키 파일은 `BROKER_CREDENTIAL_KEY_FILE`로 지정하고 소스·이미지·DB와 분리한다. app/worker/beat/마이그레이션 프로세스에 동일 파일을 읽기 전용 마운트한다. 사용자별 KIS 키는 계속 각 사용자의 행에 저장하며 서버 공용 KIS 계좌로 바꾸지 않는다. 환경변수에는 파일 경로만 넣는다.

키 파일 형식은 `{"active":"k1","keys":{"k1":"32바이트 난수의 URL-safe base64"}}`이다. 실제 키를 저장소·명령 인자·로그·PR에 넣지 않는다. 파일 0600, 부모 폴더 0700. 다음 코드는 새 파일만 생성하며 기존 키를 덮어쓰지 않는다.

```python
import base64, json, os
from pathlib import Path
path = Path('/운영자만/읽는/별도경로/broker-credentials.json')
path.parent.mkdir(parents=True, exist_ok=True, mode=0o700)
fd = os.open(path, os.O_WRONLY | os.O_CREAT | os.O_EXCL, 0o600)
with os.fdopen(fd, 'w') as f:
    json.dump({'active': 'k1', 'keys': {'k1': base64.urlsafe_b64encode(os.urandom(32)).decode()}}, f)
```

## 0031 전환과 장애 처리

자동매매 OFF → 앱·worker·beat 쓰기 중지 → 운영 백업 및 격리 복원 → 키 파일 제공 → `alembic upgrade head` → 복호화한 원래 값/계좌 해시/기존 설정·거래 기록 보존 대조 → 동일 이미지 시작 순으로 적용한다. 0031은 문자열 칸을 Text로 넓히고 기존 평문을 한 트랜잭션으로 암호화한다. 부분 변환 또는 키 설정 실패는 전체 rollback이다. DB 제약도 빈 값 또는 암호문 형식만 허용한다.

런타임은 평문을 읽는 호환 경로를 두지 않는다. 키 누락·오류·변조 시 명시적 오류로 끝내고 주문하지 않는다. HTTP DB 의존성은 `503 CREDENTIAL_STORAGE_UNAVAILABLE`로 안내한다. SQLAlchemy 연결은 파라미터를 숨겨 DB 예외에 키가 출력되지 않게 한다. 빈 키를 쓰는 미연동/Mock 계정은 그대로다.

0031 자동 downgrade는 막는다. 기존 코드로 이미 암호화된 DB를 읽게 하거나 암호문을 짧은 칸으로 자르면 안 된다. 배포 오류는 같은 암호화 계약의 코드로 전진 수정하거나, 쓰기를 멈춘 채 검증한 백업과 대응 코드·키를 함께 복원한다. 이전 백업을 복원했으면 0031 전환을 다시 완료한 뒤 서비스를 연다.

## 키 교체와 복원

1. 기존 키들을 보존한 키 파일에 새 난수 키 ID를 추가하고 `active`를 새 ID로 바꾼다. 같은 ID의 키 바이트를 덮어쓰지 않는다.
2. 쓰기를 중지하고 모든 서비스에 같은 파일을 제공한다. `python scripts/rotate_broker_credentials.py`가 모든 암호문을 복호화·새 키로 재암호화·왕복 검증한 뒤 commit한다. 일부 행이 손상되거나 옛 키가 없으면 전체 rollback한다.
3. 새 키만 제공한 격리 복원 DB에서 원래 사용자별 연결과 설정을 검증한다. 운영에서 예전 키를 제거하기 전 옛 백업에 필요한 키의 보관 기간을 확인한다.
4. DB 백업만으로는 복원할 수 없다. 대응 키 파일을 DB 백업과 분리된 제한 접근 경로에 보관하고 함께 복원 시험한다. 잃어버린 키의 암호문은 복구할 수 없다.

## #415 개발 PC 재기동과 키 마운트

`scripts/personal/start.ps1`은 `scripts/personal/compose.local.yml`이 있으면 일반 모드에서 기본 → 로컬, 개발 모드에서 기본 → 개발 → 로컬 순서로 읽는다. 로컬 파일이 없으면 기존 모드별 파일 선택을 유지한다. 모든 `start.ps1` 내부 Compose 호출에 같은 목록을 사용하며 로컬 파일 내용은 출력하지 않는다. 다른 스크립트나 직접 실행하는 Docker 명령의 파일 선택을 자동 변경하는 기능은 아니다.

실제 키가 없는 [compose.local.example.yml](../../../scripts/personal/compose.local.example.yml)을 참고해 **기존 로컬 파일을 보존하며** app·celery-worker·celery-beat에 같은 경로를 설정한다. 예시는 `/run/secrets/broker-credentials.json`으로 파일 하나를 읽기 전용 연결하고 환경변수에는 그 컨테이너 경로만 넣는다. `create_host_path: false`와 아래 시작 전 검사를 함께 사용한다. 별도 마이그레이션은 동일한 `-f` 목록의 `run --rm --no-deps app alembic upgrade head`로 실행한다. 백업·복원·쓰기 중지 조건은 앞 절과 같다.

개발 PC의 `secrets/broker/broker-credentials.json` 위치는 소스 추적·빌드에서 제외하는 로컬 보관 예시다. #406의 `.gitignore`/`.dockerignore` 제외와 부합한다. 운영 키는 기존의 저장소 밖 제한 경로/별도 읽기 전용 볼륨 보관을 유지한다. Windows 개발 PC는 사용자 ACL로 읽기 권한을 제한하고, DB와 대응 키는 별도로 백업한다. 다른 PC 키를 공유하거나 암호화된 DB의 키를 새로 생성하지 않는다. 예시나 시작 스크립트가 키 생성·교체·삭제를 수행하지 않는다.

Windows Docker Desktop 시험에서는 `create_host_path: false`만으로 누락된 파일 경로의 빈 폴더 생성을 막지 못했다. 따라서 `start.ps1`은 로컬 Compose를 사용할 때 설정 원문을 출력하지 않고 읽기 전용 마운트·host bind 키 파일의 존재를 먼저 검사해, 누락 시 네트워크/컨테이너 생성 전에 중단한다. 외부 이름 볼륨의 파일 내용은 이 호스트 검사 범위가 아니며 앞 절의 운영 검증을 따른다. 직접 Docker 명령은 이 PowerShell 사전 검사를 거치지 않는다.

10/29 PowerShell 5.1 및 격리 Docker 시험 7시나리오 통과: 로컬 파일 유무×두 모드, 실제 start 선택식/Compose 인자·종료 코드, 팀 Compose의 세 서비스 설정 병합, 네트워크 없는 시험 컨테이너의 일반→개발→일반 재생성 후 같은 키 복호화·읽기 전용 유지, 일회성 app 실행의 같은 키 사용, 누락 파일 사전 차단. 실제 DB 마이그레이션이나 운영 컨테이너 재생성 시험은 아니다. 재현: `tests/e2e/local_compose_key.ps1 -RepoRoot <저장소 절대 경로> -Image <암호화 모듈이 있는 로컬 앱 이미지>`.
