# 알림 비밀값 저장 암호화 — 0044

> 작성 2026-11-05 (S205 · 이동원). 근거: #530 2-1 · #533(오준영 님 검토 · 키 재사용 안 A 동의) · 증권사 자격증명 암호화 [0031](증권사-자격증명-암호화-운영.md)와 같은 계약.

## 범위와 계약

`notification_settings` 의 **비밀 9칸**을 AES-256-GCM 인증 암호문(`qnc1:<키ID>:<base64>`)으로 저장한다.

| 암호화(9) | 제외(이번 범위 밖) |
|---|---|
| `telegram_token` · `slack_webhook_url` · `discord_webhook_url` · `email_password` · `kakao_api_key` · `kakao_api_secret` · `kakao_sender_key` · `sms_api_key` · `sms_api_secret` | `telegram_chat_id` · `email_to/host/user/from` · `kakao_phone` · `sms_from/to` · `channels` · `preferences` |

- 전화번호 · 주소 칸은 비밀이라기보다 개인정보라 **개인정보 처리방침 판단과 함께 후속**으로 둔다. 화면에서는 지금처럼 마스킹한다.
- **키 파일은 증권사와 같은 것**(`BROKER_CREDENTIAL_KEY_FILE`)을 쓴다. 대신 접두어 `qnc1:` 와 AAD `qnc1:<키ID>:notification_settings.<칸>` 으로 도메인을 나눈다. 한 칸의 암호문을 다른 칸 · 증권사 표로 옮겨 붙이면 복호화가 실패한다. 증권사 암호문 형식 · AAD · 키 ID 는 그대로다.
- 구현: `app/lib/notification_secrets.py`(형제 모듈 · `TypeDecorator`) · `app/models/misc.py`(칸 → `Text` + CHECK 제약 `칸 = '' OR 칸 LIKE 'qnc1:%'`) · `alembic/versions/0044_notification_secrets.py`.
- **평문 읽기 호환은 없다.** 키 누락 · 변조 · 복호화 실패는 `NotificationStorageError`(증권사 예외의 하위 클래스)로 끝난다.
- **폭발 반경**: 같은 키라서 키가 새면 증권사 · 알림 두 표가 함께 노출된다. 운영상 「증권사 키 노출 시 알림 비밀도 함께 바꾼다」(오준영 님 동의).

## 런타임에서 키가 없거나 틀리면

| 경로 | 동작 |
|---|---|
| 설정 화면 GET · 저장 | `503 CREDENTIAL_STORAGE_UNAVAILABLE` · 문구는 「알림 비밀값 보호 설정을 확인하지 못했습니다」(증권사 문구와 구분) · 값 · 암호문은 응답에 없다 |
| 알림 발송 | 그 사용자의 알림은 **보내지 않는다**(`NO_SETTINGS`) · `.env` 공용 채널로도 새지 않는다(fail-closed) |
| 동의 철회 | **키 없이도 된다** — 행을 읽지 않고 `DELETE` 한다(개인정보 삭제를 막지 않는다) |

**조용히 멈추는 것이 이 설계의 가장 큰 약점**이다. 키가 틀리면 모든 사용자의 비상 정지 · 체결 알림이 멈춘다. 그래서(설계 ⑦ ①+③):

1. **기동 때 키 점검** — app(DB 에서 암호문 한 칸을 복호화해 봄) · worker · beat(키 파일만 읽음)가 기동하며 확인하고, 실패하면 `error` 로그 한 줄을 남긴다. **기동은 막지 않는다.** 값 · 암호문은 로그에 쓰지 않는다. 통과 로그는 `info` 라 기본 설정에서는 `docker logs` 에 보이지 않고, **실패(error)만 나온다**(앱 컨테이너에서 키 파일 없이 직접 실행해 출력되는 것을 확인했다).
2. **복호화 오류 구분 로그** — 발송 서비스가 일반 조회 실패(`warning`)와 달리 `[CREDENTIAL_STORAGE]` 표시의 `error` 로그를 남긴다. **기존 로그 감시 · 알림 규칙에 이 표시를 걸어 둔다.**
3. (이번 제외) 데이터 관제 · 상태 화면 표시 — 데이터 관제 서버 변경과 겹쳐 후속.

## 전환 절차 (0044) — **배포 순서가 중요하다**

마이그레이션이 끝난 DB 의 9칸은 `qnc1:…` 암호문이다. **옛 이미지**가 이 행을 읽으면 암호문을 토큰으로 써서 발송이 실패하고, **새 이미지**가 아직 평문인 DB 를 읽으면 호환 경로가 없어 복호화 오류(발송은 멈춤)가 난다. 둘 다 비밀이 새지는 않지만, 설정 화면 저장이 겹치면 옛 코드가 평문을 다시 써서 제약에 걸린다. 따라서 **세 서비스를 함께 멈추고 새 이미지로 함께 올린다.**

| 단계 | 할 일 | 확인 |
|:-:|---|---|
| 0 | 새 이미지를 **같은 태그**로 app · celery-worker · celery-beat 에 쓸 수 있게 준비 · 쓰기 중지 공지 · 마지막 전환은 11-10 까지 | 이미지 태그 · 소스 커밋 기록 |
| 1 | 자동매매 OFF → app · worker · beat **셋 모두 중지** | 컨테이너 상태 · 큐 비었는지 |
| 2 | 운영 DB **새 백업** + 격리 복원본에서 마이그레이션 리허설(전환 전 새 백업 필수) | 복원본에서 9칸 왕복 · 증권사 3칸 불변 · 표 대조 |
| 3 | 키 파일을 세 서비스 + **마이그레이션 컨테이너**에 같은 파일로 읽기 전용 마운트(0031 에서 이미 있음) | 읽기 · 권한 · 키 ID |
| 4 | **새 이미지로** `alembic upgrade head`(옛 이미지로 돌리지 않는다) | 전체 성공 또는 전체 롤백 · 복호화 값이 전환 전과 같음 |
| 5 | 새 이미지로 세 서비스 시작(같은 태그) | 헬스 · worker/beat healthy · 로그에 `CREDENTIAL_STORAGE` 없음 |
| 6 | 테스트 알림 1건 · 설정 GET 마스킹 · 저장(`****` 유지) · 동의 철회 · 삭제 | 발송 성공 1건 |
| 7 | 자동매매 ON 복귀는 마지막 | — |

- **사전 점검(마이그레이션이 자동으로 한다)**: 가림값 `****` 가 9칸 중 어디에 저장돼 있으면 그것을 비밀로 착각해 암호화하게 되므로 **멈춘다**(원인 확인 후 재실행).
- **롤백**: 자동 downgrade 는 막는다. 4단계가 실패하면 트랜잭션이 되돌린다(키 누락 · 손상 행 · 제약 위반 포함). 5단계 이후 문제면 **백업 + 키 파일로 복원**하고 같은 계약의 코드로 전진 수정한다. 4단계 성공 뒤 **옛 이미지로 되돌리는 것은 금지**(암호문을 평문으로 읽는다).
- **키 교체**: 같은 키 파일이라 **두 스크립트를 모두** 돈다 — `scripts/rotate_broker_credentials.py`(증권사 · 오준영 님 코드 · 변경 없음)와 `scripts/rotate_notification_credentials.py`(알림 · 이번에 추가). 각각 전체 성공 또는 전체 롤백이지만 **서로 다른 트랜잭션**이다. **둘 다 끝난 것을 확인한 뒤에야** 옛 키를 키 파일에서 지운다. 하나만 돌리고 옛 키를 지우면 나머지 표가 읽히지 않는다(알림이면 발송이 멈추고 다음 기동 때 `[CREDENTIAL_STORAGE]` error 로그가 찍힌다). 하나의 트랜잭션으로 합칠지는 오준영 님과 협의할 사항이다.

## 다른 개발 PC · 이 문서를 처음 받는 환경

- 앱은 기동 때 `alembic upgrade head` 를 자동 실행한다(`RUN_MIGRATIONS_ON_STARTUP`). **`BROKER_CREDENTIAL_KEY_FILE` 이 없으면 0044 가 전체 롤백으로 실패**하고 앱은 스키마를 바꾸지 않은 채 연결만 한다(「DB 마이그레이션 실패」 경고).
  - 이 상태에서는 모델이 암호문을 기대하므로 **사용자별 알림 설정 행이 평문이면 읽을 수 없어 발송이 멈춘다**(fail-closed). 개인 알림이 필요하면 0031 때 만든 개발용 키 파일(`secrets/broker/…`)을 app · worker · beat 에 같은 경로로 마운트한다([#415 절](증권사-자격증명-암호화-운영.md)).
- 평문 호환을 켜거나 키 검사를 끄지 않는다. 이미 암호화된 DB · 백업에는 **그 암호문에 대응하는 기존 키**가 필요하다.
- 코드를 받으면(`git pull`) 앱이 `--reload` 로 새 모델을 읽고 마이그레이션을 자동 실행하므로, **받기 전에 알림 설정 행이 있는 DB 라면 백업**한다.

## 남은 경계 · 후속

- 전화번호 · 채팅 ID · 이메일 주소 등은 암호화하지 않는다(개인정보 처리방침 판단과 함께 후속). 동의문 · 처리방침 문구는 이 범위에 맞게 고쳤다(판 `NOTIFY_CONSENT_VERSION` 은 올리지 않음 — 보호가 강화되는 변경이라는 전제이며 법률 판단은 아니다).
- 설정 GET 은 `kakao_sender_key` 를 가리지 않고 돌려준다(암호화 전과 같음). 가릴지는 후속.
- 키가 깨지면 설정 화면의 GET 이 503 이라 **화면에서 철회 단추까지 못 갈 수 있다**. 확인한 것은 API 수준(철회 요청은 키 없이도 200)이다.
- 데이터 관제 · 상태 화면에 「알림 암호화 키 확인 실패」 표시는 후속(오준영 님 영역과 겹침).
- 로컬 개발 환경에는 worker · beat 가 꺼져 있어 app 경로만 실측했다. worker · beat 의 같은 키 확인은 운영 전환 체크리스트(위 5단계)로 넘긴다.
