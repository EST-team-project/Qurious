정상 HF 발행과 실제 모의 주문 점검을 기다리는 동안 진행할 수 있는 코드 작업이다. 10/28 소유권 분리와 10/29 이후 공통 위험 검사·실행 기록 작업을 구현했다. 실제 KIS 모의 주문 2회차·매도 확인 및 자동매매 재개 완료로 계산하지 않는다. 10/29 10:49 앱·worker·beat에 동일 위험관리 이미지를 배포했고 자동 실행 OFF를 유지했다. 상세 증거는 [PR #395](https://github.com/EST-team-project/Qurious/pull/395)를 따른다.

## 1. 변경된 동작

| 대상 | 구현 |
|---|---|
| KIS 보유 귀속 | 새 `LiveOrder`에 계좌 해시·전략 ID·판을 기록한다. 추적 시작 전 보유 수량을 별도로 저장하고, 그 수량 + 해당 계좌의 확정 체결 순수량이 현재 잔고와 맞을 때만 사용자·전략·판의 보유를 매도할 수 있다. 수동 보유·다른 전략·다른 사용자·다른 계좌는 편입하지 않는다. |
| 가상 보유 귀속 | QUANT 및 TradingView 주문은 `Order.execution_intent_id`로 전략과 연결한다. 추적 전 보유는 기준 수량으로만 남긴다. 수동 거래 등으로 실제 보유와 전략 기록이 어긋나면 자동 주문을 보류한다. |
| 공통 위험 검사 | 카드·일반 자동매매는 `execution_control.execute`를 거쳐 전송한다. TradingView는 같은 관문을 거쳐 PAPER 장부에만 체결한다. 현금·예산·비중·일손실·일 주문 수·쿨다운·매도 소유 수량·비상 정지·자료 신선도를 검사한다. 0주는 주문하지 않는다. |
| 판 1 점검 | 기존 `StrategyDecision` 경로를 유지하며 공통 한도 검사와 Redis 확인을 적용하고 일손실 기준·주문 수를 새 관문과 공유한다. 계좌 잠금 키도 공유한다. 판 1 매도 범위 자체의 수정은 별도 PR #361에서 검토한다. |
| 반복·동시 실행 | 사용자·계좌·장부·전략·판·종목·방향·판단 시각으로 의도 키를 만들고 DB에 먼저 저장한다. 전달 경로만 바꿔도 같은 의도다. PostgreSQL 계좌 잠금은 주문 함수의 commit 뒤에도 유지한다. 입력이 바뀐 같은 키는 충돌로 보류한다. |
| 중단·통신 장애 | Redis 확인 실패 시 메모리 상태로 대신 승인하지 않는다. 전송 뒤 응답 또는 기록 확정 실패는 `unknown`/`PENDING`을 유지한다. 체결 조회에서 주문을 다시 보내거나 시간 경과만으로 `LOST` 처리하지 않는다. |
| 회차 기록 | 즉시 실행과 예약 실행이 같은 사용자·시간 칸을 공유한다. `RUNNING / COMPLETED / BLOCKED / FAILED / INTERRUPTED`를 `execution_runs`에 저장한다. 실행 잠금이 풀린 뒤 발견한 이전 `RUNNING`은 중단으로 기록하고 자동 재실행하지 않는다. |
| 알림 | `(user_id, kind, ref)`를 DB에서 선점한 다음 발송한다. 회차 실패와 TradingView 신호에 적용한다. 실패·부분 성공·발송 중 상태를 남기고 같은 사건은 자동 재발송하지 않는다. 외부 알림의 정확히 한 번 전달을 보장한다는 뜻은 아니다. |

국내주식 수동 PAPER/Open API 주문과 기존 감시 주문은 이번 공통 관문 적용 대상에 포함하지 않는다. 기존 현금·보유 검사를 유지한다. 알림 선점은 기존 모든 알림 유형으로 확대하지 않았다.

## 2. 운영 적용 후에도 남는 제약

- **게이트웨이 자동 주문은 보류한다.** 현재 응답 계약에 안정적인 계좌 식별자가 없어 공유 URL이나 사용자 ID를 계좌로 간주하지 않는다. 새 자동 주문은 개인 키 KIS 직접 모의 경로만 지원한다. 계좌 귀속이 없는 과거 주문의 자동 잔량 재주문도 보류한다.
- **과거 보유를 자동 편입하지 않는다.** 마이그레이션은 기존 `LiveOrder`의 소유권을 빈 값으로 남긴다. 기존 장부 보유를 새 전략의 매도 대상으로 사용하려면 별도 대조·이관 절차가 필요하다. 현재 자동 이관 기능은 없다.
- **미확인 주문은 확인이 끝날 때까지 막는다.** `PENDING`/`unknown` 의도를 삭제하거나 새 키로 우회하지 않는다. 계좌·주문일·주문번호·종목·방향·수량을 증권사 내역과 대조한 뒤 기록 정정이 필요하다. 이를 처리하는 운영 UI/자동 해소기는 이번 범위에 없다.
- **평균 체결가가 불확실한 보유로 손절 원가를 만들지 않는다.** 여러 매수·매도를 거친 KIS 보유의 평균 원가 재구성은 후속 작업이다. 판 2 QUANT의 확정 가상 체결 손절·ATR은 [별도 검증 기록](../../04-testing/판2-실행상태-검증-2026-10-29.md)을 따른다. KIS 판 2 체결 연결은 아직 없다.
- **혼합 PAPER 자산 평가가 필요하다.** 코인·대체자산을 보유한 계좌의 TradingView 주식 주문은 완전한 공통 평가가 준비되기 전까지 보류한다.
- **TradingView 식별자가 필요하다.** `signal_id`, `bar_time`, 기존 `time` 순으로 판단을 식별한다. 새 알림 템플릿은 `bar_time={{time}}`를 포함한다. 같은 판단을 재전달할 때 이 값을 바꾸지 않는다. 반복 응답은 `duplicate`이며 추가 체결이 아니다.
- **실패 알림과 회차 화면은 구분한다.** 회차 상태는 DB에 보존하고 기존 최근 사이클 화면은 캐시를 계속 사용한다. 새 영속 회차 전용 화면/API는 이번 범위에 없다. 발송 결과 미확인 알림은 자동 재발송하지 않아 누락 가능성이 남는다.

## 3. DB 변경과 되돌리기

마이그레이션 `0028_execution_control`은 `order_intents`, `execution_runs`, `execution_risk_days`, `broker_position_baselines`를 만들고 주문 귀속·알림 사건 컬럼을 추가한다. 사용자 데이터 삭제 경로는 기존 메타데이터 기반 FK 탐색을 사용한다.

운영 반영 시 자동 실행을 끈 상태에서 DB 백업 → 0028 적용 → 앱/워커 동일 버전 반영 → 읽기 및 격리 모의 점검 → 재개 판단 순으로 진행한다. 10/29에는 운영 백업의 격리 복원과 기존 51개 표 보존을 확인한 뒤 `0029`까지 적용하고 앱·worker·beat를 동일 이미지로 반영했다. 새 판 2 `0030` 적용 상태는 별도 검증 기록을 따른다.

코드 롤백과 스키마 downgrade를 구분한다. 운영에서 새 주문·회차가 생긴 뒤 downgrade하면 새 감사 기록이 삭제되므로 먼저 보존·대조해야 한다. 이번 왕복 시험은 일회용 DB의 스키마 사본과 합성 행에서만 진행했다.

### 4.1 10/29 주문 직전 가격 보완 (#369 · #364 · #371 · #366)

`order_preflight.execute_quant`는 서버에서 만든 판단 정보(`signal_key`, `input_hash`, `signal_price`, `signal_as_of`)를 받아 `execution_control.execute(intent, quantity, prepare, send, require_enabled=True)`를 호출한다. `prepare`는 계좌 잠금 안에서 가격·잔고를 다시 조회한다. `size_from_budget=True`인 서버 자동매매는 최종 가격으로 수량을 다시 계산하며, 정해진 수량의 호출은 요청 수량을 넘기지 않는다. 카드 상한은 `position_cap_pct`로 전달하여 계정 상한과 함께 적용한다. 이 값들은 외부 요청을 그대로 신뢰하는 계약이 아니다.

공통 관문은 `prepare`가 반환한 `quantity`에 위험 한도를 적용한 후 선점·전송한다. 기존 `max_quantity` 상한도 유지한다. 위험 설정(`quant_execution_policy`)이 준비 중 바뀌면 `SETTINGS_CHANGED`로 전송을 막는다. 주요 신규 차단은 `PRICE_UNAVAILABLE`(현재 원주가 확인 실패), `STOP_NOT_CONFIRMED`(전송 직전 손절 조건/귀속 평단 확인 실패), `ALREADY_HELD`(위험 수량 추가 매수)다.

응답과 `OrderIntent.result.price_basis`에는 판단가·판단일, 최종 조회한 `quote`의 가격/출처/시각, 수량, 위험 수량의 예상 손실/현금 사용액을 남긴다. 접수 불명에서도 이 근거를 유지한다. `quote`는 주문 전 시세이며 실제 체결가가 아니다. 최종 수량이 증권사 상한으로 줄면 예상 손실/현금도 그 수량으로 줄인다. 수동/다른 전략 보유가 섞인 가상 장부 평단이나 과거 매도 이후 재구성되지 않은 KIS 원가는 손절 근거로 쓰지 않는다.

비상 정지 감사 payload의 `actions`는 중지 설정, 취소 요청 집계, 알림 함수 결과를 구분한다. `cancel_orders.status=checked`는 취소 요청 점검 완료이고 취소 확정은 별도 조회가 필요하다. `notification=dispatched`는 알림 함수가 반환됐다는 뜻으로 채널별 전달 성공은 `notification_log`에서 확인한다. 기존 감사 저장 함수 자체의 실패를 완전히 방지하거나 전달을 보장하는 변경은 아니다.

스냅샷 Celery 작업은 `fail > 0`이면 예외로 종료해 FAILURE로 표시한다. 모든 사용자 처리는 기존대로 시도하고 성공한 사용자 기록은 유지한다. 자동 재시도와 성과 계산/스냅샷 스키마 변경은 없다.

10/29 격리 회귀 시험은 361건 모두 통과했다. 당시 상세 대상·미배포 상태·판 2 잔여 작업은 [작업계획 19.4](../../00-management/plans/오준영파트-할일.md#194-1029-오전--위험-가격조치-기록배치-실패-판별-구현)에 남긴다. `price_basis.adjusted_to_raw`와 판단일 조회 함수는 판 2 가격 단위 연결 준비이며 현재 판 2 주문 지원 완료를 의미하지 않는다.

5. 10/30 실행 기록·재시작·실패 알림 운영 검증, 11/2 통합, 11/3 예외, 11/4 문서, 11/5 최종 점검을 유지한다. 실제 모의 주문 점검/대조 전 10분 자동매매는 OFF다.

## 6. 11/2 긴급 이슈 보완 — 구현·격리 검증, 운영 미적용

기준은 main `392e482`(PR #475)다. 이 절은 별도 수정 브랜치의 동작을 설명하며, 위 10/29 운영 상태를 새 코드의 배포 증거로 사용하지 않는다.

### 6.1 일반 자동매매 위험 수량·고정 손절 (#183)

- 신규 위험 모드의 `stop_kind` 기본은 `atr`, `atr_mult=2`다. 기존 저장 정책에 종류가 없으면 `pct`로 해석해 기존 % 손절 의미를 유지한다. 기본 자동매매 수량 방식 자체는 계속 `fixed_budget`이다.
- ATR은 마지막 확정 거래일까지의 수정 OHLC에 공통 Wilder ATR(14)을 적용하고, 해당 일자의 누적 조정계수로 원주가 거리로 환산한다. 마지막 확정 봉·계수·가격 단위를 확인하지 못하면 진입을 보류한다. 장중 봉이나 다른 손절 방식으로 대체하지 않는다.
- 주문 직전 계산한 진입 가격·손절 설정·ATR 기준일·손절선을 `OrderIntent.result.price_basis.stop`에 전송 전에 기록한다. QUANT 가상 체결은 `Portfolio.risk_entry_intent_id`로 연결한다. 확정 체결 평균가로 고정한 보유 회차의 기준은 `execution_risk_stops`에 보존한다.
- 저장된 진입 기준이 없는 기존 보유는 위험 모드에서 처음 판정할 때 `origin=transition`으로 한 번 고정한다. 진입 당시 기준을 복원한 것으로 표시하지 않는다. 실제 KIS 보유는 해당 계좌·전략의 확정 체결 순수량과 평균 원가가 일치할 때만 연결한다.
- 재시작·부분 매도·설정 변경 뒤에도 저장 기준을 사용한다. 전량 청산 뒤 새 진입은 다른 회차다. 고정 기준이 있는 보유는 고정 예산 모드로 바꿔도 추가 매수를 막으며, 외부 변경으로 평균가가 달라지면 확인을 요구한다. 주문 직전 현재가로 같은 손절선을 다시 검사한다.
- `quantity_limits`와 `binding_limits`에 위험·현금·1회 예산·종목 비중·증권사 가능 수량·요청 수량 제한을 남기고, 화면에서 수량을 정한 제한과 예상 손실을 보여 준다. 기존 예산과 위험 관문은 그대로 적용한다. 갭·슬리피지·미체결로 실제 손실이 예상치를 넘을 수 있다.

### 6.2 PAPER 일일 스냅샷 가격 근거 (#371)

- 계좌·성과 GET은 일일 스냅샷을 쓰지 않는다. 명시적 수동 기록은 `origin=manual`이며 같은 날짜의 `daily` 기록을 덮어쓰지 않는다.
- 종목별 자산·심볼·출처·가격 기준 시각(`as_of`)·근거 생성 시각(`fetched_at`)·대체 사유(`fallback`)·완전성을 JSONB에 저장한다. 시세 자체는 이 메타데이터에 저장하지 않는다. `fetched_at`을 공급자 시세 시각으로 간주하지 않는다.
- 국내 주식은 해당 날짜의 검증된 수집 종가 또는 공급자의 정규장 마지막 체결 시각이 당일 15:30인 가격을 쓴다. Yahoo 표시값의 KST 시간대를 복원하며, 시각 없는 게이트웨이 값·장중 값·마감 이후 다른 시각은 종가로 간주하지 않는다. 근거가 없으면 불완전 상태로 보존한다. 해외 주식의 환율·종가 대사는 아직 지원하지 않는다.
- 코인은 업비트의 실제 `trade_timestamp`가 스냅샷 시각 기준 0~300초 이내여야 한다. 누락·미래 시각·비정상 가격·오래된 캐시는 완전한 평가에 사용하지 않는다. 연결 실패 때도 오래된 캐시를 주문 가격으로 재사용하지 않는다.
- 보유 전체의 근거가 있어야 `complete`다. 평단가 대체 등 불완전한 날도 감사용으로 저장하되 지표에서 제외한다. 기존 행은 재작성하지 않고, 근거 없는 보유 평가를 사후에 완전하다고 인정하지 않는다.
- 같은 계좌 회차의 완전한 일일 기록 두 개가 연속할 때만 수익률을 계산한다. 중간 불완전·누락·회차 변경을 0% 수익으로 넣지 않는다. `return_valid=false`인 저장값 0은 유효한 0%가 아니다. 조회 시 실제 이웃 기록으로 재계산하며 자산 곡선·배분·벤치마크에도 같은 근거/회차 필터를 적용한다.
- 배치 결과는 저장 성공/실패와 별도로 `complete`/`incomplete` 개수를 알린다. 10/22·23 누락 원인은 여전히 미확정이며, 새 코드의 15:40 예정 실행은 배포 뒤 로그와 사용자별 행으로 확인해야 한다.

### 6.3 나머지 수정과 DB 적용

고정 시험 카드(#437)는 CRLF만 LF로 정규화한 뒤 해시를 검사한다. 내용 변조는 계속 거절하며 공급원을 바꾸지 않는다. 수동 앱 장부 주문(#440)은 `virtual`만 받고, 양수 정수 수량·유한 양수 가격·buy/sell을 검증한다. 계좌를 잠근 뒤 현금·보유·비용을 함께 기록하여 동시 매도가 현금을 중복 적립하지 못하게 한다. 증권사 설정은 마이페이지에서 관리하며 실제 KIS 수동 주문 UI 연결은 이번 변경에 포함하지 않는다.

개인 알림 설정이 없거나 조회가 실패할 때 공용 채널로 보내지 않는 처리(#469)는 **기존 PR #475**에 들어갔다. 이번 변경은 실제 설정 조회 함수를 거친 두 경우의 회귀 시험을 더한다. 시험에서 실제 채널로 발송하지 않는다. Alembic은 기존 앱 로거를 비활성화하지 않도록 설정해 같은 프로세스에서 마이그레이션 후에도 실패 로그가 유지된다.

DB `0037_snapshot_evidence`는 스냅샷 근거·수익률 유효성을, `0038_risk_stops`는 진입 연결·고정 손절 표를 추가한다. 운영 적용 시 DB 이전과 앱·worker·beat의 동일 버전 반영이 필요하다. 이번에는 빈 일회용 DB 전체 upgrade와 `0036 → 0038 → 0036 → 0038` 왕복만 확인했다. 새 감사 기록이 쌓인 운영 DB의 downgrade는 해당 기록을 삭제하므로 이 시험을 운영 되돌리기 승인으로 해석하지 않는다.

검증은 Python 3.12, PostgreSQL 18, Redis 8, Node 22와 가짜 증권사/알림 전송기를 사용했다. 세부 시험 결과와 수정 전 main에서도 재현되는 기존 실패는 검토 PR에 기록한다. 작업 도구·가상환경·DB·로그는 저장소 밖 로컬 작업폴더에 두며 PR에 포함하지 않는다.
