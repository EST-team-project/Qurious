## 2. 무엇을 만드나 — 이동원 화면과 같은 방식

화면 설계 절차(3절)를 화면마다 되풀이하되, **2차 기준 설계를 먼저** 만들고 그 위에 3차 변화를 얹는다.

**2차 기본 UI 설계(소급)** — 2차 UI 명세서에 화면 묶음마다 절을 더한다. 2차 문서는 얼린 문서(바로잡기만)라서 **「소급 작성 · 2026-10-29 · 기준 태그 `phase2-final-2026-10-21`」** 을 절 머리에 밝히고, 내용은 그 태그의 코드에서만 읽어 쓴다(그 뒤의 변화는 쓰지 않는다 — 차이를 보려는 것이므로).
- 화면 한 장의 칸(UI 명세서 1절의 <표 1> 형식): 영역 · 칸 · 값의 출처(API) · 비었을 때 · 갱신.
- 그림: 태그 시점의 앱 화면 캡처 1280(필요한 화면은 390도).
- Figma: 묶음마다 새 파일 「Qurious · <묶음>」을 Qurious 폴더에 만들고 **01 지금 화면**(가져온 것 — 고치지 않음) 페이지에 2차 시점 화면을 둔다.

**3차 보완** — 3차 UI 명세서의 같은 절에 2차 → 3차 차이(바뀐 칸 · 새 칸 · 없앤 칸)를 적고 Figma 02 이후 페이지(경우 표 · 설계 · 결정 기록)를 채운다. 마크업이 바뀐 5개 화면은 차이가 이미 크다.

**팀원 변경 반영(상시)** — 팀원 PR · 글에서 화면이 바뀌면 이동원이 이 대장의 그 줄과 UI 명세서 절을 갱신한다(동기화 대장 SY 에 화면 줄을 더해 `docs_scan --sync` 가 알려 주게 하는 안은 조사 문서 3절).

## 4. 열린 것
- 2차 문서를 얼린 규칙(「바로잡기만」)과 소급 작성의 관계 — 이 대장은 사용자 결정(10-29)에 따라 소급 절을 더하되 소급임을 밝히는 방식을 쓴다. 산출물목록 · docs README 의 얼림 문구와 어긋나지 않는지 판 올릴 때 확인한다.
- 스크립트가 그리는 화면(동적 칸)의 2차 → 3차 변화는 이 표의 줄 수에 안 잡힌다 — 묶음마다 코드 차이(`git diff phase2-final-2026-10-21 main -- public/js/<화면>.js`)를 읽어 보탠다.
- 이 대장의 「Figma 0개」 는 문서에 링크가 없다는 뜻이다. 팀원이 따로 Figma 를 쓴 것이 있으면 알려 주면 줄에 더한다.
