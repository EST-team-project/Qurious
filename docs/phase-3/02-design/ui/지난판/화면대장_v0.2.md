## 1. 현황 — 팀원 담당 화면 17개

Figma 파일은 v0.1 때 0개였고, v0.2 에서 ㉲ 인디케이터 셋 화면 3개가 **화면별 파일 3개**를 얻었다(나머지 14개는 아직 0 · 조사: 파트별 할 일 · 이슈 · PR 에 Figma 링크 0).

## 2. 무엇을 만드나 — 이동원 화면과 같은 방식

화면 설계 절차(3절)를 화면마다 되풀이하되, **2차 기준 설계를 먼저** 만들고 그 위에 3차 변화를 얹는다.

**2차 기본 UI 설계(소급)** — 2차 UI 명세서에 화면 묶음마다 절을 더한다. 2차 문서는 얼린 문서(바로잡기만)라서 **「소급 작성 · 2026-10-29 · 기준 태그 `phase2-final-2026-10-21`」** 을 절 머리에 밝히고, 내용은 그 태그의 코드에서만 읽어 쓴다(그 뒤의 변화는 쓰지 않는다 — 차이를 보려는 것이므로).
- 화면 한 장의 칸(UI 명세서 1절의 <표 1> 형식): 영역 · 칸 · 값의 출처(API) · 비었을 때 · 갱신.
- 그림: 태그 시점의 앱 화면 캡처 1280(필요한 화면은 390도).
- Figma: **화면마다** 새 파일 「Qurious · <화면>」을 만들고(사용자 결정 2026-10-29 — 같은 화면을 다시 캡처하지 않게 화면별로 저장한다 · 묶음 파일 제안은 철회) **00 표지 + 01 지금 화면**(`generate_figma_design` 편집 가능 레이어 캡처 — 가져온 것 · 고치지 않음)을 둔다. ㉲ 셋은 이렇게 만들었다(폭 1920).

**3차 보완** — 3차 UI 명세서의 같은 절에 2차 → 3차 차이(바뀐 칸 · 새 칸 · 없앤 칸)를 적고 Figma 02 이후 페이지(경우 표 · 설계 · 결정 기록)를 채운다. 마크업이 바뀐 5개 화면은 차이가 이미 크다.

**팀원 변경 반영(상시)** — 팀원 PR · 글에서 화면이 바뀌면 이동원이 이 대장의 그 줄과 UI 명세서 절을 갱신한다(동기화 대장 SY 에 화면 줄을 더해 `docs_scan --sync` 가 알려 주게 하는 안은 조사 문서 3절).

## 4. 열린 것
- 2차 문서를 얼린 규칙(「바로잡기만」)과 소급 작성의 관계 — **어긋난다**(S165 판 올림 때 확인). docs README 3.3절은 2차 문서에 판을 올리지 않고 틀린 사실만 바로잡도록 하는데(예외 ②), 소급 16장은 틀린 사실이 아니라 새 절이다. `docs_scan --bump` 도 2차 문서에는 「2차는 얼린 자리다」 경고를 낸다. 그래도 사용자 결정(10-29 — 2차에도 기본 UI 설계가 있어야 2차와 3차의 차이를 확인할 수 있다)을 따라 2차 UI 명세서를 **v0.29 → v0.30** 으로 올리고(지난판 사본 `지난판/UI명세서_v0.29.md`), 절 머리와 개정 이력에 「소급 작성 · 2026-10-29 · 기준 태그 `phase2-final-2026-10-21`」 을 밝혔다. README 3.3절에 소급 예외(③)를 더할지는 사용자 결정 거리 — 더하지 않았다. 번호 겹침: 2차 v0.30(소급 16장)과 3차 `지난판/UI명세서_v0.30.md`(학습 세 갈래)는 서로 다른 문서의 판이다.
- 스크립트가 그리는 화면(동적 칸)의 2차 → 3차 변화는 이 표의 줄 수에 안 잡힌다 — 묶음마다 코드 차이(`git diff phase2-final-2026-10-21 main -- public/js/<화면>.js`)를 읽어 보탠다.
- 이 대장의 Figma 칸은 **문서에 링크가 있는 것**만 센다(㉲ 셋은 이동원이 만든 파일 · 나머지 14개는 링크 0). 팀원이 따로 Figma 를 쓴 것이 있으면 알려 주면 줄에 더한다.
