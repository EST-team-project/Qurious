## 1. 지금 코드가 이미 하는 일

```
POST /api/ingest/crawl/naver   (app/routes/ingest.py:63)
      │
      └─> crawl_naver_stock()   (app/services/crawl.py:212)
             ├─ finance.naver.com/item/main.naver?code=###### 요청
             ├─ BeautifulSoup 으로 종목명·현재가·뉴스 10건 파싱
             ├─ _chunk_text()        1,000단어 · 150 중첩
             ├─ _store_qdrant()      → Qdrant 벡터DB (RAG 재료)
             └─ _upsert_crawled_doc() → CrawledDoc (본문 5,000자)
```

즉 **수집·전처리·적재까지 이미 있다.** 요구사항 세부2 는 상당 부분 충족돼 있다.

## 2. 그러면 남은 일은 무엇인가 — "어떻게 가져왔는지"

강사님 요청의 무게는 **결과가 아니라 과정**에 있다. 지금 화면이 돌려받는 것은 로그 한 줄뿐이다.

```
✓ 삼성전자 네이버금융 → 3청크 (Qdrant 3건)
```

이걸로는 "어떻게 가져왔는지" 를 볼 수 없다. 네 단계를 드러내야 한다.

```
  ① 무엇을 요청했나
     GET https://finance.naver.com/item/main.naver?code=005930
     헤더: User-Agent · Referer
     ─────────────────────────────────────────────────
  ② 무엇이 돌아왔나   (응답 원문 일부 · 접었다 펼 수 있게)
     <div class="wrap_company"><h2><a ...>삼성전자</a></h2>
     <p class="no_today"><span class="blind">70,800</span>
     ─────────────────────────────────────────────────
  ③ 어떻게 읽었나   (선택자와 그 결과를 나란히)
     div.wrap_company h2 a        → 종목명 "삼성전자"
     p.no_today span.blind        → 현재가 "70,800"
     div.section.new_bbs ul li a  → 뉴스 10건
     ─────────────────────────────────────────────────
  ④ 어디에 넣었나
     _chunk_text  → 3청크 (1,000단어 · 150 중첩)
     Qdrant       → 3건  (컬렉션 …)
     CrawledDoc   → 1행  (본문 5,000자까지 · source=naver:stock:005930)
```

②③ 을 보여주는 것이 요점이다. 보통 크롤러 데모는 예쁜 표만 보여주는데, 그러면 **"가져온 결과"** 만 보이고 **"가져온 방법"** 은 안 보인다. ④ 까지 드러내면 적재 위치와 출처 꼬리표가 화면에 남아 요구사항 세부4(갱신일·버전)로 자연스럽게 이어진다.

## 3. 무엇을 고쳐야 하나

| 위치 | 지금 | 해야 할 일 |
|---|---|---|
| `crawl_naver_stock()` | `int`(청크 수)만 반환 | 요청 URL·헤더, 응답 원문 조각, 선택자별 파싱 결과, 적재 결과를 **구조로 반환** |
| `app/routes/ingest.py:63` | `chunks` 와 `log` 만 응답 | 위 구조를 그대로 응답에 담는다 |
| `public/app.html` (`crawl-manual` 뷰) | 로그 텍스트만 출력 | 4단계를 접이식 블록으로 표시 |

🟡 **응답 원문을 통째로 내려보내지 않는다.** 앞 2~3KB 로 자른다 — 화면에 보여줄 목적이고, 전체는 이미 파싱해 적재한다.

## 5. 약관 — 적재와 배포는 서로 다른 문제다

적재하기로 했으므로 근거를 분명히 적어 둔다.

| 질문 | 답 | 근거 |
|---|---|---|
| 네이버를 가져와도 되나 | 🟢 학습용 범위 | 강사님이 수업에서 배포한 이력이 있고, 학습용 사용은 괜찮다고 하셨다 |
| 적재해도 되나 | 🟢 요구사항이다 | PROJECT 01 세부2 「크롤링 및 **적재**」 |
| **그것이 HF 로 나가나** | 🔴 **아니다** | HF 업로드 대상은 `collector` 의 SQLite **8개 표**뿐이다(`scripts/hf_dataset.py:251` `TABLES`). `CrawledDoc`·Qdrant 는 앱 Postgres/Qdrant 라 **스캔 범위 밖**이다 |
| HF 저장소는 공개인가 | 🔴 **private 강제** | `_assert_private()` 가 업로드 직전 `repo_info` 로 원격이 실제로 private 인지 확인하고 public 이면 **중단**한다 |
| 추가 배포를 하나 | 🔴 **하지 않는다** | 팀 결정(2026-09-21) — private Organization 안에서만 공유하고 그 밖으로 옮기지 않는다 |

### 저장소가 여러 벌이라 갈린다

우리는 저장소를 용도별로 나눠 쓴다(요구사항 「데이터·지식 저장: RDBMS · VectorDB · Redis」와 대응).

```
  앱 (docker-compose)                       수집기 (독립)
  ┌─────────────────────────────┐          ┌────────────────────────┐
  │ Postgres   CrawledDoc       │          │ SQLite                 │
  │            Order·Portfolio  │          │  price_daily           │
  │            BrokerSettings   │          │  price_adjusted        │
  │ Qdrant     문서 임베딩       │          │  price_total_return    │
  │ Redis      캐시·Celery       │          │  dividend              │
  │ Neo4j      그래프            │          │  benchmark_index       │
  └─────────────────────────────┘          │  raw_response          │
              ▲                            │  ingest_day            │
              │                            └───────────┬────────────┘
     크롤링 적재가 들어가는 곳                            │
     → HF 대상 아님 🟢                        HF private 업로드 대상 🔴
```

**적재 결정과 배포 판단이 독립**이라는 점이 중요하다. 크롤링을 적재해도 HF 로 나가지 않으므로 [#53](../issues/053.md) 4절의 약관 판단은 그대로 유효하다.

⚠️ 그래도 **공개 범위를 바꾸면 이 판단이 전부 무너진다.** 저장소를 public 으로 돌리는 일은 처음부터 다시 따져야 한다.
