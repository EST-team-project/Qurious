## 본문

## 목적

1차 프로젝트(Alpha_Stack (Alpha_Stack 저장소)) 발표 후 받은 피드백입니다.

- **누구에게, 무슨 목적으로** 만든 것인지가 명확하지 않았다.
- 많은 것을 하기보다 **하나를 깊게** 하는 것도 좋다.

강사님이 덧붙인 피드백 다섯 가지(2026-09-15 전달)도 모든 산출물의 기준으로 삼습니다.

1. **목표를 명확하게** 설정하는 것이 중요하다. → D1 [#7](../discussions/007.md)
2. **분석이 생각보다 부족하다.** 결론은 있는데 심층 분석이 없어서, 결론에 문제가 생기는 경우가 많다.
3. **수행한 사람도, 모르는 사람도** 이해할 수 있어야 한다.
4. **결론에 너무 집착하지 않는다.** 프로젝트에 끌려가면 안 된다.
5. **코드 주석**과 지표 같은 **개념(기초 포함) 기록**을 남겨, 면접에서 본인이 설명할 수 있어야 한다.

→ 2~5는 D0([#6](../discussions/006.md))의 안건 ⑦ "설명·기록 기준"에서 운영 규칙으로 합의합니다.

그래서 2차(로보 어드바이저)와 3차(커스텀 인디케이터)는 코드를 쓰기 전에 **현황 파악 → 결정 → 작업** 순서로 설계하고, 그 과정을 이 저장소에 남깁니다.

이 이슈는 전체 목록과 결정 요약을 모아 두는 **인덱스**입니다. 2차 프로젝트 시작일이 **2026-09-27**로 바뀌어(2026-09-15 확인), 그 전까지 약 2주 동안 코드 작업 없이 설계 문서만 만듭니다.

## 기록 규칙

| 구분 | 담는 것 | 끝나는 조건 |
|---|---|---|
| **Issue** `[분석] A#` | 코드 현황 분석, 결함, 결정 뒤에 생기는 작업 | 문서 확정 또는 작업 완료 시 close |
| **Discussion** `[논의] D#` | 아직 답이 없는 결정: 목표, 비용, 범위, 설계 | 결론 댓글을 Answer로 표시하고 파생 Issue를 링크한 뒤 잠금 (General 카테고리는 Answer 표시가 안 되므로 "해결됨"으로 닫기) |

- 흐름은 **Issue(현황) → Discussion(결정) → Issue(작업)** 입니다. 서로 `#번호`로 연결합니다.
- 코드·문서 변경은 **feature 브랜치 → PR**로 올립니다.
  - PR 본문은 7절(Why·What·Who·How·Impact·Proof·Learn)로 씁니다.
  - **PR 하나에 TIL 한 장**(`docs/TIL/<이름>/`)을 붙입니다.
  - 머지는 사람이 GitHub 웹에서 합니다.
- GitLab은 **main만**, GitHub에서 머지된 뒤 동기화합니다.
- 커밋 메시지에 `refs #번호`를 쓰면 이슈에 커밋이 연결됩니다. PR 본문에 `closes #번호`를 쓰면 머지될 때 이슈가 닫힙니다.
- 이슈마다 담당자(Assignee)는 1명만 두고, 나머지 팀원은 댓글에서 @멘션합니다.
- 운영 방식은 **D0([#6](../discussions/006.md))에서 팀이 합의한 뒤** 이 절을 고칩니다. 흩어진 규칙은 D0 결론 뒤 **`CONTRIBUTING.md` 한 장**으로 모읍니다([#6 답글](../discussions/006.md#discussioncomment-18445593)).
