## 요약

[#62 §3.0](../issues/062.md) 이 남긴 「요구가 27개인가 29개인가」를 풀고, 요구↔설계↔코드↔시험을 가로로 잇는 **요구사항 추적표(RTM)** 를 세웁니다.

> **RTM**(Requirements Traceability Matrix, 요구사항 추적표)
> — 요구 한 줄마다 「어느 설계 → 어느 코드 → 어느 시험」이 대응하는지 **가로로 잇는 표**입니다.
> 이게 있어야 「이 요구는 구현됐는가」에 *증거로* 답할 수 있습니다.
> **헷갈리는 점**: 진척률 보고서가 아닙니다. 진척률은 결과로 나오는 숫자일 뿐이고,
> RTM 의 본체는 **「이 요구의 증거가 어디에 있는가」라는 주소**입니다.

## 1. ★ 개수 매듭 — 세어서 풀리지 않았습니다

### 1.1 먼저, 셀 수가 없었습니다

강사님 목표기능표 **원문이 저장소에 없습니다.** [#62](../issues/062.md) 에 전재된 것만 있고,
저장소에 있는 `docs/rfp-1.md`·`docs/rfp-2.md` 는 **다른 문서**입니다.

`rfp-2.md` 체크박스를 기계로 세어 봤습니다.

```
  §3 요구사항     19개  ┐
  §6 산출물        8개  ┼─ 19 + 8 = 27   ← 우연히 27이 나옵니다
  §7.2 평가        4개  │
  §9 제안 요건     4개  ┘
  ────────────────────
  합계            35개
```

**27이 두 곳에서 나옵니다.** 두 문서가 섞여 인용되며 「27」이 무엇의 27인지
흐려졌을 가능성이 있습니다. 🟡 원문을 못 봤으므로 **가능성으로만** 적습니다.

### 1.2 매듭은 번호 체계로 풀었습니다

```
   [순번 방식]  요구 1, 2, 3, … 27       ← 합계가 29로 바뀌면
                  ↓                         모든 번호가 밀린다
   산출물 대장 "요구 14번 대응"          → 가리키는 대상이 바뀐다 🔴
   시험 항목   "요구 22번 검증"          → 가리키는 대상이 바뀐다 🔴

   [계층 방식]  P01-①-1, … P02-⑤-3      ← 합계가 바뀌어도
                  ↓                         각 주소는 그대로
   산출물 대장 "P01-③-2 대응"           → 항상 「이탈률 리밸런싱」 🟢
   시험 항목   "P02-⑤-2 검증"           → 항상 「중복주문 방지」   🟢
```

**흔들릴 수 있었던 이유는 합계가 애매해서가 아니라 순번으로 부르려 했기 때문입니다.**
계층 ID 로 두면 합계는 진척률에만 쓰이고 주소로는 안 쓰입니다. [#62](../issues/062.md) §3.0 의 🔴 우려는 해소됩니다.

합계는 **29(열거 기준)** 를 정본으로 합니다 — 누락보다 과배정이 안전합니다.

## 3. ⚠️ 화면이 실제보다 더 말하고 있습니다

자산배분 4개를 확인하다 나온 것입니다. **발표에서 질문 한 번에 무너질 수 있는 자리**라 따로 세웁니다.

```
  public/app.html:2521   "자산배분 모델"                       화면 있음 🟢
  public/app.html:2536   "블랙-리터만 (Black-Litterman)"       설명 있음 🟢
  public/app.html:2547   "Risk Parity"                         설명 있음 🟢
  public/app.html:1690   "AI가 최적 자산배분 비율을 계산합니다"   ← 문구 🟢
            │
            ▼  이 화면이 실제로 부르는 것
  app/routes/ml.py:85    POST /robo/allocation
  app/routes/ml.py:95        base_alloc = {
                                "conservative": {국내주식 15, 해외주식 10, 국내채권 50, …},
                                "moderate":     {국내주식 30, 해외주식 25, 국내채권 30, …},
                                "aggressive":   {국내주식 45, 해외주식 35, 국내채권 10, …},
                             }[risk]            ← 🔴 위험성향 3택 하드코딩 표
                             + 투자기간에 따라 ±horizon_boost
```

**최적화가 아니라 조회표입니다.** 공분산도 목적함수도 제약조건도 없습니다.

> 🟢 **공정하게 적자면, 종목 스코어링은 실재합니다.** 같은 엔드포인트의 `_screen()` 은
> 유니버스 ~30종목을 실제로 훑어 샤프비율 + Ridge 회귀로 점수를 냅니다(`ml.py:113~`).
> 빈 껍데기가 아닙니다. 다만 **자산군 비중 결정**과 **종목 선정**은 다른 일이고,
> 비어 있는 쪽은 앞엣것입니다.

## 5. 표를 손으로 쓰지 않았습니다

손으로 쓴 RTM 은 코드가 바뀌어도 그대로 남아 한 달 뒤 거짓이 됩니다.
그래서 요구마다 **탐지 규칙**을 적어 두고 기계가 훑게 했습니다.

```bash
python scripts/rtm_scan.py          # 사람이 읽는 표
python scripts/rtm_scan.py --md     # RTM 문서 §5 에 붙일 마크다운
python scripts/rtm_scan.py --json   # 기계용
```

### 5.1 ⚠️ 만들면서 두 번 속았습니다 — 둘 다 초록불 쪽으로

| # | 증상 | 원인 | 고침 |
|---|------|------|------|
| 1 | 「리밸런싱 0건」이 **1건**으로 | **스캐너 자신**이 훑는 대상에 들어감. 패턴 문자열 `r"rebalanc"` 가 잡힘 | 스캐너 파일 제외 |
| 2 | 「중복주문 방지」가 **2건** 있는 것으로 | 둘 다 **주석 속 `idempotent`**. 구현은 0건 | 코드줄·주석줄 분리 |

**둘 다 「없는 걸 있다고 말하는」 방향의 오류입니다.** 자동 판정은 편한 쪽으로 틀리기
쉬우니, 몇 건은 손으로 열어 확인하고 그 경위를 RTM §7.1 에 남겼습니다.

> **이 표가 답하지 못하는 것** — 코드가 **제대로 동작하는가**, 시험이 **충분한가**,
> 요구가 **옳은가**. RTM 이 가장 위험할 때는 틀렸을 때가 아니라 **맞다고 믿길 때**입니다.
