## 1. 이번 구현

`app/services/asset_allocation.py`의 `asset_allocation(risk_profile, horizon_years)`가 자산군 비중의 정본이다. 키는 국내주식·해외주식·국내채권·대체자산·현금 그대로이며, 성향 셋 × 기간 1~10년 모두 합계 100%, 음수 없음이다. 장기 보정은 현금과 채권의 기존 잔여 비중 이내로 제한한다. 음수가 아니던 기존 결과는 유지한다. 예: 공격형 10년은 47/37/8/8/0이다.

| API | 계약 |
|---|---|
| `GET /api/ml/robo/weights?risk_profile=moderate&horizon_years=3` | 로그인 필요. `risk_profile`, `horizon_years`, `allocations` 반환. 성향·기간 오류 422. 시장·캐시·DB 계산 없음. 상품 안내 화면이 사용 |
| `POST /api/ml/robo/allocation` | 기존 시장 계산 후 사용자별 최신 결과 자동 저장. 기존 결과 필드와 `saved: {id, saved_at}` 반환. 실패하면 이전 저장본 유지 |
| `GET /api/ml/robo/allocation/latest` | 로그인한 본인의 `{id, saved_at, result, handoff}` 반환. 저장본 없으면 404. 전달할 수 없는 결과는 `handoff: null` |

`allocation_results`는 사용자당 한 행이다. `user_id`(PK·users FK CASCADE), `result_id`(UUID), `result`(JSONB), `updated_at`을 저장한다. 과거 이력을 계속 쌓지 않는다. 탈퇴 시 삭제된다. `0020_paper_epoch → 0021` 마이그레이션이 필요하다.

## 2. 국내주식 부분만 가져오는 기준 — 팀 검토 요청

현재 최적화 후보는 국내주식이다. 해외주식 비중까지 국내 종목에 합산하던 계산을 수정했다. 국내주식 자산군 비중만 최적화 상대 비중대로 나누고, 소수 둘째 자리에서 합계가 정확하도록 잔여 0.01%p를 배분한다.

리밸런싱 전달 정책은 `domestic_equity_only_v1`이다. 중립형 3년의 자산군 배분은 30/25/30/10/5로 보존하지만, 실행 가능한 목표는 국내주식 30%·현금 70%다. 해외주식 25%·채권 30%·대체자산 10%를 아직 매수하지 않는다는 사실과 종목별 비중을 확인창에 명시하고 동의받는다. 이를 완전한 5자산군 투자라고 표시하지 않는다. ETF 매핑은 후속 검토 대상이다.

추천 종목 화면도 같은 국내주식 비중을 사용한다. 예상 성과 및 목표 시뮬레이션 기본값은 국내주식 바스켓과 나머지 현금의 조합이다. 기존 현금 연 2.5% 가정은 유지하되 화면에 명시하며, 5자산군 실현 수익률로 해석하지 않는다.

## 3. 사용자 흐름과 실행 경계

1. 자산배분 계산 완료 시 결과를 자동 저장한다. `저장한 배분 보기`로 새 접속에서도 다시 볼 수 있다.
2. 리밸런싱의 `저장한 배분 가져오기`에서 저장 시각·종목·미적용 자산군·현금 비중을 확인한다.
3. 취소하면 편집값을 유지한다. 확인하면 편집안에만 목표를 채우고 편집안의 자동 실행을 끈다.
4. 저장 전 서버의 기존 플랜·예약은 그대로다. 상태 조회로 편집안을 덮어쓰지 않으며, 가져온 목표 저장 전에는 미리보기·조건 점검·실행 요청을 막는다.
5. `플랜 저장`을 눌러야 기존 플랜 API에 목표를 보낸다. 저장 자체로 주문하지 않는다. 이후 기존 미리보기→승인→예약→정산 흐름을 사용한다.

전체 자산 비중의 기준은 기존 리밸런싱의 관리 대상 자산이다. `플랜 외 종목 보호`를 켜면 해당 보유 종목은 계산에서 제외되므로, 가져오기만으로 계좌 전체 자산군 배분을 보장하지 않는다.

## 4. 검증 결과

- Python 3.14·임시 PostgreSQL 18에서 관련 pytest **177건 통과**: 신규 배분 43, 상품 화면 4, 마이그레이션 단일 head 1, 기존 리밸런싱 129.
- 신규 시험: 30개 성향·기간 조합, 이전 정상 결과 유지, 잘못된 입력, 소수점 합계, 미지원 종목 거부, 인증, 가벼운 API의 외부 호출 차단, 실제 PG에서 저장·새 세션 조회·사용자 격리·덮어쓰기·실패/롤백 보존·탈퇴 삭제·플랜/예약/주문 무변경.
- Chromium에서 실제 `public/app.html`, `robo.js`, `rebalance.js`를 사용하고 API만 고정 응답으로 대체해 **7개 흐름 통과**: 취소, 확인, 저장 전 요청 차단 및 새로고침 보존, 명시적 저장, 저장본 복원, 재계산 렌더링, 저장본 없음. 주문 실행 요청 0건. 재현: Playwright와 Chromium 설치 후 `python scripts/check_allocation_ui.py`.
- 빈 시험 DB 전체 `alembic upgrade head`, 새 migration downgrade→upgrade 통과.
- 운영 DB·실거래·원본 러너는 호출하지 않았다. 운영 적용이나 main 병합 완료를 의미하지 않는다.
