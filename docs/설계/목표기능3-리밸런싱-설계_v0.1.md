## 1. 범위와 현재 상태

기존 화면·API·모의 장부를 사용한다. 이번 구현은 5%p 경계, 현금흐름 누적과 주문 방향, 비용, 같은 날 계획 통합, 승인 정합성을 맡는다. 자산배분 모델·스크리닝 알고리즘은 별도 범위다.

거래일 달력(`/api/calendar/trading-days`)과 같은 `market_calendar.trading_days` 읽기 서비스를 리밸런싱에 연결했다. 월·분기·연의 첫 거래일 09:00 KST부터 시간 조건을 점검한다. **현재 로컬 Docker에는 실제 수집 DB가 없어 시간 예약은 확인 대기 상태다.** `data/collector/market.sqlite3` 또는 `COLLECTOR_DB_PATH`로 실제 달력이 연결되면 다음 조회/점검에서 복구한다. 시험용 달력을 운영 자료로 대신 넣지 않는다.

데이터 갱신 상태(`/api/data/status`)와 동일한 조회 서비스를 연결했다. Celery가 준비 상태를 5분마다 확인하고, 거래일에 해당 일자 12:30 이후 시작한 갱신이 성공적으로 끝나면 플랜별 하루 한 번 판정한다. 현재 로컬에는 실제 수집 DB와 러너 완료 기록이 없어 자동 점검은 대기한다.

이번 2번 작업은 **자동 정기 점검 시점**을 바꾼다. 시세 기준일이 전 거래일인지 확인하지만 실제 비중·주문 계산은 아직 조회 시세(`current_quote`)다. 전 거래일 종가 계산(3번)·다음 거래일 시가 체결·배당 자동 입금은 후속 작업이다. ‘지금 점검’과 입출금 직후 점검은 기존 방식으로 별도 동작한다(선택 질문 후 기존 동작 유지 기준으로 진행).

## 2. 구현 규칙

- 시간 기본 꺼짐, 월·분기·연 지원. 이탈 기본 5%p 이상, 3/5/10 선택 + 0.5 단위 직접 입력(0.5~50). 비교는 0.01%p 단위 정수 bp로 통일한다.
- 시간 설정을 새로 켜거나 주기를 바꾸면 다음 주기를 예약한다. 월은 다음 월, 분기는 다음 1·4·7·10월, 연은 다음 해 1월의 첫 거래일 09:00 KST다. 09시는 점검 시작 기준이며 실제 체결 시가나 개장 시각을 뜻하지 않는다. 기존 1일 예약도 같은 주기의 첫 거래일로 재계산한다. 놓친 예약은 이후 거래일 09시부터 처리하며 휴장일에 TIME을 발생시키지 않는다.
- 자동 정기 점검은 위 시간 예약 도래만으로 실행하지 않는다. 거래일 달력과 전 거래일을 정확히 확인하고, 당일 12:30 이후 시작/완료된 러너 기록, `ok=true`, 중단 없음, price/calendar 단계 성공, 실제 시세 기준일과 러너의 price_max가 모두 전 거래일인 것을 요구한다. 갱신 잠금이 남으면 4시간이 지나도 완료로 추측하지 않는다. 일부 단계 실패도 현재는 대기하며 성공한 재실행 후 다시 확인한다.
- 자동 판정 성공 시 `last_auto_check_date/at/result`를 같은 트랜잭션에 저장한다. 조건 미충족(관망)도 완료이며 재시작·동시 작업에도 하루 1회다. 갱신 미완료/실패나 시세 조회 예외는 완료로 기록하지 않고 재시도한다. 이미 기록한 부분 체결·주문 실패는 기존 중복 실행 방지 규칙을 유지한다. 수동 점검·입출금·설정 변경은 이 완료일을 초기화하지 않는다.
- 달력 없음·부분 응답·기간 내 날짜 누락·시작 월 거래일 없음은 TIME 대기 사유다. DB에는 재시도할 주기의 기준일을 보존하되 응답 `next_run_at`은 null, `time_schedule_error`는 안내 문구다. 수동·현금 이벤트 점검의 다른 독립 조건은 계속 동작하며, 자동 정기 점검에는 별도로 데이터 준비 조건도 적용한다. `scheduled` 모드는 TIME이 확인될 때까지 DRIFT도 대기한다. 다음 해 달력이 없어도 오늘의 유효한 시간 제안 승인/체결은 보존한다.
- 이탈 확인은 `always`(기존 점검마다) / `scheduled`(시간 주기 도래일에 이탈 조건까지 충족한 경우)이다. 후자는 TIME만으로 무조건 주문하지 않는다. 시간 꺼짐 + scheduled 조합은 거절한다.
- 현금흐름 기본 10만 원, 금액 무관(0)·5만·10만·50만·100만·직접 입력. 입력은 유한한 0 이상 숫자만 허용한다.
- **출금 확정(사용자 2026-10-02): 보유 현금 안에서 먼저 출금하고, 초과 보유 자산부터 매도해 현금 목표를 회복한다.** 현금 부족 출금 예약은 만들지 않는다.
- 현금흐름 단독이면 입금·배당은 매수만, 출금은 매도만. TIME/DRIFT가 함께 충족하면 전체 조정. MANUAL은 사용자가 명시한 전체 조정이다.
- 현금 목표는 100 - 목표 주식 비중 합계다. 현금흐름의 재배분 예산은 이벤트 발생 때 `금액 × (1 - 현금 목표)`로 기록한다(출금은 음수). 서로 반대 방향 이벤트는 미사용 예산을 상계한다. 실제 현금 초과/부족과 예산 중 작은 금액이 기준 이상일 때 주문한다. 따라서 일반 매매·가격 변동만으로 CASHFLOW가 생기지 않는다. 1억/현금40% 계좌에 10만 입금은 예산 6만이다.
- 최소 주문·정수 주 때문에 남은 예산은 다음 이벤트/점검으로 이월한다. 제안 생성만으로 소비하지 않고 실제 체결 순현금만큼 소비한다. 기존 이벤트는 남은 예산 0으로 이전해 과거 현금을 재사용하지 않는다.
- `exclude_unplanned` 선택 시 목표 밖 주식은 주문과 이탈 판정·관리 총자산에서 모두 제외한다. 화면에는 별도 평가액으로 표시한다. 코인·대체자산은 관리 대상이 아니며 PAPER 현금을 공유한다는 기존 한계가 있다.
- 거래비용은 trading_cost.order_costs 한 곳을 사용한다. 예상·실제 비용을 따로 표시한다. 모의 주문은 최신 가격을 다시 읽으므로 예상과 체결이 다를 수 있다. 실패·부분 체결은 성공과 구분한다.
- 자동 계기 계획은 한국 날짜별 사용자 플랜당 한 건. 사용자 단위 PostgreSQL 트랜잭션 잠금과 부분 유일 인덱스로 동시 호출을 제어한다. 같은 날 미승인 계획은 조건을 합쳐 다시 산출하되 이미 체결한 계획은 재실행하지 않는다. 수동 실행은 별도다.
- 시간 조건 제안은 다음 예약일이 갱신돼도 당일 승인 대기 동안 시간 조건을 유지한다. `scheduled` 모드의 이탈 조건은 매번 다시 확인하며, 설정이 바뀌면 기존 시간 조건을 승계하지 않는다. 한 사용자의 시세 실패가 다른 사용자의 정기 점검을 중단하지 않는다.
- 승인은 기존 이력 행을 갱신한다. 원래 계획 종류를 유지하고, 설정이 바뀐 제안은 재점검하도록 거절한다. 오래된 제안이 최근 자동 실행 뒤에 체결되지 않도록 차단한다.

## 3. 저장·API

RebalancePlan: drift_check_mode, exclude_unplanned.
자동 정기 점검 추가: last_auto_check_date, last_auto_check_at, last_auto_check_result. `0015_rebalance_daily_check.py`가 0014 다음에 컬럼을 추가하며 기존 플랜은 완료일 없음으로 시작한다. 날짜는 KST 거래일이다. `/status`의 `automatic_check`에 대기 이유·준비/완료·최근 점검 시각과 결과를 추가한다.
CashflowEvent: remaining_budget(서명 있는 미사용 재배분 금액).
RebalanceRun: triggers, plan_kind(full/buy_only/sell_only), decision_date, context(JSON: 조회 시각·가격 방식·설정 지문·예상비용).
새 마이그레이션으로 추가한다. 기존 행과 설정을 유지하며 기존 플랜의 목표 밖 종목 정책은 전량매도(false)를 유지한다. 새 플랜 기본은 보호(true)다.

`0012_rebalance_policy`와 main의 `0013` 이력은 `0014_merge_rebalance_policy.py`로 연결한다. 이미 적용된 revision은 변경하지 않는다. main DB(0013)와 기존 리밸런싱 DB(0012_rebalance_policy) 어느 쪽에서도 `upgrade head`로 0014에 도달한다.

기존 /plan, /status, /preview, /check, /cashflow, /execute, /runs 경로를 유지한다. 대표 trigger 필드는 호환용, triggers는 전체 원인이다. status는 partial을 추가한다. 금액과 이탈률 범위는 서버에서 검증한다.

## 4. 화면

선택지+직접 입력, 이탈 확인 시점, 플랜 밖 종목 보호, 현금 기준 설명을 추가한다. 상태에는 관리 자산·제외 자산·현금 초과/부족·미사용 현금흐름 예산을 표시한다. 이력에는 모든 조건, 계획 종류, 판정일, 예상/체결 비용을 표시한다. 기본 자동체결은 계속 꺼짐이다.

## 5. 인수 시험

1. 목표60%→65%와55% 모두 500bp로 같은 판정. 경계 아래는 실행 안 함.
2. 입금/배당만일 때 매도가 없고 승인 뒤에도 유지. 출금은 현금 내에서 처리 후 매도만.
3. 소액 이벤트 누적·상계·체결 후 잔여 예산·일반 매매 제외.
4. 비용 포함 예산을 넘지 않는 정수 수량, 목표 현금 보존, 최소 주문 미만 제외.
5. 목표 밖 종목 보호 시 주문과 최대 이탈에 영향 없음.
6. TIME/DRIFT 동시 조건 보존, scheduled 결합 규칙, 같은 날 동시 호출과 중복 승인에서도 한 번 체결.
7. 잘못된 수치(NaN/Infinity/음수/단위 위반) 거절. 설정 변경 제안 승인 거절.
8. 실제 PostgreSQL에서 마이그레이션·API·경쟁 요청·승인·이력 확인. 시세는 시험에서 고정하고 네트워크에 의존하지 않는다.

## 6. 후속 협업과 완료 조건

- 이동원: 거래일 달력 및 갱신 완료/기준일 상태 연결은 완료. 실제 수집 DB뿐 아니라 같은 갱신 회차의 `state/daily_update_last.json`도 앱·worker가 읽을 수 있게 준비해야 한다. HF 데이터 파일만 가져오면 현 구현의 완료 증빙이 없으므로 자동 점검은 대기한다. 갱신 전체 성공 기준과 수동/입출금 예외는 팀 검토 대상이다.
- 강민석: 다음 시가 예약 체결, 가격 누락 시 대기, 체결일/확정일 구분. 기존 즉시 주문을 전역 변경하지 않고 별도 실행 경로 제공.
- 배당 지급일 API는 준비됐지만 자동 입금은 미구현이다. 지급일 없는 배당은 추측하지 않는다. 권리 보유 수량·주당 배당금·세전/세후·정정 공시·수동 입력과의 중복 방지를 합의한 뒤 연결한다. 현재 수동 배당 입력을 사용한다.
