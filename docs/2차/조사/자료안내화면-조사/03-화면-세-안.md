## 요약

1. **자리** — 위 메뉴 「데이터」 묶음의 왼쪽 메뉴 둘째 줄(데이터 관제 바로 아래 · 모든 로그인 사용자). 관제는 「지금 자료가 며칠 것이고 오늘 수집이 돌았나」, 새 화면은 「무엇이 있고 · 어떻게 모으고 · 무엇을 읽으면 되나」 에 답한다. 늦음 판정(색)은 관제에만 두고, 새 화면은 마지막 날짜와 「관제에서 보기」 만 둔다.
2. **세 안** — A 자료 카탈로그(카드 목록 + 자료 한 장 서랍) · B 한 장 보고서(구성 · 수집 · 읽기 세 절 + 분석 그림) · C 길잡이 먼저(하려는 일 → 읽을 자료 → 한 장).
3. **추천 — 안 B 에 안 A 의 「자료 한 장」 서랍을 합친다.** 사용자 요청의 세 마디(어떻게 구성 · 어떻게 수집 · 어느 것을 읽나)와 「대시보드 느낌의 분석 페이지」 가 B 의 세 절 · 바둑판 그림과 그대로 맞고, 자료 하나를 깊이 보는 일은 서랍이 맡는다. C 의 길잡이는 B 의 셋째 절로 들어간다.
4. **지금 API 로 되는 것** — 자료별 줄 수 · 마지막 날짜(API-DATA-01) · 흐름의 단계 이름표(API-DATA-01 의 회차 기록) · 일정 · 근거 문서 · 용어 숫자. **안 되는 것** — 처음 날짜 · 연도별 줄 수(매니페스트에는 있다) · 자료마다 이용 조건(관리자 API 에 넷만) · 칸 정의 · 읽기 길잡이. 그래서 새 서버 하나를 제안한다 — 설명은 git 생성물, 숫자는 러너가 날마다 쓰는 파일, 앱은 둘을 읽기만(8절).
5. **정할 것 넷** — ① 누가 보나 ② 화면에 표 이름 · API 경로 같은 개발 말을 쓰나 ③ 어떤 분석 그림부터 ④ 숫자 정본을 어디에 두나. 추천은 각 질문의 첫 칸이다(13절).

## 1. 자리 · 겹침 · 목표

데이터 묶음의 화면과 새 화면이 각각 무엇에 답하는지는 <표 1> 과 같다.

**<표 1> 데이터 묶음 화면 다섯** · 누구 = 메뉴가 보이는 사람

| 화면 | 누구 | 답하는 질문 | 시간 축 | 바뀌는 때 |
|---|---|---|---|---|
| 데이터 관제 | 모두 | 지금 자료가 며칠 것까지 있고, 오늘 낮 수집이 돌았나 | 지금 | 30초마다 다시 본다 |
| **자료 안내(새)** | 모두 | 무엇이 있고, 어떻게 모으고, 무엇을 읽으면 되나 | 늘 — 자료 자체 | 하루 한 번(숫자) · 자료가 늘 때(글) |
| 수집 일정 · 단계 | 관리자 | 어느 단계가 언제 얼마나 걸렸고 실패했나 | 회차 | 회차마다 |
| 자료 직접 받기 | 관리자 | 빈 날을 어떻게 메우나 | 조치 | 받을 때 |
| 적재 · 백업 | 관리자 | 백업이 믿을 만한가 · 원본을 지워도 되나 | 백업 | 백업마다 |

겹치지 않게 하는 규칙 셋을 둔다.

- 늦음 판정(최신 · 정상 · 늦음 · 멈춤의 색)은 관제에만 둔다. 새 화면은 마지막 날짜를 글자로만 보이고 「지금 상태는 데이터 관제」 로 보낸다.
- 회차 결과(단계마다 성공 · 실패 · 걸린 시간)는 수집 일정 · 단계에만 둔다. 새 화면의 흐름 그림은 단계의 이름과 하는 일만 보인다.
- 값 미리보기(표의 줄)는 두지 않는다. 값은 그 값을 보는 화면(주가 차트 · 일정 · 투자 정보 리서치)으로 보낸다. 원자료 재배포 금지(공공누리 제4유형)와 화면 중복을 함께 피한다.

**목표**(검토 때 의견을 대는 기준) — 처음 온 팀원이 3분 안에 「내가 하려는 일에 어느 자료를 어디서 읽나」 를 찾는다. 일반 사용자는 「이 서비스의 숫자가 어디서 오고 언제 것인가」 를 한 화면에서 본다.

**자리 후보 · 이름** — 왼쪽 메뉴 둘째 줄 · 화면 키 가칭 `data-guide` · 이름 가칭 「자료 안내」(다른 후보: 데이터 안내 · 자료 지도 · 데이터 카탈로그 — 마지막은 개발 말 느낌이라 뒤로). 들어오는 길은 메뉴 · 관제의 「자료 안내 →」 · 다른 화면(일정 · 투자 정보 리서치 · 용어사전 · AI 투자 상담)의 「이 자료는 어디서 오나」 · 주소로 바로다. 「그 자료 한 장이 열린 채로」 여는 주소(예 `#data-guide/<자료 키>`)는 지금 화면 주소 처리(`core.js` 의 `hashchange` · `main.js` 첫 화면)가 화면 키와 똑같은 주소만 받아 그대로는 안 된다 — 공통 파일을 고치는 일이라 구현 때 정한다.

IA 의 N12(국내 주식 대시보드 — 시장 · 데이터 현황 · Q13 열림)와는 「데이터 현황」 일부가 겹친다. N12 는 시장 중심, 이 화면은 자료 중심이라 따로 두고, N12 를 설계할 때 이 화면의 숫자 띠를 카드 하나로 빌려 쓸 수 있다.

## 4. 안 B — 한 장 보고서(구성 · 수집 · 읽기)

사용자 요청의 세 마디를 세 절로 둔다. 맨 위 숫자 띠와 연도별 바둑판이 「분석 페이지」 느낌을 만든다. Sharadar 의 사양 표 · Progress 그림, dbt 의 계보 그림, Data Cards 의 층 나누기를 따랐다(02 문서 2.5 · 2.7 · 2.9).

**<그림 3> 안 B — 1280** · 값은 01 문서의 실제 값 · 바둑판 칸 ░ ▒ ▓ █ = 그해 줄 수(자료마다 따로 잰 4단계) · ① ~ ⑦ = 12절 요소 번호

## 6. 세 안 견주기 · 추천

**<표 6> 세 안 견주기** · 높음 · 중간 · 낮음

| 기준 | A 카탈로그 | B 한 장 보고서 | C 길잡이 먼저 |
|---|---|---|---|
| 요청과 맞음 — 구성 · 수집 · 읽기 | 구성만 높음 | **셋 다** | 읽기만 높음 |
| 요청과 맞음 — 대시보드 · 분석 느낌 | 낮음 | **높음** | 낮음 |
| 「무엇을 읽나」 답 속도 | 중간 | 중간(셋째 절) | **높음** |
| 전체 그림 | 낮음 | **높음** | 낮음 |
| 자료가 늘 때 | **높음**(카드만) | 중간(바둑판 길어짐) | 낮음(길잡이 글 고침) |
| 지금 API 로 그리는 몫 | 낮음 | 중간(흐름 · 기준일) | 낮음 |
| 수집 자료 없는 PC 에서 | 설명 카드는 보임 | 설명 · 흐름 · 길잡이는 보임 | 길잡이는 보임 |
| 390 폭 | 중간 | 중간(바둑판 → 막대) | **높음** |
| 사람이 계속 고칠 글 | 적음 | 중간 | 많음 |

**추천 — 안 B 에 안 A 의 「자료 한 장」 서랍을 합친다(B + A).** 까닭은 셋이다.

1. 사용자 요청이 「어떻게 구성 · 어떻게 수집 · 어느 것을 읽나」 세 마디와 「대시보드 느낌의 분석 페이지」 다. B 의 세 절과 숫자 띠 · 바둑판이 그대로 맞는다.
2. B 의 첫 그림 둘(숫자 띠 · 흐름)은 지금 API 와 매니페스트로 바로 그릴 수 있고, 바둑판도 매니페스트 두 장만 읽으면 된다 — 1단계를 작게 시작할 수 있다(8절).
3. 자료 하나를 깊이 보는 일은 A 의 서랍이, 「무엇을 읽나」 는 C 의 길잡이가 B 의 셋째 절로 들어와 맡는다 — 세 안의 장점이 한 화면에 모인다.

**뒤집을 조건** — 팀원이 검토에서 「길어서 길잡이까지 내려가지 않는다」 고 하면 C 의 칩 줄을 B 의 맨 위(숫자 띠 아래)로 올린다. 자료가 50개를 넘으면 B 의 목록을 A 의 카드 찾기로 바꾼다.

**위험 · 막는 법**

| 위험 | 막는 법 |
|---|---|
| 수집 DB 를 여는 도구가 하나 는다 — WAL 보조 파일 문제(DF-81 · `collector/README.md`) | 숫자 생성은 러너 단계 안에서만 돈다(따로 도는 도구를 늘리지 않는다) · 처음 · 마지막은 색인 칸만 읽는다 |

### ① 누가 보나

**질문** — 「자료 안내」 화면과 그 안의 정보를 누구에게 보이나?

| 고를 칸 | 뜻 |
|---|---|

| (나) 모든 로그인 사용자 · 개발 정보도 모두에게(접어 둠) | 팀원이 관리자 권한 없이도 표 이름 · API 를 본다 |

| (라) 새 역할 「팀원」 을 만들어 그 사람에게 | 역할을 하나 더 만든다 |

**판단 재료** — 앱의 역할은 `user` · `admin` 둘뿐이다(데이터 사전 표 7 · `users.roles`) · 관제는 모두, 수집 화면 셋은 관리자(UI 명세서 5.1) · 수집 자료 API 는 로그인 뒤(설계서 7절) · 일반 사용자에게는 「숫자가 어디서 오고 언제 것인가」 가 신뢰의 근거다(공공데이터포털 · Sharadar 의 사양 표 — 02 문서) · 원자료 재배포 금지(제4유형)는 값을 내보내는 일을 막는 것이라 줄 수 · 기간 같은 요약은 걸리지 않는다(추정 · 법률 판단 아님) · 이 PC 의 점검 계정은 관리자 API 를 부를 수 있다(API-DATA-05 · 08 · 10 이 200 — 2026-10-08 12:07).

### ② 화면에 개발 말(표 이름 · API 경로)을 쓰나

**질문** — 「어느 것을 읽으면 되나」 에 답하려면 표 이름 · API 경로가 필요한데, 화면 글에는 개발 티가 나는 말을 쓰지 않는다는 규칙이 있다. 어떻게 푸나?

| 고를 칸 | 뜻 |
|---|---|
| **(가) 본문은 쉬운 이름만 · 개발 정보는 자료 한 장의 펼침에(관리자)(추천)** | <표 10> 의 짝 · 「어디서」 칸은 화면 이름 · 관리자에게만 API · 백업 파일 · 명령 |
| (나) 쉬운 이름 옆에 작은 회색 글씨로 표 이름을 함께(모두) | 팀원이 바로 찾지만 규칙에 어긋난다 |
| (다) 개발 말은 화면에서 빼고 API 문서(관리자) · 데이터 사전으로 링크만 | 화면은 깨끗하지만 「무엇을 읽나」 의 마지막 걸음이 화면 밖이다 |
| (라) 「개발자」 탭을 따로 둔다 | 한 화면에 두 화면이 생긴다 |

**판단 재료** — 규칙: 화면 글은 실제 서비스 말로 · 저장소 · DB 이름이나 작업 말을 쓰지 않는다(UI 명세서 5.1 「화면 글」 칸) · 비슷한 안: API 문서 화면을 관리자에게만 두자는 안(IA Q11 안 C · 아직 정하지 않음 · 지금은 누구나 `/api-docs/` 를 연다) · 선례: 「자료 직접 받기」 는 관리자 화면이라 PC 에서 돌릴 명령을 그대로 보인다 · Data Cards 의 층 셋(telescopes · periscopes · microscopes — 02 문서 2.9) · CSS 로만 숨기면 응답에는 남는다 → 서버가 싣지 않는 쪽이 규칙을 지킨다.
