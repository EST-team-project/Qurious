## 요약

1. 두 DB 에 표 57개 · 칸 617개가 있다 — 수집 DB(SQLite) 15표 18,784,631행 🟢 실측 · 앱 DB(PostgreSQL) 42표 🟡 모델 정의. 근거 문서 DB(별도 SQLite · 4표)는 표 속성 대장과 4절 코드 값에만 있고 칸 표는 다음 판이다(부록 C).
2. 수집 DB 15표는 매 거래일 12:30 일일 갱신이 채운다 — 시세 · 배당 원자료와 그 파생 12표는 **비공개**(원자료 재배포 금지 · HF private 백업)이고, 거래일 달력 셋(특일 정보 · 계산한 달력 · 일정)은 **공개 가능**하다. 앱 DB 의 사용자 데이터는 **보존 기간을 정한 표가 없다** — 지우는 경로는 사용자 삭제 · 탈퇴(2026-09-30 · 즉시 파기) · 모의투자 초기화 · 관리자 초기화다. 참조 데이터 4표는 원천 자료의 재배포 조건을 아직 확인하지 못했고, 용어사전 4표는 저장소 파일이 원본이라 **공개 가능**한 첫 표들이다.
3. 칸 설명은 코드 주석에서 자동으로 온다 — 수집 DB 109/167칸(65%) · 앱 DB 100/450칸(22%). 새로 만든 표는 설명이 붙어 오지만(용어사전 · 달력 · 실주문 추적), 앱 DB 42표 중 22표는 아직 설명이 한 칸도 없다.

## 2. 칸 설명은 코드 주석에서 온다

3절의 「설명」 칸은 이 문서에 사람이 적은 글이 아니다. 스캐너가 코드의 주석을 옮긴다. 사전과 코드가 갈라지면 갈라졌다는 사실조차 아무도 모르게 되므로, 설명의 정본을 코드 한 곳에 둔다.

표 3 은 「설명은 어디서 오고, 고치려면 어디를 고치나」 에 답한다.

**표 3. 설명이 오는 곳**

| DB | 어디서 | 무엇을 | 예 |
|---|---|---|---|
| 수집 DB | `collector/db.py` · `collector/benchmark.py` 의 CREATE 문 | 칸 오른쪽의 `-- 주석` · 칸 바로 위 줄들의 `-- 주석` | `dividend.dps` → 「1주당 배당금(원) 보통주식」 |
| 앱 DB | `app/models/*.py` | 칸 위 줄 · 오른쪽의 `# 주석` | `orders.cost_basis` → 「none(안 뗌) \| estimated(요율표로 계산) \| broker(증권사가 준 실제 금액)」 |

**설명을 고치려면 이 문서가 아니라 코드 주석을 고친 뒤 스캐너로 다시 채운다**(부록 B). 3절을 손으로 고치면 다음 실행에서 사라진다. 설명이 붙었다고 옳다는 뜻은 아니다 — 스캐너는 주석을 옮길 뿐, 주석이 사실인지 검사하지 않는다.

### 2.1 채움 비율

표 4 는 「칸 설명이 얼마나 붙어 있나」 에 답한다.

**표 4. 설명이 붙은 칸** · 기준: 2026-10-02 스캐너

| DB | 표 | 칸 | 설명이 붙은 칸 | 비율 | 설명이 한 칸도 없는 표 |
|---|--:|--:|--:|--:|--:|
| 수집 DB — 데이터 파트가 만들었다 | 12 | 143 | 91 | 63.6% | 1 |
| 앱 DB — 강사님 코드에서 물려받은 표가 대부분 | 40 | 419 | 88 | 21.0% | 22 |
| **합계** | **52** | **562** | **179** | **31.9%** | **23** |

그림 1 은 「두 DB 의 설명 비율 차이가 얼마나 큰가」 에 답한다.

**그림 1. 설명이 붙은 칸의 비율** · 막대 한 칸 = 5% · 괄호 = v1.2(2026-09-29)

```
 수집 DB  █████████████    63.6%  (91 / 143)   ← 68% (60 / 88)
 앱 DB    ████             21.0%  (88 / 419)   ←  5% (15 / 259)
```

앱 DB 의 비율이 오른 것은 기존 표에 주석을 단 덕이 아니라, **새로 들어온 표가 주석을 달고 왔기 때문**이다 — 용어사전 5표 42/42 · 강사님 기초 코드의 리밸런싱 · TradingView · 수식 지표 표 · 모의계좌 스냅샷. 수집 DB 의 비율이 내린 것은 ETF · 지수 표가 포털 응답 칸을 그대로 옮겨 설명 없는 칸이 많아서다(`etf_daily` 13/20 · `index_daily` 7/16).

설명이 한 칸도 없는 표는 수집 DB 1표(`ingest_day`)와 앱 DB 22표다 — `alternative_positions` · `api_keys` · `audit_events` · `bank_products` · `chats` · `conversations` · `corporate_cb_stats` · `crawled_docs` · `custom_indicators` · `data_cache` · `formula_indicator_versions` · `formula_indicators` · `fund_products` · `lean_backtest_runs` · `notification_log` · `notification_settings` · `paper_accounts` · `personal_cb_stats` · `quant_virtual_accounts` · `strategy_comparisons` · `uploaded_docs` · `users`. v1.2 의 21표 가운데 `broker_settings` · `portfolio` 는 강사님 기초 코드가 칸 주석을 달아 빠졌고, 새 표 셋(수식 지표 둘 · 전략 비교)이 들어왔다. 앱 DB 의 칸 설명은 모델 파일에 칸 주석을 다는 작업을 **따로** 잡아야 는다 — 표마다 담당(요구 대장)이 단다 💬.

### 2.2 코드와 DB 파일이 다른 칸 — 사전은 코드 쪽을 쓴다

수집 DB 파일에 저장된 CREATE 문은 표를 **처음 만들 때** 것이다. 그 뒤 코드에서 주석을 고치거나 칸을 더해도 파일 쪽 CREATE 문의 주석은 바뀌지 않는다. 사전은 코드의 주석을 쓰고, 스캐너는 두 쪽이 다른 칸을 요약 출력에 알린다(ℹ️ — 틀린 것이 아니다).

표 5 는 「어느 칸의 설명이 코드와 DB 파일에서 다르고, 왜 다른가」 에 답한다.

**표 5. 설명이 코드와 DB 파일에서 다른 칸** · 기준: 2026-10-02 스캐너 — v1.2 와 같은 6칸

| 칸 | DB 파일 | 코드(사전이 쓰는 쪽) | 까닭 |
|---|---|---|---|
| `corporate_action.kind` | 세 값(split · rights · review) | 네 값 — `shares` 를 더했다 | 감자 결함 DF-01 을 고치며 값이 늘었다 |
| `dividend.div_type` | 두 값(현금배당 · 현물배당) | 세 값 — `현금ㆍ현물배당` 을 더했다 | 실제 값에 있는데 주석에 빠져 있었다(4절) |

## 4. 코드 정의 — 정해진 값만 들어가는 칸

값이 몇 가지로 정해진 칸을 모았다. 수집 DB 의 건수는 실제 DB 에서 센 값이고(🟢), 앱 DB 는 운영 DB 가 없어 코드에서 쓰는 값을 적었다. 값의 뜻은 3절 설명 칸(코드 주석)과 같아야 한다 — 다르면 코드 주석을 고친다.

## 부록 B. 만든 방법

**스캐너**

```bash
python scripts/schema_scan.py                                   # 요약 · 칸 설명 대조 · 대장 대조
python scripts/schema_scan.py --doc docs/데이터/데이터사전_v1.3.md    # 1절 · 3절 두 곳을 다시 채운다
python scripts/schema_scan.py --doc docs/데이터/데이터사전_v1.3.md --check   # 뒤처졌으면 종료코드 1
```

- 1절 · 3절은 문서 안의 HTML 주석 표시 `schema_scan:list` · `schema_scan:md` 사이를 스캐너가 채운다. 스캐너가 만든 표는 번호 없이 제목만 있다 — 스캐너는 문서의 표 번호를 모른다.
- 수집 DB 의 행 수는 매일 12:30 에 는다. 그래서 `--check` 는 **행 수만 다르면** 「같다」 로 보고 알리기만 하고(종료코드 0), 칸 · 설명 · 대장이 다를 때만 「뒤처졌다」(종료코드 1)를 낸다. 이 문서의 행 수는 판을 올릴 때 `--doc` 로 다시 채운다.
- 수집 DB 표의 **구조**(칸 · 타입 · 키 · 행 수)는 DB 파일에서, **칸 설명**은 코드의 CREATE 문에서 읽는다. DB 파일이 없는 PC 에서는 수집 DB 부분을 건너뛴다.
- 시험: TC-SS 10건(`tests/test_schema_scan.py`) — 재현성 · 설명의 출처 · 코드와 DB 파일 대조 · 대장 판정 규칙 · 문서 채우기.

**표 속성 대장**

- 머리 줄 10칸: `표 · DB · 한글명 · 업무영역 · 유형 · 발생주기 · 보존기간 · 공개 · 공개_근거 · 관련표`. 「유형」 · 「공개」 는 정한 말만 쓴다(스크립트 상수 `표속성_유형` · `표속성_공개`).
- 표를 더하면 대장에 줄을 더한다. 빠지면 스캐너 요약에 ⚠️ 가 뜨고, 1절 표에는 「⚠️ 대장에 없음」 으로 나온다. 멈추지는 않는다.
- 운영 속성은 사람이 코드를 읽고 적었다. 발생 주기 = `scripts/daily_update.py` 의 단계 · `sync_scheduler` 의 주기(1시간) · 각 라우트와 서비스의 쓰기 · 보존 기간 = `collector/` 와 `app/` 의 삭제문(`DELETE` · `db.delete` · `delete(...)`) 전수 · 공개 = `scripts/hf_dataset.py` 의 공유 결정과 모델 칸.

**스캐너 밖에서 잰 것** — 4절 표 6 의 건수(읽기 전용 `group by` · 2026-10-02 10:50 KST · 12:30 갱신 전) · 표 7 의 값(코드 검색 — 쓰는 곳의 글자 값) · 표 7 의 용어사전 건수(로컬 앱 DB 의 `group by` — 적재 결과라 파일과 같다) · 1.1절 탈퇴 범위(`account.user_owned_columns()` 를 앱 컨테이너에서 불러 26표).

**한계와 뒤집을 조건**

- 앱 DB 의 행 수와 실제 값 분포는 모른다(운영 DB 가 없다). 운영 DB 가 생기면 표 7 에 건수를 더한다.
- 참조 4표의 「미확인」 은 원천 자료의 이용 조건을 찾으면 바꾼다.
- 「정하지 않음」 은 팀이 보존 정책(개인정보 · 감사 기록 · 거래 기록)을 정하면 바꾼다.
