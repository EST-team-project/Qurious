## 개념 정리

### 1. 「이 시각은 무슨 시각인가」는 코드로 답한다

#503 은 내가 올린 협의 이슈였다. LEAN 백테스트가 15:29 에 만드는 봉이 「당일 종가에 체결한다는 뜻」인지를 강민석 님께 여섯 질문 중 하나로 물었다.

강민석 님의 답은 이랬다. **15:29 는 일봉 커스텀 데이터에 부여한 시각일 뿐이고 당일 종가 체결을 의도한 것이 아니다.** 실제 체결 시점은 LEAN 이 일봉 해상도와 장 마감까지 남은 시간에 따라 엔진 안에서 변환한다. 그래서 기존 결과를 「당일 종가 체결」로 해석하면 안 된다.

코드를 읽어 맞춰 보았다. `app/services/lean_backtest.py:826` 에서 `replace(hour=15, minute=29)` 로 봉 시각을 정하고, reader 가 넘기는 값은 close 하나뿐이다. 설명과 일치했다.

🔑 시각이 들어 있는 코드는 **그 시각이 무엇을 위한 값인지**를 읽어서 안다. 「15:29 라서 종가 체결」은 이름에서 나온 추측이었다.

### 2. 기본 동작은 그대로 두고 선택 모드로 넣는다

강민석 님은 나머지 질문에도 답했다. 승인한 방향은 **기존 화면 동작은 유지하고, 대사 전용 실행 모드에서만 일지와 같은 가격 · 체결 규칙을 명시적으로 적용**하는 것이다.

| 질문 | 승인 | 조건 |
|---|---|---|
| 다음 날 시가 체결 (`fill_timing="next_open"`) | 승인 | 기본값 불변 · `daily_lean_reconcile.py` 에서만 선택 · 주문일과 체결일 분리 |
| 입력 데이터를 수집 DB 로 | 대사 모드 한정 승인 | 신호는 수정종가, 수량 · 평가는 원주가 종가, 체결은 다음 거래일 원주가 시가. 누락되면 야후로 조용히 대체하지 않고 **실패 처리** |
| 진입 여유분 0.95 | 대사 실행의 별도 칸으로만 동의 | 30% 상한 불변 · 1.00 과 0.95 를 비교 · 검증 전에는 기본값 아님 |
| 보고서 3.2절 매도 비율 설명 | 수정 동의 | 원본 일지 주문 행을 확인하지 않았으면 「원인 확정」 금지, 「0.5 를 적용한 재계산에서 6→3→2→1→1주 패턴이 재현됐다」로 쓴다 |
| 원격 `domain-rag-lab` 날짜 규칙 | 서버 확인 뒤 확정 | 화면에는 신호 기준일 · 체결일 · 가격 종류 · 시간대 · 출처를 표시 |

🔑 새 동작은 **선택 모드로** 넣는다. 기본값과 기존 화면은 그대로 두어야 이미 쓰는 쪽을 흔들지 않는다. 그리고 데이터 소스가 없을 때는 조용히 대체하지 않고 실패하게 한다.

### 3. 같은 파일을 고치는 사람이 있으면 구현을 맡기고 내 몫을 좁힌다

강민석 님의 02번 답에 한 줄이 있었다. 「어제부터 그림자 일지와 lean 맞추려고 수정 중」. `scripts/daily_lean_reconcile.py` 는 마지막 커밋이 10-28 강민석 님이었고 로컬에는 `fill_timing` 이 아직 없었다. 내가 같은 파일에 구현을 넣으면 충돌한다.

그래서 구현은 강민석 님 몫으로 두고, 이동원은 **일지 쪽 기대값 · 11-04 도커 재실행 대조 · 0.95 비교 기준 숫자**를 맡는 쪽으로 답글 초안을 썼다. 파일에 손대기 전에는 fetch 로 그 파일이 바뀌었는지 먼저 본다는 규칙도 적어 두었다.

결과는 빨랐다. 강민석 님이 구현(`26b4c1b9`, PR #534)과 11월 4일 도커 재대조까지 끝냈다. 삼성전자 2026-09-01~11-02 구간에서 신호 41/41 · 보유 41/41 · 주문 방향 12/12 · 체결가 12/12(최대 0.0bp), 수량 12건 26주가 일치했다. 한계도 같이 밝혔다: **재현성 검증이지 수익률 · 위험지표 검증이 아니다.** `fill_timing=next_open` 은 KRX `ma_cross` 대사 한정이다.

🔑 같은 파일에 두 사람이 손대려 하면 **내 몫을 줄여서 겹침을 없앤다.** 구현을 맡기고 기대값 같은 검증 쪽을 가져온다.

### 4. 판 번호는 프롬프트의 기억이 아니라 파일에서 읽는다

판 올림 사전 점검을 하다가, 이전 세션 프롬프트에 적힌 숫자가 낡아 있는 것을 발견했다. S197 프롬프트는 RTM v1.78 · 테스트 계획서 v1.90 이라고 했는데, 파일을 열어 보니 **RTM v1.79 · 계획서 v1.91** 이었다. 또 새로 만들려던 시험 묶음 이름 `TC-CW` 가 기존 `test_collect_worker.py` 와 겹쳤다. 판 올림 때 시험 이름을 새로 붙이면 기존과 섞인다.

🔑 프롬프트의 판 번호는 쓰던 때의 값이다. **판 올림 날에는 파일 머리표에서 다시 읽는다.** 시험 묶음 이름은 만들기 전에 `rg` 로 겹치는지 본다.

## 막힌 것 · 남은 것

- 강민석 님이 `daily_lean_reconcile.py` 를 이미 고치는 중이라 이 파일에 손대기 전에는 반드시 fetch 로 확인해야 한다.
- 원격 `domain-rag-lab` 이 어떤 날짜 · 시간 규칙을 쓰는지는 서버를 보기 전까지 모른다.
- 화면 표기(신호 기준일 · 체결일 · 가격 출처 등)는 후속이다. 누가 맡는지는 강민석 님 답글에 없었고, 이동원 몫이라는 제안은 내 답글 초안에만 있다.
- 매도 0.5 의 원인은 확정하지 않았다.

## 배운 것

1. **이름에 든 시각을 이름으로 해석하지 않는다.** 코드를 읽는다.
2. **새 동작은 선택 모드로 넣고 기본을 지킨다.** 데이터 소스가 없을 때는 대체하지 말고 실패하게 한다.
3. **겹치는 파일은 내 몫을 줄여서 푼다.** 구현을 맡기고 검증을 가져왔다.
4. **「원인 확정」은 원본 행을 본 뒤에만 쓴다.** 재계산에서 재현되었다는 말과 다르다.
5. **판 번호는 파일 머리표에서 읽는다.** 프롬프트의 숫자는 낡는다.
