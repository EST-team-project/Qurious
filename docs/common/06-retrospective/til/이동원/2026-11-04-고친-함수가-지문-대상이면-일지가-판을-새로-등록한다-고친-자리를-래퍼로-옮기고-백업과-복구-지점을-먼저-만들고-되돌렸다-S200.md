## 개념 정리

### 1. 지문 대상 함수를 건드리면 판이 자동으로 바뀐다

그림자 일지(`paper_journal`)는 신호를 만드는 코드의 **지문**을 판의 이름표로 쓴다. 신호 판단에 쓰이는 함수 몇 개를 정해 두고, 그 내용이 바뀌면 같은 판으로 이어 붙이지 않는다. 일지의 수익률은 「같은 규칙으로 쌓은 기록」이라는 약속 위에 있기 때문이다.

PR #529 는 오래된 일봉으로 주문하지 않도록 신선도를 확인하는 변경이었다. 그런데 보강하는 곳을 `get_quant_indicators` 안으로 했다. 이 함수의 지문이 `9b646702ddac` 에서 `8e2a5e2b99e5` 로 바뀌었고, 12:30 회차가 **판 2 (version 3 · 4, 두 규칙)** 를 등록했다.

🔑 「신호를 만드는 함수」가 지문 대상인지부터 안다. 목록에 있는 함수는 **동작이 같아도 한 줄만 바뀌면 판이 바뀐다.**

### 2. 되돌릴지 이어 갈지는 근거를 모아서 정한다

두 가지 안이 있었다. A 는 판 2 를 인정하고 이어 가는 것, B 는 변경 위치를 지문 밖으로 옮기고 판 2 를 지워 판 1 로 돌리는 것이다. 사용자가 B 로 정했다. 읽어 보니 A 로 가면 **11-03 행이 영구 공백**이 되었다. 판 2 의 첫 행이 11-04 이기 때문이다. B 는 판 1 이 11-03 과 11-04 를 이어 채우는 길이다.

처음 쓴 분석 초안(01)과 실제 데이터는 달랐다. 실행 전에 세어 보니 **지울 것은 4파일(판 2 의 version 둘 + 노트 둘)** 이었다.

🔑 되돌리기 전에 **지울 범위를 실제 데이터에서 다시 센다.** 초안의 사실은 가정이다.

### 3. 지우기 전에 백업과 복구 지점을 만든다

B 는 DB 와 HF(허깅페이스) 저장소에서 판 2 를 지우는 작업이라 돌이킬 수 없다. 그래서 지우기 전에 다음 두 가지를 먼저 만들었다.

| 만든 것 | 위치 |
|---|---|
| 3개 테이블 `pg_dump` + 내보내기 복사본 | `docs/_local/journal-v2-backup-2026-11-04/` |
| HF 복구 지점 | 커밋 `ac4f91be` |

그다음 DB 에서 판 2 version 3 · 4 와 노트 3 · 4 를 **한 트랜잭션**으로 지우고, 판 1 에는 설명 노트 5 · 6 을 더했다. 노트 id 3 · 4 는 재사용하지 않았다. HF 에서는 판 2 의 4파일을 지우고 manifest 와 README 를 이전 커밋(`fc082ddf`)으로 되돌렸다(커밋 `5ecb5767`). 업로드 규칙(`plan_upload`) 위반은 0이었고 새로 생긴 파일은 노트 둘뿐이었다.

🔑 지우는 작업은 **복구 지점을 먼저 만든 뒤에** 한다. 트랜잭션 하나로 묶어 중간 상태를 남기지 않는다.

### 4. 고친 자리를 래퍼로 옮긴다 — 같은 동작을 지문 밖에서

신선도 보강의 위치를 `get_quant_indicators` 안에서 `stock.get_candles` 래퍼로 옮겼다. `get_candles` 의 원래 몸은 `_get_candles_source` 로 두고, 래퍼가 그 결과에 신선도를 붙인다. `signal_freshness.settle_for_trading` 과 `attach` 를 만들어 자동매매 두 곳에서 부른다. 그러면 지문 대상인 `get_quant_indicators` 는 원래 모양이다.

실증으로 **두 규칙 모두 전체 지문이 판 1 저장값과 같음**을 확인했다(다른 조각 0). 되돌린 뒤 `status` 지문 「같음」, `daily --dry-run` 이 판 1 의 11-03 부터 계산 예정, `pull` same 도 확인했다. 11-03 행은 직접 `daily` 를 돌려 14:29 에 판 1 두 규칙에 각 1행을 더했다(두 버전 모두 42행, 마지막 11-03). 참고 지문 「바뀜」 표시에 `stock.get_candles` 가 들어가는 것도 예상대로였다.

🔑 같은 효과를 내면서 **지문 목록 밖에 있는 자리**를 찾는다. 지문은 함수의 이름이 아니라 내용이다. 래퍼는 지문 대상 함수를 건드리지 않는다.

### 5. 설명한 범위는 검토 답과 어긋나지 않게 쓴다

오준영 님이 #529 를 검토하면서 12개 시험 파일을 외부 통신을 막은 임시 Docker 에서 돌렸다(193 passed · 1 skipped). 그리고 **적용 범위**를 정정했다. 신선도 가드는 일반 자동매매 경로에만 적용된다. MA20/60 판 2 와 「내 전략」은 별도 실행기(`strategy_v2_execution`)로 먼저 갈라져서 `rebalance_daily.readiness()` 를 쓴다.

코드를 직접 읽어 확인했다. `auto_trade.py` 의 867 · 892행 분기가 908행 이후 일반 경로의 `signal_freshness.for_trading` 보다 먼저 `return` 한다. `readiness()` 는 12:30 이전이면 기다리고, `price_max` 나 `as_of` 가 전 거래일과 다르면 `stale_data` 로 본다. 그래서 설명을 「일반 경로 = 사용자 키로 꼬리 보강, 판 2 · 내 전략 = readiness 대기」로 나눠 쓰기로 했다.

🔑 「모든 전략에 같은 보강」이라는 한 문장은 코드가 말하는 범위보다 넓다. 검토 답과 코드가 일치하는 범위로만 쓴다.

## 직접 해 본 것

- 판 2 가 생긴 경위를 지문으로 확인했다: `get_quant_indicators` 지문 `0bc5dcc^` = `9b646702ddac`, 이후 = `8e2a5e2b99e5`.
- 영향 범위 11개 파일 시험 223 passed. 1건 실패는 이전부터 있던 `test_no_yahoo_regression`(`lean_backtest.py` 20 > 19)였다.
- 임시로 시간별 수집 예약 작업(`Qurious-daily-data-update`)을 껐다 켰다(14:15 → 14:18). 14:30 회차 뒤에도 판 1 만 있고 행은 42, 지문은 같았다(판 3 없음).
- 강민석 님 #514 답글(스탑 차트 기간 선택 1개월 · 3개월 · 1년, PR #536)을 diff 로 대조했다. 단추 상수 `SC_PERIODS`, 기본 3개월, 기간 상태가 메인 차트와 별개라는 설명이 일치했다.
- 신장환 님 #530 답글이 닫혔다. #446 WebSocket→SSE 는 후속 또는 보류, #362 · #363 의 실제 시도 수는 기준 전략 110 만 DSR 보조 계산에 전달되는 상태다.

## 막힌 것 · 남은 것

- **다른 PC 에 판 2 가 있을 수 있다.** 그 PC 는 켜기 전에 정리 SQL 을 먼저 돌리고, 코드 PR 을 받은 뒤 회차를 돌려야 한다. 순서를 어기면 판 3 이 생기거나 판 2 가 다시 들어온다.
- 강민석 님과 오준영 님의 동의를 받기 전에 B 를 실행했다. 후속 댓글에 그 사실을 적었고 두 분의 답을 기다린다.
- 내일(11-05) 12:30 회차의 결과를 확인해야 한다. 판 3 이 생기지 않았는지가 기준이다.
- 신호 값이 불변인지 행 단위로 비교하는 일은 하지 않았다. 코드상 지문이 같으니 필수는 아니라고 보았다.

## 배운 것

1. **지문 대상 함수의 목록을 외운다.** 신호에 쓰이는 함수를 고칠 때는 지문이 바뀌는지부터 확인한다.
2. **같은 효과를 지문 밖에서 낸다.** 래퍼 한 겹으로 판 1 을 지켰다.
3. **되돌리기는 복구 지점을 먼저 만든다.** 지우는 범위는 실제 데이터로 다시 센다.
4. **합의 없이 실행한 일은 바로 기록하고 알린다.** 사용자 결정이었지만 팀 데이터라 후속 댓글에 적었다.
5. **설명 범위는 검토 답과 코드 둘 다와 맞춘다.**
