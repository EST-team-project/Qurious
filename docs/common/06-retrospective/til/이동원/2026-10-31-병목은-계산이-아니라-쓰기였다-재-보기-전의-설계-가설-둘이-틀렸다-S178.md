## 개념 정리 (특강 필기처럼)

### 1. 병목과 암달의 법칙

전체 시간에서 개선할 수 있는 부분의 몫이 작으면, 그 부분을 아무리 빠르게 해도 전체는 거의 빨라지지 않는다(암달의 법칙). 병렬화는 「나눌 수 있는 계산」 에만 듣는다. 우리 수집의 수정주가 단계(`adjusted`, 주식 분할 등을 반영해 과거 시세를 다시 계산하는 단계)는 10-31 12:30 회차에서 423초였고, 로그의 「단계 안 시간」 줄은 이렇게 나뉘어 있었다.

| 몫 | 초 | 전체 대비 |
|---|--:|--:|
| 쓰기(DB 에 다시 넣기) | 311.2 | 약 74% |
| 읽기 | 55.3 | 약 13% |
| 폐지 목록(화면에 개수만 찍는 조회) | 40.8 | 약 10% |
| 커밋 | 7.8 | 약 2% |
| **계산** | **7.6** | **약 1.8%** |

계산 7.6초를 22코어로 나눠 0 에 가깝게 만들어도 줄어드는 것은 최대 7.6초다(산술). 같은 단계의 다른 7회(10-20 ~ 10-27)도 쓰기 315 ~ 610초, 계산 9.6 ~ 13.3초라 하루만 그랬던 것이 아니다(조사 결과 4.1절).

🔑 병렬로 줄일 수 있는 몫(계산 1.8%)이 아니라 가장 큰 몫(쓰기 74%)을 먼저 본다.

### 2. 측정 먼저 — 벽시계 시간과 CPU 시간

「걸린 시간」(벽시계)만 알면 그 단계가 계산 때문에 느린지, 기다림 때문에 느린지 모른다. **CPU 초 ÷ 걸린 초**가 1 에 가까우면 한 코어를 꽉 쓰는 일(쪼갤 후보), 0.3 아래면 기다림(동시에 여러 요청을 보내는 쪽이 이득), 1 을 넘으면 이미 여러 코어를 쓴다. 이 비율을 재려고 `scripts/proc_stats.py` 를 만들었다. 10-31 수정주가 단계는 364 ÷ 423 = 86% 였다.

CPU 가 86% 찼는데도 파이썬 계산은 7.6초뿐이다. 나머지 CPU 는 SQLite 엔진 안에서 쓰였다고 읽힌다(조사 결과의 가설이고 증명하지 않았다). 「CPU 가 바쁘다」 와 「내 계산이 병목이다」 는 다른 말이다.

🔑 설계서의 가설(H2: 한 코어로 돈다 / H4: 매번 전부 다시 계산한다)은 숫자로 확인하기 전까지 가설이다.

### 3. 바뀐 행만 쓰기(diff write)와 멱등성, 그리고 WAL

수정주가 · 총수익 표는 종목마다(수정주가는 3,318개) `DELETE` 한 뒤 `executemany INSERT` 로 전부 다시 넣었다. 하루에 늘어나는 것은 종목마다 한 행인데 약 450만 행을 매일 지우고 다시 쓴 셈이다. SQLite 는 변경을 본 DB 에 바로 쓰지 않고 먼저 별도 파일(WAL, 쓰기 앞 기록)에 적으므로 전량 교체는 이 기록도 부풀린다(회차 로그에서 0 → 약 440MB).

그래서 새 행 · 달라진 행 · 없어진 행만 쓰도록 했다. 같은 입력으로 몇 번을 돌려도 결과가 같은 성질을 **멱등성**이라 하는데, 이 방식에서는 같은 입력으로 다시 돌리면 쓰는 행이 0 이어야 한다.

```python
gone = [k for k in old if k not in new]                          # 없어진 행
add  = [t for k, t in new.items() if k not in old]               # 새 행
chg  = [t for k, t in new.items() if k in old and old[k] != t]   # 값이 달라진 행
# 세 묶음만 DELETE / INSERT / UPDATE — 같은 행은 건드리지 않는다
```

값 비교는 **정확히 같을 때만** 같은 행이다(`==`). 같은 코드가 같은 입력으로 만든 값은 비트까지 같으므로 안 바뀐 행은 건드리지 않고, 계산 규칙이 바뀌면 모든 행이 다르다고 나와 알아서 고쳐진다([`diff_write.py`](../../../../../collector/diff_write.py) 머리말의 약속).

🔑 같은 결과를 매번 다시 쓰는 일을 비교 한 번으로 바꾸면, 쓰기 시간이 입력의 변화량에 비례하게 된다.

## 직접 해 본 것

### 1. 먼저 쟀다 (S178)

- 이 PC 의 회차 이력 23회차(한 단계만 다시 돌린 회차 제외)에서 회차 시간은 중앙 3,282초(55분), 최소 1,278, 최대 5,932였다(커밋 `8d4c837` 메시지). 설계서의 41.6분은 빠른 날이었다. 조사 결과의 첫 표는 전 단계가 돈 18회차만 골라 중앙 3,306초로, 표본이 달라도 같은 쪽이다. 단계 시간이 날마다 크게 달라 한 회차로 어림하면 틀린다는 점은 설계서도 측정 보정에 적어 두었다.
- 이 PC 는 10코어 · 16스레드다. 설계서의 22코어가 학원 PC 기준인지는 확인 못 했다.
- 이 숫자로 P4 의 방향을 「병렬」 에서 「쓰기 줄이기」 로 바꿨다. 수정주가 재구성이 하나의 `BEGIN IMMEDIATE` 트랜잭션이라 그동안 다른 단계는 이 DB 에 쓰지 못하므로 병렬 쓰기도 막혀 있다.

### 2. 바뀐 행만 쓰기를 구현하고 같은 입력으로 대조했다 (S178)

- [`collector/diff_write.py`](../../../../../collector/diff_write.py) 에 `sync_rows` 를 두고 수정주가 · 총수익이 쓴다. `--full` 로 예전 방식도 남겼다. 시험은 TC-DW-01 ~ 08, TC-CPU-01 ~ 06, TC-DU-BG-01 ~ 05, TC-PLP-02c 이고 [`test_diff_write.py`](../../../../../tests/test_diff_write.py) 가 첫 계산 · 하루 늘어남 · 분할 · 옛 시세 정정 · 시세 행 사라짐에서 새 방식과 예전 방식의 표 내용이 같은지 맞댄다.
- 실제 수집 DB 로 **입력이 바뀌지 않은 상태에서** 같은 입력으로 다시 돌린 값이다(10-31 14:53 ~ 14:56, 집 PC, 멱등 실측).

| 대상 | 예전 | 새 방식 | 비고 |
|---|--:|--:|---|
| 수정주가 단계 | 423초 | 59초 | 읽기 39.4 · 계산 6.3 · 쓰기 12.5(비교 포함) |
| 총수익 | 408초 | 98초 | |
| 폐지 목록 | 41초 | 0.6초 | 목록을 만들지 않고 개수만 세는 질의(`delisted_count`) |

- 수정주가 4,535,325행 · 조정 이벤트 2,768행 · 총수익 4,535,325행이 모두 「같아서 안 건드림」(새 0 · 고침 0 · 지움 0)으로 나왔다. 회차 하나에서 약 674초(11분)를 줄이는 계산이다(산술: (423 - 59) + (408 - 98)).
- **한계**: 위 대조는 입력이 안 바뀐 날뿐이다. 분할 · 정정 · 하루 늘어남은 실제 DB 가 아니라 합성 시험(TC-DW-04, 06)이 예전 방식과 맞댄다.
- 같은 PR 에서 `search` 단계를 다른 단계와 겹쳐 돌리게 했다(P2). 평소 중앙 18초(최대 786초)라 이득은 긴 날에만 있고, 리허설은 `search` + `calendar` 7.2초(순차 약 12초)였다.

### 3. 두 번째 가설을 재 보니 틀렸다 (S179, PR #458)

- 설계 단계의 가설은 「benchmark 가 시장마다 3표 조인을 여러 번 훑는다」 였다. 코드를 읽어 보니 [`_AGG_SQL`](../../../../../collector/benchmark.py)(518줄 근처)이 시장당 한 번(창 함수 `LAG` 두 겹 + `GROUP BY`)이었다.
- 읽기 전용(`mode=ro`)으로 수집 DB(6.44GB)를 재 보았다(집 PC, 기록은 로컬 변경 노트). `_aggregate` 는 KOSPI 33.9 · KOSDAQ 66.7 · KONEX 3.5초로 합 약 104초, 조인만 떼면 6.9 · 4.2 · 1.0초였다. 시간은 조인이 아니라 창 함수의 정렬(`USE TEMP B-TREE FOR ORDER BY`)에 있다.
- 증분 계산으로 얻을 몫은 회차 55분의 3 ~ 4% 라서 착수하지 않았다. 같은 날 회차의 benchmark 198초 가운데 남는 약 94초는 원인을 확인 못 했다(다른 단계와의 경합 추정).
- export 의 내용 지문을 재 보니 표 전체 합 206초로 export 중앙 286 ~ 432초의 50 ~ 70% 였다. 닫힌 연도의 지문 계산을 건너뛰는 설계 D1(약 85초 절감)은 설계만 하고 구현하지 않았다.

## 배운 것

- 병렬화에 손대기 전에 단계 안 시간을 쪼개 재면, 가설 둘이 한 번에 걸러진다.
- CPU 사용률이 높다는 것과 내 계산이 병목이라는 것은 다르다. 같은 CPU 도 DB 엔진 안에서 쓰일 수 있다.
- 효과를 말하는 숫자에는 조건을 붙인다. 423 → 59초는 「입력이 안 바뀐 날의 멱등 실측」 이지 모든 날의 평균이 아니다.
- 재는 도구도 틀릴 수 있다(CPU 0.06초). 도구를 믿기 전에 시험으로 고정한다.
