## 개념 정리

### 1. 번호가 두 군데에서 오면 둘 다 맞아도 섞여 보인다

통합 덱에서 이동원 슬라이드의 오른쪽 위에는 덱 전체 번호(`17 / 45`)가 뜨고, 슬라이드 풋터에는 이동원 자료 안의 번호(`10 / 29`)가 남아 있었다. 넘기기 스크립트가 각 장의 **첫 번째** `.pg` 하나만 채우기 때문에 가져온 슬라이드의 풋터는 손대지 못했다. 두 번호 모두 자기 기준에서는 맞았다.

고친 것은 조립기가 가져올 때 번호를 한 체계로 바꾸는 것이다.

- 풋터 `3 / 29` → 덱 전체 `N / 45`
- 눈썹의 `10 · ` 제거
- 본문과 노트의 `12 ~ 14장` 같은 참조를 통합 덱 번호로 변환(범위와 목록 모두)

담당자 자기 파일은 자기 번호를 그대로 둔다. 장을 옮길 때 번호를 손으로 고치지 않고 **조립기를 다시 돌려 불일치가 0인지** 본다.

### 2. 단계 표시(① → ④)가 거꾸로 가면 흐름이 끊긴다

11-09 오전 「각자 한 것을 구조도로 상세히」 피드백으로 「한 일」(3장)과 「구조」(4장)를 앞에 끼웠다. 단계 표시가 ① → ③ → ① → ② → ③ 으로 되돌아가서, 문제 정의와 시장 조사가 「갑자기 없어진」 것처럼 보였다. 내용을 지운 게 아니라 **놓인 자리** 때문이었다.

새 순서는 ① 문제와 시장(2~5장) → ② 빈 곳(6~7장) → ③ 우리가 만든 것(8~17장) → ④ 한계(18~19장)다. ③의 첫 장에는 「앞에서 본 배울 점과 빈 곳에 이렇게 답했다」는 다리 문장을 넣었다. 융합은 위치를 맞추는 것과 단계 사이를 잇는 문장으로 했다.

### 3. 순서는 내용이 아니라 「누가 발표하나」로 정한다

이어진 지시는 문제 정의와 시장 조사는 맨 앞에 두고 이동원이 자기 파트까지 이어 발표하며, 한계는 맨 끝에 두고 강민석 님이 발표한다는 것이다. 이유는 자료 수집과 초안은 이동원이 하지만 발표 분배는 팀이 임의로 정한 상태이기 때문이다. 자료를 만드는 사람과 발표하는 사람이 다를 때, 파일 구조(사람별 폴더)와 발표 순서(말하는 사람 순)는 따로 정해야 한다.

조립기에 「슬라이드의 마지막 N장을 맨 끝으로 보내고 발표자 표시를 바꾼다」는 설정(`TAIL_SLIDES`)을 넣었다. 슬라이드 원본은 이동원 폴더에 그대로 있고 덱에서만 자리가 바뀐다.

### 4. 줄이는 일은 사용자와 조율하고, 빠진 근거는 버리지 않는다

이동원 발표량이 많다는 지적에 질문 네 개로 조율했다(수집 · 일지 · 겹치는 장 · 도입부). 29장이 19장으로 줄었다. 빠진 장의 말문장과 근거 글머리는 대본 **부록 A**에 옛 번호로 남겼다. 예상 질문이 들어오면 거기서 꺼낸다.

사용자가 낡은 일봉도 2차에서 발표했다고 기억했는데, 가드를 만든 것은 11-04(3차)다. 제외 결정은 그대로 따르되, 한 일 표의 한 줄은 남겼다. 기억과 기록이 다를 때는 결정을 바꾸지 않고 사실만 알려 둔다.

### 5. 팀원 PR을 받을 때는 겹치는 파일부터 본다

`git fetch` 뒤 변경 파일과 내 미커밋 파일의 교집합을 먼저 계산했다. 겹친 것은 조립기가 만든 생성물 하나였다. 그래도 pull 은 두 번 막혔다.

- 줄바꿈 차이: 저장소가 `autocrlf=true` 라 LF 로 되돌린 파일이 「수정됨」으로 남았다. CRLF 로 맞추자 풀렸다.
- 로컬에만 있던 같은 이름의 `목록.json`: 치운 뒤 pull 하고, 두 목록을 `stem` 기준으로 합쳤다.

(이 두 가지는 TIL 규칙 점검에서 나온 것이 아니라 이번 pull 에서 직접 막힌 것이다.)

## 배운 것

- 숫자가 섞여 보이면 틀린 숫자를 찾기 전에 **번호를 매기는 곳이 몇 개인지**부터 센다.
