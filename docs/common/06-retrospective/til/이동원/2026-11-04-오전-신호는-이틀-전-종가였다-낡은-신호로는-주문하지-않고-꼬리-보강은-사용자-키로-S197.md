> 주문 직전 가격만 증권사 현재가로 새로 읽으니, **가격은 새것이고 판단은 낡은 모양**이었다.

## 개념 정리

### 1. 일봉은 「늦게 도착하는 확정값」이다

공공데이터포털 주식시세정보(우리 일봉 정본)는 기준일 **다음 영업일 낮 13시 이후**에 올라온다. 그래서 수집 회차가 12:30 이다.
11-04(수) 오전에 수집 DB 의 마지막 봉은 11-02(월) 종가이고, 11-03(화) 종가는 오늘 12:30 회차 뒤에야 들어온다. 이 구조에서 오전 신호는 **한 거래일이 아니라 두 거래일 전** 종가까지만 본다.

🔑 일봉 전략의 신호는 「확정된 봉」으로만 낸다. 그런데 **우리 확정 봉은 하루 늦게 도착**한다 — 도착 시각이 곧 신호의 신선도다.

### 2. 신선도 가드 — 주문 전에 데이터가 낡았는지 먼저 본다

실거래 시스템의 관례는 주문 전에 시장 데이터의 마지막 갱신 시각과 직전 가격 괴리를 확인해, 낡았거나 이상하면 주문을 막는 것이다(조사: FIA 2024-07 §3.1 시장 데이터 합리성 검사 — 원문 추출로 확인 · 다른 규제 문서는 검색 요약 수준).
우리는 두 값을 맞댄다.

| 값 | 뜻 | 어디서 |
|---|---|---|
| `expected` | 지금 있어야 할 마지막 확정 일봉 날짜 — 거래일 **15:40 이후면 오늘**, 그 전이면 직전 거래일 | 거래일 달력(`market_calendar`) |
| `as_of` | 수집 DB 가 실제로 가진 마지막 봉 날짜 | `collector_db.read_daily_candles` |

`as_of < expected` 면 **stale** 이고, 그 종목의 신호 주문은 내지 않고 사이클 기록에 「데이터 대기」 를 남긴다. 손절·익절 같은 위험 매도는 실시간 시세로 판단하므로 막지 않는다.

🔑 가드의 질문은 「값이 맞나」가 아니라 **「이 값이 지금 써도 되는 나이인가」** 다.

### 3. 꼬리 보강 — 빠진 며칠만 메모리에서 붙인다

낡았을 때 증권사 일봉에서 **확정된 날만** 가져와 수집 DB 일봉 뒤에 붙인다. 두 가지 안전장치를 걸었다.

- **저장하지 않는다.** 증권사 시세는 약관상 개인 업무에 한해 쓰고 제3자에게 주지 않으므로, 수집 DB 와 HF 에는 쓰지 않고 사이클 안 메모리에서만 쓴다.
- **겹치는 날 종가를 맞춰 본다.** 수집 DB 는 수정주가이고 증권사 원주가가 섞이면 이동평균이 튄다. 마지막 겹치는 날 종가가 0.5% 안에서 같을 때만 붙인다.

🔑 보강은 **저장하지 않고, 기준이 같은지 확인한 뒤에만** 한다.

### 4. 오늘 봉을 붙이지 않는 이유(룩어헤드)

장중에 받은 오늘 봉은 아직 진행 중이라 마감 때 값이 바뀐다. 이것을 신호에 쓰면 그날 종가에 알 수 없던 값으로 판단하는 셈(repainting)이다. 그래서 `expected` 이하의 날만 붙이고 오늘 장중 봉은 버린다.

🔑 신호는 **확정 봉에서만** 낸다 — 보강도 예외가 아니다.

## 직접 해 본 것

- 호출 경로를 따라갔다: `get_quant_indicators` → `get_candles` → 수집 DB 먼저(`as_of` = 마지막 봉 날짜) → 신호 계산 → 주문 직전 `current_quote`. 신호가와 주문가의 괴리(`price_delta_pct`)는 **기록만 하고 막지는 않았다.**
- `signal_freshness.py` 를 새로 만들었다 — `judge`(판정) · `settle`(꼬리 보강) · `for_trading`(자동매매 안에서만 켜는 문맥) · `user_kis_fetcher`(사용자 자기 KIS 키로 받기). 화면과 다른 분석은 이 문맥 밖이라 그대로다.
- 시험 `tests/test_signal_freshness.py` 30건을 썼다(오늘 15:40 경계 · 주말 · 임시 휴장 · 꼬리 붙이기 · 기준 불일치 거부 · 실패 시 쉬는 시간 · 사용자별 캐시 · 낡은 신호는 주문 0건 · 신선하면 주문). 관련 자동매매 시험과 함께 돌려 통과를 확인했다.
- **실측(11:00, 읽기 전용 조회):** 수집 DB 의 마지막 봉이 정말 11-02 였다(11-03 종가 없음). KIS 모의 키의 수정주가 일봉은 겹치는 3일(10-29 · 10-30 · 11-02) 종가가 **4종목 모두 수집 DB 와 한 원도 다르지 않았다**(차이 0.0). KIS 응답에는 **오늘 진행 중 봉이 이미 들어 있었다** — 확정일만 붙이는 필터가 필요한 이유를 눈으로 확인했다. 실제 `settle` 을 실제 클라이언트로 돌리니 두 종목 모두 `fresh` · `tail: kis+1`(11-03 봉 추가)이 됐다.
- 판단가와 주문 직전 가격이 3% 이상 벌어지면 근거 줄에 **경고만** 남기게 했다(`SIGNAL_PRICE_GAP_WARN_PCT`, 0 이면 끔 · 막지 않음). 3% 는 업계 표준 값이 아니라 처음 잡은 값이다 — 조사에서 표준 수치는 확인하지 못했다.

## 막힌 것 → 원인 → 해결

1. **꼬리 보강이 처음부터 못 도는 설정이었다.** 처음에는 강사님 게이트웨이(`STOCK_COIN_TRADE_BASE_URL`)로 증권사 일봉을 받게 했는데, 조사 에이전트가 짚어 개발 앱에서 확인하니 이 주소가 **비어 있었다.** 그대로면 꼬리 보강은 항상 「불가」 이고 오전 사이클은 전부 「데이터 대기」 가 된다. → 사용자 **자기 KIS 키**의 일봉 조회(수정주가, `get_daily_ohlcv`)로 받도록 바꿨다. 키가 있으면 우선 쓰고, 없으면 게이트웨이, 둘 다 없으면 보류한다.
2. **모듈 전역 캐시가 시험 사이에 새어 나갔다.** 「증권사 오류 → 낡은 채」 시험이 앞 시험이 채운 캐시 때문에 `basis_mismatch` 로 나왔다. → 시험 준비 단계에서 캐시를 비우게 했다(`reset_cache`). 캐시가 있는 코드는 **시험이 서로의 상태를 지워 주어야** 한다.
3. **다른 사용자의 시세를 쓰지 않게 캐시를 쪼갰다.** 한 사용자의 키로 받은 시세를 다음 사용자의 사이클이 재사용하면 제3자 제공이 된다. → 캐시 키에 사용자를 넣고(`범위, 종목, 날짜`), 시험으로 둘이 서로 다른 호출을 하는지 확인했다.
4. **모의 서버가 빠른 호출에 500 을 냈다.** 실제 클라이언트로 돌리자 둘째 종목에서 KIS 모의 서버가 HTTP 500 을 돌려줬다(유량 초과 — 수집기 주석에도 같은 증상이 적혀 있다). 호출 간격 0.6초에서 실패, 1.2초로 4종목을 부르면 모두 성공했다 → 기본 간격을 1.1초로 올렸다. 확정일 캐시 덕에 사용자당 하루 한 번만 부르므로 종목 31곳이어도 약 35초다.
5. **기존 시험이 호출 모양을 고정하고 있었다.** 소스 문자열로 호출 형태를 단정한 시험이 호출 인자를 바꾸자 실패했다 — 같은 시험에 새 모양을 반영했다. 통합 시험은 `settings` 이름을 잘못 쓴 줄(`NameError`)도 잡았다.

**버린 선택지**

- 장 마감 직후 수집을 돌린다 — 일봉 정본이 다음 영업일에야 올라와 받을 것이 없고, 증권사 시세를 수집 DB 에 쌓는 것은 약관 문제다.
- 야후로 보강한다 — 팀 결정으로 야후 참조를 늘리지 않기로 봉인돼 있고(시험이 줄 수를 고정), 사용자 말씀대로 완화 가능성은 있으나 약관 조항별 근거를 확인하지 못해 구현하지 않았다.
- 게이트웨이만 쓴다 — 공유 서버 경유라 「개인 업무」 주장이 약하고, 설정이 비어 있었다.

## 배운 것

- **데이터의 「나이」는 값과 같이 다닌다.** `as_of` 와 `expected` 를 함께 두면 낡음을 코드가 판단하고 화면이 설명할 수 있다.
- **보강은 저장하지 않는 것이 약관과 일치하는 가장 단순한 방법**이다. 다만 어느 서버를 거치는지에 따라 약관 해석이 달라지므로, 본인 키 경로를 우선으로 했다.
- **실제 값으로 한 번은 돌려 본다.** 시험이 다 통과해도 모의 서버의 유량 한도(500)는 실제 호출에서만 드러났다.
- **막는 장치는 켜진 것을 확인해야 한다.** 가드를 넣고도 보강 경로가 꺼져 있으면 오전 사이클은 전부 보류된다 — 이 사실은 설정을 실제로 읽어 본 뒤에야 알았다.

## 남은 것

- **오늘 봉이 몇 시에 확정되는지는 아직 모른다.** 11:00 에는 어제까지의 확정 일봉만 검증했다. 15:42 · 17:02 · 20:32 에 같은 종목의 종가를 읽어 값이 변하는지(2026-09-14 신설된 KRX 애프터마켓 반영 여부) 보아야 `SETTLE_TIME` 15:40 이 맞는지 알 수 있다 — 세 번 읽도록 예약해 두었다(결과가 나오면 이 줄을 고친다).
- 모의 장부만 쓰고 KIS 키가 없는 사용자는 오전 사이클이 보류된다(예전에는 낡은 신호로 주문했다).
- 과거 주문 중 낡은 신호로 낸 비율은 아직 재지 않았다.
- 약관 판단(공유 게이트웨이 경로, 야후 완화)은 **사람이 정할 일**이라 코드로 풀지 않았다.
