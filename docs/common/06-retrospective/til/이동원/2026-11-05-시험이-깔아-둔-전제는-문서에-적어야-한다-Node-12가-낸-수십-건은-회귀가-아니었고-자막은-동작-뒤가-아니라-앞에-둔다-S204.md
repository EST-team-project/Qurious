## 개념 정리

### 1. 「제품 회귀」와 「환경 문제」를 먼저 가른다

실패가 많으면 코드가 망가졌다고 읽기 쉽다. 먼저 물을 것은 **이 시험을 돌린 환경이 시험이 기대하는 환경인가**다. #567 의 환경은 Ubuntu(WSL) · Python 3.10.12 · Node v12.22.9였고, 이 프로젝트는 윈도우에서 Node 24 · Python 3.13 로 개발했다.

내 PC 에서 직접 확인한 것은 이렇다.

| 확인 | 결과 |
|---|---|
| #567 이 든 Node 시험 둘 | 둘 다 통과 (Node 24) |
| 같은 이슈가 든 `test_schedule_until` · `test_weekly_rehearsal` | 통과 (윈도우라 `os.name` 이 원래 `nt`) |
| Node 버전을 적은 곳 | `package.json` · `.nvmrc` · `.github/workflows` 모두 없음. README 는 Python 3.12 만 적었다 |
| Node 를 부르는 시험 | 53개 파일. 그중 34개가 Node 14 이상 문법(`?.` · `??`) |
| `public/js` 에서 `export` 를 쓰는 파일 | 91개, `package.json` 없음 |

Node 12 에서 수십 건이 깨지는 것이 오히려 자연스러운 숫자였다. 그렇다고 「나머지 실패도 전부 Node 때문」이라고 단정하지는 않았다. 강민석 님도 이슈에 그렇게 적어 두었다. **환경을 맞춘 뒤에도 남는 실패만 제품 회귀 후보**로 올리자고 답했다.

🔑 실패 건수는 회귀의 증거가 아니다. **환경을 고정한 뒤에도 남는 실패**가 회귀 후보다.

### 2. 시험이 깔아 둔 전제는 문서와 경고로 남긴다

Node 하한은 어디에도 적혀 있지 않았다. 「공식 지원 버전이 있었는데 바뀐 것」이 아니라 **처음부터 문서가 없었다.** 이슈에서 지적된 `test_baseline_notice` 의 최상위 `await`(Node 14.8 이상)는 내가 10-30 에 쓴 시험이었다. 시험이 틀린 것이 아니라, 전제가 적혀 있지 않았다.

PR #571 에서는 제품 코드를 건드리지 않고 시험 쪽만 고쳤다.

| 바꾼 곳 | 내용 |
|---|---|
| `tests/conftest.py` | 시험 머리와 끝 요약에 Node 버전을 찍고, 22 미만이면 「제품 회귀가 아니다」 경고를 낸다 |
| `tests/test_node_requirement.py` | 경고 문구를 고르는 함수 시험 11건 (TC-NODE-01~04) |
| `readme.md` | 「시험 환경」 한 줄 — Node 22 이상 권장 |

시험 머리에 찍은 줄은 `pytest.ini` 의 `-q` 때문에 보통 숨겨진다. 그래서 **끝 요약에도 같은 줄을 찍었다.** 처음 만든 경고가 아무에게도 보이지 않으면 만들지 않은 것과 같다.

🔑 필요한 환경을 코드 밖에 두지 않는다. 문서에 적고, 어기면 **실패 메시지 옆에서** 알려 준다.

### 3. 전역 객체를 바꾸는 시험은 시험 하나만 깨는 것이 아니다

`INTERNALERROR: cannot instantiate 'WindowsPath'` 는 별개의 원인이었다. 윈도우 작업 스케줄러 등록을 흉내 내는 시험이 `monkeypatch.setattr(du.os, "name", "nt")` 를 쓰고 있었다. `du.os` 는 모듈 안의 별칭이 아니라 **전역 `os` 모듈 그 자체**여서, 프로세스 전체의 `os.name` 이 `nt` 로 바뀐다.

리눅스(Python 3.10)에서는 `Path(...)` 가 `os.name` 이 `nt` 이면 `WindowsPath` 를 만들려다 실패한다. 시험이 그 구간에서 실패하면 **pytest 가 실패 보고서를 만들면서 같은 `Path` 호출로 다시 죽는다.** 윈도우에서는 처음부터 `nt` 라서 한 번도 드러나지 않았다.

해결은 단순했다. 이 시험은 윈도우 작업 스케줄러(`schtasks`)를 흉내 내는 것이라 윈도우 전용이 맞다. 4곳을 `skipif(sys.platform != "win32")` 로 윈도우에서만 돌게 했다.

🔑 `monkeypatch` 로 **모듈 하나가 아니라 모듈이 가리키는 전역**을 바꾸고 있지는 않은지 본다. 이름이 모듈 안에 있어도 바뀌는 것은 바깥이다.

### 4. 자막은 동작이 끝난 뒤가 아니라 시작과 같이 떠야 한다

영상 장면 파일에 「동작 → say(자막)」 순서로 써 두었다. 클릭이나 강조 표시는 1~3초 걸리고, 자막은 동작이 끝난 뒤에야 뜬다. 말은 이미 지나갔는데 자막이 늦게 나오는 것이다. `tools/demo/subtitle_sync.py` 로 점검했더니 **장면 10개 모두에서 자막이 설명하는 동작 뒤에 나왔고, 일부는 읽기 전에 다음 자막으로 바뀌었다.**

원인은 둘이었다.

1. **순서.** 자막(`say`)은 기다리지 않으므로 「say → 동작」 으로 써야 같이 뜬다.
2. **노출 시간.** 자막은 다음 `say` 까지 떠 있다. 발표용 속도에서는 동작 사이 멈춤이 줄어 글을 읽기도 전에 바뀐다.

도구는 `check`(순서 · 노출 시간 · 읽는 데 모자란 시간), `fix`(동작 뒤의 say 를 앞으로), `pad`(모자란 만큼 멈춤 추가)로 나눴다. 읽는 시간 기준은 발표용 한 글자에 1/7초, 사용법 영상은 1/5.5초로 두었다.

녹화를 두 번 돌렸고, 점검은 **실제 녹화한 기록만 신뢰**했다. 10편 모두 「동작 뒤 자막 0 · 읽을 시간 모자람 0」 이 나왔다.

🔑 사용자가 느낀 어긋남을 **도구로 재서 규약으로 만든다.** 「자막 먼저, 동작 바로 뒤」 가 장면 규약이 되었고, 규약은 도구가 점검한다.

## 막힌 것 · 남은 것

- **리눅스에서 `INTERNALERROR` 가 사라졌는지는 모른다.** 강민석 님이 Node 22 로 올린 뒤 전체 시험을 다시 돌린 결과를 기다린다. 그 전에는 이슈를 닫지 않기로 했다.
- Node 하한이 정확히 22 인지도 모른다. Node 24 에서만 돌려 봤다.
- `__pycache__` PermissionError 는 WSL 이 `/mnt/c` 파일을 쓰는 권한 문제로 **추정**할 뿐 확인하지 못했다. 우회는 `PYTHONDONTWRITEBYTECODE=1` 이다.
- 점검 도구가 보는 것은 순서와 읽을 시간뿐이다. **말과 화면의 의미가 맞는지**는 팀원 피드백으로만 확인된다.
- mp4 · 한 파일 발표 덱은 PR 에 넣지 않았다. 11-11 동결 뒤 한 번에 올린다.

## 배운 것

1. **실패 수는 원인이 아니다.** 환경을 맞춘 뒤에도 남는 실패가 진짜 후보다. 환경을 맞추는 일을 먼저 돕는 것이 빠르다.
2. **시험도 제품이다.** 시험이 요구하는 환경(Node · OS)을 코드 밖에 두면 팀원이 먼저 막힌다. 시험이 어긋났을 때 이름이 지목되는 것도 이쪽이다.
3. **보이지 않는 경고는 없는 경고다.** `-q` 가 머리를 숨긴다는 것을 확인하고 끝 요약에 한 번 더 찍었다.
4. **「재현하지 못했다」를 같이 적는다.** 코드에서 메커니즘을 확인한 것과 리눅스에서 본 것은 다르다. 답글에 이 둘을 나눠 적었다.
5. **느낌을 도구로 재면 규약이 된다.** 「자막이 밀리는 느낌」 은 순서와 읽을 시간이라는 숫자로 바뀌었고, 장면 규약과 점검 도구가 되었다.
