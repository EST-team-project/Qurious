## 한 일

- 번역 검색이 늘 0건이던 결함(DF-149)을 고쳤다. 원인은 셋이 겹친 것이었다 — `requirements.txt` 가 하한만 적어 빌드한 날의 최신 qdrant-client(1.19.1)가 들어왔고, 그 판에는 1.16 에서 없어진 `search` 가 없었고, 넓은 `except Exception` 이 그 오류를 삼켜 빈 결과로 바꿨다. Qdrant 를 부르는 길을 문지기 한 곳(`app/lib/vector_db.py`)으로 모으고 `query_points` 로 바꿨다. 「모음 없음 · 장애 · 0건」 을 404 · 503 · 200 으로 가르고, 번역 API 는 AI허브 이용정책에 맞춰 기본 꺼짐 · 켜도 관리자만으로 막았다.
- 고친 뒤 **고치기 전 코드로** 새 시험을 돌려, 11건 중 10건이 「DF-149 재발」 로 실패하는 것을 봤다. 실제 AI허브 자료는 시험에 넣을 수 없어 합성 금융 문장과 Tatoeba 한-영 문장(CC BY 2.0 FR · 문장마다 저작자)으로 고정 자료를 만들었다.
- 의존성 판을 잠갔다(`requirements.lock` · 이미지 판@다이제스트). 잠금은 **지금 이미지 안의 실제 판에서 시작해 판을 하나도 바꾸지 않았다**(132/132). 고침 판이 안 들어오는 대가는 주 1회 갱신 보고서 · 카나리아 · 서버와 클라이언트의 판 짝 점검으로 갚는다.

## 배운 것

- **넓은 except 는 결함을 결과로 바꾼다.** 「빈 결과」 는 오류보다 찾기 어렵다 — 모음이 없어서인지, 서버가 죽어서인지, 정말 0건인지 가를 수 없다. 「닿지 못함」 으로 볼 예외를 라이브러리의 예외 갈래(`ApiException`)로 좁히고, 나머지는 그대로 올라가게 했다.
- **하한만 적은 요구 파일은 「빌드한 날」 이 판을 정한다.** 같은 날 새로 풀면 132개 중 62개가 바뀌었다. 잠금은 재현을 주는 대신 보안 고침을 막는다 — 그래서 「잠그고, 주 1회 시험으로 받는」 두 겹이 한 쌍이다.
- **잠금을 처음 만들 때는 판을 바꾸지 않는다.** 잠금과 업그레이드를 한 PR 에 섞으면 문제가 생겼을 때 어느 쪽 탓인지 모른다. 이미지 안의 판 목록을 씨앗으로 풀고, 다시 만든 이미지에서 132/132 같음을 확인했다.
- **카나리아는 신호이지 문이 아니다.** 지켜볼 다섯만 최신으로 올려 같은 시험을 돌리면 다음 판에서 무엇이 깨질지 미리 보인다. 종료 코드는 늘 0 으로 두어 머지를 막지 않게 했다.
- **경고를 오류로 바꾸면 첫날 하나가 잡힌다.** 우리 코드가 내는 폐기 경고만 오류로 바꾸자 설정 클래스의 옛 꼴(`class Config` — Pydantic V2 에서 폐기)이 바로 잡혔다(DF-151). 남의 라이브러리 경고는 그대로 두었다.
