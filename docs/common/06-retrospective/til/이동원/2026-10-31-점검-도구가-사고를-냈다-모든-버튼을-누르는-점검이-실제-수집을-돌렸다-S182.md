## 개념 정리 (특강 필기처럼)

### 1. 점검의 부수 효과와 최소 권한

점검(스모크 점검, 클릭 점검)은 보기만 하는 일로 여겨지지만, 점검하는 주체가 가진 권한만큼 **쓰기도 실제로 일어난다.** 최소 권한 원칙은 일에 필요한 권한만 주는 것이다. 이번 점검은 점검 계정이 관리자였고, 관리자에게는 데이터 · 시스템 화면의 쓰기 버튼(자료 수집 「받기」 등)이 모두 살아 있었다. 점검 스크립트에는 차단 목록이 있었지만 DELETE 와 reset/init 주소만 막았다.

차단 목록(deny-list)은 **내가 떠올린 위험만** 막는다. 「받기」 는 삭제가 아니라서 목록에 없었다.

🔑 읽기만 해야 하는 일에는 읽기 권한만 주거나, 막을 것을 열거하기 전에 허용할 것을 먼저 열거한다.

### 2. 정적 분석으로 미정의 이름 잡기 (ruff F821)

파이썬은 함수 본문의 이름을 **호출될 때** 찾는다. `import` 한 줄이 빠져도 모듈은 정상으로 뜨고, 그 함수를 부르는 순간 `NameError` 가 난다. 시험이 그 라우트를 한 번도 부르지 않으면 통과 목록에는 아무 흔적이 없다. ruff 의 F821 은 실행하지 않고 「정의되지 않은 이름」 을 찾는다.

우리에게 나타난 곳은 두 곳이다. `app/routes/paper.py` 551줄 부근은 `Order` 를 import 하지 않았고, `app/services/performance_service.py` 413줄은 `.limit(limit)` 인데 이 함수에 `limit` 인자가 없었다(바로 위 함수에서 복사된 줄로 보인다). 둘 다 강민석 님 몫 모의투자 커밋(10-30, `efcccd4`)에서 들어왔다.

🔑 「시험이 통과한다」 는 「시험이 부르는 경로가 통과한다」 와 같은 말이다. 안 부르는 경로는 정적 검사가 본다.

### 3. 사고 뒤에는 영향 범위를 원격 상태로 잰다

로컬 로그만 보면 「무엇이 돌았나」 만 알 수 있다. **원격이 실제로 바뀌었는지**는 원격 쪽 표지(HF, 곧 Hugging Face 데이터 저장소 main 의 머리 해시)를 전후로 비교해야 안다. 그리고 비교로도 모르는 것은 모른다고 적어야 한다. 이번에는 머리 해시가 바뀐 것은 확인했지만 내용이 같은 데이터인지는 확인하지 못했다.

🔑 사고 보고에는 확인된 것 · 확인 못 한 것을 갈라 적는다.

### 4. 에이전트가 낸 판정은 근거를 열어 본 뒤에 쓴다

열린 이슈를 닫아도 되는지 판정하는 일은 읽기 전용 에이전트에게 맡겼다. 판정표(70줄)의 「확실」 7건은 메인 세션이 근거 파일(머지 PR, 코드 줄, 팀원 원문)을 직접 열어 맞대고 나서 보고했다.

🔑 맡긴 일의 결과는 가장 확실하다고 한 부분부터 다시 연다.

## 직접 해 본 것

### 1. 콘솔 500 두 개를 재현하고 고쳤다 (S181 발견 → S182 고침)

- 사용자가 모의계좌 현황 화면의 콘솔 오류 스크린샷을 보냈다. 개발 앱 컨테이너 안에서 라우트 함수를 실제 개발 DB 로 읽기 전용으로 불러 같은 `NameError` 를 재현했다([이슈 본문](../../../00-management/github-archive/2026-10-31/이슈-안내-모의투자-500-NameError-Order-limit-강민석/00-본문.md)의 트레이스). 이 두 라우트를 부르는 시험은 찾지 못했다.
- 고침은 import 1줄 추가와 `.limit(limit)` 제거다. 사용자 결정(「동작을 안 바꾸는 크래시 수정만 팀원 백엔드 허용」)의 범위 안이다. `.limit` 은 `efcccd4` 이전 판에 없던 줄이고 기간 선택 차트라 상한이 필요 없다.
- 새 시험 TC-PRN 4건(함수 3개, 하나는 값 둘로 돌림)과 저장소 전체 `ruff check app scripts --select F821` 통과로 막았다.

### 2. 열린 이슈 닫기 점검 → 정리 (S177 조사 → S182)

- 의뢰문의 「열린 이슈 83건」 은 목록의 **마지막 번호**였고, 닫힌 글이 빠져 실제는 70줄이었다. 에이전트 판정은 확실 7 · 근거 약함 7 · 열어 둠 51 · 판단 불가 5(합 70), 목록 밖 14건은 따로 둔다([결과](../../../../phase-3/01-analysis/research/배경조사/2026-10-31-이슈-닫기-점검/결과.md)).
- S182 에서 닫기 24 · 정리 12 · 닫기 불가 3 으로 나눠 댓글 초안 36건(닫기 + 정리)을 만들었고 사용자가 올려 닫았다. 정리 댓글 12건이 모두 올라갔는지는 확인 필요로 남았다.

### 3. 클릭 점검 사고 (S182)

- 에이전트 다섯이 화면 74곳을 나눠 눌렀다(금융 · 학습 17화면은 사고로 중단돼 부분만). 점검 계정으로 자료 수집 화면의 「받기」 가 눌려, 10-31 19:06 ~ 19:22 사이 이 PC 에서 수집 단계 20여 개(공시 · 재무 · 뉴스 · GDELT · ECOS · 일정 · 일봉 · 벤치마크 · 품질 · 일지 · 내보내기 · 대조 · 올리기)가 실제로 돌았다([PR #463 본문](../../../00-management/github-archive/2026-10-31/PR-허브서랍-이슈정리-클릭점검-표칸정리/00-본문.md)의 「점검 사고」).
- 올리기(`--upload`)까지 돌아, HF 원격 main 의 머리가 `21ede959` → `cb847dad`(19:21:52)로 바뀌었다. 파일은 147개 그대로였고 시세 기준일도 20261029 로 같았다. 아직 시작 전이던 3건(`sector_laws` · `journal_upload` · `ohlcv_upload`)은 큐에서 취소했다.
- 조치: 점검 스크립트의 차단 목록에 수집 요청 주소를 더했고, 점검 계정을 **일반 계정 + 관리자 계정 둘**로 나눴다(보이는 화면이 달라서).
- 다음 날(S183)에는 점검 스크립트가 못 누르던 곳을 다시 보았다. 화면을 누를 때마다 새로 여는 `--reload` 를 더하니 market-calendar 26 → 0, ml-compare 7 → 0, robo-portfolio 9 → 0, settings 10 → 1 로 줄었다. 못 누름의 대부분이 점검 스크립트의 한계였고, 일반 · 관리자 둘로 끝낸 뒤 남은 화면 결함은 교재 링크 404 넷뿐이었다.

### 4. 숫자 맞대기

전체 시험(`test.ps1 -Split`, **실행** 건수) 3,585건 · 697초가 표 5 합 3,364 + 대장 밖 파일 171 + 컨테이너 50 과 맞는지 따져 보다 TC-SFD 가 표 5 에만 있고 시험-요구 대장에 없는 것을 찾았다. 결과는 통과 3,556 · 실패 11(알려진 5 + cp949 6) · 건너뜀 18 이다. 같은 방식의 합계 맞추기는 [S176 TIL](2026-10-31-판-올림은-합계가-맞아떨어질-때까지-센다-표-더하기-대장-밖-더하기-컨테이너-S176.md)에 있다. 산출물목록의 판 칸이 UI 명세서 · 화면 IA · 화면 대장에서 한두 판 뒤처져 있던 것은 사용자 지적이 맞았다.

## 배운 것

- 점검 계정의 권한이 곧 점검의 부작용 범위다. 이 계정이 무엇을 쓸 수 있는지 먼저 센다.
