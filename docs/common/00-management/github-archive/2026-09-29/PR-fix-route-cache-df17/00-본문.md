## Why

- 수집 DB 다리(#33 · DF-08)는 서비스 함수 `stock.get_candles` 안에서 캐시를 거치지 않습니다. 그런데 화면이 실제로 부르는 **라우트** — `GET /api/stocks/candles` · `GET /api/stocks/quant/indicators` — 가 그보다 먼저 `data_cache`(PostgreSQL)를 6시간 보고, 다리가 준 결과를 그 캐시에 다시 써 넣었습니다.
- 그래서 12:30 일일 갱신 뒤에도 **최대 6시간 동안 옛 기준일**이 `from_cache: true` 와 함께 나갔습니다. 지표 화면(`indicator-strategy` · `quant-backtest` · `quant-dashboard`)의 「현재가」 도 갱신 전 종가였습니다.
- 매시간 도는 캐시 데우기(`sync_scheduler`)가 31종목의 지표를 같은 캐시 키에 채우고 있어, 라우트만 고치면 아무도 읽지 않는 쓰기가 남습니다.
- API 명세서 v0.1(#51) 3절 F2 에서 찾은 결함입니다. 다리의 옛 시험(TC-CD)은 서비스 함수만 불러서 라우트 층을 재지 못했습니다.

- **판정에 「DB 파일이 있는가」 까지 넣었습니다.** 수집 DB 가 없는 팀원 PC 에서는 다리가 늘 옛 경로(야후)로 넘어가므로, 그때는 라우트 캐시가 외부 호출을 줄이는 원래 역할을 그대로 해야 합니다.

- 버린 것 — ① **응답으로 가르기**(캐시에서 꺼낸 값이 `source: collector` 면 버리기): 요청마다 PostgreSQL 을 한 번 더 부르고, 캐시를 먼저 보는 구조가 그대로 남습니다. ② **라우트 캐시 통째로 없애기**: 지수 · 해외 응답의 `from_cache` 표시와 지표 캐시까지 사라져 이 결함보다 범위가 넓어집니다. ③ **캐시 시간 줄이기**: 옛 기준일이 나가는 시간이 줄 뿐 없어지지 않습니다.
