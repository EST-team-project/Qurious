## 1. 시세 신선도 정책 유지 및 화면 안내 수정

기존 5분 정책을 30초로 변경하는 것이 아니라, 적용 목적을 분리합니다.

| 구분 | 기준 | 적용 |
|---|---:|---|
| 업비트 시세 캐시 갱신 | 5초 | 기존 유지 |
| 일반 시세 반환 및 가격 증빙 | 300초(5분) | 기존 #371 정책 유지 |
| 실제 주문 가격 유효기간 | 30초 | 별도 주문 검증 유지 |

- `upbit_tickers()`의 300초 일반 시세 검증은 변경하지 않습니다.
- `upbit_trade_price()`의 30초 주문 신선도 검증도 유지합니다.
- 거래소 체결 시각(`as_of`)과 로컬 캐시 수신 후 경과 시간(`cache_age_sec`)을 모두 검증합니다.
- 두 기준 중 하나라도 30초를 초과하거나 시각 정보가 유효하지 않으면 매수·매도·미리보기를 거절합니다.
- `COIN_SOURCE_NOTE`와 `COIN_ORDER_NOTE`를 수정해 일반 평가 시세의 5분 기준과 실제 주문의 30초 기준을 명확히 구분합니다.

## 2. 기존 거래비용 모듈 설계 재사용

기존 `app/services/trading_cost.py`의 설계 원칙을 따릅니다.

다만 해당 모듈의 `order_costs()`는 KRX 전용 위탁수수료·유관기관 비용·증권거래세를 계산하므로 코인 주문에 그대로 사용하지 않습니다.

별도 모듈을 만들되 기존 `OrderCost`와 동일한 데이터 설계 원칙을 사용합니다.

신규 파일:
`app/services/crypto_trading_cost.py`

비용은 다음 세 가지로 구분합니다.

- 확정 비용: 업비트 원화마켓 기본 거래 수수료
- 추정 비용: 호가 데이터가 없는 상황에서 적용하는 슬리피지
- 미반영 비용: 출금 수수료 등 별도 근거가 없거나 이번 모의매매 범위에 포함하지 않는 비용

### 적용할 기본 요율

| 항목 | 적용 기준 | 성격 |
|---|---:|---|
| 매수 수수료 | 0.05% | 업비트 KRW 마켓 기본 요율 |
| 매도 수수료 | 0.05% | 업비트 KRW 마켓 기본 요율 |
| 매수 슬리피지 | 10 bps | 추정 |
| 매도 슬리피지 | 10 bps | 추정 |

수수료는 업비트의 일반 KRW 마켓 기준을 기본값으로 사용합니다. 이벤트 및 계정별 별도 요율은 공개 시세 API로 확인할 수 없으므로 별도 사용자 요율을 임의로 적용하지 않습니다.

슬리피지는 기존 `trading_cost.py`의 `DEFAULT_SLIPPAGE_BPS = 10.0`을 기준으로 사용하되, 실제 호가에서 측정한 값이 아닌 초기 추정값임을 명시합니다.

요율은 상수 한 곳에서 관리하고 향후 변경할 수 있도록 구성합니다.

참고:
- 업비트 거래 수수료: https://support.upbit.com/hc/ko/articles/900006143046
- 업비트 KRW 마켓 기본 수수료 참고: https://docs.upbit.com/kr/docs/upbit-strategy-toolkit-reference
- Qurious 기존 거래비용 모듈: `app/services/trading_cost.py`

## 3. 체결가격과 거래비용 계산

핵심 원칙은 슬리피지를 체결가격에 먼저 반영하고, 그 체결금액을 기준으로 수수료를 계산하는 것입니다.

슬리피지를 별도의 현금 비용으로 다시 차감하지 않습니다.

### 매수

- 기준 시세에 +10 bps 슬리피지를 적용합니다.
- 슬리피지가 적용된 가격으로 수량과 실제 체결금액을 계산합니다.
- 체결금액에 0.05% 수수료를 추가합니다.
- 현금 차감액 = 체결금액 + 수수료
- 보유 원금 = 체결금액 + 매수 수수료

기존 `buy_krw` 입력값은 수수료 별도인 주문 체결금액 기준으로 유지합니다. 따라서 미리보기에서 수수료와 최종 현금 차감액을 별도로 보여주고, 최종 차감액이 계좌 잔액을 초과하면 주문을 거절합니다.

### 매도

- 기준 시세에 -10 bps 슬리피지를 적용합니다.
- 슬리피지가 적용된 체결가격으로 매도금액을 계산합니다.
- 체결금액에 0.05% 수수료를 적용합니다.
- 순정산액 = 체결금액 - 매도 수수료
- 실제 현금 증가는 순정산액으로 처리합니다.

### 부분 매도

- 기존 보유 원금에서 매도 수량 비율만큼 원금을 배분합니다.
- 배분된 원금에는 기존 매수 수수료가 포함되어 있어야 합니다.
- 실현손익 = 매도 순정산액 - 매도 수량에 배분된 매입 원금
- 잔여 보유 원금과 평균 매입단가도 함께 갱신합니다.

## 4. DB 체결 기록 확장

대상 모델: `CryptoOrder`

기존 주문 기록을 유지하면서 다음 정보를 추가합니다.

| 필드 | 내용 |
|---|---|
| `reference_price` | 슬리피지 적용 전 기준 시세 |
| `price` | 슬리피지가 적용된 모의 체결가격 |
| `amount` | 실제 체결금액(Gross Amount) |
| `commission` | 수수료 |
| `fee_rate` | 적용 수수료율 |
| `slippage_bps` | 적용 슬리피지 |
| `slippage_amount` | 추정 슬리피지 금액(참고용) |
| `net_amount` | 실제 현금 정산금액 |
| `cost_basis` | 비용 산출 근거 |
| `allocated_cost_basis` | 매도 시 배분된 매입 원금 |
| `realized_pnl` | 매도 시 실현손익 |

슬리피지 금액은 체결가격에 이미 반영되어 있으므로 추가 차감하지 않고, 비용 분석과 기록을 위한 정보로만 보관합니다.

신규 거래는 `cost_basis=estimated`로 기록합니다.

기존 거래는 과거 체결가격과 금액을 변경하거나 소급하여 수수료를 부과하지 않습니다. 기존 거래에는 `cost_basis=none`을 적용하고, 신규 필드의 기본값과 기존 정산금액을 보존합니다.

## 6. 검증 계획

다음 항목을 테스트합니다.

1. 매수·매도 각각 10 bps 슬리피지가 체결가격에 올바르게 적용되는지
2. 매수·매도 수수료가 각각 0.05%로 정확히 계산되는지
3. 슬리피지가 별도 비용으로 이중 차감되지 않는지
4. 매수 현금 차감액에 수수료가 포함되는지
5. 수수료를 포함한 최종 차감액이 잔액을 초과하면 주문이 거절되는지
6. 매도 시 수수료를 차감한 순정산액만 현금에 반영되는지
7. 부분 매도 시 기존 매입 수수료를 포함한 원금이 비율대로 배분되는지
8. 실현손익과 잔여 보유 원금이 일치하는지
9. 미리보기 계산과 실제 매수·매도 계산이 동일한지
10. 기존 거래 내역이 소급 변경되지 않는지
11. 기존 30초 주문 신선도 및 300초 일반 시세 검증이 모두 유지되는지
12. 기존 주식·직접매매·자동매매 거래비용 테스트에 회귀가 없는지

화면에서도 기준 시세, 예상 체결가격, 예상 수수료, 슬리피지 가정, 최종 정산금액을 구분해 사용자가 실제 비용 구조를 확인할 수 있도록 합니다.

모든 신규 거래비용 계산은 모의 장부에만 적용하며 업비트로 실제 주문을 전송하지 않습니다.
