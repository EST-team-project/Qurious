## 0. 진행 방식

강사님 안내에 따라 모의 인터뷰처럼 진행합니다. 질의자는 기획 의도 · 기술 선택 · 구현 방식과 결과를 날카롭게 묻고, 답을 들은 뒤 근거를 묻는 후속 질문을 잇습니다. 답하는 사람은 자기가 한 일과 결과를 중심으로, 실제 코드 · 화면 · 시연 결과를 근거로 답합니다. 순서는 질문 → 답변 → 후속 질문입니다.

이 문서도 그 순서로 썼습니다. 답 아래의 「왜 이렇게 나왔나」 는 숫자를 어떻게 쟀는지, 왜 그런 결과가 나왔는지, 어디까지가 한계인지를 한 줄로 적은 것입니다. 후속 질문에서 숫자의 출처를 물으면 「근거」 칸의 파일과 화면을 엽니다.

모르는 것을 물으면 세 마디로 답합니다. 「지금은 모릅니다. 이렇게 확인하겠습니다. 언제까지 알려 드리겠습니다.」 이 문서에서 아직 확인하지 못한 것은 「확인 필요」 로 표시했습니다.

## 1. 강사님 예시 질문 넷 · 날카로운 질문 둘

가장 나올 만한 여섯 문항이다. 1-1 ~ 1-4 는 강사님이 예로 든 질문이고, 1-5 · 1-6 은 발표를 본 질의자가 물을 만한 날카로운 질문이다. 자세한 근거는 2 ~ 6절의 해당 문항으로 이어진다.

### 1-1. 왜 이 기술을 선택했나요?


- **답** 제가 직접 고른 것 두 가지를 말씀드리겠습니다. 시세 수집기는 일부러 도커 밖에 두고, 파일 하나짜리 SQLite 에 씁니다. 앱 스택은 서비스 다섯 개가 떠야 시작되는데, 수집을 거기에 묶으면 스택이 안 뜨는 날의 시세를 통째로 놓치기 때문입니다. 근거 답은 낱말 검색과 의미 검색을 섞었습니다. 법령은 조 번호처럼 정확한 낱말이 중요하고, 사용자는 일상 말로 묻습니다. 같은 50문항으로 재 보니 정답 조가 상위 5개 안에 드는 비율이 낱말만 0.78, 의미만 0.86, 둘을 섞으면 0.94였습니다.
- **왜 이렇게 나왔나** 낱말 검색은 「코스피」 처럼 법령에 없는 일상 말에서 놓쳤고(일상 말을 법령 말로 넓히지 않으면 0.70), 의미 검색도 혼자서는 0.86 에 그쳤습니다. 둘이 놓치는 질문이 달라서 섞었을 때 올라갔습니다. 두 점수는 눈금이 달라 더하지 않고 순위만 합칩니다. 다만 50문항은 작은 표본이고 저희가 만든 평가셋입니다.
- **근거**
  - 수집기를 따로 둔 까닭: `collector/README.md` 2절 「왜 앱과 따로 도는가」 · `docker-compose.yml`(서비스 10개 · 수집기는 들어 있지 않음)
  - 검색 구조: `app/services/kb_search.py` `lexical`(낱말 · FTS5 bm25) · `dense`(bge-m3 벡터 · Qdrant) · `search` → `app/services/kb_text.py` `rrf`(순위 합치기 · k=60)
  - 숫자: `docs/시험/근거답-품질보고서.md` 표 6(2026-10-04 측정 · 근거검색 평가셋 v1 · 50문항)
  - 화면: AI 투자 상담의 근거 답(출처 카드)
  - 발표 자료: 「기술 선택 표」. FastAPI · DB 두 개 · Celery 같은 나머지 기술은 2절에 있다. 다른 파트의 기술 선택은 그 주담당이 답한다
- **후속 질문**
  1. 「SQLite 에 5GB 넘게 넣어도 되나요? 읽고 쓰는 게 겹치면 잠기지 않나요?」
     → 쓰는 쪽은 수집기 하나뿐이고 앱은 읽기 전용으로 붙습니다. 원 DB 는 약 5.4GB 입니다(10-19). 그런데 이 구조 때문에 실제로 멈춘 적이 있습니다. 이 PC 쪽 마지막 연결이 닫히면 보조 파일이 지워지는데, 읽기 전용으로 붙은 앱은 그 파일을 만들 수 없어서 근거 찾기와 데이터 API 가 멈췄습니다. 두 번 다 고쳤고 시험으로 고정했습니다(결함대장 DF-74 · DF-81 · 닫힘).
  2. 「더 큰 모델이면 낫지 않나요? 왜 4B 로컬 모델인가요?」
     → 같은 10문항에서 8B 모델 둘은 정답 6 으로 지금 기본(qwen3:4b-instruct · 정답 7)보다 적었고, 그중 llama3.1 8B 는 근거 밖 질문에 답을 지어냈습니다. 생성도 30 ~ 43초로 더 느렸습니다(10-03 · 품질 보고서 표 9). 크기보다 거름이 먼저였습니다. 로컬이라 비용이 들지 않고 질문이 밖으로 나가지 않는다는 점도 있습니다. 유료 상용 모델은 비용을 정하기 전이라 같은 평가셋으로 재지 않아서 비교 숫자가 없습니다.
  3. 「이 PC 에서 로컬 모델이 버티나요?」
     → 약점이 있습니다. 내장 GPU 가 문맥 약 4,365토큰에서 끊긴 적이 있고, 문맥을 줄인 뒤에도 오래 돌린 끝에 한 번 더 끊겼습니다(열린 결함 DF-65). 근거는 지금 4,500자(약 3,500토큰)로 묶여 있고, 답 모델이 실패하면 서버가 답 대신 근거 발췌를 돌려줍니다(품질 보고서 5절).

### 1-2. 본인이 직접 구현한 부분은 어디인가요?


- **답** 2차에서 제 몫은 목표 기능 ①의 세부 넷, 용어사전 · 자료 수집 · 근거 답 · 정기 배치입니다. 코드로는 세 곳을 열어 보여 드릴 수 있습니다. 첫째, 매일 12:30 에 도는 수집 러너입니다. 시세부터 백업까지 21단계를 한 목록에 두고, 단계마다 종료코드와 실패 까닭을 남깁니다. 둘째, 근거 답의 서버 거름입니다. 답에 붙은 출처 번호가 실제 근거에 있는지, 「규정은 없다」 고 단정하지 않는지, 질문을 되풀이만 하지 않는지를 서버가 다시 봅니다. 셋째, 기준일에 맞는 법령 판을 고르는 함수입니다. 그 밖에 시세 · 배당 · 공시 · 재무 수집기, 백업과 복구 리허설, 화면에서 PC 로 수집을 맡기는 통로도 제가 만들었습니다. 화면은 강사님 기초 코드가 출발점이었고, 이것들은 새로 세웠습니다.
- **왜 이렇게 나왔나** 팀원 기능이 같은 수집 DB 와 같은 기준일을 읽어야 결과를 서로 맞대 볼 수 있어서, 데이터 관문과 매일 러너를 팀장 몫으로 먼저 세웠습니다. 화면 수로는 점검표 72화면 중 53화면이 제 주담당인데, 그중 22화면은 주인이 없던 화면을 10-07 에 맡은 것입니다. 「53화면을 혼자 새로 만들었다」 는 뜻은 아닙니다.

### 1-3. 기능이 실패하면 어떻게 대응하나요?


- **답** 경우마다 대응이 다릅니다. 매일 12:30 회차의 한 단계가 실패하면 종료코드와 까닭이 기록되고 데이터 관제 화면에 보입니다. 그 단계는 화면의 「다시 받기」 로 다시 돌립니다. PC 가 꺼져 회차를 놓치면 켜진 뒤 따라잡기 회차가 돌고, 회차 도중에 끊기면 그 회차 전체를 다시 돌립니다. 자료가 늦게 오면 화면에 기준일을 밝히고, 리밸런싱 점검은 자료 준비 판정이 끝난 뒤에만 돕니다. 답할 근거가 없으면 답 대신 찾은 조문 발췌를 보이고, DB 가 망가지면 백업으로 되살립니다. 되살리기는 매주 실제로 해 보고 있습니다.
- **왜 이렇게 나왔나** PC 한 대가 서버 역할을 하니 「안 돈 날」 을 없앨 수는 없다고 보고, 놓친 것을 알고 다시 받을 수 있게 하는 데 힘을 썼습니다. 회차 기록 파일에서 직접 세 보면 정기 회차는 19번 중 18번 성공했고(09-28 ~ 10-19), 실패한 하루(10-10)는 DART 점검 때문이었으며 시세는 멀쩡했습니다. 끊긴 회차를 한 단계만 다시 돌리지 않는 까닭은, 그러면 앞 회차 기록의 그 단계 줄이 오늘 결과로 덮이기 때문입니다. 10-17 처럼 절전으로 프로세스째 끊긴 회차는 기록이 거의 남지 않는다는 점도 열린 결함으로 올려 두었습니다.

## 2. 기술 선택

### 2-1. 왜 FastAPI 인가요?

- **답** 솔직히 말씀드리면 여러 프레임워크를 견줘서 고른 것은 아닙니다. 강사님 기초 코드가 FastAPI 였고 그 위에서 시작했습니다. 그래도 계속 쓴 까닭은 둘입니다. 수집 · 분석 · 머신러닝 코드가 모두 파이썬이라 API 까지 한 언어로 이을 수 있고, 앱이 스스로 명세(`/openapi.json`)를 내놓습니다. 저희는 소스에서 라우트를 뽑아 API 명세서를 만들고, 그 표를 앱 명세와 맞댑니다. 10-19 에 라우트 266개 가운데 일부러 뺀 하나를 빼고 265개가 모두 일치했습니다.
- **왜 이렇게 나왔나** 명세서를 손으로 옮기면 코드와 어긋나서, 스캐너가 소스를 읽어 표를 만들고 앱 명세를 정답으로 삼아 대조하게 했습니다.
- **근거** `app/main.py`(첫 등록 커밋 09-15) · `docs/인터페이스/API명세서.md` v0.34 머리(정답 대조 265/265) · `scripts/api_scan.py`(앱을 import 하지 않는 정적 분석 · 시험 TC-AP 15건)
- **후속 질문**
  1. 「API 가 266개면 너무 많지 않나요?」 → 강사님 기초 코드를 두 번 받은 것과 저희 기능이 합쳐진 수입니다. 화면이 실제로 부르는 API 는 명세서에서 따로 셉니다.
  2. 「다른 프레임워크로 바꿀 생각은요?」 → 바꿀 까닭이 생기지 않았습니다. 3차도 같은 앱 위에서 합니다.

### 2-2. DB 가 왜 PostgreSQL 과 SQLite 두 개인가요?

- **답** 쓰는 쪽과 쓰는 방식이 달라서 나눴습니다. 앱 DB 인 PostgreSQL 에는 사용자 · 주문 · 대화 · 용어사전처럼 여러 요청이 동시에 쓰는 표 45개가 있습니다. 수집 DB 인 SQLite 에는 시세 · 배당 · 공시 · 재무처럼 수집기 하나만 쓰고 앱은 읽기만 하는 표 21개가 있습니다. 수집 DB 가 파일 하나라서 도커 없이도 수집이 돌고, 매일 파케이로 내보내 백업하기도 쉽습니다.
- **왜 이렇게 나왔나** 앱 DB 는 강사님 기초 코드의 구성이고, 수집 DB 는 「스택이 안 떠도 수집은 돌아야 한다」 는 조건에서 나왔습니다. 대가도 치렀습니다. 읽기 전용으로 붙은 앱이 SQLite 보조 파일을 만들지 못해 멈춘 결함이 두 번 있었습니다.
- **근거** `docs/데이터/ERD.md` v1.9(수집 21표 · 앱 45표 · 10-13 다시 셈) · `collector/README.md` 2절 · 결함대장 DF-74 · DF-81(닫힘)
- **후속 질문**
  1. 「수집 DB 에 외래키가 없던데, 무결성은 누가 지키나요?」 → 대량 적재에서 외래키는 적재 순서를 강제합니다. 배당 공시가 시세보다 먼저 오면 거부합니다. 그래서 DB 밖에서 봅니다. 매일 백업 대조(파일 지문 · 행 수), 주 1회 값까지 보는 깊은 대조, 수정주가로 지수를 다시 만들어 공식 지수와 맞대는 검사입니다(ERD 448줄).
  2. 「앱 DB 는 백업하나요?」 → 하지 않습니다. ERD 에 「백업 절차 없음」 으로 적어 두었습니다. 실제 사용자를 받지 않는 로컬 환경이지만, 계정 정보가 들어 있어 공개 서비스로 간다면 먼저 할 일입니다.

### 2-3. 수집기는 왜 도커 밖에 두었나요?

- **답** 수집은 API 키와 디스크만 있으면 되는 일인데, 앱은 PostgreSQL · Redis · Qdrant · Neo4j · Ollama 가 다 떠야 시작합니다. 둘을 묶으면 스택이 안 뜨는 날의 시세를 놓치고, 놓친 시세는 결국 아무도 메꾸지 않습니다. 그래서 수집기는 표준 라이브러리와 `requests` 만 쓰고, 윈도 작업 스케줄러가 매일 12:30 에 돌립니다. 화면에서 수집을 누르면 앱은 요청을 적기만 하고, PC 쪽 작업자가 매 분 그 요청을 가져가 러너를 돌립니다.
- **왜 이렇게 나왔나** 처음에는 Celery 예약에도 저녁 수집이 셋 있었습니다. 그런데 앱 컨테이너에는 수집기 패키지가 없어서 실행될 수가 없었고, 예약기가 둘이면 같은 수집 DB 를 서로 다른 잠금으로 쓰게 됩니다. 그래서 10-15 에 예약을 작업 스케줄러 한 곳으로 모았습니다.

### 2-4. Celery 는 무엇에 쓰나요?

### 4-1. 왜 RAG 인가요?

- **답** 강사님 보충 설명이 「근거와 출처는 실제 업종의 외부 기준이나 법률이고, 2026년 기준으로 판단한다」 였습니다. 그러면 모델이 기억으로 답하면 안 됩니다. 예를 들어 증권신고서를 내야 하는 금액은 시행령이 2026-07-28 에 고쳐져 30억원인데, 흔히 알려진 숫자는 10억원입니다. 그래서 기준일에 맞는 법령 판에서 조문을 찾고, 찾은 조문만 보고 답을 쓰고, 서버가 검사한 뒤 출처 번호와 함께 보여 주는 순서로 만들었습니다. 근거 문서는 법령 10개와 감독규정 4개, 조 단위 청크 4,067개입니다.
- **왜 이렇게 나왔나** 법은 계속 바뀌어서 「어느 판으로 답했나」 가 답의 일부입니다. 판 고르기 함수는 시행일이 기준일 이하인 판 가운데 가장 늦은 판을 고르고, 그 뒤 공포된 개정이 그 판에 담겼는지 조마다 대조합니다. 지금 근거 문서는 2026-10-02 판입니다.
- **근거** 계획서 표 5 강사님 보충 설명(①-3) · 품질 보고서 82줄(증권신고서 금액 예) · `app/services/kb_answer.py` `ask` · `app/services/kb_text.py` `select_version` · `missing_changes` · ERD 83줄(근거 문서 DB) · `data/collector/state/data_guide_stats.json`(근거 문서 판 2026-10-02)

## 6. 실시간 시세 · 한계 · 확장

### 6-1. 「현재가」 가 실제와 달랐다던데요?

- **답** 맞습니다. 10-19 에 투자 인디케이터의 기본 인디케이터 전략 화면에서 삼성전자 「현재가」 가 210,000원으로 보였는데, 실제 시세는 217,000원이었습니다. 약 3.3% 차이입니다. 그 칸은 수집 DB 의 마지막 종가를 보이고 있었습니다. 수집 DB 는 공공데이터포털이 다음 영업일 낮에 주는 값이라 월요일 오전에는 목요일 종가가 가장 새 값입니다. 서버 응답에는 기준일과 출처가 이미 들어 있었는데, 화면이 그것을 버리고 「현재가」 라고만 썼습니다.
- **왜 이렇게 나왔나** 판단 · 학습 · 백테스트를 같은 자료로 다시 돌릴 수 있게 공공데이터 일봉을 정본으로 잡았고, 그 값을 「현재가」 이름으로 보인 곳이 남아 있었습니다. 같은 꼴이 화면 넷과 자동매매 체결가에 있었습니다. 210,000 이 뜬 화면은 앱 로그에 요청 줄이 없어서 코드로 좁힌 추정입니다.
- **근거** `docs/조사/실시간시세-지연표기-조사.md` v1.0 1절(화면별 「현재가」 출처 표 · 2026-10-19) · `app/services/stock.py` `get_quant_indicators`(`current_price` = 마지막 봉 종가) · 결함대장 DF-15

### 6-2. 어떻게 고치나요?

- **답** 기능을 둘로 나눴습니다. 같은 자료로 다시 돌려 같은 답이 나와야 하는 백테스트 · 모델 비교 · 리밸런싱 정산 · 근거 답은 저장 자료를 씁니다. 지금 값이 틀리면 돈이나 신뢰를 잃는 「현재가」 표시 · 모의 주문 체결가 · AI 상담의 「지금 주가」 는 실시간이 필요합니다. 둘에 걸친 기능은 「판단은 저장 자료, 실행 직전 확인과 표시는 실시간」 으로 나눕니다. 실시간 값을 못 받으면 「실시간」 이라고 쓰지 않고 「10월 16일 종가」 처럼 날짜를 밝힙니다.

- **근거** 조사서 7절(기능별 두 갈래 · 한 줄 원칙) · `app/services/rebalance_prices.py` 머리 주석(외부 현재가 대체를 쓰지 않음)
- **후속 질문**
  1. 「2차에서는 어디까지 고쳤나요?」 → 값마다 출처와 기준 시각을 붙이는 서버 함수 하나(`app/services/quote_now.py`)를 만들었습니다. 내 증권사 키가 있으면 증권사 조회 값과 시각, 없으면 「지연 시세(약 20분)」 와 체결 시각, 그것도 없으면 「10월 16일 종가」 를 보입니다. 「현재가」 화면 넷과 모의 주문 체결 직전 확인을 이 함수로 바꿨고, AI 상담은 기준 시각이 없는 주가 숫자를 말하지 않고 「현재가」 칸을 보라고 안내하게 했습니다. 손절 · 익절 발동도 같은 확인을 거칩니다.
  2. 「자동매매는요?」 → 자동매매 체결가는 엔진 쪽 일이라 2차에는 표기만 하고, 주문 직전 확인은 엔진 담당(오준영 님)과 3차에 합니다.

### 6-3. 실시간 시세를 모든 사용자에게 보여 주면 되지 않나요?

- **답** 이용 조건상 안 됩니다. 증권사 약관은 시세를 개인의 업무에만 쓰고 제3자에게 제공하지 말라고 합니다. 서버 키 하나로 받은 시세를 모든 사용자 화면에 보이면 제3자 제공이 됩니다. 거래소 시세를 맡은 코스콤 정책도 여러 사용자에게 보여 주는 서비스는 정보 이용 계약 대상으로 봅니다. 그래서 사용자가 자기 키로 자기 화면에서 보는 데까지만 하고, 실시간 시세는 저장하지도 백업에 올리지도 않습니다.
- **왜 이렇게 나왔나** 실제로 「실시간」 이라고 쓰는 서비스는 모두 거래소나 코스콤과 계약이 있는 곳이고, 계약이 없는 곳은 「20분 지연」 처럼 밝힙니다. 저희가 남길 수 있는 것은 「언제 · 어디서 받은 어떤 값으로 판단했나」 기록 한 줄뿐입니다.
- **근거** 조사서 3절(코스콤 정보이용정책 원문 · 한국투자증권 고객 이용약관 제5조③ · 야후 약관 · 2026-10-19 조회) · 3.4절 판정 표 · 2절(실제 서비스 표기)
- **후속 질문**
  1. 「키가 없는 사용자는요?」 → 대부분이 그렇습니다. 그분들께는 지연 시세(약 20분)와 체결 시각, 또는 「10월 16일 종가」 처럼 날짜를 밝힌 값만 보입니다. 이용 조건 안에서 할 수 있는 최선입니다.
  2. 「야후 지연 시세는 괜찮나요?」 → 야후 약관도 재배포 · 자동 수집 · 상업 이용을 막습니다. 학습용 비상업 시연의 회색 지대라서, 「실시간」 이라고 쓰지 않고 출처와 지연을 밝히는 데까지만 씁니다.

### 6-4. 3차에는 실시간을 어떻게 넣나요?

- **답** 사용자마다 자기 증권사 웹소켓 세션을 열어 체결가를 받고, 서버는 종목별 최신 값 하나만 Redis 에 짧게 둡니다. 값이 바뀌면 알림을 보내고 화면은 SSE 로 갱신합니다. 처음 화면은 REST 로 그 값을 읽습니다. 신호는 마감된 봉으로만 계산하고, 주문 직전에만 실시간 값을 확인하며, 받은 지 오래된 값이면 주문을 막습니다.
- **왜 이렇게 나왔나** 증권사 웹소켓은 앱키 하나에 1세션, 합산 41건까지라서 서버 하나가 모두에게 나눠 주는 구조가 아니라 사용자마다 자기 세션이어야 합니다. Redis 알림은 놓치면 사라지므로 최신 값은 키에 두고, 알림은 갱신 신호로만 씁니다.
- **근거** 조사서 5절(공통 구조 그림) · 6.2절(3차 확장 표) · 4절(한도 수치 · 공지를 옮긴 2차 자료 여럿이 일치하는 「대체로」 확실도)
- **후속 질문**
  1. 「몇 초 지난 값이면 막나요?」 → 그 기준은 3차에 정할 값으로 남겨 두었습니다.
  2. 「대체거래소(NXT) 값은요?」 → 「현재가」 가 어느 시장 값인지도 갈립니다. 증권사 현재가 조회가 어느 시장까지 덮는지는 원문으로 확인하지 못했습니다(확인 필요).

### 7-1. 역할은 어떻게 나눴나요?

- **답** 강사님 일정표의 네 역할 대신 기능별 주담당으로 나눴고, 10-01 에 확정했습니다. 2차 목표 기능 가운데 ① 데이터 · 지식의 세부 1 ~ 4 는 제가, ①-5 설명(XAI)과 ② 패턴 인식은 신장환 님, ③ 자산배분 · 리밸런싱은 오준영 님, ④ 성과 해석 · 모의 투자 의사결정은 강민석 님이 맡았습니다. 주담당은 그 기능의 설계부터 코드까지 맡고, 부담당은 질문을 먼저 받아 확인합니다.
- **왜 이렇게 나왔나** 일정표는 칸마다 네 역할의 산출물을 요구하는데, 한 기능을 네 사람이 쪼개 맡으면 책임이 흐려집니다. 그래서 칸의 주제가 한 기능이면 그 주담당이 네 역할의 산출물을 함께 지게 했습니다.

- **왜 이렇게 나왔나** 리뷰 방식(「읽었음」 한 줄로 할지, 승인을 필수로 할지)을 팀이 정하지 못한 채 진행됐습니다. 3차 전에 정해야 할 일입니다.
