# 자동매매 계정 분리 수정·검증 (2026-10-16)

새 계정에 다른 사용자의 자동매매 기록이 표시되고, 한 사용자의 중지가 다른 사용자의 즉시 실행을 취소하던 두 결함을 수정했다. 기준은 main `0ce7ee7`이다.

## 변경

- `get_status()`는 `quant:cycle_log:{uid}`의 사용자별 저장 기록만 읽는다. 기록 없음·만료·삭제·캐시 조회 실패 때 공용 메모리 기록으로 대체하던 경로를 제거했다. 기록이 없으면 빈 로그·빈 위험 상태를 반환한다.
- 즉시 실행 작업을 사용자 UUID별로 관리한다. 시작 알림도 해당 호출의 사용자 ID를 사용한다. 다른 사용자가 실행 중이어도 자신의 즉시 실행을 시작할 수 있다.
- 사용자별 시작·중지를 프로세스 내 잠금으로 직렬화하고, 중지는 해당 작업의 취소 정리가 끝날 때까지 기다린다. 이전 작업의 종료 콜백이 재시작한 새 작업을 지우지 않는다.
- 수동 중지와 비상 정지는 대상 사용자만 취소한다. 일손실 한도가 자기 사이클에서 발동하면 자기 작업을 중간에 취소하지 않고 미체결 취소·알림·감사 기록·최종 로그를 마친다.
- 사용되지 않는 과거 인프로세스 반복 루프와 공용 실행·위험 상태 변수를 제거했다. 인자 없는 `stop_auto_trade()`는 프로세스 종료 시 전체 정리용으로 남겼다.

사용자별 활성 플래그와 Celery Beat 주기 실행 모델은 유지한다. 이번 작업은 프로세스 내 즉시 실행의 사용자 분리다. 여러 API 프로세스·Celery 워커 사이의 분산 취소나 분산 실행 잠금을 새로 구현한 것은 아니다. 캐시 장애 때 기록이 일시적으로 보이지 않을 수 있지만 다른 사용자의 기록은 대신 보여 주지 않는다.

## 검증

`tests/test_auto_trade_isolation.py`의 11개 시험:

- A 기록이 있는 상태에서 B의 캐시 없음·빈 기록 각각 로그와 위험 상태가 비어 있음.
- 캐시 만료·삭제 이후 이전 메모리 기록이 되살아나지 않음.
- A/B 교차 저장 시 각각 최근 50개 기록·마지막 위험 상태 유지.
- B의 미실행 중지와 실행 중 중지 모두 A를 취소하지 않음.
- 같은 사용자의 동시 시작 8건이 실행·시작 알림 1건만 생성.
- 중지의 취소 정리 이후에만 재시작, 이전 콜백의 새 작업 삭제 방지.
- 자기 일손실 정지의 최종 로그 유지 및 B 작업 보존.
- 외부에서 A를 비상 정지해도 B 작업 보존.
- A의 실행 예외가 B의 작업 상태를 지우지 않음.

관련 회귀 시험은 **328 통과, 실패·건너뜀 0**. 자동매매 사이클·재주문·위험 수량·위험관리·KIS 시작·배치·배분·리밸런싱을 포함했다. 외부 증권사 주문 없이 시험 대역과 일회용 PostgreSQL을 사용했다.

최초 회귀 실행에서 main의 기존 `test_open_live_buy_orders_count_toward_position_cap` 기대값 충돌 1건이 다시 나왔다. 이는 #183에서 이미 작성한 `9e43aa9`의 시험·설명 주석 수정을 그대로 재사용하여 해결했다. 같은 종목의 열린 주문이 있으면 새 주문을 보류하는 실제 정책은 바꾸지 않았다.
