## 요약 5줄

1. 지금 강사님 길(`stock.get_candles`)은 수집 DB → KIS → Yahoo 로 넘어가고, 모델 비교 라우트가 `source` · `as_of` 를 버려 넘어간 사실이 보이지 않는다. KIS 는 「2년」 을 300봉(약 14개월)으로 줄이고 `as_of` 가 없으며, Yahoo 는 수정 종가(`adjclose`)가 아닌 `close` 를 쓰는 데다 팀이 약관으로 뺀 출처다 — 같은 「일봉」 이라도 셋의 수정 방식이 서로 다르다(<표 2>).
2. 실무는 「공급처 우선순위 대체는 자료 층에서 검증 뒤 골든 카피 하나로 끝내고, 계산 · 보고는 그 하나만 읽는다」 — BCBS 239 원칙 3 · 36(d) 「단일 권위 출처」 · 43 「예외는 밝히고 설명」, EDM(Eagle) 출처 순위 · 검증 실패분 제외, Zipline 번들 · QuantConnect 수정 방식 하나, MLflow 지문 · 출처 기록(<표 6>).
3. 출처는 **안 1 보강**을 추천한다 — 수집 DB 수정주가만 · 대체 없음 · 응답에 출처 · 수정 방식 · 기준일 · 지문 · 출처 표시 글, 없을 때는 까닭별 글과 다음 행동(관리자에게만 할 일). 명확성 · 흐름 · CTA 와 정확성 · 재현성 · 일관성 · 말없는 대체 금지에서 모두 앞선다(<표 7>).
4. 캐시는 **자료 지문으로 맞춰 보는 결과 캐시**를 추천한다 — 수정주가 표가 매일 통째로 다시 만들어지고 기간 창이 오늘에서 계산돼, 기준일이 같아도 봉 묶음이 바뀔 수 있다. 앱 표준 `data_cache` · `이름:판:대상` 열쇠 · 같은 열쇠 한 번만 계산(single-flight) · 안전 TTL 7일 · 오류는 캐시하지 않음(<표 8> · <표 10>).
5. 화면은 10 ~ 14초가 주의의 경계(10초) 바로 위라 경과 · 예상 시간 · 하는 일을 정직하게 보이고(지어낸 백분율 금지), 결과 위에 「자료 기준일 · 계산 시각 · 걸린 시간 · 저장된 결과」 한 줄, 「다시 계산」 은 관리자만 둔다. 없는 종목 · 짧은 자료 · DB 없음은 까닭별 글 + 단추로 막다른 길을 없앤다(<표 9> · <표 12>).

## 1. 지금 코드 사실

기준 — `main` `8921f92`(2026-10-15 작업 트리 · 읽기만). 모델 비교 서버 파일(`app/services/model_compare.py` · `app/routes/model_compare.py`)은 이 조사와 함께 새로 썼다 — 구현은 [시간 순서 평가 조사](모델비교-시간순서평가-조사.md) 3절.

용어 풀이(처음 나오는 곳):

- **수정주가(adjusted price)** — 분할 · 병합 · 권리락처럼 주식 수가 바뀌는 날 앞의 값을 계수로 고쳐, 그날 차트가 끊기지 않게 한 값. 이 글에서는 세 가지가 섞여 나온다 — 우리 수집 DB 의 「기준가 계수」 수정주가(`adj_base`), 한국투자증권(KIS) 서버가 고친 수정주가, Yahoo 의 `close`(수정 종가 `adjclose` 가 아닌 값). 헷갈리는 점: 같은 「수정주가」 라도 무엇을(분할만 · 권리락까지 · 현금 배당까지) 고쳤는지가 출처마다 달라 과거 값이 서로 다르다.
- **대체(fallback)** — 첫 출처가 비면 다음 출처로 넘어가는 것. 이 글에서 「말없는 대체」 는 넘어간 사실이 응답 · 화면에 나오지 않는 것을 말한다.
- **자료 기준일(`as_of` · `data_as_of`)** — 계산에 쓴 마지막 봉의 날짜. 오늘 날짜가 아니다(수집기는 거래일 값을 다음 날 낮에 받는다).

## 2. 실무 · 실제 서비스 조사

조회일은 모두 2026-10-15. 검색 결과의 요약 글은 출처로 쓰지 않았고, 원문을 직접 읽은 것만 적었다(github.com 은 읽지 않음). 읽지 못한 것은 6.2절에 따로 적었다.

용어 풀이:

- **골든 카피(golden copy) · 단일 권위 출처(single authoritative source)** — 여러 공급처의 값을 검증 · 비교해 「이 종목 · 이 날은 이 값」 하나로 확정한 기록, 또는 그 기록을 두는 한 곳. 이 글에서는 우리 수집 DB 의 수정주가 표(`price_adjusted`)를 말한다. 헷갈리는 점: 골든 카피도 안에서는 여러 출처를 쓸 수 있다 — 대체는 **골든 카피를 만드는 자료 층**에서 하고, 계산 · 보고는 확정된 하나만 읽는다.
- **우선순위 대체(waterfall · source hierarchy)** — 출처를 중요도 차례로 줄 세워, 앞 출처가 없거나 검증에 떨어지면 다음 출처를 쓰는 규칙.
- **계보(lineage) · 지문(digest)** — 계보는 「이 값이 어디서 왔나」 의 기록, 지문은 자료 내용으로 만든 짧은 해시. 이 글에서는 「계산에 쓴 봉 전체의 SHA-256 앞 16자리」 를 지문이라 부른다. 헷갈리는 점: 기준일(마지막 봉 날짜)이 같아도 과거 봉이 바뀌면 지문은 달라진다.
- **결과 캐시(result cache)** — 비싼 계산의 답을 저장해 두고 같은 물음에 다시 내주는 것. **cache-aside** 는 앱이 먼저 캐시를 보고 없을 때만 계산해 채우는 꼴이다.
- **stale-while-revalidate** — 기한이 지난 답을 일단 내주고 뒤에서 새 답을 만드는 HTTP 캐시 규칙(RFC 5861). 이 글에서는 「어제 자료로 만든 결과를 먼저 보이고 오늘 자료로 다시 계산」 하는 앱 안 꼴을 그렇게 부른다.
- **single-flight** — 같은 열쇠의 계산이 동시에 여러 번 시작되지 않게, 하나만 계산하고 나머지는 그 결과를 기다리게 하는 잠금.

조사에서 바로 나오는 규칙(3 · 4절이 따른다):

1. **대체는 자료 층에서, 계산은 골든 카피 하나로**(S1 36(d) · S2 · S3 · S4). 여러 출처가 필요하면 수집기 안에서 검증 · 자동 대조(S1 각주 16)한 뒤 같은 표에 넣고 줄마다 출처를 적는다 — 분석 화면이 런타임에 공급처를 바꾸지 않는다.
2. **예외는 밝히고 설명한다**(S1 43 · S21 · S22). 없을 때는 까닭 · 다음 행동을 준다 — 막다른 길을 만들지 않는다.
3. **결과는 「무엇으로 계산했나」 와 함께 남긴다**(S5 · S6) — 출처 · 수정 방식 · 기준일 · 지문.
4. **같은 입력이면 다시 계산하지 않는다**(S3 · S17 · S18). 「같은 입력」 은 기준일이 아니라 **내용 지문 + 계산 판 + 설정 + 라이브러리 판**으로 판단한다(S4 — 수정값은 이력 전체로 다시 매겨진다).
5. **기다림은 정직하게 보인다**(S19 · S20) — 모르는 백분율을 지어내지 않고, 예상 · 경과 · 하는 일 · 그만 기다리는 길을 준다.

곁 사실(앱 안 — 출처 정책 · CTA 와 맞물림):

- 화면 수집 요청은 **관리자만 · 단계 단위**(「단계 하나 · 전체 수집 · 빠진 날 채우기」)다 — 종목 하나를 골라 받는 요청은 없다(수집기가 상장 주식 전부를 매일 받는다). 그래서 「종목이 없어요」 의 사용자 CTA 는 「수집 요청」 이 아니라 「코드 확인 · 이름으로 찾기 · 다음 정기 수집 뒤 다시」 이고, 관리자 CTA 는 「빠진 날 채우기 · 한 단계 다시」 다 — `app/services/collect_requests.py:1-28 · 42-44` · `app/routes/data.py:39-42 · 76-77`.
- 수정주가 다시 만들기는 전 종목을 **한 트랜잭션**(`BEGIN IMMEDIATE` … `COMMIT`)으로 묶는다 — 읽는 쪽은 반쯤 다시 만든 표를 보지 않고, 끝나는 순간(10-14 회차 12:56) 지문이 한 번에 바뀐다 — `collector/preprocess.py:327-392`(마지막 고친 커밋 `aba89e9`).

읽는 법 — 안 2 의 장점(거의 늘 답이 나옴)은 「흐름」 하나뿐이고, 그 흐름이 정확성 · 재현성을 깎는다. 안 3 은 안 2 의 투명성을 고치지만 품이 크고, 「참고용」 이 많아 명확성 · CTA 가 오히려 흐려진다. 안 1 의 약점(막다른 길)은 대체가 아니라 **까닭별 글과 다음 행동**으로 메울 수 있다 — 그것이 추천안이다.

실무와의 대응 — 실제 금융사도 공급처 우선순위(S2)를 쓴다. 다만 그 일은 **가격 마스터(자료 층)에서 검증 뒤 골든 카피 하나로** 끝내고, 위험 · 평가 · 연구는 그 하나를 읽는다(S1 36(d) · S3 · S4). 우리에게 자료 층은 수집기다 — 이미 조정 이벤트 「확인 필요」 판정 · 「두 신호가 어긋나 적용하지 않은 배당」 같은 검증을 한다(<표 3>). 그래서 KIS 를 두 번째 출처로 쓰고 싶어지면 화면이 아니라 수집기에 넣고, 우리 수정주가와 자동 대조(S1 각주 16)한 뒤 줄마다 출처를 적는 것이 실무 꼴이다.

### 3.2 계산 시간 · 캐시 — 후보 다섯 + 추천

견준 후보:

- **① 기준일 열쇠 결과 캐시** — 열쇠에 `data_as_of` 를 넣는다(지난 설계의 처음 후보).
- **①′ 지문으로 맞춰 보는 결과 캐시(추천)** — 열쇠 = 계산 판 · 종목 · 기간 · 설정 지문, 값 안에 자료 지문 · 기준일 · 계산 시각 · 걸린 시간. 요청마다 봉을 읽어(수십 ms — `data_ohlcv.py:29`) 지문을 내고, 저장된 지문과 같을 때만 저장된 답을 준다. 다르면 다시 계산해 **같은 줄을 덮어쓴다**.
- **② 매일 러너에서 미리 계산** — 12:30 회차 뒤 정한 종목 · 기본 설정을 미리 계산.
- **③ 캐시 없음** — 새 화면 넷과 같은 꼴.
- **④ 비동기 작업 + 진행 표시** — Celery 작업 + `GET /api/tasks/{id}` 꼴 · 겹 · 모델 단위 진행률(S16).
- **⑤ 지난 결과 먼저 + 뒤에서 다시 계산** — stale-while-revalidate 꼴(S11) · 「어제 자료 기준 · 새 자료로 계산 중」 표시.

왜 기준일(①)만으로는 모자라나 — 수정주가 표는 **매 거래일 종목마다 지우고 다시 만든다**(<표 3> 마지막 줄). 수정값은 이력 전체로 매겨지므로(S4) 규칙을 고치거나 「확인 필요」 이벤트를 바로잡거나 빠진 날을 채우면, 마지막 봉 날짜가 그대로여도 과거 봉이 바뀐다. 게다가 기간 창의 시작이 오늘에서 계산돼(4.2절) 같은 기준일이라도 요청한 날에 따라 첫 봉이 달라질 수 있다. 지문은 그 경우를 모두 잡는다. 비용은 봉 읽기(어차피 계산 전에 읽음) + 약 500줄 해시로, 10 ~ 14초 계산에 비해 무시할 크기다(확실도 높음 — 단 빈도는 확인 필요).

추천 — **①′ + 동기 계산 + 같은 열쇠 한 번만 계산 + 정직한 진행 표시**. 10 ~ 14초는 주의의 경계(10초 · S19) 바로 위라 ④ 는 품에 비해 얻는 것이 작고(FastAPI 문서도 무거운 계산은 Celery 라 하지만 그 품은 S15), ⑤ · ② 는 「12:30 뒤 첫 기다림」 이 실제로 문제일 때 얹는다(5절 뒤집을 조건). ③ 은 같은 종목을 여러 번 · 여러 명이 볼 때 CPU 를 다시 쓰고, 동시에 두 계산이 돌면 둘 다 느려진다.

출처 정책과 맞물리는 곳(한 줄씩):

- 열쇠의 「자료 판」 은 `data_as_of` 가 아니라 `data_digest` 다 — `data_as_of` 는 값에 넣어 화면에 보인다.
- 출처가 `collector` 가 아닌 결과는 캐시하지 않는다(추천 출처 정책에서는 생기지 않지만, 안 2 · 3 을 고르면 이 규칙이 필요하다 — 섞인 출처의 결과는 같은 요청에 다른 답이라 캐시 열쇠가 뜻이 없다).
- 오류(404 · 422 · 503)는 캐시하지 않는다 — 다시 묻는 비용이 작고, 오늘 상장 종목은 다음 회차 뒤 바로 보여야 한다(S14 「Handle missing records explicitly」).
- 「판정 안 함」(시험 행 < 200)도 정상 결과라 캐시한다 — 같은 자료면 같은 답이다.

## 4. 추천 · 응답 칸 · 글 초안

### 4.1 출처 정책 — 추천

**우리 수집 DB 수정주가만 읽고 대체하지 않는다. 대신 응답에 출처 기록을 싣고, 없을 때는 까닭별 글과 다음 행동을 준다(안 1 보강).**

까닭 셋:

1. 정확성 · 재현성 — 수정 방식이 하나이고(우리 · KIS · Yahoo 가 서로 다르다 — <표 2> · S4 · S7), 「2년」 이 늘 2년이며(KIS 는 300봉), 기준일 · 지문으로 같은 입력임을 증명할 수 있다(S6).
2. 실무 꼴 — 공급처 우선순위는 자료 층에서 검증 뒤 골든 카피 하나로 끝내고 계산은 그 하나를 읽는다(S1 36(d) · S2 · S3). 우리 자료 층은 수집기이고 이미 검증을 한다.
3. 명확성 · 흐름 · CTA · 일관성 — 새 화면 넷과 같은 꼴(<표 4>)이고, 안 1 의 약점인 막다른 길은 대체가 아니라 까닭별 글 · 단추로 메운다(S21 · S22).

뒤집을 조건은 5절.

### 4.2 계산 결과 캐시 — 추천 설계

**지문으로 맞춰 보는 결과 캐시(앱 DB `data_cache`) + 동기 계산 + 같은 열쇠 한 번만 계산 + 정직한 진행 표시 + 관리자만 「다시 계산」.**

| 캐시하지 않는 것 | 오류(404 · 422 · 503) · 출처가 `collector` 가 아닌 결과 | S14 「Handle missing records explicitly」 · 3.2절 |
| HTTP 머리 | `Cache-Control: private, no-cache`(로그인 응답 — 공유 캐시 금지 · 브라우저는 매번 확인) · `ETag` 재검증은 다음 단계 후보 | S12 |

쓰는 중에 확인한 코드 사실 — 기간 창의 시작이 **요청한 날(오늘)** 에서 계산된다: `start = _months_before(today, months)`(`app/services/collector_db.py:175-178`). 그래서 같은 기준일이라도 토요일과 일요일에 부르면 창의 첫 봉이 달라질 수 있다 — 「같은 기준일이면 같은 답」(시제품 TC-MC-11)이 앱 안에서는 요청한 날에 따라 깨질 수 있다는 뜻이다. 추천 — 모델 비교는 창을 **기준일에 붙인다**(기간보다 조금 넉넉히 읽고 `[기준일 − 기간, 기준일]` 로 자름). 그러면 기준일이 같은 동안 창이 같고, 지문은 과거 봉이 바뀐 경우만 가른다. 지문 대조는 이 경우도 어차피 잡으므로 캐시가 틀린 답을 내지는 않는다(확실도 높음 — 코드 줄로 확인).

지문 · 열쇠 · 흐름 견본(설계 설명용 — 저장소에 넣을 코드가 아니다):

```python
import hashlib, json

def data_digest(candles: list[dict]) -> str:
  """계산에 쓴 봉 전체의 지문 — collector_db._candle 이 이미 둘째 자리로 반올림해 같은 자료면 늘 같다."""
  rows = [[c["time"], c["open"], c["high"], c["low"], c["close"], c["volume"]] for c in candles]
  raw = json.dumps(rows, separators=(",", ":"), ensure_ascii=False)
  return "sha256:" + hashlib.sha256(raw.encode("utf-8")).hexdigest()[:16]

def cache_key(code: str, period: str, settings: dict) -> str:
  raw = json.dumps(settings, sort_keys=True, separators=(",", ":"))   # 겹 수 · 간격 · … · 라이브러리 판
  return f"model_compare:v1:{code}:{period}:{hashlib.sha256(raw.encode()).hexdigest()[:12]}"

# 흐름: 봉 읽기(없으면 404 · DB 없으면 503) → 지문 → cache_get(열쇠, 7일)
#   → 지문이 같으면 저장된 답(cached=True) · 관리자 「다시 계산」 이면 건너뜀
#   → 아니면 열쇠별 잠금 안에서 한 번 더 확인 → asyncio.to_thread(계산) → cache_set(열쇠, {지문 · 기준일 · 계산 시각 · 걸린 시간 · 결과})
```

## 5. 뒤집을 조건

출처 정책:

1. **ETF · 오늘 상장 · 해외 종목을 이 화면에서 보자는 요청이 잦으면** — KIS 런타임 대체가 아니라 수집 자료를 넓혀 같은 길로 읽는다. ETF 일봉은 수집 DB 에 이미 있다(`etf_daily` · 수정 방식 `raw` — `data_ohlcv.py:59-62`). 수정 방식이 달라 `price_basis` 를 `raw` 로 바꿔 보이고 결과도 따로 캐시한다.
2. **배포 환경에 수집 DB 를 붙일 수 없게 되면**(클라우드 배포 등) — 그때 안 3(우선순위 + 줄마다 출처 + 대체분 판정 안 함)을 다시 본다.
3. **KIS 를 두 번째 출처로 쓰기로 하면** — 수집기 안에서 우리 수정주가와 자동 대조(S1 각주 16)하고 같은 표에 줄마다 출처를 적는다. 화면은 계속 한 표만 읽는다.
4. **KIS 수정주가가 우리 수정주가와 같은 규칙이라는 원문 · 대조 결과가 나오면** — 섞임의 위험이 줄어 안 3 의 품이 작아진다(지금은 공식 원문을 읽지 못함 — 6.2절).

계산 시간 · 캐시:

1. **앱 안 실측이 30초를 넘거나 여러 명이 동시에 쓰면** — 비동기 작업 + 겹 · 모델 단위 진짜 진행률(S16).
2. **앱 안 실측이 3초 안쪽이면** — 캐시 없이(새 화면 넷과 같은 꼴).
3. **봉 읽기가 1초를 넘으면**(지문 비용이 커지면) — 지문 대신 러너가 남기는 회차 표지(수정주가를 다시 만든 시각)를 자료 판으로.
4. **12:30 뒤 첫 사용자 기다림이 문제로 드러나면**(발표 시연 등) — 기본 종목 몇 개만 회차 뒤 데우기(S13 미리 데우기) 또는 「지난 결과 먼저 + 뒤에서 다시」(⑤ · S11).
5. **앱을 여러 프로세스로 띄우면** — 열쇠별 잠금을 Redis `SET NX PX` 로(S14).
6. **`data_cache` 표가 커지면** — 오래된 `model_compare:` 줄을 지우는 정리 작업(지금은 덮어쓰기라 종목 × 기간 × 설정 수만큼만 생긴다).
