## 1. 무엇을 했나

- **팀원 신호 배치를 매일 러너에 붙였다(이슈 #142).** 일봉 뒤 · 목록표 앞에서 수집 DB 의 마지막 거래일 하루를 계산해 앱 DB 의 T2 에 401줄을 쓴다. 배치 코드는 고치지 않고 부르기만 한다.
- **PC 에서 돌 때의 앱 DB 주소를 compose 에서 만든다.** 처음 실제로 돌리자 앱 DB 가 떠 있는데도 연결이 거부됐다. 앱 설정은 `ENV_FILE` 이 없으면 `.env.dev` 를 읽고, 컨테이너가 쓰는 주소는 compose 에만 있었다. 앱 서비스의 `DATABASE_URL` 과 DB 포트 짝(`15432:5432`)으로 `127.0.0.1:15432` 를 만들어 앱 DB 를 쓰는 단계에만 넘긴다.
- **앱 DB 가 꺼진 날은 돌리기 전에 안다.** 러너가 포트를 먼저 확인하고, 닫혀 있으면 돌리지 않고 「건너뜀 · 앱 DB 꺼짐」 과 빠진 거래일 · 채우기 명령을 남긴다. 회차 ok 는 그대로라 리밸런싱 하루 점검을 막지 않는다. 포트가 열렸는데 실패하면 경고, 주소를 못 만들면 돌리지 않고 경고다.
- **한 단계 다시 뒤 시세 기준일을 다시 잰다(DF-85).** 시세 단계를 다시 받아도 회차 기록의 기준일이 그대로라 리밸런싱 준비 판정이 「기준일이 다름」 으로 기다리던 결함이다.
- **적재 · 백업의 남은 셋을 실제로 돌렸다.** 깊은 대조(검사 63건 · 104초) · 복원 리허설(2,162만 행 · 495초) · 원격 다시 확인(3초) — 판정이 처음으로 「지워도 된다」 가 됐다(지우지는 않았다).
- **수정주가 「확인 필요」 한 줄을 공시로 갈랐다(DF-89).** 131400 은 10주 → 1주 병합이라 주식 수가 맞고, 계수(11.0966)는 거래 재개일 시초가 등락이 섞인 값이었다.

## 2. 막힌 것 · 알게 된 것

- **시험은 통과했는데 실제로 돌리자 붙지 못했다.** 시험은 가짜 단계라 앱 DB 에 붙지 않는다. 실제 `run --only signals` 에서 처음 종료코드 3 을 봤고, 그 3 은 「DB 꺼짐」 이 아니라 「주소 틀림」 이었다.
- **같은 종료코드가 두 뜻이다.** 배치의 3 은 꺼짐과 주소 · 계정 결함을 가르지 못한다. 3 만 보고 건너뜀으로 바꿨다면 오늘의 주소 결함이 매일 노랑 한 줄 뒤에 숨었을 것이다. 실무 도구도 「돌다가 실패」 와 「조건이 없어 안 돎」 을 다른 상태로 둔다(Airflow 의 skipped · systemd 의 ExecCondition).
- **못 만든 값을 기본값으로 메우면 다른 곳에 쓴다.** 처음 판은 주소를 못 만들면 앱 설정의 기본 주소로 돌게 두었는데, 그 기본값은 `.env.dev` 나 기초 코드의 다른 DB 다. 조사가 짚어 「돌리지 않고 경고」 로 바꿨다.
- **회차 뒤에 더한 단계는 회차 기록에 줄이 없다.** 신호 단계를 처음 다시 돌리자 결과가 이력에만 남고 화면 표에는 없었다 — 단계 목록 차례 자리에 끼우게 했다.
- **포털의 「전일 대비」 는 늘 전날 종가 기준이 아니다.** 감자 뒤 거래 재개일에는 시초가가 그날 기준가격이 된다. 그래서 첫날 등락이 조정 계수에 섞이고, ±5% 안이면 「분할 · 병합」 으로 통과해 보이지 않는다.

## 3. 원칙으로 다시 보기

- **SSoT** — 앱 DB 주소는 compose 한 곳에서 만들고(개발 모드 스크립트와 같은 값인지는 시험이 맞댐), 빠진 날 채우기 명령은 단계 정의 한 곳에 두어 단계 목록 → API → 화면으로 흘린다.
- **말없는 fallback 금지** — 주소를 못 만들면 돌리지 않고 경고, 기준일을 못 재면 옛 값을 지우지 않되 `after_error` 를 남긴다. 건너뛴 줄마다 까닭 코드를 붙인다.
- **판단은 기록하는 쪽에서** — 「꺼짐」 · 「설정 결함」 은 러너가 가르고 기록에 쓴다. 앱은 종료코드를 다시 해석하지 않는다(규칙 사본이 생기지 않게).
- **멱등성** — 신호 배치는 같은 날을 다시 써도 값만 바뀌어, 빠진 날 채우기를 몇 번 돌려도 결과가 같다.
