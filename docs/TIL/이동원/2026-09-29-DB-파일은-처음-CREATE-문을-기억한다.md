## 3. 어떻게 했나 — 고른 것과 버린 것

- **고른 것 — 사전을 다시 뽑기 전에 옮길 한 줄이 실제로 나오는지 먼저 봤다.** 안 나왔다. DB 파일의 `sqlite_master` 에 저장된 CREATE 문에는 `shares` 줄이 없었다 — 표를 DF-01 수정 전에 만들었기 때문이다. 그래서 스캐너가 설명을 코드에서 읽게 고쳤다(구조는 여전히 DB 파일에서).
- **고른 것 — 운영 속성은 TSV 대장으로.** API ID 대장처럼 사람이 적고 스캐너가 싣는다. 빠진 표는 요약 출력이 알린다.
- **고른 것 — 「대장이 모든 표를 덮는다」 는 실제 저장소 시험에 걸지 않았다.** 팀원이 표를 더하는 것은 좋은 일인데 그 순간 시험이 깨진다(API 명세 스캐너 시험과 같은 원칙). 판정 규칙은 합성 대장으로 쟀다.
- **고른 것 — 파트 대신 업무 영역.** 표에 파트를 붙이면 역할 결정(D9)을 앞지른다.
- **고른 것 — 앱 DB 그림을 영역 넷으로.** 26표 한 그림은 선이 엉킨다(기준 6.3 — 15개 안팎) → 12 · 5 · 4 · 5표, 다른 영역의 `users` 는 기본키만.
- 버린 것 — **사전 3절의 `kind` 한 줄만 손으로 고치기.** 사전이 「손으로 고치지 말 것 · 설명은 코드에서」 를 약속하는데 그걸 깨는 셈이다.
- 버린 것 — **그림 번호를 스캐너가 붙이게.** 스캐너는 문서의 그림 번호를 모른다. 자동 블록은 제목만 두고 절 번호로 가리킨다 — 기준 v0.2 재료로 부록 C 에 적었다.

## 6. 배운 것

- **DB 파일은 처음 CREATE 문을 기억한다.** `CREATE TABLE IF NOT EXISTS` 는 이미 있는 표를 건드리지 않고, `ALTER TABLE ADD COLUMN` 은 주석 없이 끝에 붙는다. 설명의 정본이 코드라면 설명은 코드에서 읽어야 한다.
- **구조와 뜻은 출처가 다르다.** 칸이 있는지는 실물(DB 파일)이 말하고, 칸이 무엇인지는 코드가 말한다. 한 곳에서 둘 다 읽으면 한쪽이 조용히 낡는다.
- **값을 세어 보면 주석이 틀린 곳이 보인다.** 코드 정의를 모으려고 `group by` 를 돌리자 주석에 없는 배당 형태(`현금ㆍ현물배당` 15건)가 나왔다.
- **새 틀로 옮겨도 사실은 하나도 빠지지 않았다.** 숫자 · ID · 링크는 그대로이고, 경위와 회차만 개정 이력으로 자리를 옮겼다.
