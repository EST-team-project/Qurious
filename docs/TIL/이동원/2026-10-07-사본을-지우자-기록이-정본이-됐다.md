## 1. 무엇을 했나

- **러너 단계의 이름표 · 묶음 · 하는 일을 러너 한 곳(`Step`)에 두었다.** 묶음은 받기 · 계산 · 백업 · 근거 문서 넷이고 이름표는 Figma 에서 정한 설계 1 과 같다. 러너가 회차마다 단계 목록 파일과 회차 기록의 단계 줄에 함께 쓰고, 앱은 그 기록만 읽는다. 앱에 손으로 옮겨 두었던 이름표 사본(19줄)은 지웠다 — 단계를 더하면 화면이 따라온다(결정 ④).
- **수집 일정 · 단계 API 를 만들었다(관리자).** 마지막 회차 · 회차 기록(단계별 결과는 오늘 뒤 회차부터) · 단계 목록 · 이 PC 용량(러너가 회차 끝에 잼) · 한 단계 다시 돌리는 명령을 한 답에 준다.
- **러너에 「한 단계만 다시」 를 더했다.** `run --only <단계>` — 12:30 회차와 겹치는 때 · 다른 실행이 도는 동안은 막고, 마지막 회차의 그 줄만 새 결과로 바꾸며 이력에 「다시 돌림」 한 줄을 남긴다. 화면은 이 명령과 막히는 때만 보여 주기로 했다 — 앱이 러너를 부르는 통로를 따로 만들지 않는다.
- **주소 검사를 만들고 받는 길 셋에 걸었다.** 형식 → 내부망 → 허용 목록 → robots 차례로 보고 처음 걸린 곳에서 멈춘다. 수동 크롤링 둘과 네이버 길은 막히면 400 이다.
- **Figma 남은 흠을 고쳤다.** 경우 표 18칸을 낱말 단위로 줄바꿈 · 「예시 값」 꼬리표를 화면 밖 주석으로 · 설계 3 의 자료 올리기 · 위험 구역 칸 삭제 · 표지 · 지금 화면 설명의 작업 말.

## 2. 막힌 것 · 알게 된 것

- **앱은 러너를 불러올 수 없었다.** 앱 컨테이너에는 `app/` 만 들어 있고 수집 폴더는 읽기 전용이라, 「한 곳에 두기」 는 공용 모듈이 아니라 **러너가 쓰는 기록 파일**로 해야 했다. 이름표가 없는 옛 기록을 위해 「그 회차 기록 → 단계 목록 → 이름 그대로」 차례로 찾는다.
- **한 단계를 다시 돌리는 일이 매일 회차를 통째로 날릴 수 있었다.** 12:25 에 20분짜리 단계를 돌리면 12:30 회차가 잠금에 걸려 건너뛰고, 작업 스케줄러는 다시 시도하지 않는다. 그래서 「회차 시작 − 그 단계의 시간 한도」 부터 「회차 시작 + 60분」 까지 막는다 — 오늘 회차도 60분 돌아 13:30 에 끝났다.
- **깨 보기가 우연히 통과한 시험을 찾았다.** 「회차와 겹치면 막는다」 시험이 막는 검사를 꺼도 통과했다. 시험 단계의 종료코드가 마침 「막힘」 과 같은 3 이었고, 시험 시각(12:10)은 그 단계의 막는 때(12:29 ~ 13:30) 밖이었다. 성공하는 단계 · 막는 때 안의 시각 · 이력 줄 수로 다시 썼다.
- **내부망은 「사설」 만으로 막히지 않는다.** 클라우드 메타데이터 주소(169.254.169.254)는 링크 로컬이고, 100.64.0.0/10 공유 주소는 파이썬이 사설로 보지 않는다 — 마지막에 「공인 주소인가」 를 따로 본다. 이름이 가리키는 IP 는 **전부** 보고, 허용 목록 밖 주소에는 robots.txt 를 받으러 가지도 않는다.
- **Figma 는 한국어를 글자 중간에서 끊는다.** 칸 너비를 임시 글 상자로 재서 띄어쓰기 자리에 줄바꿈을 넣었고, 굵은 머리가 섞인 글은 바꿀 부분만 지우고 끼워 넣어 서식을 지켰다.
- **새 명령을 실제로 한 번 돌리자 앱이 멈췄다(DF-81).** 「한 단계 다시」 로 목록표 단계를 돌린 뒤 앱의 데이터 API 8개가 「unable to open database file」 로 멈췄다. 수집 DB 는 WAL 이고 앱은 `data/` 를 읽기 전용으로 붙여 여는데, 이 PC 의 **쓰기** 연결이 마지막으로 닫히면 SQLite 가 보조 파일(-wal · -shm)을 지운다. 매일 회차가 멀쩡했던 까닭은 마지막 단계들(내보내기 · 대조 · 상태 읽기)이 읽기 전용 연결이라 보조 파일을 다시 만들어 두었기 때문이다 — 아무도 적어 두지 않은 안전판이었다. 시험은 가짜 단계라 DB 를 열지 않아 통과했고, 실제로 돌린 뒤의 기능 점검이 잡았다. 단계 뒤에 읽기 전용으로 한 번 여는 마무리를 넣고, 진짜로 DB 에 쓰는 단계를 돌리는 시험을 더했다.
- **응답 캐시는 느린 질의를 가린다(DF-80).** 데이터 상태 API 가 30초 캐시가 끊길 때마다 19 ~ 31초 걸렸는데, 캐시 덕에 대부분의 호출이 빨라 W7(10-04)부터 드러나지 않았다. 질의 열넷을 하나씩 재니 재무 표의 `MAX(known_at)` 하나(색인 없음 · 188만 행)가 23초였다. `known_at` 은 정의상 접수번호 앞 8자리라, 색인이 있는 접수번호의 끝 한 칸으로 같은 값을 0.003초에 읽었다. 같은 꼴이 다시 생기지 않게 시험은 결과값이 아니라 **질의 계획**(색인을 쓰는가)을 본다.
- **팀원 머지 뒤 다시 돌린 전체 시험이 남의 회귀를 잡았다(DF-83).** PR 을 올리려고 다시 받은 main 에 들어온 팀원 #137 이 모의투자 성과 지표 API 자리에 관리자 `simulate` 를 넣어 같은 길이 둘이 됐고, API 스캐너 시험(TC-AP-04 — FastAPI 는 같은 메서드 · 경로를 두 번 등록해도 말없이 앞의 것만 쓴다)이 실패 2 로 잡았다. 그러나 화면 셋이 부르던 `metrics` 가 사라진 것은 부르는 시험이 없어 못 잡았다. 다른 주담당 코드라 고치지 않고 결함대장 · 이슈 초안으로 넘겼는데, PR 을 올리기 직전에 한 번 더 받으니 팀원 #138 이 그사이 고쳐 두었다.

## 3. 다음에 할 것

- 「DB 초기화」 단추와 서버 길(`POST /api/admin/reset`)을 함께 없앤다 — 모든 사용자의 기록을 지우는 길이다(DF-78) · 크롤링 세 화면 구현 때.
- 받을 범위 · 백업 상태 API — 크롤링 세 화면의 남은 서버.
- 리다이렉트를 따라가는 크롤러가 받은 뒤 마지막 주소를 다시 검사하게 한다.
- 수집 DB 를 롤백 저널로 바꿀지 정한다 — DF-81 의 뿌리(WAL 인데 앱은 읽기 전용)다. 러너가 쓰는 파일이라 회차 밖에서 바꾼다.
- 「화면이 부르는 API 가 서버에 있다」 시험 — `public/js` 가 부르는 `/api/…` 길을 앱 라우트와 맞댄다(DF-83 의 사라진 길을 못 잡았다) · 공용 시험이라 팀 글을 먼저 쓴다.
