# 화면이 실제보다 더 말하고 있었다 — 요구를 세다 사각지대 8개를 찾은 날

> 2026-09-21 (월) · Qurious 2.0 · RTM v1.0
> 관련 PR: `docs/rtm-v1-0` · `docs/요구사항/RTM_v1.0.md`

## 한 줄

**요구가 27개인지 29개인지 세러 갔다가, 요구 문서가 둘이라는 걸 알았고,
한쪽에만 있는 요구 8개 중 넷은 화면만 있고 계산이 없었다.**

---

## 1. 세러 갔는데 셀 수가 없었다

이슈 #62 가 이렇게 남겨 놨다.

> 강사님 문서 머리글은 P01 14 + P02 13 = **27개**인데, 열거하면 **29개**입니다.
> 🔴 개수가 틀리면 **산출물 대장과 시험 항목 번호가 전부 어긋납니다.**

그래서 세러 갔다. 그런데 **원문이 저장소에 없다.** 강사님 목표기능표는 #62 에 전재된
것만 있고, 저장소에 있는 건 `docs/rfp-1.md`·`docs/rfp-2.md` 라는 **다른 문서**다.

`rfp-2.md` 의 체크박스를 기계로 세어 봤다.

```
  §3 요구사항     19개  ┐
  §6 산출물        8개  ┼─ 19 + 8 = 27   ← 우연히 27이 나온다
  §7.2 평가        4개  │
  §9 제안 요건     4개  ┘
  ────────────────────
  합계            35개
```

**27이 두 곳에서 나온다.** 목표기능표의 27과 우연히 같다. 두 문서가 섞여 인용되면서
「27」이 무엇의 27인지 흐려졌을 수 있다 — 단정은 못 하지만 적어 뒀다.

## 2. 매듭은 세어서 풀리지 않았다

한참 세다가 방향을 틀었다. **무엇이 진짜 문제인지**를 다시 봤다.

```
   [순번 방식]  요구 1, 2, 3, … 27       ← 합계가 29로 바뀌면
                  ↓                         모든 번호가 밀린다
   산출물 대장 "요구 14번 대응"          → 가리키는 대상이 바뀐다 🔴

   [계층 방식]  P01-①-1, … P02-⑤-3      ← 합계가 바뀌어도
                  ↓                         각 주소는 그대로
   산출물 대장 "P01-③-2 대응"           → 항상 「이탈률 리밸런싱」 🟢
```

**번호가 흔들릴 수 있었던 건 합계가 애매해서가 아니라, 순번으로 부르려 했기 때문이다.**
계층 ID 로 두면 합계는 진척률 계산에만 쓰이고, 주소로는 안 쓰인다. 매듭이 풀렸다.

세는 문제인 줄 알았는데 **부르는 방식의 문제**였다.

## 3. 그런데 더 큰 게 나왔다

A계열(rfp)을 B계열(목표기능표)에 대응시키다 보니, **B계열 어디에도 대응이 없는
A계열 요구가 8개** 나왔다.

| rfp-2 요구 | 목표기능표 대응 |
|-----------|----------------|
| §3.1.3 자산배분 4개 (Markowitz·리스크패리티·블랙리터만·동적배분) | **없음** |
| §3.1.4 스크리닝 4개 (팩터·재무필터·기술적·랭킹) | **없음** |

29는 전부가 아니었다. **합집합으로 보면 37이다.**

## 4. 그리고 화면을 봤다

자산배분 4개가 정말 없는지 확인하려고 grep 했다.

```
  public/app.html:2521   "자산배분 모델"                      화면 있음 🟢
  public/app.html:2536   "블랙-리터만 (Black-Litterman)"      설명 있음 🟢
  public/app.html:2547   "Risk Parity"                        설명 있음 🟢
  public/app.html:1690   "AI가 최적 자산배분 비율을 계산합니다"  ← 문구 🟢
```

다 있어 보였다. 그래서 그 화면이 **실제로 부르는 것**을 따라갔다.

```python
# app/routes/ml.py:95
base_alloc = {
    "conservative": {"국내주식": 15, "해외주식": 10, "국내채권": 50, …},
    "moderate":     {"국내주식": 30, "해외주식": 25, "국내채권": 30, …},
    "aggressive":   {"국내주식": 45, "해외주식": 35, "국내채권": 10, …},
}[risk]
```

**최적화가 아니라 조회표였다.** 공분산도 목적함수도 제약조건도 없다.
`markowitz`·`cvxpy`·`PyPortfolioOpt` 는 저장소 전체에 **0줄**이다.

화면은 "AI가 최적 자산배분 비율을 계산합니다"라고 말하고 있다.

> 🟢 공정하게 적자면, **종목 스코어링은 실재한다.** 같은 엔드포인트의 `_screen()` 은
> 유니버스 30종목을 실제로 훑어 샤프비율 + Ridge 회귀로 점수를 낸다. 빈 껍데기가 아니다.
> 다만 **자산군 비중 결정**과 **종목 선정**은 다른 일이고, 비어 있는 쪽은 앞엣것이다.

## 5. 스캐너를 만들다 두 번 속았다

RTM 을 손으로 쓰면 한 달 뒤 거짓이 된다. 그래서 `scripts/rtm_scan.py` 를 만들어
요구마다 「구현됐다면 저장소에 뭐가 보여야 하나」를 탐지 규칙으로 적었다.
그런데 판정이 두 번 뒤집혔다.

**① 스캐너 자신이 흔적으로 잡혔다.**
「리밸런싱 코드 0건」이 **1건**으로 나왔다. 범인은 스캐너 안의 탐지 패턴 문자열
`r"rebalanc"` 였다. 자기가 찾는 단어를 자기가 갖고 있었다.

**② 주석 속 단어를 구현으로 셌다.**
「중복주문 방지·손실한도·비상정지」가 **2건** 있는 것으로 나왔다. 둘 다 이랬다.

```python
# app/services/auto_trade.py:225
        # 가상계좌 idempotent 초기화        ← 주석
# collector/benchmark.py:711
  재실행 안전(idempotent)이 네 겹으로 보장된다 ::   ← 설명문
```

**구현은 0건이었다.** 코드줄과 주석줄을 갈라 세도록 고쳤다.

이게 제일 섬뜩했다. **사고를 막는 항목인데 저장소에는 그 이름만 있었다.**
grep 이 초록불을 켜 주는데 실제로는 아무것도 없는 상태 — RTM 이 가장 위험할 때는
틀렸을 때가 아니라 **맞다고 믿길 때**다.

## 6. 오늘 배운 것

**1. 매듭이 안 풀리면 문제 정의를 의심한다.**
「27이냐 29냐」를 한참 셌는데, 풀린 건 세어서가 아니라 **순번을 안 쓰기로** 해서였다.
세는 문제인 줄 알았던 게 부르는 방식의 문제였다.

**2. 요구의 원천이 하나라고 가정하지 않는다.**
문서가 둘이면 개수도 둘이고, 한쪽에만 있는 요구가 생긴다. 8개가 그렇게 숨어 있었다.
그리고 그 8개가 **전부 한 파트(P-C)에 몰린다** — 인정하면 그 파트 부하가 3 → 11이 된다.

**3. 화면 문구는 구현의 증거가 아니다.**
"AI가 계산합니다"는 화면이 하는 말이지 코드가 하는 일이 아니다.
**화면에서 출발해 그 화면이 부르는 코드까지 따라가야** 판정이 된다.
발표 전에 이걸 못 찾았으면 질문 한 번에 무너졌을 자리다.

**4. 검증 도구도 검증해야 한다.**
스캐너가 자기를 세고, 주석을 구현으로 셌다. 둘 다 **초록불 쪽으로 틀리는** 오류였다 —
없는 걸 있다고 말하는 방향. 자동 판정은 편한 쪽으로 틀리기 쉬우니,
**몇 건은 손으로 열어 확인**하고 그 과정을 문서에 남겼다(RTM §7.1).
