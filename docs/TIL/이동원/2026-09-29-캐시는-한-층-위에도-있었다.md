## 1. 무엇을 했나

- **DF-17 닫음** — `GET /api/stocks/candles` · `GET /api/stocks/quant/indicators` 가 수집 DB 가 받는 요청(국내 주식 · 일봉 · DB 파일 있음)에는 라우트 캐시를 **읽지도 쓰지도 않는다.** 판정은 새 함수 `collector_db.handles()` 하나로 한다.
- 매시간 캐시 데우기(`sync_scheduler`)도 같은 판정으로 그 종목을 건너뛴다.
- API 명세 스캐너가 「캐시보다 먼저 수집 DB 요청을 돌려보내는 라우트」 를 알아보게 했다(순서까지 본다). 명세서 표는 `--doc` 로 다시 채웠다.
- 시험 **151 → 169**(TC-DF17 17 · TC-AP-14 1). 지난 세션 번호 채움 — S63 PR #51 · D9 #52 · #4 닫힘.

## 2. 왜 했나

- 다리(DF-08)의 약속 「캐시를 거치지 않는다 · 12:30 갱신이 바로 보인다」 는 **서비스 함수까지만** 맞았다. 화면이 부르는 라우트가 그 앞에서 6시간 캐시를 보고, 다리 결과를 그 캐시에 다시 썼다. 갱신 뒤에도 최대 6시간 옛 기준일이 나갔다.
- S63 에 명세 스캐너가 라우트마다 「닿는 곳」 을 늘어놓자 「라우트 캐시 6h」 가 다리 옆에 붙어 보였다. 코드로는 확인했지만 실행으로 재현하지 않은 🟡 후보였다.

## 3. 어떻게 했나 — 고른 것과 버린 것

- **고른 것 — 시험부터, 라우트 함수를 직접 불렀다.** 캐시가 옛 응답(기준일 09-25)을 돌려주게 막고, 수집 DB 에는 09-28 까지 넣었다. 옛 코드는 09-25 를 그대로 돌려줬다 — 🟡 가 🟢 로 바뀐 순간이다.
- **고른 것 — 캐시 앞에서 요청 모양으로 가른다.** 판정에 「DB 파일이 있는가」 를 넣었다. 수집 DB 를 안 받은 팀원 PC 에서는 다리가 늘 야후로 넘어가니, 그때는 캐시가 원래 일(외부 호출 줄이기)을 해야 한다.
- **고른 것 — 쓰는 쪽도 찾았다.** 라우트가 캐시를 건너뛰면 그 키를 채우던 `sync_scheduler` 가 아무도 안 읽는 쓰기를 매시간 한다. 캐시를 끊을 때는 **읽는 곳과 쓰는 곳을 함께** 찾아야 한다(`grep cache_set` 한 번).
- **고른 것 — 판정 함수 하나를 다리와 나눠 쓴다.** `handles()` 와 `read_daily_candles()` 가 같은 `_match()` 를 부른다. 「안 맡는다」 고 한 요청은 다리도 `None` 인지 시험이 함께 본다.
- 버린 것 — **응답으로 가르기**(캐시 값이 `source: collector` 면 버림). 요청마다 PostgreSQL 을 한 번 더 부르고, 캐시가 먼저인 구조가 남는다.
- 버린 것 — **라우트 캐시 통째로 없애기.** 서비스 함수가 같은 키로 캐시하긴 하지만, 지수 · 해외의 `from_cache` 표시와 지표 캐시까지 없어져 범위가 결함보다 넓다.
- 버린 것 — **캐시 시간 줄이기.** 옛 값이 나가는 시간이 줄 뿐 없어지지 않는다.

## 4. 어떻게 확인했나

- 새 17건을 옛 코드로 — **12 실패 · 5 통과.** 통과 5건은 모두 「바뀌면 안 되는 쪽」(DB 에 행이 없는 기호 · DB 없는 PC 의 데우기 · 지수 · 주봉 · DB 없는 PC 의 지표 캐시).
- 새 코드 — Postgres(15432) 붙여 **169/169**(59초) · DB 없이 **163 · 6**.
- 시험 밖 — 실제 수집 DB 로 HTTP 경로(`TestClient`): 일봉 · 지표 모두 `as_of` 2026-09-28 · 라우트 캐시 조회 0회.
- 스캐너 새 시험은 옛 스캐너 사본(`git show HEAD:`)에 끼워 돌려 실패를 봤다. 그 확인 스크립트가 cp949 창에 줄표를 찍다 한 번 더 죽었다 — DF-11 교훈이 내 임시 스크립트에도 그대로다.

## 5. 막힌 것 · 남은 것

- **라우트 캐시 규칙 한 장**(누가 · 몇 시간 · 무엇으로 무효화) — 이번엔 수집 DB 앞의 두 곳만. `/api/ml/robo/allocation` 의 3시간 학습 캐시는 계산 비용 캐시라 그대로(P-C).
- 올리지 않은 #35 갱신 댓글이 이미 올라갔는지 먼저 확인해야 했다. 이슈 댓글은 비로그인 화면에 없어서 검색(`comments:>0`)으로 「없음」 을 봤다 — 목록이 번호 역순이라 잘림과 구별된다.
- **사용자 지적 — 문서가 「개인 프로젝트 스타일」 이다.** 세션 번호 · 내 작업 용어(「다리」 · 「짝 시험」) · 발견 경위가 본문에 섞여 팀원이 읽기 어렵다. 실무 문서화 양식을 조사해 팀원이 읽는 틀을 정하고, 표 · 그림을 상세히 하는 방향은 살린다 — 다음 작업 후보(산출물목록 12절 2-3).

## 6. 배운 것

- **약속은 소비자가 부르는 층에서 잰다.** 서비스 함수에서 지킨 성질이 그 위 층에서 깨질 수 있다. 앞 TIL 의 「층이 둘인데 한 층만 쟀다」 를 코드로 닫은 셈이다.
- **캐시는 신선한 원천 뒤에 둔다.** 원천이 싸고(로컬 파일) 하루 한 번 바뀌면, 그 앞의 캐시는 옛 값을 내보내는 장치일 뿐이다.
- **캐시를 끊으면 쓰는 쪽이 남는다.** 읽는 곳만 고치면 아무도 안 읽는 쓰기가 조용히 돈다.
- **스캐너는 「있음」 이 아니라 「순서」 를 봐야 할 때가 있다.** 캐시를 먼저 보고 나서 가르면 옛 값은 이미 나간 뒤다.
