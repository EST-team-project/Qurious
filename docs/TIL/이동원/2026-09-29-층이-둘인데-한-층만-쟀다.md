## 1. 무엇을 했나

- **① API 명세서 v0.1** — 앱 API **146개**(라우터 19)를 라우터별 표로. 칸은 API ID · 메서드 · 경로 · 인증 · 요청 · 응답 · 오류 · 닿는 곳 · 화면 · 파트(제안) · 요구 ID · 코드 줄. 같은 문서에 **인터페이스 정의서**(IF-01~16)와 **데이터 매퍼**(DM-01~02)를 절로 시작했다.
- **`scripts/api_scan.py`** — 앱을 import 하지 않고 `app/` 를 AST 로 읽는다. 라우트 본문에서 시작하는 **정적 호출 그래프**로 「닿는 곳」(수집DB · 야후 · 증권사 관문 · 주문 · PostgreSQL · Redis …)을 붙이고, `view_scan.py` 로 「부르는 화면」 을, 기능 설계서 부록 A 로 「요구 ID」 를 붙인다. `--doc` 은 문서 안 표시 사이만 다시 채우고, `--check` 는 뒤처졌는지만 본다. ID 는 순번이 아니라 **대장**(TSV)에서 온다.
- **② 기능 설계서 v0.1** — 강사님 요구 29 + rfp 사각지대 8 + 화면 필수 요소 10 마다 「설계 근거 · 지금 · 빈 곳 · 설계 초안(API ID · ERD 표 · 화면 ID · TC ID) · 사용자 스토리 한 줄 · 결정 의존 · 일정 칸」. 공통 부품 C1~C6 · AWS → 로컬 대체표 · 새 API 13 · 새 표 9 · 새 시험 묶음 21 **안**.
- **D9 역할 희망 논의 본문**(사용자 요청 · 세션 중) — 기능을 **카드 62장**으로 늘어놓고 1~3지망을 댓글로 받는 글 + Discord 안내 글.
- 시험 **138 → 151건**(TC-AP 13). 봉인 시험(TC-YH) 기준선 +1(`scripts/api_scan.py: 1`).
- 산출물목록 v2.1 · 테스트계획서 6.1절 다섯 줄 · S62 PR #48 번호 채움 · 안 올린 옛 `#71` 본문 직접 수정 · 올린 인덱스 v2(#47)에 갱신 댓글 파일 · 새 번호 채움(#47 · #49 · #50) · #35 갱신 댓글 파일.

## 2. 왜 했나

- S62 사용자 지적 — 「API 나 ERD 등 산출물 문서 작업을 하나도 안 하는 이유를 모르겠다」. API 명세서는 **S42 부터 산출물목록 12절 2순위**였는데 한 번도 세션 계획에 들어가지 않았다.
- 세션 프롬프트 — 「깃허브 이슈 사태로 설계가 중간에 멈췄을 수 있다. RTM §5 「설계」 칸이 29개 중 거의 다 「—」」. 멈췄는지를 가려야 했다.
- 사용자(세션 중) — 「파트별 추천도 좋지만 **모든 기능을 나열해서** 팀원들이 확인하고 자신이 무엇을 하고 싶다를 어필할 수 있는 논의」.

## 3. 어떻게 했나 — 고른 것과 버린 것

- **고른 것 — import 하지 않는 정적 추출 + 정답과 한 번 대조.** 로컬 파이썬엔 앱 의존성이 없다(`neo4j` 없음 · 실측). 도커 이미지를 `app/`·`public/`·`alembic/` 만 모은 컨텍스트로 빌드하고(`data/` 2.9GB 를 싣지 않으려고) **네트워크를 끊은 컨테이너**에서 `app.openapi()` 만 불렀다. 처음 대조에서 2건이 달랐다 — `AlpacaTestBody | None` 선택형 본문. 고친 뒤 **145/145**(146 번째는 스키마 제외 1).
- **고른 것 — 「다리에 닿는다」 와 「기준일이 실린다」 를 갈랐다.** 처음 판정은 `/api/system/sync` · 모의투자 계좌까지 「`as_of` 가 실린다」 로 냈다 — 틀렸다. **싣는 함수 집합을 고정점으로** 구하니 정확히 6개(다리 2 · 서비스 2 · 라우트 2).
- **고른 것 — 「관문」 과 「주문」 을 갈랐다.** 관문 함수가 증권사 클래스 일곱 개를 가리켜 시세만 보는 라우트도 「주문」 이 됐다. 클래스 몸통에서는 주문을 세지 않게 했다 — 주문 3곳.
- **고른 것 — 새 스캐너는 돌연변이로 잰다.** 옛 코드가 없으니 규칙을 하나씩 망가뜨려 **의도한 시험 하나만** 떨어지는지 봤다(3건 모두).
- **고른 것 — 설계를 새로 짓기 전에 흩어진 설계부터 모았다.** 결정 대장 64행 · 분석 A5~A13 · 옛 `#61` · 분배안을 요구 ID 로 다시 묶으니 29개 중 **19개는 초안이 이미 있었다**. 진짜 빈 곳은 7개.
- **고른 것 — 옛 분석의 사실을 코드로 다시 쟀다(10가지).** 설계 초안이 이미 고쳐진 결함 위에 서면 헛돈다. 10가지 모두 그대로였다(`citations` 늘 `[]` · 리밸런싱 0 · 승률 두 벌 · LEAN 야후 …).
- **고른 것 — 요구 → API 의 정본은 설계서, API 명세서는 역방향.** 설계서 부록 A 블록만 스캐너가 읽는다(블록 밖 언급 · 낮은 판 무시 · TC-AP-13). 105/146 이 붙었다.
- **고른 것 — D9 는 파트가 아니라 카드로.** 파트 하나에 수학 · 화면 · 데이터가 섞여 있어 「이 파트는 싫지만 이 카드는 하고 싶다」 가 안 보인다. 제안 파트는 **참고 칸**으로만 두고 사람 이름은 넣지 않았다.
- 버린 것 — **문서가 뒤처지면 실패하는 시험.** 다른 파트의 PR 을 내 문서 때문에 막게 된다(팀 공용 장치는 논의 먼저 · ADR-0003). `--check` 로만 둔다.
- 버린 것 — **야후 글자를 피하려는 이름 바꾸기.** 봉인 시험은 호스트 이름을 찾는 코드도 센다. 표 한 줄로 모으고 기준선에 이유를 적었다(3줄 → 1줄).
- 버린 것 — **설계서에서 역할을 정하기.** 설계서는 「제안 파트」 만 적고, 사람은 D9 희망 → 조율안 → 전원 찬성으로 정한다.

## 6. 배운 것

- **층이 둘이면 두 층을 다 재야 한다.** S57 다리는 서비스 함수에서 「캐시 안 거침」 을 약속하고 시험으로 지켰다. 화면이 부르는 것은 라우트였고, 라우트가 그 앞에서 자기 캐시를 봤다.
- **「설계가 없다」 와 「설계가 모여 있지 않다」 는 다르다.** RTM 의 「—」 25칸 중 18칸은 논의 · 분석 글에 설계 초안이 있었다. 칸이 비었다고 일이 안 된 것이 아니라, 추적이 안 된 것이었다.
- **표만 대조하면 머리글을 놓친다.** RTM 은 세부기능 표끼리 맞추다 P01-③ 머리글(「포트폴리오 최적화 · 주식 스크리닝」)을 안 읽었다. 「대응 없음」 8개가 「머리글에만 있음」 으로 바뀌었다.
- **정답이 있으면 한 번은 맞춰 본다.** 정적 추출은 빠르지만 틀려도 조용하다. 한 번의 대조가 선택형 본문 2건을 잡았다.
- **글을 고치기 전에 올렸는지부터 본다.** 인덱스 v2 를 「안 올린 글」 로 알고 본문에 D9 줄을 넣었는데, 그날 12:31 에 이미 #47 로 올라가 있었다(사용자가 `Github-링크.md` 에 적어 둠). 게시본과 기록이 갈라지기 직전에 되돌리고 갱신 댓글 파일로 옮겼다 — 세션 첫머리의 「새 번호 확인」 을 건너뛰면 이렇게 된다.
