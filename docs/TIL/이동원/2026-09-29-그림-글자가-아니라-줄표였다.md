## 1. 무엇을 했나

- **DF-11** — 사람이 직접 돌리는 진입점 **15곳**(수집기 6 · `scripts/` 9)이 `main` 첫머리에서 표준출력 · 표준오류를 UTF-8 로 바꾼다. 수집기는 새 `collector/console.py` 의 `utf8_stdio()`, `scripts/` 는 기존 세 스크립트(`daily_update` · `post_check` · `discussion_scan`)와 같은 세 줄.
- **DF-16** — `python -m collector.preprocess` 가 DB 를 열기 **전에** argparse 로 인자를 본다. `--help` 는 설명만 찍고, 모르는 인자는 종료코드 2 로 멈춘다. 받는 인자는 여전히 없다.
- **S60 관찰(「⚠️ 상식 밖 1」)** — 주식 수가 뒷받침하는 계수(깨끗한 `shares` + 새 주식 수가 다음 기준일에도 같음)는 경고 대신 따로 센다. 요약 줄이 「⚠️ 상식 밖 0 · 상식 밖이지만 주식 수로 뒷받침 1」 이 된다.
- 시험 **117 → 138건**(TC-CE +12 · TC-DF16 3 · TC-DF01 +6). 테스트계획서는 판을 올리지 않고 6.1절에 변경 노트 다섯 줄을 쌓았다.

## 2. 왜 했나

- 일일 러너는 자식 단계에 `PYTHONIOENCODING=utf-8` 을 넣어 피하지만, **사람이 Git Bash 에서 직접 돌리는** 수집기 명령(S59 「DB 다시 만들기」 같은)은 한 글자에 죽는다. S60 에 `benchmark status` 가 그랬다.
- **도움말이 쓰기 트랜잭션을 시작하면 안 된다.** S60 에 `--help` 가 전 종목 재계산을 시작했고, 예약 회차와 겹쳐 잠금을 기다리다 멈췄다(한 트랜잭션이라 DB 는 되돌려졌다).
- 매일 같은 경고가 한 줄씩 찍히면 진짜 이상치가 그 줄에 묻힌다. 그 한 줄은 DF-01 로 **맞게 고친** 제일바이오 1,500 이었다.

## 3. 어떻게 했나 — 고른 것과 버린 것

- **고른 것 — 범위부터 다시 쟀다.** v1.2 는 `print` 안 **그림 글자**를 세어 10파일이라 적었다. 그런데 S60 에 죽인 글자는 줄표 `—`(U+2014)였다. **cp949 로 못 쓰는 글자 전체**로 다시 세니 15곳 — 더해진 다섯은 `collector/backfill.py`(러너 첫 단계) · `verify_fill_sync` · `verify_jwt_revocation` · `verify_trading_cost` · `take_screenshots` 다. 다섯 다 내가 쓴 파일이라 파트 경계 안이다.
- **고른 것 — 시험은 `--help` 로 진입점을 실제로 탄다.** argparse 는 본문 전에 끝나서 DB · 네트워크 없이 `main` 을 지난다. 끝에 `✅ —` 한 줄을 더 찍게 해서, 도움말이 우연히 cp949 로 써지는 모듈(manifest · rtm_scan · schema_scan)도 잡는다.
- **고른 것 — 자식 프로세스 안에서 `db.connect` · `sqlite3.connect` 를 먼저 막았다.** 옛 `preprocess` 는 `--help` 를 보지 않고 전 종목 재계산을 시작한다. DF-16 을 재현하는 시험이 DF-16 사고를 되풀이하면 안 된다.
- **고른 것 — 정적 검사를 짝으로 뒀다.** 파일마다 고치면 새 파일이 또 빠진다(S54 에 둘 · S60 재측정에 열 · 오늘 다섯). `__main__` 이 있고 cp949 밖 글자를 찍는데 UTF-8 설정이 없으면 실패한다.
- **고른 것 — `shares` 를 통째로 빼지 않았다.** 비율이 50 을 넘으면 「깨끗한 비율」 검사(`RATIO_TOL` 0.01)가 **늘 통과**한다 — 가장 가까운 정수와의 차이는 0.5 를 넘지 않으니 0.5 ÷ n ≤ 0.01. 재개일 하루만 주식 수가 잘못 찍혀도 깨끗한 `shares` 가 된다. 그래서 「다음 기준일에도 같은 주식 수」 로 좁혔다(1.4절 S59 원칙 — 예외는 좁게, 몇 건인지 늘 찍는다).
- 버린 것 — **확인된 사건 목록(허용 목록).** 가장 좁지만 새 사건마다 코드를 고쳐야 한다. 지속성 규칙이 같은 일을 자료로 한다.
- 버린 것 — **`preprocess` 에 `--codes` 같은 인자 더하기.** 결함은 「인자를 안 본다」 였지 「인자가 모자란다」 가 아니었다. 오히려 `--codes 005930` 을 「모르는 인자」 시험 입력으로 썼다 — 다른 수집기 명령에 있어서 가장 짐작하기 쉬운 인자다.
- 버린 것 — **`scripts/` 도 공용 도우미로.** 경로로 실행되고 셋(rtm_scan · schema_scan · take_screenshots)은 저장소 모듈을 전혀 안 가져온다. 도우미를 쓰려면 `sys.path` 손질이 새로 생긴다.
- 버린 것 — **사용자 셸에 `PYTHONUTF8=1` 을 켜기.** 내 셸은 고쳐지지만 팀원 셸은 그대로다.

## 4. 어떻게 확인했나

- **옛 코드에서 먼저 돌렸다** — 새 21건 중 **16 실패 · 5 통과.** 통과 5건(TC-DF16-03 · TC-DF01-16~19)은 전부 「건드리면 안 되는 쪽」 이다. 실패는 이유까지 진입점마다 뽑았다 — `--help` 자체가 죽음 7(`—` 5 · `⚠` 2) · 도움말 뒤 출력에서 죽음 3 · DB 를 열려다 막힘 1. 돌리는 동안 수집 DB 세 파일 시각은 그대로였다.
- **새 코드** — Postgres(15432) 붙여 **138/138**(67초) · DB 없이 **132 통과 · 6 건너뜀**(S59 이후 처음 다시 잼).
- **시험 밖에서 한 번 더** — cp949 셸 조건으로 `benchmark status` **종료코드 1 → 0** · `preprocess --help` 0 · `--codes 005930` 2 · DB 세 파일 시각 전후 같음.
- **실제 DB 읽기 전용 전수**(48초) — 이벤트 2,699(분할 1,403 · 권리락 1,045 · 확인 필요 249 · shares 2)가 오늘 09:06 로그와 한 건도 다르지 않다. 상식 밖은 052670 20260209 ×1,500 하나이고, 다음 기준일 20260210 도 19,419 주라 「뒷받침」 이다.

## 5. 막힌 것 · 남은 것

- 인자 없이 곧바로 Postgres · Redis · 브라우저를 여는 4곳(`verify_*` 3 · `take_screenshots`)은 **정적 검사로만** 지킨다 🟡.
- `shares` 의 「선언된 병합 비율」 은 n ≥ 50 이면 검증이 아니다 — 제일바이오 1,500 도 주식 수 비율 1,500.03 을 반올림한 값이고 감자 공시와 대조하지 않았다(6.1절 관찰 · DF-01 가장자리).
- 매일 로그에 「⚠️ 확인 필요」 249줄이 찍힌다. 같은 「묻힘」 문제지만 이번 범위 밖이다 🟡.
- 12:30 예약 회차는 **그 시각 작업 트리의 코드**로 돈다. 이 변경은 DB 에 쓰는 값을 바꾸지 않는다 — 요약 줄 문구만 바뀐다.

## 6. 배운 것

- **센 방법이 범위를 정한다.** 「그림 글자」 로 세면 10, 「cp949 로 못 쓰는 글자」 로 세면 15. 실제로 죽인 글자는 그림 글자가 아니었다. 증상을 일으킨 글자로 세야 한다.
- **결함을 재현하는 시험이 그 결함을 되풀이하면 안 된다.** DF-16 시험을 옛 코드로 그냥 돌렸다면 전 종목 재계산이 한 번 더 시작됐다. 막는 장치를 먼저 두고 돌렸다.
- **상대 오차 기준은 큰 수에서 무력해진다.** 「정수에서 1% 안」 은 2:1 에서는 엄격하지만 1,500:1 에서는 아무것도 거르지 않는다.
