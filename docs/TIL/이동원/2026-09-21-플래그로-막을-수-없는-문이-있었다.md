# 플래그로 막을 수 없는 문이 있었다 — 실거래를 막고, 막혔는지 검사할 장치를 세운 날

> 2026-09-21 (월) · Qurious 2.0 · 실거래 주문 차단 + CI 게이트
> 관련 PR: `fix/live-trading-guard-and-ci`

## 한 줄

**막아야 할 문이 1개인 줄 알았는데 3개였고, 그중 하나는 자물쇠가 아예 들어가지 않는 문이었다.**
그리고 문을 잠근 뒤에야, 잠겼는지 확인할 사람이 이 저장소에 **아무도 없다**는 걸 알았다.

---

## 1. 무엇을 막아야 했나

발주 요구사항(`docs/rfp-2.md`) §4.2 **제외 범위**의 첫 줄이 이렇다.

> - 실제 증권 계좌를 통한 실거래 자동 주문 실행

즉 이 프로젝트는 **모의투자까지**다. 실제 돈이 움직이면 범위를 벗어난다.
그런데 코드는 실거래를 낼 수 있는 상태였다.

> **용어 — 모의투자(paper trading)**
> 증권사가 따로 운영하는 **연습용 서버**에 주문을 낸다. 체결·잔고가 실제처럼 계산되지만
> 돈은 움직이지 않는다. 한국투자증권은 실전이 `openapi.koreainvestment.com:9443`,
> 모의가 `openapivts.koreainvestment.com:29443` 으로 **주소부터 다르다.**
> **이 문서에서는** "실계좌에 닿지 않는 상태"를 뜻한다.
> **헷갈리는 점**: `paper=True` 는 *연습*, `paper=False` 가 *실제*다. 이름만 보면
> 반대로 읽기 쉽다 — "페이퍼(서류)니까 진짜?" 가 아니라 **"종이 돈"** 쪽이다.

---

## 2. 문이 1개인 줄 알았다

세션 프롬프트에 적힌 지시는 이랬다.

> `auto_trade.py:187 get_broker_client(..., paper=False)` · 차단이 `quant_mode != "live"` 한 줄뿐.
> **한 줄 + 설정 1개**

한 줄 고치면 되는 일로 보였다. 그래서 고치기 전에 **같은 모양의 다른 곳**을 먼저 훑었다.
세 갈래가 나왔다.

| # | 경로 | 어떻게 실계좌로 가나 |
|---|------|---------------------|
| 1 | `auto_trade.py:183` 자동매매 | `paper=False` 를 **코드에 박아** 넘긴다 ← 프롬프트가 지목한 곳 |
| 2 | `stocks.py:639` **수동 주문 API** | DB 칸 `broker_settings.paper` 를 **그대로** 넘긴다 |
| 3 | `ebest.py` LS증권 | `paper` 인자를 **아예 받지 않는다** |

2번이 서늘했다. 코드를 한 줄도 고치지 않고, **DB 칸 하나만 `False` 로 두면** 실계좌로 나간다.
1번만 고쳤다면 "막았다"고 보고했을 텐데, 사실은 절반만 잠근 것이다.

### 2.1 자물쇠가 들어가지 않는 문

3번은 성격이 달랐다. `EBestClient` 를 열어 보면 주소가 하나뿐이다.

```python
BASE_URL = "https://openapi.ebestsec.co.kr"   # 모의도 실전도 같은 곳
```

LS증권은 모의투자 서버가 따로 없다. 그래서 `paper=True` 를 **건네줄 자리 자체가 없고**,
건네줘도 갈 곳이 실서버 하나뿐이다.

여기서 배운 것:

> **플래그로 막았다고 믿는데 막히지 않는 것은, 아예 막지 않은 것보다 나쁘다.**
> 안 막은 건 알고 조심하지만, 막았다고 믿으면 마음 놓고 버튼을 누른다.

그래서 3번은 플래그가 아니라 **클라이언트 자체를 Mock 으로 갈아 끼웠다.** 자물쇠가 안 들어가면
문을 바꾸는 수밖에 없다.

## 3. 왜 호출부가 아니라 팩토리에 걸었나

세 곳을 각각 고칠 수도 있었다. 그러지 않은 이유는 **네 번째 경로**다.

```
[ 전 ]  호출부마다 따로 막는다 → 새 경로가 생기면 또 빠진다

  auto_trade ──┐
               ├──→ get_broker_client() ──→ 실전 서버  🔴
  stocks     ──┘


[ 후 ]  모두가 지나는 목에 관문을 둔다

  auto_trade ──┐     ┌─────────────────────┐
               ├─────┤ 승인 없으면:          │
  stocks     ──┤     │  paper=False → True   │──→ 모의 서버  ✅
               │     │  ebest → Mock         │
  (앞으로 생길)─┘     └─────────────────────┘
```

호출 지점을 세는 방식은 **오늘 있는 세 곳**만 막는다. 팩토리는 증권사 클라이언트를 만드는
유일한 통로라, 여기 한 번 걸면 **내일 생길 경로까지** 같이 걸린다.

여는 열쇠는 환경변수 하나다.

```bash
export QURIOUS_ALLOW_LIVE_TRADING=1   # 이것을 넣는 것은 실수로 일어나지 않는다
```

`.env` 도 설정 파일도 아니고 **환경변수**로 한 이유는, 저장소에 흔적이 남지 않기 때문이다.
설정 파일에 두면 커밋되고, 커밋되면 팀원 전부의 환경이 열린다.

## 4. 막혔다는 걸 누가 확인하나 — 아무도 없었다

여기서 두 번째 발견이 나왔다.

| 점검 | 실측 |
|------|------|
| `tests/` 디렉터리 | **없음** |
| 자동화 시험 | **0건** |
| `.github/` | **없음** |
| 저장소 룰셋 | `[]` |
| `main` 브랜치 보호 | API `404` |

즉 **`main` 에 직접 푸시해도 아무것도 막지 않는 상태**였다. 규칙 문서에는 「main 직커밋 금지」라고
적혀 있었는데, 그걸 강제하는 장치는 없었다.

> **규칙이 문서에만 있으면 규칙이 아니라 희망이다.**

우리 팀은 넷의 작업 시간대가 달라 PR 에 **사람 승인을 필수로 걸 수 없다.** 기다리면 멈춘다.
사람이 못 막으면 **코드가 막아야 한다.** 그래서 시험 23건과 CI 워크플로를 만들었다.

### 4.1 시험을 짜면서 배운 것 — 통과가 통과가 아닐 때

차단 시험을 짤 때 조심한 함정이 셋이었다.

**(1) 내 셸에 승인 변수가 남아 있으면 시험이 거짓 통과한다.**
그래서 `conftest.py` 가 매 시험마다 그 변수를 지운다. 실제로 변수를 켜 둔 채 돌려 보니
23건이 그대로 통과했다 — 격리가 도는 것이다.

**(2) "항상 막힘" 과 "승인하면 열림" 은 다른 이야기다.**
차단만 시험하면, 기능이 **죽어 있어도** 통과한다. 그래서 짝으로 시험했다.
승인하면 실전 URL 이 나오는지도 확인한다.

**(3) 막는 게 과하면 목표가 죽는다.**
이 프로젝트의 목표가 *모의투자*(rfp-2 Phase 5)다. `paper=True` 요청까지 막으면
차단이 아니라 고장이다. 그래서 "모의투자는 그대로 통과한다"도 시험에 넣었다.

### 4.2 시험이 첫날 잡아낸 것

처음 돌렸더니 **1건 실패**했다. `paper=False` 하드코딩이 남아 있다는 것이었다.
열어 보니 **관문 파일 자신의 설명문**이었다. 무엇을 막는지 적으려면 그 문자열을 써야 한다.

막아야 할 하드코딩이 아니라 **정의**였으므로 제외하고, 왜 제외했는지를 시험에 적었다.
시험이 없었다면 "전부 지웠다"고 믿었을 자리다.

### 4.3 아직 안 끝났다

워크플로를 만들었다고 게이트가 되는 게 아니다.

> **워크플로는 검사를 *실행할 뿐*이고, 그 결과를 병합 조건으로 삼는 것은 룰셋이다.**

룰셋은 저장소 **설정 변경**이라 내가 건드리지 않는다(계정 정지 이력 · 프로젝트 규칙).
그래서 절차서를 `docs/배포/CI-CD명세_v1.0.md` 4절에 적고 스위치는 남겨 뒀다.
**CI 는 준비됐고, 올리는 일만 남았다.**

## 5. 덤으로 나온 것 — 같은 사고가 두 번째다

산출물 목록을 만들다가 계획서 v1.1 파일이 안 보였다. 확인해 보니 **S39 의 커밋 5개가
main 에 없었다.**

```
   05:23:49  PR #57 ──merge──→ main        ✅
   05:23:57  PR #58 ──merge──→ #57 브랜치   ❌ 이미 떠난 배에 짐을 실었다
```

`#58` 의 base 가 `main` 이 아니라 `#57` 의 브랜치였다. 순서대로 `#57` 을 먼저 머지했는데,
**먼저 머지했기 때문에** 8초 뒤 `#58` 이 들어간 브랜치는 이미 main 과 상관없는 가지가 돼 있었다.

main 에 빠진 것 중엔 문서만 있는 게 아니었다.

- `5afc2d1` — ETF 면제 배선. **매도 정산 0.20%p 과대 계상**이 main 에 그대로 남아 있다
- `edb60d1` — HF 업로드를 4시간 반 막던 한글 `license_name` 수정

그리고 이건 **재발**이다. PR #44 가 같은 사유로 열렸었다 — "머지 순서가 어긋나 orders 확장이
main 에 빠졌다".

> 같은 사고가 두 번 나면 그건 실수가 아니라 **구조**다.
> 스택 PR 은 "순서대로 머지" 로 충분하지 않다. **위 PR 의 base 를 main 으로 바꾼 뒤** 머지해야 한다.

GitHub 은 base 브랜치가 이미 머지됐어도 그 브랜치로의 머지를 막지 않는다. 사람이 기억해야
하는 규칙인데, 두 번 다 기억하지 못했다. 다음 판에서 CI 로 검사할 수 있는지 살펴본다.

## 7. 세 문장 요약

1. **막아야 할 문을 세기 전에 문을 세어 봐야 한다.** 1개인 줄 알았던 것이 3개였고,
   그중 하나는 자물쇠가 들어가지 않는 문이었다.
2. **막았는지 확인하는 장치가 없으면 막은 게 아니다.** 시험 0건 · 게이트 0개인 저장소에서
   "고쳤다"는 말은 아무것도 보증하지 않는다.
3. **같은 사고가 두 번 나면 사람을 탓할 게 아니라 장치를 만들어야 한다.** 머지 순서 사고는
   오늘로 두 번째다.
