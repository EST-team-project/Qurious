## 1. 무엇을 했나

- **화면의 「한 단계 다시」 · 「전체 수집」 을 앱이 직접 돌리지 않게 했다.** 앱은 컨테이너 안에서 수집 폴더를 읽기만 하고 러너는 이 PC 의 프로세스라, 앱은 요청 표(`collect_requests`)에 줄만 남기고 PC 작업자(`scripts/collect_worker.py`)가 매 분 와서 가져가 러너를 부른다. Airflow · Dagster · GitHub 러너가 쓰는 꼴(웹은 요청만 · 실행 쪽이 가져감)과 같고, 이 PC 에 새로 여는 포트가 없다.
- **API 넷(`API-DATA-12 ~ 15`)** — 만들기 · 목록 · 취소 · 작업자 상태. 관리자만이고, 상태를 바꾸는 둘은 화면 머리글(`X-Qurious-Action: collect`)이 더 있어야 한다. 같은 요청은 한 번만(새 줄 202 · 있으면 그 줄 200), 목록 밖 단계는 422, 대기가 아니면 취소 409.
- **표 둘 · 이전 `0018`(#88 번호 규칙)** — 상태를 바꾸는 함수는 `app/services/collect_requests.py` 한 곳에 두고 앱 API 와 작업자가 같이 쓴다.
- **러너** — 「지금은 못 돈다」 를 종료코드 75(EX_TEMPFAIL)로 가르고, 막는 때를 `guard_window` 한 함수로 세며, 수동 회차(전체 수집 · 11:00 ~ 13:30 막음)와 이력 줄의 요청 번호 · 종료코드 · 로그를 더했다.
- **시험** — TC-CQ 15 · TC-CW 12 · TC-DU +5. 저장소 밖 사본에서 31곳을 깨 31곳 모두 잡았고, 12:30 정기 회차 실측에서 찾은 겹침(아래)을 고친 뒤 32번째로 깨 봤다.

## 2. 막힌 것 · 알게 된 것

- **같은 종료코드가 두 뜻이면 작업자가 판단할 수 없다.** 한 단계 다시의 「막힘(회차와 겹침 · 다른 실행)」 이 3 이었는데, 달력 단계의 공휴일 받기 실패 · 신호 단계의 앱 DB 꺼짐도 3 이다. 작업자는 막힘이면 다시 기다리고 실패면 결과를 적어야 하는데 3 으로는 가를 수 없어 막힘을 75 로 옮겼다.
- **조사안과 사용자 결정이 다르면 숫자가 줄줄이 바뀐다.** 조사는 「로그온할 때 하나 · 30초 꺼짐 · 10분 만료 · 꺼지면 503」 이었지만 사용자는 「매 분」 을 골랐다. 그래서 꺼짐 판정은 3분, 만료는 3시간(전체 수집의 막는 때 150분을 기다려도 남게), 꺼진 때도 요청은 받고 「대기 — PC 작업자 꺼짐」 이 됐다(조사서 3.10절 표).
- **같은 셈을 두 곳에 두면 어긋난다.** 막는 때를 앱이 따로 세게 쓰다가 멈췄다 — 앱 이미지에는 `scripts/` 가 없어 러너 함수를 부를 수 없다. 러너가 셈해 단계 목록 파일에 싣고 앱은 그대로 보인다.
- **위험한 시험도 있다.** `--request` 검사 시험은 검사를 깨면 진짜 회차를 돌릴 수 있었다. 러너 함수를 「부르면 실패」 로 바꿔 끼웠다. 막힌 요청을 같은 바퀴에 다시 잡게 깨면 시험이 끝없이 돌 수 있어, 가짜 러너에 「다섯 번 넘게 부르면 멈춤」 을 넣었다.
- **사람이 읽는 글은 실제 회차에서 한 번 읽어야 한다.** 12:30 정기 회차가 도는 동안 작업자 상태 글이 「다른 실행이 돌고 있다 — 다른 실행이 돌고 있다 (PID …) · 끝나면 돈다」 였다. 러너가 준 까닭 앞에 같은 말을 또 붙인 것이고, 시험은 「들어 있나」 만 봐서 못 잡았다(DF-93). 회차가 끝난 뒤(도는 동안은 `scripts/` 를 고치지 않는다) 한 줄 고치고 시험에 「한 번만 · 끝말」 확인을 더했다.
- **새 표가 사용자 표를 가리키면 탈퇴가 그 줄을 지운다.** 탈퇴 코드는 모델 메타데이터에서 사용자를 가리키는 칸을 모두 찾는다. 수집 요청은 감사 기록처럼 운영 기록이라 줄은 남기고 요청자 칸만 비우는 표 목록에 넣었다.

## 3. 원칙으로 다시 보기

- **멱등성** — 같은 대상(종류 + 단계)의 활성 줄은 하나다. 정본은 DB 부분 고유 색인이고 서비스는 `INSERT … ON CONFLICT DO NOTHING` 뒤 있던 줄을 돌려준다. 두 관리자가 동시에 눌러도 한 줄이다(TC-CQ-09 · 12).
- **원자성** — 요청 줄과 감사 줄은 한 트랜잭션이다. 상태 바꾸기는 모두 「지금 상태가 X 일 때만」 조건 UPDATE 라, 두 작업자가 같은 줄을 가져가려 하면 DB 가 하나만 통과시킨다(TC-CQ-13 — 둘 중 하나만 성공).
- **SSoT** — 막는 때는 `guard_window` 하나 · 상태 전이는 서비스 한 곳 · 앱 DB 주소는 compose 한 곳(작업자도 같은 함수).
- **말없는 fallback 금지** — 러너 기록에 요청 줄이 없으면 「끝」 이 아니라 실패 「결과 기록 없음」 이다. 꺼진 작업자는 「대기 — PC 작업자 꺼짐」 으로 보인다.
