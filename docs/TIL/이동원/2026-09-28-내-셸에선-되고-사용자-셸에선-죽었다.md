## 1. 무엇을 했나

- `daily_update.py`·`post_check.py` 가 표준출력·표준오류를 **UTF-8 로 맞추고** 시작하게 했다(두 줄 · 저장소에 이미 있던 `discussion_scan.py` 방식).
- 사용자 셸 조건(`PYTHONIOENCODING=cp949`)을 고정한 시험 3건을 더했다.
- 기록 색인과 TIL 목록에 #19 · #23 · #24 · #25 를 채웠다. S52·S53 TIL 세 장의 「번호는 올린 뒤」 칸도 채웠다.

## 2. 왜 했나

- 세션을 시작하며 git bash 에서 `python scripts/daily_update.py status | head -5` 를 돌렸더니, 한글은 `▒▒` 로 깨지고 첫 ✅ 에서 `UnicodeEncodeError: 'cp949'` 로 죽었다. 같은 명령이 Claude 셸에서는 멀쩡했다.
- 원인을 찾아 보니 **`post_check.py` 도 같은 자리에서 죽는다.** PR 블록의 「올릴 글 검사(초과 0 이어야 함)」 단계가 S51~S53 블록에 5번 들어 있었는데, 사용자 셸에서는 **한 번도 끝까지 돌지 않았다.** 블록에 `set -e` 가 없어서 오류가 화면에 지나가고 다음 줄이 그대로 돌았다.
- 올라간 글이 한도를 넘은 일은 없었다. Claude 가 자기 셸에서 따로 재 봤기 때문이다(오늘 09-28 폴더 9개 · 초과 0). 검사가 두 겹이었던 덕에 운 좋게 막힌 셈이다.

## 3. 어떻게 했나 — 고른 것과 버린 것

- **원인**: git bash(mintty)는 파이썬에게 콘솔이 아니라 파이프다. 파이썬은 파이프에 쓸 때 로케일 인코딩(한국어 Windows = cp949)을 고르는데, ✅(U+2705)는 cp949 에 없다. Claude 의 셸에는 `PYTHONIOENCODING=utf-8` 이 잡혀 있었다(실측 · 사용자 셸에는 없다).
- **고른 것 — 스크립트가 스스로 맞춘다.** 누가 어느 셸에서 돌려도 같은 결과가 나온다. `hasattr(stream, "reconfigure")` 로 거르므로, 작업 스케줄러의 `pythonw`(표준출력이 None)는 그대로 지나간다.
- 버린 것 ① **사용자 `~/.bashrc` 에 `PYTHONUTF8=1`** — 이 PC 만 고쳐진다. 팀원이 같은 스크립트를 돌리면 같은 자리에서 죽는다.
- 버린 것 ② **블록마다 `python -X utf8 …`** — 명령이 길어지고, 한 번만 빠뜨려도 다시 조용히 죽는다.
- 버린 것 ③ **이모지를 찍는 스크립트 7개를 전부 고치기** — 사용자 블록에 들어가는 것은 이 둘뿐이다. `hf_dataset.py` 는 러너가 자식에게 `PYTHONIOENCODING=utf-8` 을 넣어 주고, 나머지는 Claude 가 돌린다. 한 PR 에 한 가지만 한다.

## 4. 어떻게 확인했나

- **고치기 전에 시험이 실패하는 것을 먼저 봤다.** cp949 시험 3건 중 2건이 옛 코드에서 `UnicodeEncodeError` 로 실패했다. 나머지 1건(pythonw 는 표준출력이 없다)은 원래 통과했다. 고친 뒤에는 3건 모두 통과했다.
- Claude 셸에서 `env -u PYTHONIOENCODING` 으로 사용자 조건을 흉내 내 `status` 를 돌렸다 → 종료코드 0 · ✅ 줄까지 다 나온다.
- 전체 시험: **48 통과 · 6 건너뜀**(Postgres 시험 · DB 주소 없음). 이 PR 이 더한 시험은 3건이다.
- 12:30 예약 회차는 **고친 작업 트리 코드**로 돌았다(작업은 작업 트리의 지금 브랜치 코드를 돈다) → ✅ 3분 13초 · 파생 3단계 「새 자료 없음」 건너뜀 · 업로드 파케이 2개(`raw_response` 12,709 → 12,712행) · HF 커밋 `40c13d5a` · 원격 = 매니페스트. `pythonw` 에서 `utf8_stdio()` 가 조용히 지나간 것을 실제로 확인했다.
- 같은 날 두 번째 업로드라 태그 `snapshot-2026-09-28` 은 11:43 커밋(`6d612d36`)에 그대로 있다 — 「이미 있으면 그대로 둔다」 설계대로다.

## 5. 막힌 것 · 남은 것

- **0-B(계정 공개 상태 확인) 네 줄이 전부 403** 이었다. flagged 의 신호는 404 인데, 403 은 그와 다르다. 가장 흔한 원인은 로그인 없는 조회의 IP당 시간당 60회 한도다(같은 공유기를 쓰면 한도도 나눈다). 같은 시각에 `git fetch` 는 됐다. **약 35분 뒤(12:37 무렵) 다시 돌리니 404 · 200 · 200 · 200 으로 정상**이었다 — 일시적이었다. 원인(한도인지)은 메시지를 못 찍어 확인하지 못했다 🟡. 다음 0-B 부터 403 이면 메시지와 한도가 풀리는 시각을 함께 찍는다.
- **긴 블록 붙여넣기가 깨졌다.** 두 번째 0단계에서 붙여 넣은 글 앞에 이전 터미널 화면(프롬프트 줄 · 지난 출력)이 섞여 `bash: $: command not found` · `syntax error near '('` 가 났다. 명령은 돌았지만 끝에서 `>` 에 걸렸다. → 커밋·push·PR 은 **단계별 `.sh` 파일**로 건네 `bash 파일` 한 줄로 돌리게 바꿨다(`_git-drafts/2026-09-28-S54/*.sh`).
- **HF 는 끊기지 않았다.** 세션이 바뀐 사이에 멈췄을까 봐 확인했다. 원격 최신 커밋은 `6d612d36`, 태그는 `snapshot-2026-09-28` 이고, 원격이 로컬 매니페스트와 같다. 잠금 파일도 남지 않았다.
- **정정** — [단계마다 멈춘 날이 달랐다](2026-09-28-단계마다-멈춘-날이-달랐다.md)에 「남은 것: 올리는 사람을 한 명으로 정하는 것(팀 합의)」이라고 적었다. 이제 정해졌다. **데이터 파트(이동원)가 올린다.** 규칙 5(고치지 않는다)에 따라 그 TIL 은 두고 여기서 바로잡는다.
- 남은 것: 이모지를 찍는 나머지 스크립트 5개(`hf_dataset` · `probe_kis_fee_rate` · `rtm_scan` · `schema_scan` · `sync_fills`)는 사람이 git bash 에서 직접 돌리면 여전히 죽는다. #14 v0.2 댓글을 올렸는지도 아직 색인에 적지 못했다.

## 6. 배운 것

- **「내 셸에서 통과」는 「사용자 셸에서 통과」가 아니다.** 환경이 다르면 시험 조건으로 고정한다(`PYTHONIOENCODING=cp949`). 그러면 어느 OS 의 CI 에서도 같은 결과가 나온다.
- **조용히 죽는 검사는 없는 검사와 같다.** 블록은 한 줄이 실패해도 다음 줄로 넘어간다. 그래서 「통과해야 다음으로」인 단계는 출력이 아니라 **끝까지 돌았는지**부터 본다.
