## 1. 무엇을 했나

로그아웃한 토큰을 적어 두는 **폐기 목록**(denylist — 아직 만료 시각은 안 됐지만 무효로 칠
토큰 명단)의 키를 `token[:32]` 에서 `jti` 로 바꿨다. 그 과정에서 같이 걸려 있던 결함 네 개를
더 고쳤다. 6개 파일 · 341줄 추가 · 38줄 삭제. 그중 180줄은 검증 스크립트다.

| 무엇 | 어디 |
|---|---|

| 자리표시자 비밀값 가드 `_require_real_secret` | [`jwt_auth.py:56`](https://github.com/devlee328288/Qurious/blob/0efdad9/app/lib/jwt_auth.py#L56) |

`requirements.txt` 의 `python-jose` 하한을 `>=3.3.0` → `>=3.4.0` 으로 올렸다
(CVE-2024-33663·33664 · #22 결함 11). 다만 두 CVE 는 JWE·비대칭키 경로라 HS256 만 쓰고
`algorithms` 를 명시하는 우리 코드의 실제 노출은 아니다. 상한도 락파일도 없어 빌드마다
버전이 달라지니 바닥만 올려 둔 것이다.

DB·화면(`public/`)·나머지 39개 엔드포인트는 한 줄도 안 바뀐다.

## 2. 왜 했나

#22 에 11건을 적어 놓고 사흘(09-17 → 09-20) 동안 하나도 고치지 않고 있었다.
그중 이것 하나만 실제 피해가 "전 사용자, 최대 7일"이다.

JWT 는 점으로 나뉜 세 토막인데, **앞 토막은 "무슨 알고리즘을 썼는지"만 적힌 머리말**이라
같은 설정을 쓰는 한 모든 사람의 토큰에서 글자까지 같다. HS256 의 그 머리말은 36자다.

```
                         ← 폐기 이름표로 쓰던 앞 32자 →
┌────────────────────────────────────┬─────────────────────┬──────────┐
│ eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9│ eyJzdWIiOiJ1c2Vy... │ K3xT9v…  │
│ ① 머리말 — 누구나 똑같다 · 36자     │ ② 알맹이(누구인지)  │ ③ 서명   │
└────────────────────────────────────┴─────────────────────┴──────────┘
                                   31│32
                                     └─ 32에서 끊으면 ① 안에서 끝난다
```

그래서 Redis 에 `jwt_bl:` 로 시작하는 키가 **하나밖에 존재할 수 없었다.**
누가 로그아웃하든 그 하나가 켜지고, 전원의 토큰 검사가 거기에 걸린다.
게다가 리프레시 토큰을 넣고 로그아웃하면 TTL 이 그 토큰의 남은 수명인 **7일**로 잡힌다.

`32` 라는 숫자가 잘못된 게 아니다. **"길이로 잘라도 고유하겠지"라는 가정**이 잘못이었고,
그 가정은 토큰의 구조를 한 번만 들여다봤으면 깨졌을 것이다. 나는 그걸 안 했다.

## 3. 어떻게 했나 — 고른 것과 버린 것

### 3.1 이름표를 무엇으로 할 것인가

| 선택지 | 결과 | 이유 |
|---|---|---|
| `token[:64]` 로 길이만 늘리기 | 버림 | 증상만 미룬다. 알맹이 앞부분도 클레임 순서가 같으면 겹칠 수 있고, 아래 변조 문제가 그대로 남는다 |
| `sha256(토큰 전체)` | 버림 | OWASP JWT Cheat Sheet 가 **명시적으로 반대**한다 (아래 3.2) |
| `sha256(머리말.알맹이)` | 부분 채용 | `jti` 가 없는 **옛 토큰**의 폴백으로만. 서명 앞까지는 HMAC 입력 바이트 그 자체다 |
| **`jti`(uuid4)** | **고름** | RFC 7519 §4.1.7 의 고유 식별자. OWASP 가 폐기 키로 권하는 값 |
| 사용자 단위 폐기(epoch) | 버림 | 이번 범위가 아니다. "한 사용자의 모든 토큰"을 끊는 건 별개 기능이고 DB 가 필요하다 |
| 리프레시 회전(RFC 9700 §4.14.2) | 버림 | 클라이언트 변경을 부른다. `jti` 가 생겼으니 다음에 할 수 있다 |

구현은 [`jwt_auth.py:154`](https://github.com/devlee328288/Qurious/blob/0efdad9/app/lib/jwt_auth.py#L154).

### 3.2 왜 `sha256(토큰 전체)` 가 아닌가 — malleability

**malleability**(가단성): 뜻은 그대로인데 글자는 바꿀 수 있는 성질을 말한다.
여기서는 **서명 토막의 base64 표현**을 가리킨다. 서명이 덮는 범위는 `머리말.알맹이` 까지이고,
서명 토막 자신은 그 바깥이라 같은 서명을 여러 문자열로 쓸 수 있다.

토큰 전체를 해싱하면 한 글자만 바꾼 변조본이 **다른 해시**가 되어 폐기 목록을 비켜 간다.
서명 검증은 그대로 통과하니까 그 토큰은 살아난다.

조사 중 python-jose 3.5.0 · HS256 에서 같은 서명이 서로 다른 여러 문자열로 통과하는 것을
직접 재 봤다. 문서에 적힌 위험이 아니라 우리가 쓰는 버전에서 실제로 일어난다.

### 3.3 고치다 나온 함정 셋 — 이게 이번의 본론이다

`jti` 를 넣기만 하면 끝날 줄 알았다. 아니었다. **셋 중 하나라도 놓쳤으면 같은 결함이
범위만 좁혀서 되살아났을 것이다.**

| # | 함정 | 안 고쳤다면 되살아나는 모습 | 어떻게 |
|---|---|---|---|
| ① | `create_token_pair` 가 **같은 payload 를 두 번** 쓴다 ([`jwt_auth.py:117`](https://github.com/devlee328288/Qurious/blob/0efdad9/app/lib/jwt_auth.py#L117)) | 액세스와 리프레시가 같은 `jti` → 하나를 폐기하면 둘 다 죽는다 | `jti` 를 생성 함수 **안에서** 민팅. 호출부 값은 일부러 덮어쓴다 |
| ② | refresh 가 클레임을 통째로 복사한다 (`type/iat/exp` 만 뺐다) | 리프레시의 `jti` 가 새 액세스에 상속 → **한 사용자의 모든 토큰이 한 이름표** | 제외 목록에 `jti` 추가 ([`auth.py:227`](https://github.com/devlee328288/Qurious/blob/0efdad9/app/routes/auth.py#L227)) |
| ③ | python-jose 는 `exp` 가 없으면 만료 검사를 **건너뛴다** (`require_exp` 기본값 False) | 만료도 폐기도 안 되는 **영구 출입증** | `options={"require_exp": True}` ([`jwt_auth.py:144`](https://github.com/devlee328288/Qurious/blob/0efdad9/app/lib/jwt_auth.py#L144)) |

①과 ②는 "전역 이름표"가 각각 "토큰 쌍 단위 이름표", "사용자 단위 이름표"로 축소된 것일 뿐
성질이 같다. 범위가 작아졌다고 고쳐진 게 아니다.

③은 성격이 다르다. **라이브러리의 기본값이 안전한 쪽이 아니었다.** 나는 `jwt.decode` 가
당연히 만료를 본다고 믿었는데, 볼 클레임이 없으면 그냥 넘어간다.

### 3.4 검사 순서를 바꾼 것

```
[ 전 ]  요청 → is_revoked(토큰 앞 32자) → decode(서명검증) → 통과
               └ 서명도 안 본 문자열로 이름표를 만든다

[ 후 ]  요청 → decode(서명검증 + exp 필수) → type 확인 → is_revoked(jti) → 통과
               └ 서명이 검증된 알맹이에서만 이름표를 꺼낸다
```

이건 "정리"가 아니라 **경계**다. 검증 전 문자열로 키를 만들면 공격자가 조회할 키를 직접
지목할 수 있다. [`jwt_auth.py:200`](https://github.com/devlee328288/Qurious/blob/0efdad9/app/lib/jwt_auth.py#L200) 에 주석으로 이유를 남겼다.

### 3.5 폐기 API 자체에 인증이 없었다

`POST /auth/token/revoke` 는 누구나 부를 수 있었고, 오프라인 표시 대상을 **본문 토큰의 id**
에서 가져왔다. 남을 오프라인으로 만들 수 있었다는 뜻이다.
호출자 인증(`Depends(get_current_user_any)`)과 소유권 확인(주인 ≠ 호출자면 403)을 넣었고
([`auth.py:238`](https://github.com/devlee328288/Qurious/blob/0efdad9/app/routes/auth.py#L238)),
`mark_offline` 은 호출자 자신에게만 한다
([`auth.py:272`](https://github.com/devlee328288/Qurious/blob/0efdad9/app/routes/auth.py#L272)).

여기서 하나 아낀 게 있다. 인증을 새로 짜지 않고 이미 있던 `get_current_user_any` 를 그대로
걸었다. 이 의존성은 **Bearer 와 쿠키 세션을 둘 다 받는다** — 그래서 화면으로 로그인한
사용자도 이 API 로 자기 JWT 를 끊을 수 있다. 시그니처가 그대로라 같은 의존성을 쓰는 나머지
39개 엔드포인트는 손댈 일이 없었다.

## 4. 어떻게 확인했나

임시 Redis 하나를 띄우고 `scripts/verify_jwt_revocation.py` (180줄) 를 돌렸다.
**통과 16 · 실패 0.**

```bash
docker run -d --name qurious-jwt-test -p 16380:6379 redis:7-alpine
PYTHONPATH=. python scripts/verify_jwt_revocation.py
docker stop qurious-jwt-test && docker rm qurious-jwt-test   # 실행 후 정리 완료
```

이 검사에서 내가 가장 신경 쓴 건 항목 수가 아니라 **"예전 코드였다면 실패했을 것"을
함께 잰다**는 점이다. 예를 들어 1번은 두 줄이다.

| 재는 것 | |
|---|---|
| A 와 B 의 폐기 키가 다르다 | 통과 |
| **옛 방식(`token[:32]`)이었다면 같았을 것** | 통과 — 결함이 실재했음을 같은 실행에서 증명 |

둘째 줄이 없으면 "처음부터 멀쩡했는데 괜히 고친 것"과 구별이 안 된다.
나머지도 같은 식으로 짝을 이룬다 — A 로그아웃 뒤 B 생존, 액세스·리프레시 `jti` 분리,
리프레시 `jti` 가 새 액세스에 안 묻는 것(일부러 넣어 줘도 덮어쓴다), 서명부 변조본이 같은
이름표로 떨어지는 것, `exp` 없는 토큰 401, 자리표시자 비밀값이면 발급 차단과 탈출구 동작,
A 가 B 토큰을 폐기할 때 403 과 B 토큰 생존, 자기 토큰 두 개는 폐기.

**미측정**: 앱을 실제로 기동한 E2E, 동시 요청·부하, Redis 장애 주입.
검사는 함수 단위로 부른 것이고 HTTP 계층을 통과시키지는 않았다.

## 5. 막힌 것 · 남은 것

### 고치는 중에 더 나쁜 것이 드러났다

폐기 목록을 고치던 중에 `JWT_SECRET` 이
[`app/config.py:19`](https://github.com/devlee328288/Qurious/blob/0efdad9/app/config.py#L19) 의 기본값
`change-me-jwt-secret-32chars-min!!` **그대로** 동작 중이라는 것을 알았다.
`.env` · `.env.dev` · `.env.prod` 어디에도 이 항목이 없다(각 0건). 이 저장소는 Public 이다.

즉 위 공격에 **계정조차 필요 없었다.** 폐기 목록만 고쳤으면 반쪽이다.
그래서 자리표시자면 토큰 발급·검증을 막는 가드를 넣었다
([`jwt_auth.py:56`](https://github.com/devlee328288/Qurious/blob/0efdad9/app/lib/jwt_auth.py#L56)).

가드를 어디에 둘지가 한 번 막혔다. 모듈 import 시점에 두면 깔끔한데, `app.config` 를 함께
쓰는 수집기(`collector/`)와 스크립트가 **JWT 와 아무 상관이 없는데도** 못 돌게 된다.
그래서 **토큰을 실제로 다루는 시점**으로 옮겼다. 탈출구는 `JWT_ALLOW_INSECURE_SECRET=true`.

> 머지 뒤에 `openssl rand -hex 32` 로 만든 값을 `.env` 에 넣어야 한다. 안 넣으면 JWT 발급이
> 500 으로 막힌다. 웹 화면(쿠키 세션)은 영향 없다.

### 고쳐 놓고 못 따라간 것

`app/lib/redis_cache.py:154` 의 네임스페이스 규약 주석이 아직
`jwt_bl:{token_prefix}` 라고 적혀 있다. 키가 `jti:…` · `sha:…` 로 바뀌었으니 이 줄은 이미
틀렸다. 코드는 고치고 **코드 옆의 설명은 안 고친** 전형적인 경우다. 동작에는 영향이 없어
PR 에서 놓쳤고, 다음 작업에 얹는다.

### 안 고친 것 — 지금도 열려 있다

| 남은 것 | 왜 미뤘나 |
|---|---|
| 리프레시 **회전** 없음 | 클라이언트 변경을 부른다. `jti` 가 생겼으니 다음에 가능 |
| 리프레시를 폐기해도 **이미 나간 액세스는 15분** 산다 | 사용자 단위 폐기(epoch)가 따로 필요 |
| refresh 가 **DB 를 다시 안 본다** → 권한 강등·탈퇴가 7일 미반영 | #22 결함 7 · 구조 변경 |
| **쿠키 로그아웃이 JWT 를 안 끊는다** | 두 인증 체계를 잇는 설계 판단이 먼저 |
| **레이트 리밋이 0곳** | #22 결함 9 · 미들웨어가 하나도 없어 별건 |
| 폐기 목록이 RDB 스냅샷에만 남는다 (AOF 꺼짐) | 비정상 종료 시 폐기가 되살아날 수 있다 |

마지막 줄 옆에 하나 적어 둔다. Redis 가 죽으면 인증이 500 이 된다. 이건 fail-**closed** 라
안전한 쪽이지만, 그게 **의도**라는 게 어디에도 안 적혀 있다. 누가 나중에 "장애 때 통과시키자"로
바꾸면 폐기가 통째로 무력해진다.

## 6. 배운 것

- **보안 결함은 하나를 고치면 다음 하나가 모양을 바꿔 되살아난다.** 이번에 `jti` 만 넣고
  덮었으면, "전 사용자"가 "토큰 쌍"으로, 다시 "한 사용자"로 줄었을 뿐 같은 결함이 남았다.
  고치고 나서 **"이 결함의 본질이 다른 경로로도 성립하나"** 를 한 번 더 묻는 습관이 필요하다.
- **검사 순서가 경계다.** "무엇을 검사하느냐"만큼 "무엇을 검증한 뒤에 검사하느냐"가 중요하다.
  검증 전 입력으로 만든 키는 공격자가 고르는 키다.
- **라이브러리 기본값은 내 편이 아니다.** `require_exp=False` 가 기본이라는 걸 몰랐다.
  "당연히 볼 것"이라고 믿은 검사는 옵션을 직접 확인한다.
- **"예전 코드였다면 실패했을 것"을 같은 실행에서 재라.** 수정 후 통과만 보여 주는 검증은
  결함이 실재했는지를 증명하지 못한다.
- **가드는 필요한 자리에만 놓는다.** import 시점에 두는 편이 코드는 짧지만, 무관한 컴포넌트를
  같이 세운다. 범위를 좁히는 데 몇 줄 더 쓰는 게 낫다.
