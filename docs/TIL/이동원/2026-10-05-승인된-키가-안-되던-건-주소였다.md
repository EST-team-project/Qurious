## 1. 무엇을 했나

- **뉴스를 두 출처로 모았다.** 정책브리핑 정책뉴스(공공데이터포털)는 2020-01 ~ 어제를 3일 창 823번으로 받아 32,948건(7분)이고, 기사마다 오는 공공누리 유형이 제1유형인 기사만 본문을 둔다. 언론사 기사는 GDELT 의 15분 원자료에서 한국어 원문 기사의 제목 · 원문 주소 · 시각 · 언론사만 둔다(30시간에 2,305건 · 46곳). 둘 다 매일 12:30 러너 단계가 됐고, 검색 색인에 들어가 결과마다 출처 표시가 붙는다.
- **주주총회 과거분을 받았다.** 2024-01 ~ 의 소집결의 본문 12,363건(DART 12,454회 · 두 프로세스 · 건너뜀 0)에서 회의일을 99.8% 읽었다. 삼성전자 2024-03-20 · SK하이닉스 2024-03-27 처럼 알려진 날짜와 맞았다.
- **일정 · 리서치 화면을 Figma 로 정했다.** 일정 2판은 「칸에는 종류별 개수 · 날짜를 누르면 그날 목록」(안 B), 리서치는 「찾기 + 거름 칸, 종목을 고르면 시간표」(B + C 해석 1). 서버 쪽은 먼저 만들었다 — 한 달 요약 API · 그날 목록의 쪽 넘기기 · 검색의 출처 거름과 출처별 개수.
- **섹터 법령을 근거 답에 넣을지 쟀다.** 운영 근거 DB 는 그대로 두고 사본 DB · 다른 컬렉션에 섹터 법령 2026 판 9,725조각을 넣은 「넣은 길」 을 만들어 같은 평가 도구로 견주었다(섹터 질문 18문항은 넣은 길 정답 15 · 지금 앱 미룸 17, 기존 질문 15문항은 정답 12 → 10 — 그래서 「섹터 질문일 때만 찾는다」 로 정했다).

## 2. 막힌 것 · 알게 된 것

- **승인된 키가 안 되던 건 키가 아니라 주소였다.** 정책뉴스 활용신청이 승인(자동)된 뒤에도 두 시간 넘게 「등록되지 않은 서비스키」(코드 30)가 왔다. 앞 세션은 이것을 「키 반영 대기」 로 읽었다. 데이터 페이지에 박힌 swagger 원문을 열어 보니 주소가 `policyNewsService2/policyNewsList2` 였다 — 우리가 부르던 `policyNewsService/policyNewsList` 는 다른(옛) 서비스라, 그 키로 부르면 같은 오류가 난다. 오류 문구가 같다고 원인이 같은 것은 아니었다. 「기다리면 된다」 보다 원문 명세를 먼저 열어야 했다.
- **기사마다 공공누리 유형이 따로 왔다.** 데이터셋은 제1유형이지만 응답에는 기사마다 `KoglType` 칸이 있다. 지금 32,948건이 모두 「1」 이어도, 본문은 그 칸이 1 인 기사만 두게 했다. 모든 기사 끝에 「사진의 경우 제3자에게 저작권이 있으므로 사용할 수 없습니다」 라는 안내가 붙어 있어 사진은 받지 않는다.
- **태그를 띄어쓰기로 바꾸면 없던 띄어쓰기가 생겼다.** 한글 문서에서 바꾼 기사 HTML 은 낱말을 `<span>` 여러 개로 자른다. 태그를 공백으로 바꾸니 「TV 는 3 일」 이 됐다. 줄을 끊는 태그만 줄바꿈으로 두고 나머지는 그냥 지웠다 — 띄어쓰기는 원문이 이미 글자로 갖고 있다. 원문 XML 을 남겨 두어 네트워크 없이 다시 읽었다(6건 고침).
- **같은 서버라도 문이 달랐다.** GDELT DOC API 는 세 번째도 첫 호출부터 429 였지만, 15분 원자료 서버는 129파일을 막힘 없이 내줬다. 표본 여덟 창으로 「언론사 16곳」 이라 잰 것은 30시간을 다 받아 보니 46곳(이데일리 · 조선일보 포함)이었다 — 표본이 작으면 적게 잰다.
- **RSS 는 「쓸 수 있다」 가 아니었다.** 연합뉴스 RSS 안내는 「비상업적 블로그와 개인적인 용도로만」, 서울경제는 「다수 이용자 대상 … AI학습 이용을 금지」 라고 적었다. 안내 문구가 없는 곳도 허락은 아니다(언론진흥재단 규칙은 재RSS 금지).
- **주총이 들어가자 3월이 3,532건이 됐다.** 지금 화면처럼 한 달을 통째로 받으면 2,000건에서 잘린다. 칸에는 개수만, 하루는 쪽으로 받게 서버를 고치니 같은 6주를 0.2초 · 6.7KB 에 받았다(통째로는 0.75초 · 975KB 에 잘림). 실제 증권사 월간 증시캘린더도 칸이 넘치면 그날 「더보기」 로 넘긴다.
- **「융합」 은 다시 물어야 했다.** 리서치 화면을 「B, C 융합」 으로 고르셨을 때 「한 화면 안의 두 보기」 와 「한 메뉴 안의 두 탭」 두 뜻이 될 수 있어, 두 그림을 나란히 그려 다시 물었다.
- **평가 도구가 정답을 잘못 읽어 0점을 냈다.** 「넣은 길」 이 정답 조를 1위로 찾았는데 R@5 가 0 이었다. 정답 칸 「문서:조」 를 첫 콜론에서 나누는데 실험 문서 ID(`sec:은행법`)에도 콜론이 있었다. 마지막 콜론에서 나누게 고치고 시험으로 묶었다(DF-69). 숫자가 이상하면 모델보다 자를 먼저 의심한다.
- **스크립트 한 줄이 50분을 날릴 뻔했다.** 평가를 이어 돌리는 PowerShell 스크립트가 시작하자마자 죽었다 — BOM 없는 UTF-8 한글 스크립트를 Windows PowerShell 5.1 이 깨뜨려 읽었다. 세션 밖으로 띄운 작업은 「시작했다」 가 아니라 「첫 줄을 남겼다」 까지 봐야 한다.
- **좋은 문서를 더했는데 원래 맞던 답이 틀렸다.** 섹터 법령 9,725조각을 근거 후보에 한 묶음으로 넣자 「펀드 가입 뒤 청약을 철회할 수 있는 기간」 에 주택법의 「조합 가입 철회」 가 1위로 왔고, 「손실 보전 약속」 은 정답 조(자본시장법 제55조)가 문맥에서 빠져 답이 「제67조 자기계약 금지」 라는 틀린 근거를 댔다. 낱말이 같은 다른 업의 조문이 끼어든 것이다. 넣지 않은 길도 안전하지만은 않았다 — 「건설업 등록」 에 「등록」 만 맞는 자본시장법 조문으로 단정했다. 문서를 늘릴 때는 새 질문이 풀리는지와 함께 원래 맞던 질문이 그대로인지를 같은 날 같이 재야 한다. 같은 질문 세 번은 같은 날 안에서 글자까지 같았지만, 날이 바뀐 10-04 결과와는 20문항 가운데 셋이 낱말만 달랐다.
