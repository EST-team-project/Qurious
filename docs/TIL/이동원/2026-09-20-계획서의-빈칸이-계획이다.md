적을 것이 셋인데 서로 다른 것이어서였다.**

| 층 | 누가 정하나 | 지금 |
|---|---|---|
| ㉠ 과제 명세 — *"모델 자체 개발 및 성과 검증 역량 확보"* | 강사님 | 🟢 고정 · 우리가 못 바꿈 |

처음에는 이 셋을 매끄러운 한 문단으로 녹이려 했다. 그게 계획서다운 글로 보였기

그래서 ㉠㉡㉢ 기호를 그대로 본문에 남기고 층을 드러냈다. 글이 덜 매끄러워졌지만,
**09-27 이후 "이건 언제 정해졌나"를 물었을 때 답할 수 있는 문서**가 됐다.

> 계획서를 읽는 사람은 문장의 매끄러움이 아니라 **어디까지가 합의인지**를 알고 싶어 한다.

## 4. 배운 것 ② — 비어 있는 칸이 가장 많은 정보를 담는다

"예상 산출물" 칸을 쓸 때 처음에는 만들 것을 나열했다. 양식 예시가 그렇게 돼 있기도
했다. 그런데 그렇게 쓰면 **벤치마크가 없다는 사실이 문서 어디에도 안 남는다.**

그래서 칸을 셋으로 갈랐다.

```
① 이미 있는 것    수집기 3,779줄 · 시세 4.46M행 · 배당 9,188건 · TR 4.46M행
② 2차에 만들 것    자산배분 모델 · 스크리닝 · 비용 차감 성과 보고서
③ 지금 비어 있는 것  🔴 벤치마크 · 🔴 1차 주 검정 · 🟡 ETF · 🔴 trading_journal
```

③을 적고 나니 진척 막대의 모양이 달라졌다.

```
 ①~④ 데이터        🟢 ████████████████████  다 됐다
 ⑤~⑧ 비용·백테스트  🟡 ████████████░░░░░░░░  장치는 있고 검증이 남았다
 ⑨   자산배분       🔴 ░░░░░░░░░░░░░░░░░░░░  ★ 2차 본 과제
 ⑩   벤치마크       🔴 ░░░░░░░░░░░░░░░░░░░░  ★ 마지막 구멍
 ⑪   주 검정        🔴 ░░░░░░░░░░░░░░░░░░░░  ★ 1차가 넘긴 숙제
```

**①~④가 끝난 것은 재료가 준비됐다는 뜻이지 결론이 나왔다는 뜻이 아니다.** 데이터를
4백만 행 모았다는 사실이 진척률 80%처럼 보이기 쉬운데, 2차가 평가받는 것은 ⑨⑩⑪ 이다.

특히 ⑩이 뼈아프다. **벤치마크가 없으면 ΔSharpe 의 분모가 없다.** 1차가 스스로 정한
주 지표를 2차에서도 못 재게 된다.

## 5. 막힌 것 — heredoc 이 한글 마크다운을 삼켰다

계획서를 bash heredoc 으로 쓰려다 `unexpected EOF while looking for matching quote` 로
실패했다. quoted heredoc(`<<'EOF'`)이라 본문은 리터럴로 들어가야 하는데도 그랬다.

원인을 끝까지 파지는 않았다. 세션 규칙에 이미 *"긴 한국어 마크다운은 Write 도구로"*
라고 적혀 있었고, 그 규칙이 이런 이유로 생겼을 것이다. **Write 로 바꾸니 한 번에 됐다.**

| 방법 | 결과 |
|---|---|
| `cat > file.md <<'EOF'` + 323줄 한글 | ❌ 파싱 실패 |
| Write 도구 | ✅ |

## 6. 규칙 하나를 파일에 박았다

`.docx` 원본은 강사님 배포 자료다. 교재·강의자료 커밋 금지 규칙에 걸린다. 그런데
`docs/계획서/` 폴더 자체는 있어야 해서, **확장자로 막았다.**

```bash
$ git check-ignore -v "docs/계획서/프로젝트계획서양식_AI퀀트예시.docx"
.gitignore:59:docs/계획서/*.docx  docs/계획서/프로젝트계획서양식_AI퀀트예시.docx
```

규칙을 기억에 두면 언젠가 `git add -A` 로 실수한다. **파일에 박으면 실수할 수 없다.**

## 6.5 제출본은 .docx 여야 했다 — 그런데 두 벌을 손으로 맞추면 어긋난다

작업 중에 요청이 왔다. **계획서는 `.docx` 로도 갖고 있어야 하고, 설명이 더 쉽고
상세해야 한다**(용어 포함). 맞는 요청이다. 제출 문서는 Word 양식이고, 읽는 사람 중에
비전공자가 있다.

문제는 **두 벌이 생긴다**는 것이다. 계획서는 앞으로 세션마다 숫자가 바뀐다. `.md` 를
고치고 `.docx` 를 잊으면 **제출본이 틀린 채로 남는다.** 가장 나쁜 쪽이 틀린다.

| 방법 | 판단 |
|---|---|
| `.md` 와 `.docx` 를 따로 관리 | ❌ 반드시 어긋난다 |
| `.docx` 만 두고 `.md` 를 버림 | ❌ `git diff` 로 어느 칸이 바뀌었는지 못 본다. 압축 바이너리다 |
| **`.md` 정본 + 스크립트로 `.docx` 생성** | ✅ 골랐다 |

그래서 [`scripts/build_plan_docx.py`](../../../scripts/build_plan_docx.py) 를 썼다.
Markdown 을 읽어 Word 표·제목·고정폭 코드블록으로 옮긴다.

```
$ python scripts/build_plan_docx.py
만들었습니다: docs/계획서/프로젝트계획서_v1.0.docx
  제목 27 · 표 14 · 코드블록 8 · 문단 43
```

**옮기다 부딪힌 것 둘**

| 문제 | 해결 |
|---|---|
| 한글이 다른 글꼴로 나옴 | `run.font.name` 만 지정하면 **라틴 문자에만** 적용된다. `w:rFonts` 의 `w:eastAsia` 까지 XML 로 지정해야 한글이 따라온다 |
| mermaid 흐름도 | Word 가 못 그린다. **버리되** "[그림] 흐름도 — 원본 Markdown 에서 볼 수 있습니다" 한 줄을 남겼다. 조용히 사라지면 읽는 사람이 빠진 줄 모른다 |

**`.gitignore` 는 한 번 더 고쳤다.** 아침에 `docs/계획서/*.docx` 를 통째로 막아 뒀는데,
그러면 **우리가 만든 제출본까지 막힌다.** 막아야 할 것은 강사님 배포 양식이지 우리
문서가 아니다.

```gitignore
docs/계획서/*.docx
!docs/계획서/프로젝트계획서_v*.docx   ← 우리 것만 예외
```

검증은 `git check-ignore` 로 했는데 **여기서 한 번 헷갈렸다.** 부정 패턴(`!`)이
매칭되면 그 줄을 보여주면서도 **종료코드가 0** 이라, 내가 짠 확인 문구가 "차단됨"으로
잘못 찍혔다. 판정 기준은 `git status` 다 — `??` 로 보이면 무시되지 않은 것이다.

## 7. 버전 규칙을 문서 안에 넣은 이유

이 계획서는 앞으로 세션마다 숫자가 바뀐다. 요율표를 실측하면 분석 방법이, ETF 를
적재하면 산출물이, D1 결론이 나오면 목표가 바뀐다.

갱신 기준을 **문서 밖(내 머릿속·세션 프롬프트)** 에 두면 다음 사람이 어느 자리에
무엇을 적을지 모른다. 그래서 §8 에 넣었다.

| 구분 | 언제 |
|---|---|
| Major (+1.0) | 목표·분석 방법·산출물의 **성격**이 바뀔 때 |
| Minor (+0.1) | 숫자·진척·상태 갱신 |

+ **틀린 칸은 지우지 않는다** — 취소선 + 🔴 + 이유를 같은 칸에. 이슈 본문을 고칠 때
  쓰는 방식과 같게 맞췄다. 나중에 *"왜 이렇게 바뀌었나"* 를 되짚을 수 있어야 한다.
