## 2. 왜 했나

- 강사님 일정의 10-06(화) 오전 칸 전에 요구사항 · 시험 산출물을 새 틀로 올려 두기로 했다. 결정 대장(의견 기한 09-30 23:59)과 IA(D1 ③ 확정 뒤)는 기다려야 해서 막힘 없는 두 문서를 먼저 했다.
- RTM v1.0 은 시험 23건 때 쟀다. 그 뒤 시험이 여덟 배 가까이 늘었는데 「어느 요구가 검증됐나」 는 아무도 다시 세지 않았다.
- 3차는 제안요청서가 따로 없어 RTM 이 얇았다. 강사님 공식 일정표가 3차의 사실상 요구 목록이다.

## 3. 어떻게 했나 — 고른 것과 버린 것

- **고른 것: 요구 정의를 대장(TSV)으로.** 버린 것: 요구 한 줄 칸을 스캐너 코드(파이썬 목록)에 넣는 것. 요구 문장은 사람이 고치는 것이라 표 파일이 맞고, 대장이 곧 관행 명칭의 「요구사항정의서」 다. API ID 대장 · 표 속성 대장과 같은 방식이라 팀원에게 새로 가르칠 것이 없다.
- **고른 것: 시험 대응에 확실도(🟢 직접 · 🟡 전제나 일부).** v1.0 은 야후 참조 특성화 시험(TC-YH)을 「같은 조건의 LEAN(★)」 의 시험으로 셌다. 그 시험은 야후 참조가 늘지 않게 막을 뿐이고, LEAN 은 지금도 야후 데이터 · 비용 0 으로 돈다. 확실도를 두니 이 요구가 🟢 에서 🟡 로 내려왔다.
- **고른 것: 파트 칸을 두지 않기.** 요구마다 파트를 붙이면 역할 희망 논의(D9)를 문서가 앞질러 정하게 된다. ERD · 사전 v1.2 가 「업무 영역」 으로 비켜 간 것과 같은 이유다.
- **고른 것: 일정표의 기능 칸만 요구로.** 착수 · 설계 공통 칸과 통합 · 시험 · 배포 · 인수 과정 칸은 산출물이라 산출물목록이 이미 추적한다. 기능 칸 28개 가운데 23개는 원문 · 제안요청서가 이미 받았고, 새 ID 는 5개뿐이다.
- **버린 것: 일정표 칸 ID 에 날짜를 넣기(`SCH-1028` 같은).** 일정이 바뀌면 ID 가 틀린다. 칸의 이름(`SCH-DQ` = 데이터 품질)으로 붙였다.

## 4. 어떻게 확인했나

- 일정표 날짜는 문서를 옮겨 적지 않고, 강사님 JS 의 달력 규칙(주말 · 10-05 · 10-09 쉼 · 10-21 오후 뺌)을 파이썬으로 그대로 돌려 55칸을 다시 계산했다.
- 스캐너의 새 시험 11건을 커밋된 트리(`git archive HEAD`)의 옛 스캐너로 돌려 11건 모두 실패하는 것을 봤다. 흔적 결함은 옛 스캐너로 따로 재현했다 — 옛 스캐너는 `P02-⑤-2`(★ 중복 주문 방지)를 「코드 희소 · 2파일」 로 적는다.
- 전체 시험: 시험 DB(Postgres 15432)를 붙여 **188/188**(108초) · 떼고 **182 통과 · 6 건너뜀**(71초). 시험 DB 는 돌리는 동안만 띄우고 지웠다.
- 결함 DF-02 는 `benchmark verify` 를 실제 DB 로 다시 돌렸다(3분 25초 · DB 파일 시각 전후 같음) — 코스닥 연말 평균 0.871% 그대로. #26 · #35 는 GitHub 이슈 페이지를 한 건씩 읽어 열림을 확인했다.
- 흔적은 문서 작성 기준 부록 B 의 정규식으로 쟀다 — RTM 1 · 7 · 1 · 0 · 0 → 0 · 0 · 0 · 0 · 0 · 테스트계획서 85 · 15 · 39 · 0 · 11 → 0 · 0 · 3 · 0 · 0.

## 5. 막힌 것 · 남은 것

- **흔적의 거짓 양성이 또 나왔다.** v1.0 은 「스캐너 자신」 과 「주석 속 낱말」 을 잡았다. 이번에는 **여러 줄 docstring 의 가운데 줄**이 코드로 보였다 — 줄 앞머리만 보는 판별로는 가운데 줄이 `"""` 로 시작하지 않는다. 파이썬은 `ast` 로 문서화 문자열 범위를 가리게 고쳤다(DF-18 · TC-RT-07).
- **미뤄 둔 결함 한 줄을 하마터면 놓칠 뻔했다.** 갱신 대장 6.3절에 「테스트계획서 v1.3 결함대장에 한 줄」(ETF 백테스트의 매도세)이 적혀 있었는데, v1.3 을 거의 다 쓴 뒤 `v1.3` 으로 저장소를 훑다가 찾았다. 코드를 다시 읽어 지금도 그대로임을 확인하고 DF-19 로 넣었다.
- 흔적 정규식은 옛 이름을 풀이하는 용어집 줄도 센다(테스트계획서 v1.3 의 3곳). 기준 v0.2 에서 예외로 적을지 정한다.
- 채점 · 사고 방지 항목 셋은 직접 재는 시험이 없고, 둘은 코드도 주석뿐이다. 2차 10-14 오전 칸이 손실 한도 · 비상 정지를 먼저 요구한다.

## 6. 배운 것

- **시험 수는 커버리지가 아니다.** 시험이 23건에서 188건으로 여덟 배 늘 때, 시험이 붙은 원문 세부 기능은 3개에서 6개로 두 배 늘었다. 한 파트가 모든 시험을 쓰면 시험은 그 파트의 영역에만 쌓인다.
- **특성화 시험은 요구의 시험이 아니다.** 「더 나빠지지 않는다」 를 지키는 시험을 「된다」 의 증거로 세면 요구가 검증된 것처럼 보인다. 확실도 칸이 그 차이를 적는 자리다.
- **줄 앞머리로 주석을 가리는 판별은 언젠가 틀린다.** 구조(문서화 문자열 범위)는 파서가 안다. 표준 라이브러리로 충분했다.
- **미룬 일은 「다음 판에」 라고 적은 문서에서 다음 판 이름으로 찾아야 한다.** 판을 올리기 전에 저장소 전체에서 그 판 이름(`v1.3`)을 한 번 훑는다.
