# 막는 장치와 알리는 장치는 다르다 — 어제 세운 CI 게이트를 하루 만에 내린 날

> 2026-09-21 (월) · Qurious 2.0 · CI 방침 전환
> 관련 PR: `docs/ci-as-signal-not-gate` · ADR-0002

## 한 줄

**어제 "사람이 못 막으니 CI 가 막는다"고 썼는데, 막히는 대상이 남이 아니라 나 자신이었다.**
그런데 반대로 CI 를 지우려다 보니, 지우면 **사람이 원리상 볼 수 없는 것**까지 같이 죽었다.

---

## 1. 어제의 논리

S40 에서 실거래 경로를 막고(ADR-0001), 그게 되돌아오지 않게 CI 를 들였다.
CI/CD 명세 v1.0 §1 에 이렇게 적었다.

> 팀원 넷의 작업 시간대가 달라 PR 에 사람 승인을 필수로 걸면 병합이 멈춘다.
> 그래서 **사람 대신 CI 가 막는다.**

그리고 「저장소 룰셋에 필수 상태 검사를 등록해야 비로소 게이트가 된다」며,
사용자가 웹 UI 에서 할 절차를 §4 에 남겼다. 다음 세션의 숙제로.

## 2. 오늘 들어온 반론

> "저희는 자기가 작업하고 올린 것에 대해서는 자기가 merge 하고,
> 이슈나 PR 확인 요청을 통해서 이중 검증하는 방식으로 진행했는데,
> 쓸데없는 CI 같아서 제거하는 방향을 생각 중입니다."

읽고 나서야 내가 무엇을 빠뜨렸는지 보였다. **"사람 승인을 못 건다"와 "그러니 기계가
막아야 한다"는 이어지지 않는다.** 승인을 못 거는 이유는 *기다릴 사람이 없어서*인데,
게이트는 기다릴 사람을 만드는 게 아니라 **기다릴 조건**을 만든다. 승인자를 0명으로 둬도
필수 상태 검사가 빨간색이면 병합 버튼은 잠긴다. 즉 내가 세우려던 장치는

> 남의 부주의를 막는 문 **(내가 생각한 것)**
> 내 병합을 잠그는 문 **(실제로 만들어지는 것)**

이 둘을 구분하지 않고 있었다.

> **용어 — 룰셋(ruleset)과 필수 상태 검사(required status check)**
> **룰셋**은 GitHub 저장소 설정에서 브랜치에 거는 규칙 묶음이다.
> **필수 상태 검사**는 그중 하나로, 「이 이름의 검사가 성공해야만 병합 가능」을 등록한 것.
> **이 문서에서는** 둘을 묶어 "게이트"라 부른다.
> **헷갈리는 점**: 워크플로(`.github/workflows/*.yml`)와는 **완전히 다른 물건**이다.
> 워크플로는 *검사를 실행할 뿐*이고, 그 결과로 병합을 잠그는 것은 룰셋이다.
> 워크플로만 만들어 두면 **아무것도 막히지 않는다** — 이게 오늘 결정의 핵심이 됐다.

## 3. 그런데 지우려고 보니

제거하는 쪽으로 손을 대기 전에, 시험 23건이 실제로 무엇을 보는지 세어 봤다.
20건은 평범한 단위 시험이었다. 나머지 **3건이 달랐다.**

| 시험 | 훑는 범위 |
|------|-----------|
| `test_저장소_어디에도_paper_False_하드코딩이_남아있지_않다` | `app/**/*.py` 전체를 `rglob` 으로 순회 |
| `test_야후_참조가_기준선과_같다` | 저장소 전체, 파일별 참조 줄 수를 기준선과 대조 |
| `test_기준선에_없는_파일이_야후를_쓰지_않는다` | 저장소 전체, 새 파일만 따로 |

이 3건은 **PR 리뷰로는 원리상 잡히지 않는다.** 리뷰어는 diff 를 본다.
diff 는 「이 변경이 맞는가」를 보여 주지 「저장소가 여전히 맞는가」를 보여 주지 않는다.

## 4. 이 저장소에 실제 전력이 있었다

추측으로 끝내기 싫어서, 어제 막은 `paper=False` 가 **언제 들어왔는지** 추적했다.

```bash
git log --oneline -2 ae501e1~1 -- app/services/auto_trade.py
```

```
005ad7d  강사님 lumina-invest 최신본 반영 + AWS 걷어내기
            └─ paper=False 가 이때 들어왔다
                      ▼
49d8159  주문이 정산금액으로 현금을 옮긴다 — orders 확장 + order_fills 신설
            └─ 같은 파일을 또 건드렸다. 그런데도 안 잡혔다
                      ▼
ae501e1  실거래로 나가는 문이 셋이었다 (어제)
            └─ 전수 조사를 해서야 찾았다
```

**실거래로 나가는 코드가 여러 차례 사람 눈앞을 지나갔다.** 리뷰가 게을러서가 아니다.
`49d8159` 는 "주문 정산" 을 보는 PR 이었고, `paper=False` 는 그 관심사 밖의 줄이었다.
diff 리뷰는 그렇게 동작한다.

## 5. 결정 — 제거도 게이트도 아닌 세 번째

| 안 | 자기 머지 | 회귀 탐지 | 채택 |
|----|:--------:|:--------:|:----:|
| 워크플로 유지 + 룰셋 미설정 | ✅ 그대로 | ✅ 빨간 X 로 보임 | **✅** |
| 워크플로 제거 | ✅ 그대로 | ❌ 없음 | |
| 워크플로 + 룰셋 게이트 | ⚠️ 잠김 | ✅ 강제 | |

**워크플로는 두고 룰셋은 걸지 않는다.** 실패해도 병합은 막히지 않고 빨간 X 만 뜬다.
넘길지 고칠지는 사람이 판단한다.

게이트를 버린 이유를 하나 더 적어 둔다. 게이트는 급할 때 껐다 켜게 되는데,
**그렇게 우회되는 게이트는 켜져 있다는 착각만 남기고 실제로는 막지 않는다.**
어제 ADR-0001 §1.1 에서 이미 같은 모양을 봤다 — `ebest` 는 `paper=True` 를 줘도
그 값을 볼 자리가 없어 실서버로 나갔다. *막았다고 믿는데 막히지 않는 것은
막지 않은 것보다 나쁘다.* 그 문장을 내가 만들려던 장치에도 적용해야 했다.

## 6. 오늘 배운 것

**1. "막는다"와 "알린다"를 섞어 쓰고 있었다.**
어제 문서에는 둘이 구분 없이 들어가 있다. 게이트는 막는 장치, 워크플로는 알리는 장치다.
필요한 게 어느 쪽인지 먼저 정하고 나서 도구를 골랐어야 했다.

**2. 반론이 옳아도 결론까지 옳은 건 아니다.**
"게이트가 우리 방식과 안 맞는다"는 맞았다. 하지만 거기서 "그러니 CI 를 지우자"로
바로 가면 전역 스캔 3건을 잃는다. 전제가 맞다고 결론이 따라오지 않는다 —
**어디까지가 맞는 말인지 잘라 봐야** 세 번째 안이 보인다.

**3. 하루 만에 되돌린 결정은 ADR 로 남길 가치가 더 크다.**
빨리 뒤집혔다는 건 판단 근거가 얕았다는 뜻이고, 얕았던 자리를 적어 두지 않으면
다음에 같은 자리에서 또 얕아진다. ADR-0002 §1.2 에 "충분히 따지지 않았다"를 그대로 적었다.

**4. 되돌릴 절차는 지우지 않는다.**
룰셋 설정 절차는 CI/CD 명세 v1.1 **부록 A** 로 옮겨 보존했다. 게이트가 필요해지는
조건(§4.3)도 같이 적었다 — 빨간 X 머지 2건 누적, 실계좌 진입, 강사님 요구 변경.
**되돌릴 조건을 미리 적어 두면, 되돌릴 때 감정이 아니라 기준으로 판단한다.**
