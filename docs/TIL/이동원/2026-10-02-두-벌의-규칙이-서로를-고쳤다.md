## 1. 무엇을 했나

- **HF 백업에 OHLCV 원자료 표 넷을 넣었다(DF-40).** ETF · 지수 일봉의 순자산가치 · 기초지수 칸은 규격 자료에 없고, 5분봉은 야후가 60일 지난 것을 다시 주지 않는다 — 7월 초 ~ 8월 초 5분봉은 이미 이 PC 에만 있었다. 같은 날 내보내고 · 검증하고 · 넷을 되살려 보고 · 올렸다.
- **`GET /api/data/ohlcv` 를 만들었다.** HF `krx-ohlcv` 와 같은 줄을 한 종목 · 한 기간만. 앱 이미지에 수집기 코드가 없어 같은 규칙(평평한 봉 · 수정 거래량 · 주봉)을 앱에 따로 두고, 시험이 내보내기 함수와 **줄마다** 대조하게 했다.
- **데이터 상태 API 의 첫 호출을 21초 → 0.3초로.** 행 수 세기만 뒤에서 하게 바꿨다.
- **데이터 관제 · 일정 화면** — Figma 에서 실제 값으로 세 안씩 그려 묻고, 같은 날 만들었다. 위 메뉴의 「자료 10-01 · 정상」 · 서랍 · 관제 화면 · 월 달력 · 다가오는 일정 카드 · 휴대폰 목록.
- **「사전에 없는 말」 을 실제 사전은 어떻게 하나** 조사했다 — 시소러스 표준의 「후보 용어」 · 위키백과의 빨간 링크 지침 · 실무 용어집 도구의 초안 상태. 비교 쌍 용어 7개는 후보로 넣고 검토 뒤 공개하기로 했다.

## 2. 막힌 것 · 알게 된 것

- **두 벌의 규칙을 줄마다 맞춰 보자 이미 올린 자료의 틀린 칸이 나왔다(DF-43).** API 는 분봉의 시장을 「그 종목이 든 가장 최근 유니버스 판」 에서 읽게 짰는데, 대조 시험이 내보내기와 어긋났다. 내보내기는 **최신 판에만** 물어보고 없으면 「KOSPI」 로 채우고 있었다 — u2 에서 빠진 코스닥 38종목, 분봉 304,710줄이 이틀 동안 KOSPI 로 팀 저장소에 올라가 있었다. 규칙을 한 벌만 두었다면 둘 다 같은 실수를 했을 것이다. **같은 규칙을 일부러 두 벌 두고 대조하는 시험은, 한쪽이 틀리면 다른 쪽이 알려 준다.**
- **날짜 모양 하나가 그해를 통째로 지웠을 뻔했다(DF-40).** 연도 파일의 경계가 `'2026' + '0000'` ~ `'2026' + '9999'` 였다. `YYYYMMDD` 에는 맞는데 분봉의 `YYYY-MM-DD` 는 `'-'` 가 `'0'` 보다 작아 `'2026-10-02' < '20260000'` — 2026 년 분봉이 0행이 된다. 「그해 이상 · 다음 해 미만」 으로 바꾸면 모양을 가리지 않고, 옛 표의 결과는 그대로다(시험 둘로 확인).
- **합이 넘치면 한쪽은 죽고 한쪽은 조용히 틀린다(DF-41).** 검증이 숫자 칸의 합을 DB · 파일 양쪽에서 대조하는데, 지수 상장 시가총액 합이 9.87 × 10¹⁹ — int64 상한의 10.7 배였다. SQLite `SUM()` 은 `integer overflow` 로 멈췄고, pyarrow `pc.sum` 은 **음수를 돌려주며 아무 말도 안 했다.** 주식 시가총액 합도 이미 상한의 51% 였다. 실수 합(`TOTAL()` · float64)으로 바꿨다.
- **일부만 본 기록이 「지워도 된다」 를 초록으로 만들 수 있었다(DF-42).** 표 넷만 검증한 기록도 매니페스트 지문만 맞으면 통과로 읽혔다. 내가 방금 넷만 검증해서 알았다. 판정이 「전체를 본 기록」 만 인정하게 했다 — 확인하지 않은 것은 통과가 아니다.
- **느린 질의는 칸의 자리 탓이었다.** 「언제 받았나」 를 원문 지문으로 찾으면 2.8초 — 지문 칸이 원문(BLOB) **뒤**에 있어 SQLite 가 원문을 넘겨 읽는다. 대신 인덱스에 있는 (출처, 대상)으로 찾으면 10ms 인데, 그 값이 같은지부터 확인했다: 같은 날을 두 번 받은 날도 정규화 줄은 늘 마지막 원문을 가리켰다(4,968날 전부).
- **스캐너가 읽는 모양으로 쓰지 않으면 문서가 조용히 틀린다.** 화면 진입 훅을 상수로 적었더니(`view === VIEW`) 화면 스캐너가 훅을 못 읽어, API 명세서의 「부르는 화면」 칸이 새 주소 셋 모두 「(다른 곳)」 으로 남았다. 두 파일에 같은 함수 이름(`renderView`)을 쓴 것도 스캐너가 이름으로 함수를 찾으니 섞어 읽을 뻔했다. 훅을 글자 그대로 적고 이름을 나눈 뒤, 같은 일이 다시 생기면 시험이 잡게 했다.
- **합치기 전에 한 번 더 브라우저로.** 팀원 PR #90 이 같은 `app.html` 을 고쳐 받아서 합쳤다(겹친 줄 0 · 3-way). 합친 화면을 다시 눌러 보다가 일정의 설명 창이 화면을 옮겨도 남아 다른 화면을 덮는 것을 찾았다 — 처음 확인 때는 창을 닫고 옮겨서 몰랐다.
- **「융합」 이라는 답은 뜻이 둘이었다.** 화면 세 안 중 「A + C 융합」 을 고르셨는데, 한 화면 안의 융합인지 · 달력 화면 + 다른 화면 카드인지 갈렸다. 만들기 전에 두 해석을 그림 설명과 함께 다시 물었다 — 다르게 만들었다면 반나절이 사라졌다.
