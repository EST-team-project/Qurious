## 1. 무엇을 했나

- **거래일 달력을 만들었다 — 지난날뿐 아니라 아직 오지 않은 날까지.** 주말 · 공휴일(한국천문연구원 특일 정보) · 근로자의 날 · 연말 휴장일(12-31, 주말이면 그 앞 평일) 네 겹 규칙으로 2020-01-01 ~ 2027-12-31 을 하루 한 행씩 만들고, 지난날은 수집한 시세로 확인한다. 휴장 · 코스피200 만기(두 번째 목요일 · 휴장이면 앞당김) · 배당 기준일 · 배당락일을 일정 표로 함께 만든다.
- **데이터 상태 API 를 만들었다.** 매일 12:30 갱신이 돌았는지, 표마다 마지막 날짜가 언제인지, 그 뒤로 **거래일이** 몇 개 비었는지(0 최신 · 1 정상 · 2 늦음 · 3 멈춤), HF 에 마지막으로 올린 태그가 무엇인지를 한 번에 돌려준다. 거래일 달력 · 금융 일정 API 둘은 로그인 없이 읽는다. 기능 점검에 「데이터」 묶음 셋을 더했다.
- **연관 개념을 서버 쪽부터 만들었다.** 용어집의 「PER vs PBR | 이익 대비 주가 | 순자산 대비 주가 | 성장주는 PER, 가치주는 PBR 우선」 같은 비교 쌍 표를 용어 사이 관계로 바꿔(헷갈리는 말 25 · 연관 2), 용어 카드가 「헷갈리기 쉬운 말」 과 차이 한 줄을 보여 준다.

## 2. 막힌 것 · 알게 된 것

- **「틀린 달력은 없는 것보다 나쁘다」 는 맞았지만, 없는 달력도 틀렸다.** 수집기는 일부러 휴장일 달력을 두지 않고 「시세가 쌓인 날」 을 거래일로 썼다. 그런데 그 달력에는 내일이 없다. 배당락일을 셀 때 아직 시세가 없는 기준일은 달력 끝에서 세어 버려, 기준일 10-13 의 배당락일이 09-29 로 들어가 있었다(맞는 값 10-12 — 10-09 한글날). 오늘 12:30 갱신이 새 공시(기준일 10-16)를 받자마자 같은 실수를 또 했고, 새 달력 단계가 바로 고쳤다. **매일 새로 생기는 결함은 한 번 고쳐서는 안 끝난다 — 계산이 기대는 자료를 고쳐야 한다(DF-39).**
- **규칙을 믿기 전에 과거와 맞춰 봤다.** 공휴일만으로는 평일 휴장 10일이 설명되지 않았다 — 5-1 네 번과 연말 여섯 번. 그중 2022-12-30 · 2023-12-29 는 12-31 이 주말이라 앞당긴 날이었다. 규칙 넷을 넣자 6년 9개월(1,655 거래일)이 한 날도 어긋나지 않았고, 이 대조를 실제 DB 로 도는 시험으로 남겼다.
- **같은 자료를 같은 날 두 번 세면 판단이 갈린다.** 기준일 09-30 인 배당 8행 중 2행만 배당락일이 하루 이르게 들어가 있었다. 09-30 시세가 들어오기 **전날** 계산된 행이었다. 계산 시점이 결과를 바꾸면, 그 계산은 다시 돌 때마다 다시 맞춰야 한다 — 그래서 달력 단계가 매일 배당락일을 다시 센다.
- **「16초」 는 코드가 아니라 자리 탓이었다.** 갱신이 큰 표를 다시 쓰는 동안 상태 API 가 16초 걸렸다(평소 1초 안). 앱 컨테이너가 Windows 폴더를 거쳐 DB 를 읽기 때문으로 보인다. 행 수는 DB 파일이 그대로면 다시 세지 않게 했다 — 단 처음 읽을 때 생기는 빈 WAL 파일(0바이트) 하나 때문에 「파일이 바뀌었다」 로 읽혀, 시험이 먼저 잡아 주었다.
- **사전에 없는 말을 지어내지 않았다.** 비교 쌍 30개 중 5개는 한쪽 이름(기본적 분석 · 종신보험 등)이 사전에 없다. 이어 붙이려면 용어를 새로 세워야 하는데, 그건 자료가 아니라 내 판단이 된다. 빌드가 「잇지 못한 12줄」 을 알리게 하고, 더할지는 묻기로 했다.
